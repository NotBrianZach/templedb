Session-scoped VCS staging — design

TempleDB’s VCS has one shared staging area per project/branch, so parallel agents sweep each other’s in-progress work into their commits (or, worse, commit it under the wrong message). This document proposes replacing the boolean vcs_working_state.staged flag with session-scoped staging keyed off TEMPLEDB_SESSION_ID, drops the dead vcs_staging table on the way through, and outlines how the change ships in phases. Related but separate: the memory-noted "vcs commit reverts file set writes" regression is likely orthogonal and gets its own investigation.

Why it’s worth naming as a fundamental

This session hit the exact pattern that motivated this doc. vcs commit would have swept a different agent’s staged src/cli/commands/vibe.py into a commit for the agent Org rendering refactor if I hadn’t paused on unfamiliar staged state and asked. The pause-and-ask worked this time because I noticed. It won’t always. The fix is structural: make cross-agent sweeps impossible, not require every agent to check every time.

The pattern to prevent Agent A stages files X, Y. Agent B stages file Z. Agent B runs vcs commit. The commit contains X, Y, Z under agent B’s message.

What’s actually in the codebase today

Findings from src/services/vcs_service.py, src/repositories/vcs_repository.py, src/cli/commands/vcs.py, and migrations/database_vcs_schema.sql:

  • Active staging is a boolean flag: vcs_working_state.staged BOOLEAN DEFAULT 0. stage_files flips it to 1. unstage_files flips it to 0. commit reads all rows where staged = 1. No identity attached anywhere.
  • A better shape already exists in the schema and is dead code: the vcs_staging table at line 115 of database_vcs_schema.sql has a staged_by TEXT column. It is never touched by the service. Zero references in vcs_service.py. Vestigial from a v1 design.
  • Author is resolved at commit time only, via vcs.py:_get_author which shells out to git config user.name. There is no notion of “who staged this row” anywhere in the write path.
  • No session concept exists in the VCS layer. agent_sessions (migration 073, Temple Agent chat sessions) is unrelated and shouldn’t be reused — it’s a heavier lifecycle with providers/models/messages, not a lightweight identity anchor.

The design space

0. Discipline — ask before every commit skip

Current state. Works when the agent notices; fails silently when it doesn’t. Not a fix, it’s a hope.

1. Per-file commit filter (vcs commit -- <paths>) too narrow

Mirror git commit -- path1 path2. Smallest possible change. Fixes the immediate blast-radius problem but requires every agent to correctly enumerate its files every commit — and a forgetful agent still sweeps in others’ work. It patches the symptom, not the concurrency model.

2. Env-var author (TEMPLEDB_AUTHOR) insufficient

Add a staged_by TEXT column, key it off an env var, scope operations by author. Simpler than sessions, but authors are long-lived. Two parallel invocations from “the same agent” (same TEMPLEDB_AUTHOR, different windows) still collide. Also loses the audit trail — can’t answer “which of Zach’s five agents staged this?”.

3. Session-scoped staging pick

Introduce a lightweight vcs_sessions table. Each staging operation references a session ID. Sessions have start/end lifecycle, are listable, and can be tagged with a human-readable name for debugging (“cleanup-org-render”). Env var TEMPLEDB_SESSION_ID identifies the caller; a synthetic session auto-starts on first write op if unset, so single-shell human usage stays frictionless.

Buys us: hard isolation (commit only reads its own session’s staged rows), auditability (you can list all sessions and see who staged what), and a natural attachment point for future features like session-scoped locks or session-shaped policy.

4. Branch-per-agent too heavy

Force every agent onto its own branch. Isolation falls out of the branch model — each branch has its own working state row. But the checkout-switch cost is real, especially in edit mode, and forcing branches makes small collaborative work (“three quick edits from three agents on the same branch”) needlessly ceremonial. The FUSE branch views feature (memory) enables this but doesn’t make it cheap.

Recommended design: session-scoped staging

Data model

CREATE TABLE vcs_sessions (
    id INTEGER PRIMARY KEY,
    name TEXT,                    -- optional human label
    author TEXT NOT NULL,         -- resolved from env / git config at start
    host TEXT,                    -- socket.gethostname() at start
    pid INTEGER,                  -- start pid (debugging)
    started_at TEXT NOT NULL DEFAULT (datetime('now')),
    ended_at TEXT,                -- NULL = active
    ended_reason TEXT             -- 'explicit-end' | 'commit-cleanup' | 'stale-timeout'
);

ALTER TABLE vcs_working_state
    ADD COLUMN staged_by_session_id INTEGER
        REFERENCES vcs_sessions(id) ON DELETE SET NULL;

DROP TABLE vcs_staging;    -- dead code, never referenced

Rows staged by a session have staged_by_session_id set. Not staged ⇒ NULL. The old staged BOOLEAN column stays for one release as a compat mirror (staged = (staged_by_session_id IS NOT NULL), maintained by triggers or by the service), then drops in a follow-up migration once nothing reads it.

Session lifecycle

  • Explicit start: templedb vcs session start [--name X] [--author Y] creates a row, prints the ID (and optionally an export line for shell eval).
  • Implicit start: if a write op runs without TEMPLEDB_SESSION_ID, service auto-creates a session named <host>-<pid>-<short-ts>. The session ID is not re-exported (the process only knows what it needs to know). This preserves the current single-shell zero-friction UX; humans don’t need to change their workflow.
  • Explicit end: templedb vcs session end [--id N]. Default policy: leave staged rows alone (staged_by_session_id stays set); the row still shows up as “staged by ended session X.” This is a deliberately safe default — ending a session should not silently unstage work.
  • Implicit end at commit: when a session runs vcs commit and commits all its staged rows, the session gets ended_at set with ended_reason = 'commit-cleanup'. Auto-created implicit sessions do this by default; explicitly-started sessions stay open until session end.
  • Stale sessions: vcs session list --stale surfaces sessions older than N days with rows still staged. Cleanup is manual — automatic reset would risk losing work.

Identity resolution order

  1. TEMPLEDB_SESSION_ID env var (must reference a live session row)
  2. Auto-created synthetic session (write ops only)
  3. Author for the auto-created session: TEMPLEDB_AUTHOR env var, then git config user.name, then "unknown"

Command behavior after the change

Command Semantics after change
vcs add Sets staged_by_session_id to current session
vcs reset Clears only where staged_by_session_id = current session; refuses (with a clear message) to unstage other sessions’ rows unless --force
vcs commit Commits only rows where staged_by_session_id = current session; clears the session’s rows post-commit; ends implicit session
vcs status Default: current session’s staged + all modified/untracked. --all: grouped view with session badges ([session #12 zach-refactor])
vcs session {start,end,list,current,show} New. Lightweight lifecycle management.

Backward compatibility

The important invariant: a human running templedb in a terminal with no env vars set behaves identically to today. The mechanism:

  • First write op auto-creates a synthetic session in-process. The session ID lives only on the staged rows.
  • vcs commit in the same process commits those rows. No conflict, no confusion — there was only one session and it committed everything it staged.
  • Existing scripts and CI runners that do file set X; vcs add X; vcs commit -p project continue to work: each run gets a fresh implicit session, does its own thing, ends at commit.

The only user-visible new failure mode: if two shell sessions on the same machine each set TEMPLEDB_SESSION_ID to the same value (deliberate) and then race, the winner still wins — because they’re one logical session by declaration. That’s fine; it’s exactly the semantics of “same session”.

Migration and backfill

-- migration NNN_add_vcs_sessions.sql
CREATE TABLE vcs_sessions (...);

ALTER TABLE vcs_working_state
    ADD COLUMN staged_by_session_id INTEGER
        REFERENCES vcs_sessions(id) ON DELETE SET NULL;

-- One-time backfill: any existing staged=1 row gets a legacy session
INSERT INTO vcs_sessions (name, author, started_at, ended_at, ended_reason)
    VALUES ('legacy-backfill', 'unknown',
            datetime('now'), datetime('now'), 'backfill');

UPDATE vcs_working_state
    SET staged_by_session_id = (SELECT id FROM vcs_sessions
                                WHERE name = 'legacy-backfill' LIMIT 1)
    WHERE staged = 1;

DROP TABLE vcs_staging;

CREATE INDEX idx_vcs_working_state_staged_session
    ON vcs_working_state(staged_by_session_id);

The staged BOOLEAN column stays until a follow-up migration confirms nothing reads it. Service reads switch to staged_by_session_id IS NOT NULL; writes maintain both columns temporarily.

The related regression (memory: 2026-08-20)

Memory notes: “vcs commit -p again reverts file set writes in deployed 0.7.0 binary. Use templedb commit <slug> <fresh-checkout> workflow; watch for deletion sweeps and in-flight user work.”

This session’s commits (04856C82, D29C1D0B) did not visibly regress. I verified post-commit that protocol.py still has events_by_run, templedb-agent.el has the new helpers, and org_renderer.py is gone. Possible explanation: I set TEMPLEDB_DEV_MODE=1 on every file set, which bypasses the deployed 0.7.0 code path that the regression names. If true, the regression is specifically in the deployed binary’s write path, not in the checkout-mode path.

Hypothesis to verify The regression may involve commit re-reading working state from the checkout filesystem rather than the DB, so writes made via file set (DB-only) get overwritten by the older checkout content at commit time. If true, the fix is to make commit authoritative on the DB, not the checkout. This is a separate investigation from the staging change.

Interaction with the staging change

The staging change touches stage_files, unstage_files, and the commit query — which is exactly where the regression lives, if the hypothesis is right. Doing the two changes together means each PR reviewer sees the full picture; doing them separately means clean revertability if either turns out to be wrong. Recommendation: staging first as its own commits, regression second.

Non-goals

  • Distributed multi-machine sessions. This is single-DB, single-node. If you’re running two agents against two databases, that’s a different problem.
  • Session ↔ agent-session identity merge. Temple Agent’s agent_sessions table stays a separate concept. A Temple Agent invocation could optionally set TEMPLEDB_SESSION_ID to a value it uses across its templedb calls, but the schemas don’t need to know about each other.
  • Automatic stale-session GC. Sessions accumulate; listing shows them. Cleanup is manual. Auto-GC would mean auto- unstaging, which risks losing work.
  • Per-file locking. Two sessions can each stage the same file. Whichever commits first wins; the loser sees a stale-content error at commit time (this is essentially optimistic concurrency — matches git’s model, not RDBMS-style row-locking).

Phased implementation plan

  1. Phase 1 — Schema + service foundation (one commit). Migration + backfill + drop vcs_staging. Rewire stage_files/unstage_files/ get_status/commit to session-scope. Old staged BOOLEAN stays as compat mirror.
  2. Phase 2 — CLI + env var (one commit). vcs session {start,end,list,current,show}. TEMPLEDB_SESSION_ID resolution. vcs status session badges. Human-friendly output changes.
  3. Phase 3 — Regression investigation. Reproduce on a scratch project. If fix is under an hour post-diagnosis: land it. If bigger: separate design report, defer the fix, ship staging without it.
  4. Phase 4 — Tests (one commit). tests/vcs/test_sessions.py: two-session isolation, commit scoping, backfill correctness, backward compat when env is unset. Existing VCS tests must still pass.
  5. Phase 5 — Docs + session recap (one commit). Update docs/advanced/STAGING_OPERATIONS.md. Add a TEMPLEDB_SESSION_ID line to top-level CLAUDE.md. Recap HTML per convention.

Open questions to resolve during Phase 1

  • Whether the staged BOOLEAN compat mirror is maintained by a trigger, by service code, or dropped immediately. Recommendation: service code (fewer moving parts than triggers, more revertible than a same-migration drop).
  • Whether vcs commit should refuse to run if there are other sessions’ staged rows in the same branch, or silently ignore them. Recommendation: silently ignore (that’s the whole point of isolation); print a footer noting “3 files staged in other sessions were not included” so the user can inspect if surprised.
  • Whether vcs reset -a without a session should error or default to current-session-only. Recommendation: default to current-session-only; --force --all to clear everyone.
