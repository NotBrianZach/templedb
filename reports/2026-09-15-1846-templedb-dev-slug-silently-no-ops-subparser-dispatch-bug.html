templedb dev slug silently no-ops subparser dispatch bug

templedb dev <slug> exits 0 while printing the top-level usage and never launches the dev server. templedb dev --help still works and shows the subparser expects project as a positional, so the dispatch path (or its wrapper) is silently swallowing the resolved subparser invocation.

Reproduction

$ templedb dev bza
usage: templedb [-h] [--version] [--json] [-C PATH]
                {dev,project,vcs,file,env,var,search,...} ...
...
Use 'templedb <command> --help' for details on any command.
$ echo $?
0

Confirmed foreground and background. Neither an explicit --env staging nor rearranging positional/option order changes the behavior.

Contrast: subparser help works

$ templedb dev --help
usage: templedb dev [-h] [--env ENV] [--command COMMAND] project
positional arguments:
  project              Project slug
options:
  -h, --help           show this help message and exit
  --env, --target ENV  Environment target (default: staging)
  --command COMMAND    Custom command to run (overrides auto-detection)

So the subparser exists and its schema is intact — the wrapper that hands off to the dev handler is where the drop happens.

Impact

templedb dev is the sanctioned way to boot the dev server with decrypted env + secrets. Working around it means running node_modules/.bin/next dev directly from the checkout, which ships no secrets — Supabase middleware then 500s and no page renders. Agents and humans lose the ability to click-through changes without hand-injecting env vars. Uncovered while trying to browser-verify a BookReader refactor (see commit 51813E18).

Signal for the fix

Silent success (exit 0 + top-level help) suggests the handler is called, the argparse subparser returns a Namespace missing the expected func or handler attribute, and a fallback prints top-level help instead of erroring. Compare the dispatch site to a subcommand that does work (templedb vcs status <slug>) to see the diverging path.
