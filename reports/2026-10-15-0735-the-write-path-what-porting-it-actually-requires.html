The write path: what porting it actually requires

templedb-rust answers every read-only command and verifies each one by byte-diffing stdout against Python. Step 12 of its porting order is “any write path, and not without a design document.” This is that document. Its conclusion is that the two things blocking writes are not SQL: the verification method cannot test a mutation, and the trait the whole port is built on has no way to perform one. Both have fixes, and the fixes are the first work, before any command.

Where the port stands

Steps 1 through 11 are complete. Verified on 2026-10-15 against the live database: cargo test --workspace passes 187 tests in templedb-db plus the CLI set; all three #[ignore]d CPython-oracle tests pass, covering both the unified and context renderers against difflib; and scripts/parity-sweep.sh python reports 40 invocations, 34 stdout-identical, 6 deliberate, 0 unexpected.

So the read layer is as complete as it can get without sessions, and the remaining question is a real design question rather than a backlog of translation.

Problem one: the verification method dies here

The port's method is byte-level: run both binaries, diff stdout. That method has a precondition nobody had to state while the port was read-only — both implementations get the same input. A write is a mutation of that input. Run Python's commit and then the port's against one database and the second sees a database the first changed. There is no same-input run to diff.

It is worse than sequencing, because the output is non-deterministic by construction. commit.py:497 mints the commit id as: 

commit_hash = hashlib.sha256(
    f"{project['id']}-{message}-{time.time()}".encode()
).hexdigest()[:16].upper()

Wall-clock in the hash input. Two runs a microsecond apart disagree, so even against a pristine copy of the same database, stdout cannot match and neither can the row.

What replaces it

Three techniques, none of which is a stdout diff:

TechniqueWhat it checksWhat it needs
State diff Copy the database twice. Run Python's write against copy A and the port's against copy B. Diff the two resulting databases, not the two stdouts. An injectable clock and id source, so commit_hash and every datetime('now') are equal by construction rather than excluded from the diff. Excluding them would hide exactly the columns most likely to be wrong.
Refusal parity Every guard refuses with a specific exit code and message. For a write, the refusals are the contract. The Error exits are all 1 known gap closed first. Today every error leaves through one anyhow path. That is tolerable for a reader and not for a writer.
Cross-read The port writes; the already-trusted read layer reads the result back and is diffed against Python reading the same rows. Nothing new. This is the one technique available today, and it is why the first write to port should be one whose effect is fully visible through existing read commands.
The clock seam is shared with summary. The README defers summary because its output carries relative ages and a session id from os.getppid(), so a byte diff is meaningless — it needs injected time and a fixed session id. That is the same seam the state-diff harness needs. Doing summary first builds the seam against a read command, where a mistake costs nothing, and delivers a command on the way.

Problem two: Store cannot express a write

The trait is two methods — dialect() and query() (store.rs:50). There is no execute, no transaction, and the SQLite backend opens the file with SQLITE_OPEN_READ_ONLY as a flag rather than a URI parameter specifically so the restriction is visible in the type (backend/sqlite.rs:44).

There is already a precedent for writes that does not touch the trait: mirror holds a concrete postgres::Client, opens a real transaction and streams with COPY (mirror.rs:330). It writes only the Postgres replica it owns.

Recommendation: do not widen Store

Add a separate concrete SqliteWriter owning a writable Connection. Leave Store read-only and leave the read path's READ_ONLY flag exactly as it is. Three reasons:

  • A write trait would have one implementation. Postgres is a read replica and a parity target; writing to it is not wanted and would not be correct. A trait abstracting one backend buys nothing.
  • Widening the trait costs the read path its guarantee. Every reader would hold a handle that could, in principle, write. The flag in the type is cheap insurance and there is no reason to spend it.
  • Transactions do not fit behind a trait object anyway. rusqlite::Transaction borrows the Connection, so it cannot be returned through &dyn Store — the same lifetime reason store.rs already records for keeping query_map out of the trait.

A write therefore means a second, explicitly-opened handle, and the read handle stays what it is.

Problem three: the database writes back

The schema is not inert. Measured on the live database (~/.local/share/templedb/templedb.sqlite): 164 tables, 45 views, 61 triggers, 362 indexes. The port reads 11 tables and 1 view. Triggers fire for whoever writes, so the port inherits them whether or not it knows they exist.

TriggerFires onConsequence for the port
update_branch_head_on_commit AFTER INSERT ON vcs_commits Moves vcs_branches.head_commit_id to the new row. Free, and it dictates ordering: the parent must be read before the insert, which is what commit.py:511 does and why.
link_intent_to_commit AFTER INSERT ON vcs_file_states, WHEN content_hash IS NOT NULL A correlated UPDATE over edit_intents picking one row by hash, path and timestamp. Reimplementing it in Rust would double-apply it.
file_contents_fts_file_* project_files update/delete Rebuilds the FTS5 index. Reads never touch it — step 3 moved matching into Rust — but a write does, through these.
*__crsql_itrig / utrig / dtrig 10 sync_* tables 58 of the 61 triggers. Their bodies call crsql_internal_sync_bit() and crsql_after_insert().

Two hard boundaries this exposes

cr-sqlite is a hard stop. Those 58 triggers call functions that live in a loadable extension. The port loads no extensions — there is not one reference to crsql anywhere in crates/. Any INSERT into a sync_* table from templedb-rs fails with no such function, and that is the good outcome: the alternative would be CRDT metadata silently not maintained, which is a divergence that only surfaces on the next sync between machines. So the write path must not touch sync_* until cr-sqlite is deliberately loaded, which needs rusqlite's load_extension feature and a version matched to whatever Python loads.

Two SQLite versions, one FTS5 index. The port bundles its own SQLite — libsqlite3-sys 0.35.0, which reports 3.50.2 in the release binary. Python uses the system interpreter's, 3.53.3. For reads this is irrelevant and has been all along. For writes, both versions would maintain one FTS5 index through the triggers above. Probably fine; SQLite is conservative about format. But it is an untested overlap, it is invisible until a search returns the wrong hit set, and the cheap mitigation is to decide it deliberately — either link the system SQLite for the writer or pin the bundled version against Python's.

The guards are the deliverable

The INSERTs in commit.py are the easy part and the least of it. What surrounds them is a set of invariants each of which exists because something went wrong on a specific date. A port that reproduces the SQL and not these is a regression even if every byte of output matches.

GuardWhy it exists
Mass-deletion
commit.py:268		 The diff is taken against whatever directory was passed, so a path that was never a project root — the parent of a session workspace — makes every tracked file look deleted. Deletions tombstone paths, and re-adding a tombstoned path hits a UNIQUE constraint. Floor plus fraction, with --allow-mass-delete.
Double-encoded UTF-8
commit.py:311		 UTF-8 read as Latin-1 and written back as UTF-8 is still valid UTF-8, so hashes match and --verify passes. bza's page.tsx shipped that way for two weeks. Enforced on the count for modifications only — additions have no baseline and vendored blobs trip it legitimately.
Intent-conflict refusal
commit.py:428		 --strategy force reads as “take my workspace”, but against a conflict created by a newer file set it reverts that write. Reverted 4 agent-freeze fixes plus 4 test files on 2026-09-13, and gui.py and gui_helpers.py the same way on 2026-09-14.
Session resolution outside the transaction
commit.py:466, db_utils.py:233		 Session creation inserts into vcs_sessions with commit=True. Called from inside the transaction, its commit ended the caller's — so a later per-file failure rolled back the file states but could not undo the already-committed commit row. Result: a commit with zero vcs_file_states, listed in the log, breaking the parent chain. Reproduced on demand 2026-10-03. transaction() now suppresses the inner commit; the hoist is so the session survives a rollback.
Checkout resolve(purpose)
checkout_repository.py:228		 Rows are classified canonical / edit / scratch; scratch is never resolved to, only used when named explicitly. PURPOSE_WRITE refuses outright when a project has no checkout rows: 10 of 24 projects had none, and every one passed the old write check and then took the repo_url fallback into an imported source directory.
Parent linkage
commit.py:501		 Omitted entirely at first, so every commit through this path was a root. 541 of templedb's 554 commits were unreachable from any branch head as of 2026-10-03.
commit_hash format
commit.py:475		 [:16].upper(), not the 40-char lowercase this minted until 2026-10-13. Migration 126 gave commit_hash one meaning on the premise that 40-char lowercase identified an imported git SHA. The writer kept minting values the new rule read as git SHAs; commit_hash_is_canonical went red across 77 rows in five projects.

Note what this list is: seven invariants, five of them dated incidents, none discoverable from the schema. It is the strongest argument for porting writes slowly, and the reason the rest of this document recommends starting somewhere other than commit.

Recommended order

Not templedb commit first, despite being the obvious write. It is the widest door in the system: workspace scan, three guards, conflict detection with resolution strategies, session head bookkeeping, commit metadata, and per-file writes across four tables.

  1. The clock and id seam, via summary. Injectable time and a fixed session id, built against a read command where being wrong is free. Delivers summary, which is otherwise blocked on exactly this.
  2. Close the error-exit gap. Distinguish the exit codes and match the stderr text. Refusals are the write contract, and this is currently a documented divergence on every error path.
  3. The state-diff harness. Two database copies, one write each, diff the results. No command ported yet — this is the replacement for the method that stops working, and it should exist before the thing it verifies.
  4. First write: single-file file set with --if-match. One logical change across content_blobs, file_contents, project_files and edit_intents; no workspace scan; no resolution strategies. It carries its own optimistic-concurrency guard, so a repeat run is safe, and its entire effect is visible through read commands the port already verifies — file cat, source revisions, search content. It also exercises every structural problem in this document at the smallest possible scale: blob insert-or-ignore, flipping is_current, the FTS triggers, and an edit_intents row.
  5. Then vcs commit, then workspace commit, in that order, guards first and SQL second.

Two things that are not in that list but must be decided with it

Any write makes the Postgres mirror stale, and nothing currently notices. The mirror is a read replica refreshed by running mirror; a write to SQLite silently invalidates it. Either the writer marks it stale or the mirror learns to detect it. A parity sweep run across backends after a write would otherwise report differences that are neither bugs nor deliberate.

Two writers is the situation the read-only rule has been preventing. The pragmas already match Python — busy_timeout 30s, journal_size_limit 64 MiB — and WAL supports concurrent writers, but the port must not hold a write transaction across a workspace scan. Keep the writer behind an explicit opt-in (an env var, not a default), and keep the binary named templedb-rs: the README's rule still holds, that shadowing templedb on PATH while incomplete breaks callers silently.

Open questions

These are decisions, not research tasks. Each changes what gets built.

  • cr-sqlite: load it, or refuse every sync_* write? Refusing is cheap and safe and leaves CRDT sync Python-only, possibly forever. Loading it means matching the extension version Python uses and taking on the CRDT semantics.
  • May the harness copy the live database? The state-diff method wants two copies at roughly 340 MB each. If that is unacceptable, the alternative is a seeded fixture, which tests less.
  • Does the writer link system SQLite instead of bundling 3.50.2? This removes the version-skew question at the cost of the reproducible build the bundled dependency gives.
  • Does Postgres-as-primary stay out of scope? The README couples it to the write path. This document assumes it stays out: writes go to SQLite, Postgres stays a replica. Deciding otherwise changes every recommendation above.

What this document commits to

Nothing is implemented. The claim is narrower than a plan and should be read as the precondition the porting order asked for: the blocking problems are the verification method and the Store trait, in that order; the guards are the deliverable rather than the SQL; cr-sqlite is a boundary not to cross by accident; and the first three pieces of work are a clock seam, an exit-code fix and a harness, none of which is a write.
