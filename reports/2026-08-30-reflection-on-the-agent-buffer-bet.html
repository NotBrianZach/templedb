Reflection on the agent buffer bet

Written after a marathon day rebuilding the Temple Agent rendering pipeline end-to-end: persistence firewall, section anchors, an ewoc-driven Conversation region, agent-writable sections with MCP tools, and a working Python test suite. This report captures the missing-features list, the project philosophy as observed from inside a full day of dogfooding, analogies that helped me reason about the design, and concrete ideas for making the human/agent shared-state UX better.

Missing features (in leverage order)

1. Reverse channel: user edits notify the agent

Right now the agent sees the user's ask_user responses, but if the user marks a todo done via keybinding, edits a Note, or deletes a finding Claude just added, the agent has no idea. This makes the collaboration one-way: the agent writes into a buffer where the human can silently override it. Fix: emit agent.user.section_edited events (change type, section, entry id, before/after) and inject a compact summary into the next turn's context so the model knows its state was mutated.

2. Cross-session knowledge search

Findings/todos/questions accumulate per-session and then evaporate at session boundaries. A new tool templedb_agent_search_findings(query, project?) that walks agent_session_sections across every prior session (optionally scoped to a project) would let each Claude benefit from what prior Claudes discovered. Right now every session re-discovers the same non-obvious facts. Add a matching _search_todos and _search_questions.

3. Multi-agent coordination

We hit real SQLite write-lock contention today when the MCP tools fired concurrently. Retry-on-lock helps, but the underlying gap is that two agents on the same DB have no coordination model beyond hoping their write bursts don't overlap. The vcs_sessions primitive already exists as per-shell staging isolation — extend the pattern to agent sessions with advisory claims (“Claude 2 is editing this file, don't touch”), not hard locks.

4. End-to-end MCP test harness

ERT covers the Emacs side (26 tests); unittest covers the store layer (55 tests, working now after today's pytest fixes); nothing drives a fake MCP client through the full tool → poll → emacs event chain. If we'd had one, today's templedb_launcher.py deadness — six weeks of a broken templedb_ask_user nobody noticed — would have been caught in a single CI run.

5. Diff view for Edit tool results

Claude's Edit tool renders its diff as a plain #+begin_src block. Emacs has ediff one function call away. Same for Read tool results (syntax-highlight the preview). Small change, big legibility win.

Nice-to-have, not urgent

  • Cost/context section (agent-tracked token spend rendered live)
  • “Undo the last N agent writes” command
  • Time-window view (“what did Claude do in the last 5 minutes”)
  • Auto-collapse by relevance (recently-referenced files) rather than exchange age

Project philosophy, as observed from the inside

Two convictions worth naming, because they're not standard:

The DB is truth, not the filesystem

Datomic's bet applied to a dev environment. Materialize files only when a tool needs them. Queries over commits are cheap. Branches are views, not divergent trees. Cross-project queries (graph who-uses, section search across sessions) are one SQL statement, not a corpus scrape.

Costs: everything is a store hop, git interop is glue code, humans instinctively edit files on disk and get burned when the DB overwrites them. Payoff shows up in questions you can ask and manipulations you can perform that would be totally impractical in a filesystem-native world.

Every surface is a first-class client

CLI, FUSE, Emacs, MCP, HTTP GUI — same data, different I/O paths. A LOT of glue code. But the payoff showed up today: MCP tools weren't a new subsystem, they were just another surface writing to the same tables the CLI writes to. Agent-friendliness came free because agents are just another surface.

Live tension Both convictions collide with the naïve implementation of a living buffer. The Emacs buffer wants to be the surface (edit-through, mutable, immediate) AND the truth (persisted, canonical). It can't be both without a firewall between them. Every architectural refactor today (persistence firewall, section anchors, ewoc rewrite) was a variation on that same theme: separate the view from the truth so state can be reasoned about.

The shared-state UX: what would make it feel great

The buffer today is a competent shared canvas but feels one-sided: the agent writes; the human reads and sometimes types a reply. A handful of concrete additions would flip it from “chat log with sections” to “live collaborative workspace where an AI and a human can actually collaborate on shared state.”

Presence & provenance

  • Highlight the last N writes for a few seconds with a fade-out overlay. Same trick multi-user Google Docs uses. Currently a finding just appears and the human has to scroll to find it.
  • Author badges on entries. Each Finding / Todo / dynamic-section entry should show [claude] vs [you] at insertion. Right now everything looks equally authoritative.
  • Cursor telemetry. Show “Claude is looking at this file” in the Now section (agent tells the buffer what it just read via a new event). It's the multi-cursor Google Docs pattern applied to attention rather than typing.

Reversibility & safety

  • Per-entry undo. Every agent-written entry gets a , u keybinding to (a) delete it and (b) emit a corresponding agent.section.*.remove event so the DB and the buffer stay in sync. Related tool call gets a “user reverted this” tag Claude sees next turn.
  • Soft delete with a “trash” view. Removed entries move to a hidden fold rather than being gone; can be recovered until session close. Emboldens the human to keep the surface clean without fearing information loss.

Discoverability & density

  • Section summary in modeline. [F:3 T:5 Q:1 D:2]: number of findings, open todos, unanswered questions, dynamic sections. Users know at a glance if state has accumulated they should look at.
  • Notifications for high-signal writes. A new Finding while the agent buffer is hidden should surface via the existing --notify-if-hidden path (already used for run-complete). Todos and dynamic-section writes probably should not — too noisy.
  • Structured filter/query on sections. , / f auth narrows Findings to entries whose text or refs match “auth.” Not org-search; a dedicated query on the underlying data model. Once we have a data model (we do now), this is trivial.

Bidirectional editability

  • Promote-to-user-section. , p on an agent finding moves it into Notes as a user-owned copy, decoupled from further agent updates. Turns “this finding matters” into a persistent human artifact.
  • Prompt scaffolding from Todos. Selecting a todo and hitting , s drops it into Next Prompt as “please do <todo text>” and marks it in-flight. Closes the loop between planning and doing.
  • Inline agent-callout markers. Any text the user types can include @claude and hit Send — the buffer highlights it, and the agent gets a callout in context (“user mentioned you in Note X”). Same pattern GitHub uses for cross-issue references.

Latency & feedback

  • Optimistic UI on MCP writes. When Claude calls a tool, immediately render a “pending” placeholder in the section, replace with the real entry when the event arrives. Right now there's a ~300ms poll gap between tool call and section update; the latency isn't awful but a placeholder makes the causality obvious.
  • Progress ticker on long tool runs. Bash / subagent tools that take >5s should emit periodic tool.progress events (or the agent service should infer them from stderr) so the RUNNING heading updates. Currently a stuck run just sits there.
Unifying pattern Everything above is one idea: make the shared state legible in both directions. Today the buffer is a great canvas for the agent to write on; it's a mediocre canvas for the human to write on with the agent watching. Fix the reverse channel + presence/provenance/undo, and the buffer becomes an actual collaboration surface.

Analogies that helped me reason about it

Concept in TempleDB Analogy What it explains
Persistence firewall React controlled components Buffer text isn't truth; state is. The --save-user-sections function is the onChange handler that gates when state updates. The scratch-pollution bug is what you get when you setState from every render.
Section anchors vs regex DOM id vs XPath Anyone who's built a scraper by structural traversal knows the regret. Text-property anchors are the org-mode id.
Ewoc for Conversation Virtual DOM diffing Declarative render from a data model, efficient per-node invalidation. Same reason React beats jQuery for anything with mutable state and async events.
MCP tools + pending events Actor message-passing over the DB as bus Very Erlang, especially the round-trip vs one-way split (agent_pending_asks needs a response; agent_pending_events doesn't). SQLite is the mailbox.
The whole system Modern Lisp Machine One addressable, introspectable, live-updateable environment. Genera or Smalltalk energy, but bolted onto Unix via thin adapters (bash, FUSE, git-daemon, systemd) rather than replacing it wholesale.
Dogfooding Ouroboros I used templedb file cat, templedb commit, and templedb nixos system-switch to modify the code that implements those commands. Every incremental change was tested by the next commit's usage — a stronger integration test than any CI could provide.

What's genuinely novel here

Most AI-in-your-editor stories put the LLM in a sidebar and pass files back and forth (Cursor, Copilot, the standard Claude Code invocation). The bet in Temple Agent is treating the AI as a first-class collaborator on shared state: it writes into * Findings, marks todos done, spawns a * Blockers section — into the same buffer the human is typing their next prompt in. That's a real bet on a different metaphor for human/AI collaboration, and it's mostly untried at this level of ambition. If the UX improvements above land, it becomes a pattern worth stealing widely.
