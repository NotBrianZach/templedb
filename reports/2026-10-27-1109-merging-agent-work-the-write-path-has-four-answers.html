merging agent work — the write path has four answers

templedb has a real three-way merge with diff3, conflict markers, per-file decision records and an AI assist hook. Concurrent agent work never reaches it. Agents do not branch — every session writes to main — so the thing sessions isolate is staging, not content, and two agents editing one file serialise by wall clock. On 2026-10-27 that overwrote a published file with no conflict, no warning, and an audit trail naming the wrong author. It was safe only by luck.

The question

Prompted by watching it happen. While publishing three fixes to src/cli/commands/file.py, a sibling agent rewrote the same file in the database underneath the publish. Nothing errored. Nothing warned. The reasonable question was whether that is the system working as designed or a mess — and if it is a mess, what the alternatives are given what is already built.

The short answer: the pieces of a good answer are all present, and they are wired to the three write paths that are not how agents actually work.

Four write paths, four different concurrency stories

This is the whole finding. The guard you get depends entirely on which command you reached for, and the difference is not documented anywhere as a difference.

PathConcurrency guardOn conflict
templedb commit <workspace>
workspace diff		 Real. Two independent checks in _detect_conflicts: version-based (another session committed while this workspace was editing) and intent-based (a file set moved the DB while the workspace copy went stale). Refuses, names the file, prints your version vs current and who changed it. --force still will not push through an intent conflict without --allow-revert-intents.
templedb vcs merge <branch> Real. ThreeWayMerge over base/ours/theirs trees, per-file _merge_file records carrying confidence, decided_by and prose reasoning. Records the conflict; manual resolution. --strategy ours|theirs|ai-assisted is recorded but not applied — its own help string says the resolver is not wired in.
templedb merge from-git Real. Same resolver plus AIMergeAssistant.suggest_resolution and an interactive review loop. Interactive review of suggestions, then applies resolutions.
templedb file set
the path agents actually use		 Opt-in only. --if-match <hash> is a compare-and-swap and it is the only guard. Omit it and there is no check of any kind. Nothing. Last write wins, whole file, silently.

The asymmetry is not that file set is unguarded — it has a perfectly good CAS. It is that the guard is opt-in on the one path that is used by processes which cannot be relied on to opt in. CLAUDE.md's first hazard is three paragraphs instructing the reader to always pass --if-match, which is documentation standing in for a default.

Why the merge engine never runs on agent work

A three-way merge needs two divergent lineages and a common ancestor. Agent sessions produce neither, because sessions are not branches. vcs_sessions rows scope staging: which rows a given vcs commit may sweep up. They do not scope content. Every active session resolves to the project's default branch — templedb and system_config have exactly two branches each (main, plus a legacy master), and templedb-rust has one, across a fleet that has run 80+ sessions.

file_contents holds one is_current=1 row per path. Two agents writing one file are not two branches to reconcile; they are two UPDATEs. The second wins. There is no ancestor to diff against because the first version was never anywhere except in the row the second one replaced.

Edit workspaces look like the missing isolation and are not. A workspace is a materialised view that diffs against the DB at commit time — which is exactly why the workspace-diff path is the one that grew real conflict detection. An agent that uses file set instead bypasses the workspace, and with it the only concurrency check that fires by default.

What actually happened on 2026-10-27

Reconstructed from edit_intents, which is the one place the sequence survives.

7d67200c5b78   my published version (git f354a78), containing a session_id fix
0d8505b5bce6   that, plus a sibling agent's three rust-port write-path fixes

#1255  15:58:18  session 1191 (agent-fixups = me)              7d67200c -> 0d8505b5
#1256  15:58:24  session NULL                                  file_repository.py
#1257  15:58:25  session NULL                                  test_write_path_regressions.py
#1258  15:58:42  session 1188 (claude-code-agent-12418)        0d8505b5 -> 0d8505b5

Three files rewritten in a seven-second window, then a fourth write 24 seconds later. Read the hashes and two things fall out.

The clobber was invisible and survived on luck

Intent #1255 replaced my just-published file wholesale. No conflict was detected because none can be on this path. It was harmless only because 0d8505b5 happened to be a superset — the other agent had started from a copy that already contained my fix, so their whole-file write carried it forward. Had they started from a copy fetched thirty seconds earlier, my fix would have vanished with no error, no conflict marker, and a green --verify: verify confirms that what you wrote is what landed, not that you meant to drop the rest. That is hazard 1 in CLAUDE.md, and it is still live.

The audit trail names the wrong author

This is the sharper problem. The write that changed the content, #1255, is stamped session 1191 — mine. I did not author that content. The agent whose work it is, claude-code-agent-12418, appears 24 seconds later at #1258 writing 0d8505b5 -> 0d8505b5: a no-op, recorded as the only thing it did.

So provenance is not merely missing here, it is inverted. A reader reconstructing this afternoon from edit_intents would conclude agent-fixups made the rust-port changes and 12418 did nothing. Both halves are wrong. Two sibling intents in the same batch (#1256, #1257) carry session_id NULL, which is the older bug — the deployed binary was still pre-fix until the switch completed at 16:00:41 — but NULL is honest about not knowing. #1255 is confidently wrong, and I cannot explain the mechanism from the data available; it needs its own investigation.

Worth separating two failure classes that look alike. Lost content is survivable: git holds the published copy, and git show <rev>:<path> recovers it. Lost attribution is not recoverable after the fact — once a write is stamped with the wrong session, nothing else in the system records who actually made it.

And nothing above the intent layer records a session at all

The intent inversion turns out to be the better-instrumented half. Checking whether the commit layer could be used to cross-check it:

SELECT COUNT(*), SUM(session_id IS NULL), SUM(files_changed = 0) FROM vcs_commits;
   1463 commits   |   1387 session_id NULL   |   1460 files_changed = 0

95% of all commits carry no session. That is not a historical backfill gap: the commit that added this report was made with an explicit --session 1193, printed Session: #1193 (agent-mergereport) in its own confirmation, and wrote session_id NULL. The flag that CLAUDE.md documents as outranking both environment variables is accepted, echoed, and dropped on the floor.

files_changed is the same story — 1460 of 1463 rows say zero, including the commit above which reported Files: 2. Two columns that exist to answer "who changed what, and how much" answer neither, which is how a project can run an 80-session fleet and have no queryable record of which agent did anything.

So the attribution problem is not one bug in the intent recorder. It is that session identity is resolved independently at every layer and persisted correctly at almost none of them: the stage gets it right, the intent gets it wrong or NULL, and the commit discards it even when told explicitly.

So: is it messy?

Yes, but not in the way "messy" usually means. Nothing here is sloppily built — merge_resolver.py is 506 careful lines, the per-file merge records carry reasoning strings, and the workspace-diff conflict detector has been fixed twice with the reasoning written down both times. The mess is structural: the sophistication sits behind vcs merge and merge from-git, and the traffic goes through file set. Four write paths disagree about what safety means, and the weakest one is the default for automation.

The honest summary is that templedb currently has no merge strategy for concurrent agent work. It has a clobber strategy with an opt-in interlock.

Alternatives

Ordered by cost. These compose; 1 and 2 are close to prerequisites for the rest being trustworthy.

1. Make the CAS mandatory instead of opt-in

Have file set require a base hash, or default to "the hash I last read for this path in this session" and fail loudly when the row has moved. The primitive exists and works — --if-match already takes a prefix of ≥8 hex and exits 2 naming both hashes. Flipping the default turns every silent clobber into a retry.

Cost: low mechanically, breaking for callers. --force or --no-if-match gives the escape hatch, and the intent row already stores base_revision, so the value needed is being recorded even now. Caveat: base_revision was the literal string 'current' on all 886 early rows and is catalogued in unmaintained_columns_baseline as a constant — the column designed to record what an edit was made against only recently started recording anything. Making it load-bearing means auditing that it is actually populated, not merely present.

2. Fix attribution before building anything on top of it

Every strategy below assumes you can tell whose write is whose. The measurements above say you cannot, at any layer. One command, one answer: the session resolved for the stage must be the session stamped on the intent, on the commit, and on any lease. This session fixed one third of it — the stage's session is now threaded into the intent rather than re-read from an env var — but #1255 shows an intent path that still lands the wrong id, and vcs_commits.session_id is dropped even when --session is passed explicitly.

Ranked by cost-to-fix against value, the commit layer is the place to start: it is a single column on a single INSERT, the value is already resolved and printed to the user one line earlier, and it is the only layer whose rows are permanent and user-visible through vcs log. Fixing files_changed in the same pass is near-free and would stop two no_new_unmaintained_columns complaints from being load-bearing lies rather than merely empty.

3. Branch per session, merge on completion

The option that uses what is already built. vcs session start creates a branch; the agent commits to it; finishing the session runs vcs merge, which is a genuine three-way with ancestor tracking and per-file records. It converts invisible clobbers into visible conflicts, and conflicts are a solved genre.

Cost: real but bounded. Two gaps block unattended use. First, --strategy is recorded and not applied, so every non-trivial conflict needs a human — with 80+ sessions that is the whole cost of the scheme. Wiring the resolver is the unlock, and AIMergeAssistant already exists for the ai-assisted case on the from-git path. Second, branch-per-session multiplies the checkout-role ambiguity this session spent hours on: more branches means more materialised trees means more "whichever is newest wins". Fix 2 first.

4. Make intents patches rather than snapshots

edit_intents already has the right shape — base_revision, new_content_hash, patch_summary, a status lifecycle, an applied_commit_id. But the payload is whole content, so patch_summary is a byte count and an intent is a snapshot wearing a patch's clothes.

If an intent carried the diff, a write whose base has moved could be rebased rather than rejected: apply my hunks to the new current content, and only escalate on genuine hunk overlap. That is the difference between "your base is stale, start over" and "your base is stale, here is your change applied anyway" — the latter is what makes mandatory CAS tolerable at fleet scale rather than a source of constant retries.

Cost: highest here, and the most leverage. It also makes intent apply meaningful as a replay mechanism rather than a bookkeeping echo.

5. Pessimistic leases per path

Sessions already exist as a durable identity with a liveness notion, so a short lease on (project, path) is cheap: refuse the write, or queue it, while another live session holds the path.

Cost: low to build, poor fit. Lease holders here die without releasing — every one of the five "open" sessions audited this session had a dead PID, and reaping is age-based, so a crashed agent would park a lock on a hot file for up to 24 hours. Liveness detection is the hard part and it is already the known-weak part. Worth it only for a narrow set of paths where a clobber is unrecoverable.

6. CRDT / convergent replication

Tempting because the substrate is already linked in: the DB carries crsql_master, crsql_site_id and __crsql_clock/__crsql_pks companions for the sync_* tables. Convergent merge is present and used for config sync; it is simply not applied to file_contents.

Cost: wrong tool, and worth saying why so it stops coming up. A text CRDT guarantees the replicas converge on the same bytes, not that the bytes compile. Two agents editing disjoint regions of one Python file converge to a file where both edits are present and the function signature one of them changed no longer matches the call the other added. For source, semantic conflict is the thing you need to surface, and convergence is precisely the property that hides it. The crsqlite dependency is also fragile here — a silent load failure cost ten days of hourly git-ingest failures once, and no doctor check covers a recurrence.

Recommendation

Do 2, then 1, and stop there until something demands more.

Attribution first, because it is cheap and everything else is untrustworthy without it, and because a wrong author is the one damage class that cannot be undone later. Then flip the CAS default: it is a small change that converts the actual observed failure — a silent whole-file clobber of published content — into an exit code. Together they make the current single-branch model honest, which is a better outcome than making it sophisticated.

Branch-per-session (3) is the right end state and the wrong next step: it needs the unwired resolver and it worsens checkout ambiguity, so it should follow 2 rather than substitute for it. Patch-shaped intents (4) are the most interesting long-term idea here and the one worth designing properly rather than reaching for under pressure. Leases (5) and CRDTs (6) should be declined explicitly so they stop being re-proposed.

One structural note that outlasts this report. Three times in two days the load-bearing defect was a good implementation that nothing called: --strategy's resolver, the entire templedb nix command group, and scan_generations as the only backfill for nix_generations. The merge engine is the fourth instance and by far the most expensive, because its absence does not look like a missing feature — it looks like concurrent writes being fine.
