Math Workbench: the spec, and the engine it did not know existed

A new spec arrived declaring the project's direction: an Emacs/Org mathematics workspace over Calc and SymPy, with "correlation games" that branch creative interpretations off an investigation and return new mathematical questions to it. Recording it surfaced a problem with its own premise. The spec treats aireadalong.com as an unretrievable third party whose interface must be guessed at; aireadalong.com is this user's own bza project, and it already ships a correlation-game engine with a richer vocabulary than the one the spec invents. No code was written this session. What changed is what the next session should build.

What triggered the session

The ask was a declaration, not a task: "going forward this project will implement the following spec," followed by the full Math Workbench specification dated 2026-10-12. The correct response to a declaration is to make it durable and verify its premises — not to start writing Emacs Lisp.

The work branched twice. First a hook fired: MEMORY.md had grown to 197 lines, near the 200-line read limit, because ~180 lines of TempleDB architecture content had been inlined into what is supposed to be a one-line-per-entry index. Second, and more consequentially, writing the index pointer for the new project required naming bza.md — whose first line reads BZA (aireadalong.com). That single parenthetical falsified a load-bearing assumption of the spec.

The premise that was wrong

The spec says of its integration target: "its public interface was not retrievable, so no existing API, authentication mechanism, export format, or implementation is assumed." Milestone 3 is accordingly gated on "obtain an example game record or export, the actual site interface or repository."

That repository is local, indexed in TempleDB as bza (556 files), and it contains:

  • frontend/app/api/correlate/turn/route.ts — a full turn engine. POST {sessionId, medium, offeringId?, composed?, framing?, claimedRelation?, prediction?, parentTurnId?, tuning?, selfReply?}, bearer auth via getUserFromToken, quota via checkQuota.
  • frontend/lib/correlate/ — types.ts, games.ts, graph.ts, media.ts, relations.ts, tuning.ts, prompt.ts, continuation.ts, scope.ts.
  • docs/CORRELATION_GAMES.md — the design doc, which independently reasons through several questions the spec also raises.
  • supabase/setup/52_correlation_games.sql (+ 54 trash, 56 presets) — persistence. Tables keep their historical listen_turns / listen_sessions names from the music-only /listen origin.
  • frontend/components/correlate/ — CorrelationBoard, BranchMap, GamePicker, OfferingPicker, TuningPanel, PresetPicker, OfferingCard.

So milestone 3 is not blocked on discovery. It is blocked on a design decision that nobody has made yet, because the spec did not know there was a decision to make.

Where the two vocabularies disagree

ConcernSpec proposesbza already has
The atomic unit payload: {kind, object_id, snapshot} Offering = (content or action, medium, framing). The design doc calls framing "the load-bearing new field": without it "two players respond to different things without noticing." Required, never defaulted to "all of it."
Kinds of connection 5 moves and 5 interpretive relations, overlapping (break_the_analogy the move vs breaks_analogy the relation) 7 relations: association, translation, transformation, counterpoint, embodiment, continuation, reinterpretation — in a registry deliberately separate from media, which is what makes "a change of medium is itself a move" expressible rather than accidental. Each carries requiresMediumChange, and the engine rejects a declared relation the chosen medium cannot support before spending a model call.
Media song link, image link, scene reference, movement description 12 media: music, artwork, passage, gesture, stretch, exercise, movement, scene, and the knowledge media theorem, phenomenon, organism, place.
Anti-fabrication "AI must not fabricate scene timestamps, song details, or media URLs" — stated as a rule Enforced structurally by origin: a catalogue offering must resolve against a real collection and a miss is recorded; a composed one cannot lean on "the search found it," so it must carry ordered concrete steps (performability). The model never asserts a thing exists.
Analogy limits interpretation.mapping[] and interpretation.limits carried and lost columns — "what survived the crossing, and what did not. The interesting half of a cross-medium game." A near-exact match, arrived at independently.
Branching milestone 3: "branch handling" Shipped: parentTurnId (present-and-null starts a thread, absent continues), graph.ts, BranchMap.tsx.
Disagreement "preserve conflicting interpretations as branches" claimed_relation stored alongside the interpreter's ruled relation, specifically "so a disagreement between the two stays visible instead of being silently overwritten."

The theorem medium deserves singling out. Its comment in types.ts already states the spec's central epistemic worry: 

// The knowledge media. Catalogued rather than composed, and the reason is the
// most important thing about them: a theorem is a *proposition*, so its content
// can be confidently wrong rather than merely bad, and performability — the
// guard that makes a composed medium honest — catches vague mush, not fluent
// error.

That is the same insight as the spec's evidence taxonomy, reached from the other direction. The spec worries that a vivid analogy will be mistaken for mathematical evidence; bza worries that a fluent theorem will pass a guard designed to catch mush. Both are the problem of a false statement that reads well.

The updated schema

This is a proposal, not a decision — the choice between aligning and translating is still open (see Open threads). But the alignment is close enough that it is worth seeing concretely, because seeing it is what makes the decision cheap.

The move is: a mathematical object becomes a composed Offering in a knowledge medium. This fits better than it has any right to. Composed offerings require ordered concrete steps — which is what a derivation is. They require a framing — which forces the author to say whether the summand, the cancellation, or the boundary terms is the thing in play, a distinction mathematical writing routinely leaves implicit and then suffers for.

What each change buys

Change from the specWhy
payload.snapshot → move_offering (Offering shape) Round-trips against the live contract with no translation layer. Gains required framing, which the spec's schema simply lacks.
5 spec moves → 7 bza relations Drops the move/relation duplication. Maps cleanly: accept_and_extend → continuation; change_representation → translation; break_the_analogy → counterpoint.
interpretation.mapping → carried; interpretation.limits → lost Same concept, existing column. The spec's requirement that structurally_analogous_to carry "an account of where the analogy stops working" is lost being non-empty.
"challenge" is not a relation In bza the player judges (Judge = 'player' | 'narrator') and a rejection is a verdict, not a kind of connection. The spec's challenge move is a review state; modelling it as a relation would have put a judgement in the taxonomy of connections.
math_obligation retained as-is The genuinely new contribution. bza has no slot for "this interpretation owes mathematics an answer." Return-to-mathematics is the one spec move with no bza relation, and the one thing the Emacs side adds rather than duplicates. It rides in meta until a column exists.
external block Honours the spec's "keep external IDs separate from local IDs" against a real remote that assigns its own. idempotency_key makes the uncertain-submission retry safe.
Evidence rides in meta, never in the relation Preserves the spec's firmest rule: an accepted interpretation is not mathematical evidence. A turn can be beautiful and its evidence_kind still be proposed.

The residual mismatch is worth naming: bza's engine is server-authoritative and model-driven. It re-fetches offerings by id because "the server is what decides which record a move is," and an interpreter rules the relation. The spec's Emacs workspace is local-first and human-authored, where Org owns the content and execution is explicit. These are compatible for export — a composed offering has nothing to re-fetch — but a fetch_game that pulls model-ruled relations back into Org would import an authority the spec deliberately excludes. Export before import.

What I noticed about my process

keep doing

Writing the index entry is what caught the error. The premise collapse was not found by auditing the spec. It was found because adding a pointer line to MEMORY.md meant reading the neighbouring lines, and bza.md's title is BZA (aireadalong.com). The housekeeping task that felt like a detour was the task that did the work. Cross-referencing a new thing against the existing index is cheap and occasionally decisive — the pattern generalises past this incident.

keep doing

Verifying the claim instead of asserting it from memory. I had a 96-day-old memory saying bza exposed /api/import-bza. It would have been natural to report that as the integration path. It no longer exists — the current routes are /api/extension/import and /api/import/math-academy. Had I trusted the memory I would have corrected one wrong premise by supplying another. The same check found /api/correlate/turn, which the memory never mentioned at all.

didn't

I did not check whether the thing being specified already existed before recording the spec as direction. I wrote SPEC.md and the memory file first, then discovered the engine, then went back and amended. The order was wrong and the amendment is visible in the memory file as a bolted-on correction. For a spec that names an integration target, "does this already exist here" is a thirty-second templedb project list away and belongs before the spec is enshrined, not after.

didn't

I let an index accumulate 180 lines of content before a hook made me fix it. The rule that MEMORY.md holds one line per entry and never content is explicit. Each individual addition presumably looked harmless. The correction was mechanical and took one pass; the cost was that for some unknown number of sessions the index was too large to read comfortably, which is precisely when it stops doing its job.

notice

Two independent designs converged on the same hard parts, and that is the actual signal here. The spec and CORRELATION_GAMES.md were written separately, and both concluded: the limits of an analogy must be recorded alongside it (limits / lost); a model must never assert that a media item exists; disagreement must be preserved rather than overwritten; and a proposition can be fluently wrong in a way vagueness-detection won't catch. When two passes at a problem independently isolate the same four constraints, those constraints are probably real and probably the expensive ones to get wrong. They are where the implementation attention should go — not the Org property names.

notice

The spec's self-awareness was load-bearing and almost worked. It repeatedly labels its own claims as proposed, flags that aireadalong's interface is unconfirmed, and tells the implementer to obtain the real contract before milestone 3. That discipline is why the error was recoverable: the spec quarantined its weakest assumption instead of building on it silently. What it could not do is notice the assumption was checkable from inside the same machine. A caveat tells you where to look; it does not look for you.

Alignment costs a rewrite of one spec section; translation costs a permanently maintained mapping. Nothing in milestones 1–2 depends on this, so it can wait — but not past the first line of game code.

Concrete followups

Ranked by value per unit of effort.

  1. Decide align-vs-translate. Minutes of thought; determines whether a whole translation layer ever gets written. Highest leverage item on the list by a wide margin.
  2. Build milestone 1 and ignore games entirely. Investigation template, stable IDs, Calc capture, the stdio worker, exact SymPy operations, the run ledger, revision/stale handling. Four acceptance tests gate it (arithmetic, domain, stale-result, recovery) and none of them touch correlation games. This is the part with no prior art to reconcile against, and it is the part that is actually useful on day one.
  3. Refresh bza.md. Cheap, and it is the file that will mislead the next session the same way it nearly misled this one.
  4. Export one real turn by hand. Take the telescoping example, write the JSON above by hand, POST it to /api/correlate/turn. This validates the schema against the live contract for roughly the cost of a curl command, and it is the cheapest possible test of whether alignment is as clean as it looks on paper.
  5. Re-examine whether the spec's game layer should be built at all. Deferred deliberately, because it is a question for the user and not for me. But the honest reading of this session is that the correlation-game half of the spec substantially re-specifies a working system, while the Org/Calc/SymPy half has no equivalent anywhere. If the Emacs side exported turns and let bza remain the game engine, the spec would shrink by about a third and lose little.

Meta-meta

Three recaps in this series have now turned on the same failure mode, and it is worth stating as a pattern rather than a recurring coincidence. The half-done AST config migration found design docs claiming a pipeline had landed when phase 1 was build-and-diff only. What the CLI does when you run it found templedb nix documented throughout a memory file and never registered as a command. This session found a spec declaring an interface unretrievable while its implementation sat in the same database.

In each case the written record described an intention and was read as describing a state. The existing memory Verify "landed" claims covers the first two. This session is the third instance and extends it in a direction that memory does not currently name: the claim to check is not only "did this ship?" but also "does this already exist?" A spec asserting an absence is making a factual claim about the world, and absence is the one claim that cannot be confirmed by reading the document that makes it.

The cheap countermeasure is unglamorous and would have caught all three: templedb project list, then file ls and grep the plausible slug, before treating any document's account of what exists as current. Roughly a minute. It is already the substance of the CLI first memory — which suggests the gap is not that the habit is unknown, but that it does not fire when the document in hand sounds authoritative. Confident prose is exactly what suppresses the check, and confident prose is what all three of these documents had.
