Session recap 11: NixOS rebuild landed the sync CLI (and surfaced 4 latent infrastructure bugs)

Follow-up to recaps 9 and 10. User asked to rebuild NixOS so the new templedb sync CLI would work without dev-mode + env-var overrides. What should have been one command turned into hunting down four separate infrastructure regressions before the rebuild could complete: .authinfo.gpg/flake.lock wiped by templedb publish, bza project missing its flake.nix, templedb file set not un-deleting soft-deleted files, and bza's npmDepsHash gone stale. Also fixed a UNIQUE-constraint crash in templedb ai vibe start along the way. Ended at system-268 with templedb sync status working cleanly.

The four latent bugs, restated as memory

Materialize sweeps eat untracked files

templedb publish run system_config removes any file in the checkout that isn't in the DB's active set. Since .authinfo.gpg (binary) can't be sent through templedb file set's stdin (rejects non-utf8) and flake.lock isn't in the scanner's include list, both die on every publish. Git log shows this has happened at least three times before (b45a7fb, 3e38cec, another earlier). Needs a design pass — either binary support in file set, or an "unmanaged files" allowlist per project, or a scanner override that pins specific paths.

Soft-delete + re-set silently drops

templedb file set writes to file_contents unconditionally but doesn't reset project_files.status. A file that was previously deleted stays deleted — the content lives on but file ls, publish materialize, and every other status-filtered path skips it. Silent failure mode: user thinks they wrote a file; downstream sees nothing. Should either flip status back to 'active' on set, or refuse the set and require an explicit undelete first. Task #17.

Aspirational flake input

bza.url = "git://localhost:9419/bza" in system_config's flake.nix expected bza to be a flake, but bza's git tree has never contained a flake.nix (verified via git log --all --oneline -- flake.nix on the bza bare clone). The last known-working rebuild used a cached nix store path from a rev that's no longer served by the git daemon. So the only reason NixOS rebuilds ever worked was accidental nix cache hits — a rebuild after a nix-store GC would have hit this same wall. Added a minimal stub flake this session; the follow-up is to figure out whether bza should be a real flake or the input contract should change to flake = false.

npmDepsHash bit rot

my-overlays.nix's pkgs.bza pins npmDepsHash = "sha256-CjoA4FddI1Y62qGqDABbbM7CorVYUUuZNfHTF2qa8No=". Every time bza's package-lock.json changes, that hash needs updating or every nixos-rebuild fails at the bza build step. This is a general problem with buildNpmPackage pinning source that's actively developed; a CI job that rebuilds the overlay on every bza push and opens a PR with the new hash would prevent the recurring "rebuild broken" surprise. Task #19.

Metacognition

What I did right: stopped and asked the user twice when I hit non-trivial decision points (whether to proceed with prod migration, and how to fix the bza flake gap). Kept the rebuild bounded by scoping down (dropping pkgs.bza rather than trying to fix the whole overlay hash chain in-session). Preserved the working ~/.local/bin/bza wrapper so the user's bza usage wasn't affected.

What I got wrong: spent too long chasing nix's git ref cache trying to force a fresh HEAD fetch, when the fastest fix was to manually edit flake.lock (which is what I ended up doing). Also over-relied on templedb nixos rebuild wrapper for a while; direct nixos-rebuild would have avoided the materialize-loop that kept wiping my restored files.

Pattern to internalize: when a "simple rebuild" fails, the four questions in order should be:

  1. Is my code even in the built package? (Did I rebuild? Did the flake input update?)
  2. Are all the flake inputs actually valid flakes? (Especially locally-served ones)
  3. Are all the referenced hashes still current? (npmDepsHash, cargoLock, etc.)
  4. Did the last publish/materialize preserve everything nix needs? (dotfiles, unlisted files)

Each of the four blockers today was one of these categories. If I'd asked all four questions after the first failure, the rebuild would have taken 15 minutes instead of an hour.
