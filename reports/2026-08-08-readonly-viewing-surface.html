A read-only viewing surface for TempleDB projects

Sketch of how to expose project content for browser viewing without the FUSE edit-truncation footgun. Three tiers ordered by cost. Recommendation and concrete next-step at the bottom.

The problem

TempleDB currently exposes project content in two ways:

  • FUSE mount at ~/temple/<project>/ — read and write via normal filesystem. Convenient for editors but has a documented truncation risk on non-trivial writes. The DB write reports success, file cat returns truncated content, and only a byte-count check catches it.
  • Materialized checkout at ~/.config/templedb/checkouts/<slug>/ — the launcher's source of truth for the running Python code, refreshed by publish run or manual file checkout. Documented as "read-only, auto-generated" but actual permissions are the default rw-r--r--; nothing prevents an editor from writing to it and those writes get silently overwritten on the next materialize.

For viewing HTML overview docs like the ones in the agent-reports project, we don't want either surface — FUSE has the write risk, and the checkout dir is buried and not actually read-only. What we want is:

  1. Path is browsable — xdg-open or file:// works.
  2. Path is stable — bookmark-friendly.
  3. Path is enforced read-only — accidental edits fail loudly rather than silently.
  4. Refreshes on DB change — no stale content.

What we can already reuse

The infrastructure covers most of this:

  • SystemService.materialize_from_db() at src/services/system_service.py:112 — writes all current project files to ~/.config/templedb/checkouts/<slug>/, with conflict detection.
  • templedb file checkout — per-file extraction, already used to refresh the launcher's copy after every DB edit.
  • templedb publish run — commits + materializes + pushes. Whole-project refresh already integrated with commit flow.
  • nix_store_paths table (migration 075) — already tracks store_path, store_hash, nar_size, nar_hash, closure_size, is_valid for any registered store path. Ready to hold viewing paths without schema changes.

So the missing pieces are: enforcement (chmod), a browsable location (or symlink), and a view verb.

Tier A — chmod the existing checkout, add a view verb RECOMMENDED

Bolt read-only enforcement onto what already exists. Concretely:

  1. In SystemService.materialize_from_db(), after writing all files, walk the checkout dir and chmod -R a-w. Files become r--r--r--, dirs r-xr-xr-x. Editors will refuse to save. The next materialize needs to chmod u+w before writing, then re-chmod after.
  2. Add templedb view <project> [path]. Default path is index.html if present, else opens the checkout dir in $BROWSER or xdg-open. Auto-runs a fresh materialize_from_db first if the checkout is stale relative to the last VCS commit.
  3. Symlink ~/temple-ro/ → ~/.config/templedb/checkouts/ for discoverability. Muscle memory becomes ~/temple/<slug>/ (edit surface, FUSE) vs ~/temple-ro/<slug>/ (view surface, chmod'd). The -ro suffix is a visible cue.

Rough size: 

# SystemService.materialize_from_db (add ~10 lines)
for root, dirs, files in os.walk(checkout_dir):
    for f in files: os.chmod(os.path.join(root, f), 0o444)
    for d in dirs:  os.chmod(os.path.join(root, d), 0o555)

# New CLI file: src/cli/commands/view.py (~40 lines)
def view(args):
    slug = args.project
    checkout = Path.home() / ".config/templedb/checkouts" / slug
    if _stale(slug, checkout):
        SystemService().materialize_from_db(slug, force=False)
    target = checkout / (args.path or "index.html")
    if not target.exists():
        target = checkout
    subprocess.run(["xdg-open", str(target)])

# One-time: mkdir ~/temple-ro; ln -s ~/.config/templedb/checkouts/<slug> ~/temple-ro/<slug>
# Or auto-create the symlink at project create time.
Solves Truncation footgun (edits fail loudly), discoverability (obvious "-ro" path), browsability (view verb). Stability: path is a stable location per project. Content freshness: guaranteed by materialize-before-open.
Doesn't solve Content-addressed sharing — ~/temple-ro/agent-reports/ is the same path regardless of what version is materialized. You can't send someone a URL and prove they're seeing what you saw. That's the Tier B property.

Effort

About 60 lines of new code. Half a session. No new tables, no migrations, no daemon dependency.

Tier B — Nix store paths as the read-only surface LATER

Stage each materialized project into the Nix store, get back a content-addressed path, and maintain a stable symlink that atomically flips on each rebuild. This is the philosophically-consistent version — the ontology doc's argument that TempleDB should lean into content-addressed identity applied at the viewing layer.

How it works

# Trigger: after any successful materialize_from_db, or on commit.
store_path = subprocess.check_output([
    "nix", "store", "add-path",
    "--recursive", str(checkout_dir)
]).strip()
# e.g. /nix/store/xxxxxxxxxxxxxxxxxxxxxxxx-agent-reports

# Register in existing table (no schema change):
INSERT INTO nix_store_paths (store_path, store_hash, name, ...)
VALUES (?, ?, ?, ...)
ON CONFLICT DO UPDATE SET last_seen_at = datetime('now');

# Also record the pointer:
INSERT INTO project_view_paths (project_id, store_path_id, materialized_at)
VALUES (?, ?, datetime('now'));

# Atomic symlink flip:
ln -sfn <new store_path> ~/temple-ro/<slug>.tmp
mv ~/temple-ro/<slug>.tmp ~/temple-ro/<slug>

# GC root so nix-collect-garbage doesn't reclaim the current view:
nix-store --add-root ~/.local/share/templedb/gc-roots/<slug> --indirect <store_path>

What you get that Tier A doesn't

PropertyTier ATier B
Read-only enforcement chmod store perms (stronger)
Path stability yes yes (via symlink)
Content-addressed identity no store hash is the identity
Shareable URL that proves version no file:///nix/store/<hash>-...
Old versions remain valid no (overwritten) yes (until GC)
Two identical projects share storage no automatic (hash equality)
Nix daemon required no yes
Cost per write chmod walk NAR hash + copy to store

Effort

Roughly 150-300 lines, one migration (optional — a new project_view_paths table linking projects to their current store path, plus GC-root path). Real dependency on the Nix daemon (which is already required for the rest of TempleDB, so not a new dependency at the project level, but a new dependency for a viewing workflow that could otherwise be daemon-free).

When this pays off When the sharing property becomes a real workflow. For agent-reports specifically, the sharing question has never come up — reports live locally, are read by one human. If reports ever get sent to other agents ("look at this version of the analysis") or to other humans by URL, Tier B's provable identity is worth having. Until then it's over-engineering.

Tier C — Scope Tier B to viewable projects DEFER

If Tier B lands, it doesn't need to run for every project. Source-heavy projects like templedb itself, bza, or system_config have thousands of files that nobody browses in a browser — copying them into the store on every commit is pointless. A simple filter: 

-- add to projects table (or as an override):
ALTER TABLE projects ADD COLUMN viewable BOOLEAN DEFAULT NULL;
-- NULL = auto-detect (has index.html at root); TRUE/FALSE = explicit

Skip this until Tier B is real and the store cost is measurably annoying.

The three-surface end-state

FUSE isn't binary good-or-bad. The truncation risk is a bug in the write path; reads are fine. So the honest architectural target is three surfaces, each optimized for its actual use:

SurfaceLocationForEnforcement
Read (interactive) ~/temple/<slug>/ Editor navigation, quick vim, greps None; user knows this is live
Write (canonical) templedb file set / edit All tool-driven and agent-driven edits Enforced by CLAUDE.md, verified by --verify
View (browsable) ~/temple-ro/<slug>/ or templedb view HTML docs, index pages, static previews chmod (Tier A) or store perms (Tier B)

The point of splitting them is that each surface's path shape is a cue about what you can do with it. A URL starting with ~/temple/ means "you can edit here." A URL starting with ~/temple-ro/ means "you can't, and if you tried, the FS would refuse." A CLI command means "the DB is authoritative." Muscle memory follows path shape more reliably than documentation.

Recommendation

Do Tier A now, defer B until sharing is real Tier A takes ~60 lines and eliminates the footgun. It's compatible with Tier B if you later want content-addressed viewing — chmod'd checkout works as the intermediate that Tier B stages into the store. Doing them in that order costs nothing extra.

Tier B is architecturally correct — the ontology doc argues for exactly this kind of content-addressed viewing surface — but its concrete payoff is shareable, version-provable URLs. If nobody is sharing URLs today, Tier B is aesthetic rather than useful. Build it when the first "send me the exact version of X you were looking at" conversation happens; you'll want it fast enough at that point.

One follow-up worth doing regardless: audit whether any existing tooling reads from ~/.config/templedb/checkouts/<slug>/ and expects to write to it. The launcher only reads (verified). If nothing writes, chmod'ing to 0555 / 0444 is safe. If something writes, Tier A needs to whitelist that path or convert the writer to a CLI call first.

Tier A: ~60 LOC, eliminates the footgun, ships in one session. Tier B: real content-addressed viewing surface, worth it when sharing becomes a workflow. Three-surface split (read/write/view) is the honest end-state — each path shape becomes its own cue about what's safe to do.
