Own vs observe: TempleDB's fork in the road

Companion to yesterday’s Nix as a projection of TempleDB. That report proposed inverting the authority ordering between Nix and the DB. This one steps back one turn of the wheel and asks a harder question: whether the DB should be an authority over source code at all. Synthesizes three lines of analysis — unpacking “consumers speak the DB protocol,” the standard git multi-copy problem and its standard fixes, and the read-only projection pattern used by every serious static analysis tool — into a single argument. Adds meta-analysis on the identity crisis, the dogfood trap, and the complexity budget. The unified recommendation is: keep TempleDB’s ownership over things that are legitimately DB-native (agent state, cross-project graph, deployment history), and give up its ownership over source code content in favor of the observer pattern.

The three tracks, briefly

This report synthesizes three threads pulled through consecutive conversations:

  1. Cost analysis of “DB protocol.” The Nix-as-projection proposal hand-waved past the phrase “make consumers speak the DB protocol.” Unpacking that phrase into its four concrete implementations (curated git-daemon, custom Nix fetcher, NAR endpoint, substituter) revealed that only the first is pragmatic, and the first is essentially what we already do — just with a materialize step that keeps introducing bugs.
  2. The standard git multi-copy problem. The class of drift bugs we’ve been hitting (edited-the-wrong-copy, materialize sweeps, nix-store staleness) is a well-understood family in software engineering. Git has been living with it for 20 years and has good tools: lock files, watchers, drift diagnostics, single-canonical-working-copy conventions, symlink escape hatches. Under any model where source stays in git, these fixes work.
  3. The static analysis pattern. Every LSP server, Sourcegraph, GitHub’s semantic code navigation, and rust-analyzer converged on the same architecture: source stays authoritative on disk, tool parses and indexes into an in-memory or DB projection, queries hit the projection, edits go back to disk via the editor and never through the tool. The tool observes code rather than owning it.

The three tracks converge on one insight: the drift-bug family we’ve been chasing is a symptom of a category mistake, not a technical problem. TempleDB has been trying to be an authority over source code content, and every mechanism it needs to maintain that authority (materialize, file set write-through, FUSE mount) is a bug factory. The tools that succeed in this space explicitly gave up authority and became well-informed observers.

Unpacking “consumers speak the DB protocol”

Nix builds by getting a source tree and turning it into a store path. Every consumer of templedb today obtains its source tree by asking git. To take git out of that chain, the consumer has to acquire the source tree by some other means. Four options, in order of decreasing pragmatism:

  • B1 — DB-curated git-daemon. What we already do. Templedb materializes to disk, git-daemon serves it, consumers see “a normal git repo.” This is the DB protocol as consumers see it; the pain is that materialize is a batch/sweep operation that mangles working trees. The .authinfo.gpg incident yesterday was a materialize sweep. Fixable inside this option by making materialize incremental and gitignore-aware.
  • B2 — Custom Nix fetcher. Consumers write inputs.templedb.url = "templedb:templedb?rev=abc123". Requires a Nix builtin (fork nix, upstream to nixpkgs) or IFD-based glue that only works in impure eval mode.
  • B3 — NAR endpoint. Templedb serves narinfo + NAR files keyed on commit hash. Loses git semantics entirely: no history, no blame, no branches. Adds an HTTP server as a hard runtime dependency of every build.
  • B4 — Templedb as a binary cache. Complementary, not a source-tree alternative. Doesn’t solve the problem.

Almost the entire cost of the “DB is truth” proposal is concentrated in B2, because that’s the version that actually makes consumers speak a new protocol. Under B2:

  1. Consumer ergonomics collapse. When someone clones system_config, inputs.templedb no longer resolves to a filesystem path they can cd into. Can’t git log, can’t git blame, can’t open in an editor without installing templedb. Turns templedb from “a repo that happens to have a helpful CLI” into “a closed ecosystem you must opt into fully.”
  2. Pure-eval mode breaks. Custom fetchers via IFD are restricted at eval time. Needs either an upstream Nix builtin (multi-year political project) or impure eval, which breaks reproducibility and nix flake check.
  3. Bootstrap paradox multiplied. If templedb is the only way to obtain templedb’s source, you need templedb to install templedb. You’d maintain a hand-authored bootstrap-flake.nix that fetches a tarball, keeping two representations of the same code in sync forever. Guix does this. It’s why Guix has PhD theses about its bootstrap chain.
  4. CI/CD becomes hostile. GitHub Actions, Hydra, anyone running nix flake check on a PR — none have templedb. Either you provide a stateless public mirror (which is just a git repo, defeating the point) or external CI can’t verify PRs.
  5. Debugging regresses. Every nix repl session pays a shell-out tax to peek at source.
  6. AST parser completeness becomes load-bearing. Today’s parser gaps (the “outputs FnDef body silently dropped” memory) are annoying under the index model — a query returns incomplete data. Under B2 they are fatal — unparseable Nix means the DB literally can’t hold your code.
  7. Round-trip byte-fidelity kills git blame. Every DB → emit cycle re-normalizes formatting. Comments migrate. Whitespace shifts. git blame for emitted output shows the emitter as the author of every line. Historical context evaporates.

The standard git multi-copy problem

Take the DB-as-authority idea off the table for a moment and look at what we’re actually left with. The bugs are a family: same content in multiple filesystem locations, each with its own edit path, no single act that guarantees they all agree.

This is a well-known problem shape:

  • Vendored dependencies — package X’s code in project A’s and project B’s vendor/. Fixes in A don’t reach B.
  • Generated files — dist/, .pb.go, schema.sql.dump. Someone edited source, forgot to regenerate.
  • Multiple working copies — dev machine, CI runner, deploy target.
  • Long-lived branches — diverge faster than they can be merged.

Our case — templedb source → flake input → nix store → home-manager symlink → Emacs — is a mix of the first two: vendored code that also flows through a generation step.

The deep fix’s appeal is “no more policing needed,” which is real — but as the cost analysis showed, the price of eliminating policing is higher than the price of doing it well.

The static analysis pattern

Every serious static analysis tool built in the last 15 years follows the same architectural shape:

authored source files                     (source of truth, human/tool writes here)
         |
         v  parser (usually tree-sitter or hand-rolled)
   syntactic model                        (AST or CST, one per file)
         |
         v  resolver (imports, name binding, types)
   semantic model                         (cross-file, project-wide)
         |
         v  indexer
    fact database                         (queryable, persistent-or-not)
         |
         v  query engine
   answers to "where is X defined?"       (read-only)

The critical property: the arrow only goes one way. The tool never writes back to the source. Edits happen in the editor, on disk, via git; the tool observes, re-parses, and updates its projection. This is why LSP servers, Sourcegraph, and rust-analyzer coexist gracefully with every editor, VCS, build system, and workflow ever invented — they consume rather than own.

Four canonical implementations

  • LSP servers (rust-analyzer, gopls, TypeScript language server): in-process, in-memory, per-editor-session. Editor sends textDocument/didChange with buffer content. Server maintains AST + symbol tables in RAM, invalidates on change. Never writes.
  • Sourcegraph / GitHub code search: persistent, multi-repo, batch-indexed. Language-specific indexers emit a standardized fact stream (LSIF or SCIP). Every commit produces its own index; freshness comes from re-indexing on push.
  • Tree-sitter: incremental parser generator. Grammar-to-parser that re-parses only changed subtrees. What templedb’s nix_ast_parser.py already uses.
  • GitHub’s semantic: tree-sitter + a Haskell analyzer runs on push, symbols go to a DB, “jump to definition” queries the DB, not the source.

The invalidation loop is where all the complexity lives

Building an initial index is easy. Keeping it correct as source changes is the engineering challenge:

  • Full re-index — wipe and rebuild. Simple, correct, slow. Sourcegraph does this per commit. Templedb’s graph build-deps is a full re-scan.
  • Coarse-grained incrementality — track changed files, re-parse them plus their reverse imports. Correct if the import graph is accurate.
  • Fine-grained incrementality (memoized queries) — Salsa (rust-analyzer). Every derived fact is a memoized query; edits invalidate only the transitive query closure that depended on the changed input. Sub-second edit-to-diagnostic latency in million-line codebases.

Fact schemas: the interop layer

LSIF and SCIP standardized the fact format so indexers and consumers can evolve independently. Every LSIF-emitting indexer produces the same shape, so Sourcegraph can consume lsif-go, lsif-clang, lsif-tsc uniformly. If templedb ever wants external tools to consume its graph queries, adopting SCIP for language-agnostic facts (and keeping templedb-native tables as extensions) removes a translation layer.

How templedb already fits the pattern

Pieces already in the shape of a static analyzer:

  • nix_ast_parser.py uses tree-sitter-nix — parser layer.
  • config_nodes table — syntactic model, persistent.
  • graph search / who-uses / importers / callers — query layer.
  • project_files + file_contents — source snapshotting, analogous to Sourcegraph’s per-commit indexing.
  • The AST-deploy work — resolver layer for Nix specifically.

Pieces that don’t fit and cause the drift pain:

  • file_contents as a writable store rather than a snapshot. Static analyzers snapshot for query purposes but never claim to be the source. templedb file set inverts this.
  • Materialize sweeps. No LSP would ever delete files from your working tree because they weren’t in its index. That’s the “I own the source” pattern showing through.
  • No watcher. Every serious tool has one; templedb requires manual graph build-deps runs.

Meta-analysis: TempleDB’s identity crisis

The three tracks converge because they’re all consequences of the same underlying decision. TempleDB has been trying to be N things at once, and the friction we’ve been hitting is these roles conflicting.

observer <-------------- own vs observe spectrum --------------> owner
  |           |         |         |            |
Sourcegraph  LSP    GitHub  templedb(now) git repo
                           templedb(deep fix)  

Every position on this spectrum is coherent. The trouble is picking one and staying there. Templedb’s current position is unstable because the code was built up feature-by-feature over a year:

  • Started as a project registry (pure observer, minimal ownership).
  • Added VCS to unify project histories (moved right — now owns commit graph).
  • Added file_contents for cross-project queries (moved further right — now owns snapshots).
  • Added file set for scripted edits (moved further right — now owns writes).
  • Added FUSE mount for filesystem access to DB state (moved further right — now owns filesystem view).
  • Added materialize for nix build integration (moved further right — now owns working trees).
  • Added AST parsing for cross-project graph queries (moved left — observer of Nix source).
  • Added the agent runtime (own state that has no filesystem analog — legitimately DB-native).

The result is a system that occupies two positions on the spectrum simultaneously. The observer parts want to consume; the owner parts want to author. When they meet in the middle — as they do every time templedb project checkout materializes a tree and graph build-deps indexes it — you get the drift bugs.

The three-body problem of writable state

When (a) the DB, (b) the filesystem checkout, and (c) the nix store copy of the same content can all be edited (or, in the store case, replaced), you have a small distributed systems problem. CAP applies: consistency, availability, and partition-tolerance can’t all be satisfied. Templedb has been trying for all three:

  • Consistency: after any write, all three views agree. Requires atomic multi-mirror writes, which is what materialize tries to do (and why materialize is dangerous).
  • Availability: any of the three can be read at any time. Currently satisfied (each is on the local filesystem or DB).
  • Partition-tolerance: temporary divergence is tolerable (e.g. dev-mode uses a stale nix store while the checkout has the fresh code). Also currently satisfied.

The observer pattern implicitly picks: give up consistency (mirrors are eventually consistent via re-indexing) in exchange for a simpler ownership model. The DB-as-truth model tries to keep consistency, which is exactly why materialize has to sweep working trees and every regression hurts.

The dogfood trap

TempleDB dogfoods itself heavily — templedb the project is stored in templedb the DB. This is normally a strength (own eating own food, forces the tool to be usable). It becomes a trap when it locks you into your own poor design choices, because every path forward requires migrating your own workflow first. The mirror-drift class of bugs hits templedb the project harder than any external consumer, because templedb the project has the most mirrors (checkout, edit-workspace, nix store, spacemacs layer, FUSE historical). If we pick a new direction, we have to migrate templedb the project first — and that migration is on the critical path for every other improvement.

The complexity budget

Every architectural decision has ongoing maintenance cost. TempleDB has spent complexity budget on ambitious integrations: FUSE, AST-deploy, native VCS, MCP tools, agent-writable sections, config compiler, fleet deployment, Nix store tables, agent runtime, session-scoped VCS staging. Each is powerful. Together they eat all the budget for maintenance and evolution — there is no slack. The reflection report from two days ago noted this in passing (“it accreted, all at once, over a marathon week”). It’s worth naming explicitly: this is a system built from a maximum-ambition-per-component budget. That style has run its course. The next several months should probably be spent on subtraction, not addition.

What TempleDB is uniquely good at

Not everything should be given up. There’s a real set of things TempleDB does that nothing else in the ecosystem does:

  • Cross-project awareness. One graph over N projects, queryable by symbol / import / caller / dependency. No other tool spans project boundaries this cleanly.
  • Session-scoped VCS staging. Multiple parallel agents can stage changes without stepping on each other. This has no filesystem analog and can only live in a DB.
  • Agent runtime. Sessions, MCP tools, pending events, agent-writable sections, work log. All genuinely DB-native.
  • Deployment history. Which flake rev built which store path, deployed to which host, at which timestamp. This is business logic, not source code.
  • Machine + secret management. Project metadata, tags, fleet config, sops keys. DB-native.
  • Reports. An archive of design decisions with a stable index. Explicitly meant to be authored, and explicitly non-source-code.

The recommendation isn’t “become pure observer” — it’s “become an observer of source code, and remain the owner of everything above.”

The recommendation, spelled out

One sentence: TempleDB should observe source code and own the graph of facts about it, but should not author the source itself.

Concretely, in decreasing order of urgency:

  1. Freeze the “author source” surface area. Deprecate templedb file set as a first-class edit path. Not delete — useful for agent scripts — but move it out of the recommended workflow. Editing means editing files on disk, in a normal git checkout, via templedb edit <slug>.
  2. Fix materialize. Make it gitignore-aware and incremental. It should never delete an untracked file. Yesterday’s .authinfo.gpg sweep would have been prevented by a one-line rule.
  3. Add drift diagnostics. templedb file where <slug> <path> and content-hash xattrs on writable mirrors. Fixes the “edited the wrong copy” class without touching the ownership model.
  4. Add a watcher. templedb watch <slug> uses inotify to trigger graph build-deps incrementally when source changes. Closes the loop between authored edits and their propagation.
  5. Adopt SCIP for language-agnostic facts. Keep templedb-native tables for what SCIP doesn’t cover. Export the code-facts subset as SCIP so external tools can consume templedb queries.
  6. Reframe file_contents as a snapshot table, not an authoring surface. Preserve the ability to query “what did this file look like at commit X,” but stop treating it as the write path.
  7. Symlink escape hatch for the Emacs layer. Mirror TEMPLEDB_DEV_MODE=1 for the CLI. Under TEMPLEDB_DEV_MODE_EMACS=1, replace the read-only nix-store symlink with a symlink to the writable checkout. Editing “the wrong copy” becomes editing the right copy.

Estimated cost: 4–6 weeks of focused work. Doesn’t require Nix expertise. Doesn’t affect any consumer. Doesn’t require the AST parser to be complete. Doesn’t change the bootstrap story. Doesn’t break pure eval. Reduces the mirror-drift bug class by an order of magnitude. Preserves 100% of what TempleDB is uniquely good at.

What we’d be giving up

Honesty section: the DB-as-truth model has real appeal that the index model can’t match.

  • “No drift possible” guarantee. Real. The index model reduces drift; it doesn’t eliminate it. The escape hatch is git status-style diagnostics and human/agent policing.
  • Content-addressed source globally. Every store path traceable to a DB snapshot. The index model gives you traceability of derived facts (“which snapshot produced this graph query result”) but not of store paths themselves. A partial fix would be to register nix store paths in the DB with their producing-source-rev — the nix_store_paths table already exists for this.
  • Cross-machine consistency by construction. Under DB-as-truth, syncing the DB syncs everything. Under the index model, sync happens per-mirror (git for source, nix for store paths, DB for facts). More moving parts, well-understood standards for each.
  • The philosophical elegance of “one truth.” This is real and shouldn’t be dismissed. Elegance matters. But the pattern of “elegant model + hostile ecosystem interaction” has been played out enough times (Guix, NixOS itself in its early days, Bazel outside Google) that the correct default is “coexist gracefully.”

Meta-meta: why did we get here

Two forces drove the drift from observer toward owner:

Force 1: dogfooding. When templedb’s own source is stored in templedb, every workflow feature has to work for editing templedb itself. That created pressure for templedb file set, for materialize, for FUSE — each was a real ergonomic win for the developer who had to type git add into a checkout of the tool they were writing.

Force 2: agent-driven edits. When agents (Temple Agent, Claude Code via MCP) started editing source, they needed a scriptable write path. Filesystem edits are scriptable, but they don’t give agents the durability, session-scoping, and provenance guarantees that DB writes do. templedb file set was the natural answer — a DB write path with a filesystem-compatible interface.

The observer pattern doesn’t reject either of these. Dogfooding still works (templedb the project is a normal git checkout, edited normally, snapshotted by templedb the DB). Agent edits still work (agent writes to a filesystem checkout, and templedb watches; or agent uses templedb file set as an internal shortcut with the understanding that it’s writing into the eventual-consistency layer). What the observer pattern rejects is the invariant that every edit go through the DB. That invariant was never enforceable anyway — humans edit in Emacs, nix rebuilds create store paths, git commits create refs — and pretending it was cost us the drift bug family.

What’s next

Concrete first step, if the direction is accepted: implement templedb file where, fix the materialize gitignore bug from yesterday, and land the Emacs layer symlink escape hatch. Those three changes cost about a week and buy most of the daily-life improvement.

The larger direction — adopting SCIP, retiring file set as a first-class path, adding the watcher — can happen incrementally over a quarter. Nothing about it is urgent; nothing about it blocks any other improvement. It’s a philosophical realignment first, an implementation project second.

The report ends where it started: TempleDB has been trying to be an authority over source code. That’s a costly position and there’s a well-trodden alternative — observer rather than owner — that’s cheaper, robust, and preserves everything TempleDB is uniquely good at. The fork in the road is here.
