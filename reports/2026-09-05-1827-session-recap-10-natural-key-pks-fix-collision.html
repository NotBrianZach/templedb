Session recap 10: natural-key PKs fix the shadow.id collision

Follow-up to recap 9. Landed migration 102 which drops the surrogate INTEGER PRIMARY KEY on sync_entities and sync_relations in favor of composite natural-key PKs. The two-instance convergence test that failed in recap 9 (with colliding autoincrement IDs on both sites) now converges cleanly. Committed as 81625C44, applied to prod.

What changed

Migration 102

Drops the mig-101 shadows + their triggers + any CRSql companion tables (in case sync init had been run). Recreates the shadows with: 

sync_entities   PRIMARY KEY (kind, external_ref)
sync_relations  PRIMARY KEY (from_kind, from_external_ref,
                              kind,
                              to_kind, to_external_ref)

Both tables marked WITHOUT ROWID since the composite PK already provides identity and skipping the rowid removes a redundant b-tree.

Rewritten write-through triggers

The entities triggers are straightforward — NEW.kind and NEW.external_ref are directly available. Relations triggers need a JOIN because relations carry surrogate endpoint IDs; the trigger looks up both endpoints via SELECT ef.kind, ef.external_ref, ... FROM entities ef, entities et WHERE ef.id = NEW.from_entity_id AND et.id = NEW.to_entity_id. The SELECT returns 0 rows if either endpoint is missing, non-fleet, or has a NULL external_ref, so the INSERT is a no-op in those cases.

The entities_sync_del trigger now also cleans sync_relations where either endpoint matches the deleted entity's natural key. This handles FK cascade: when an entity is deleted, SQLite fires the child (relations) DELETE trigger before it can look up the parent's natural key through the now-orphaned surrogate id. The parent-side trigger does the cleanup while OLD.kind / OLD.external_ref are still available.

Reconcile simplified

Both sides now key on natural keys, so reconcile_to_main no longer needs any ID translation. Entities: straight upsert on (kind, external_ref). Relations: JOIN local entities by natural key to get local surrogate IDs, then upsert on (from_entity_id, kind, to_entity_id).

SQLite gotcha found the hard way

SQLite 3.35+ upsert-with-SELECT

INSERT INTO t SELECT ... FROM x ON CONFLICT ... parses ambiguously — is ON the start of a JOIN or of ON CONFLICT? SQLite requires WHERE true between the SELECT and the ON CONFLICT to disambiguate. Even when the SELECT has no JOIN. Documented in the SQLite docs but easy to miss. Cost about 5 minutes and a confused near "DO": syntax error.

Validation

Convergence with colliding IDs

The exact test that failed in recap 9. Two scratch DBs (/tmp/scratch.sqlite, /tmp/scratch2.sqlite), each initialized to a distinct crsql_site_id, each performs one INSERT INTO entities with no explicit id. Both SQLite instances independently allocate ROWID 30460. 

Before mig 102:
  A: [('conv-A', 'from-A'), ('conv-B', 'from-B')]
  B: [('conv-B', 'from-B')]                        <-- conv-A lost

After mig 102:
  A: [('conv-A', 'from-A'), ('conv-B', 'from-B')]
  B: [('conv-A', 'from-A'), ('conv-B', 'from-B')]  <-- converged

Same test, same collision, different outcome. Natural PKs disambiguate the shadow rows entirely from the surrogate ID space.

Also verified

  • Idempotent reconcile. Running reconcile_to_main() twice on the same scratch produces zero drift (entity count delta = 0).
  • Relation sync across peers. A creates a relation between an existing Machine and its new conv-A entity; ships to B; B's reconcile projects it into main with locally-correct endpoint IDs. Shadow carries endpoint natural keys, so no ID translation table is needed.
  • Shadow-side delete propagation. Delete an entity on A, sync to B — B's sync_entities row disappears. Confirmed via row count.

Known limitation: main-side delete propagation

Deletes reach the peer's shadow correctly (via CRSql tombstones) but reconcile_to_main is INSERT+UPDATE only, so the peer's main entities row doesn't get deleted. Adds and updates converge fine; deletes don't fully propagate.

A DELETE-what's-missing reconcile pass would fix this, but it needs a first-populated guard — otherwise an empty shadow on a fresh peer (before its own sync init populates) would delete every fleet entity in main. Deferred as a follow-up task; fleet kinds (File, Commit, Deployment, Generation) are append-only in practice, so this is low urgency.

Metacognition

What worked: reading the failure mode from recap 9 literally — "shadow.id collides on concurrent inserts" points directly at using a non-surrogate PK. Two of the three options in recap 9 were workarounds; option 3 (natural keys) removed the problem class entirely rather than working around it. Testing the exact same test that failed before, without changing the test itself, is the cleanest way to prove the fix — no risk of "test rot" hiding a regression under different scenarios.

What I should watch for next time: I initially reached for INSERT OR REPLACE in the write-through triggers, which caused the earlier UNIQUE-on-id failure that drove me toward ON CONFLICT DO UPDATE in recap 9. With natural PKs I could have simplified further and used INSERT OR REPLACE again (the CRR concerns were specific to the surrogate ID shape), but by then the pattern was ingrained and I didn't reconsider. Not a bug, just a small local cleanup opportunity I could have taken.

Also worth noting: the WHERE true syntax requirement for upsert-with-SELECT was a solid 5-min detour that I would not have found without reading the SQLite docs. Old assumption "if it parses on VALUES it parses on SELECT" was wrong. Pattern for future: any UPSERT bug on a SELECT source, check the docs first.
