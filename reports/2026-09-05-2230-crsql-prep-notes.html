CRSql prep: what's actually built, what's missing

Item 1 from docs/NEXT_SESSION_PICKUPS.md: "CRSql for fleet sync (Q5 remainder)". The pickup notes said "CRSql itself is not enabled anywhere. No __crsql_clock or __crsql_pks tables exist. The design is spec'd... the plumbing hasn't been built." Empirically wrong. CRSql is fully loaded and 6 shadow tables are actively syncing. What's missing is smaller than advertised: two shadow tables (sync_entities, sync_relations) plus scope-filtered population. Report captures actual current state + concrete next-actions so the next session can start with the right premises.

What's actually running today

Each shadow follows the CRSql-standard 7-object layout: sync_X + sync_X__crsql_clock + sync_X__crsql_pks + sync_X__crsql_pks_pks + sync_X__crsql_clock_dbv_idx + _dtrig/_itrig/_utrig triggers.

Sync engine has full protocol plumbing

src/sync_engine.py::SyncEngine (~470 lines):

  • initialize() — creates shadow tables, marks as CRRs, populates from main tables. Idempotent.
  • get_changes(since_version) — returns changes newer than a version + the current DB version.
  • apply_changes(changes) — applies a peer's changes.
  • reconcile_to_main() — projects shadow-table state back into the main tables (INSERT OR REPLACE).
  • get_site_id(), get_db_version().

SyncServer class (in the same file) speaks a socket-based sync protocol on the configured port (default 9420 per programs.templedb.sync.port in the homeManagerModule).

CLI: templedb sync {init, status, serve, pull, push, do-sync, peers}

Six subcommands wired in src/cli/commands/sync.py. Not exercised in single-host use (which is what zMothership2 is), but there.

sync_scope column: shipped in migration 099

entities and relations both have sync_scope with a CHECK constraint on ('fleet' | 'machine-local' | 'none'). Populated on every insert by _upsert_entity per the _SYNC_SCOPES classification dict. Doctor invariant every_entity_has_sync_scope is green.

What's missing (the real Q5 work)

1. Two shadow tables + CRR registration

sync_entities
sync_entities__crsql_{clock,pks,dtrig,itrig,utrig}
sync_relations
sync_relations__crsql_{clock,pks,dtrig,itrig,utrig}

Follow the exact pattern in SYNC_SHADOW_SCHEMA. The DDLs strip UNIQUE constraints (CRSql prohibits them on CRRs) and DEFAULT-init every column (CRSql prefers non-NULL).

2. Scope-filtered population

_populate_shadow_tables currently does unconditional SELECT ... FROM main_table. For entities/relations, add a scope filter: 

INSERT OR IGNORE INTO sync_entities (id, kind, external_ref,
                                     source_authority, label,
                                     sync_scope, observed_at,
                                     attributes_json)
SELECT id, kind, external_ref, source_authority, label,
       sync_scope, observed_at, attributes_json
  FROM entities
 WHERE sync_scope = 'fleet';

Same shape for sync_relations. Result: only 3,021 entity rows enter the CRR (not 30k), keeping the CRSql overhead proportional to real fleet traffic.

3. Write-time trigger: keep shadow in sync with main

The existing shadows use one-shot population + peer-driven writes. For entities/relations, adapters continuously write to entities — the shadow needs to receive those writes too. Options:

  • SQLite trigger on main tables: AFTER INSERT/UPDATE OF sync_scope ON entities WHEN NEW.sync_scope = 'fleet' → INSERT/UPDATE the shadow. Zero adapter code changes. Preferred.
  • Adapter-side dual-write: adapters explicitly touch shadow when scope='fleet'. More code, more places for drift.

4. Reconcile-to-main direction

When a peer's changes arrive via apply_changes, they land in shadow. reconcile_to_main() currently handles the existing 6 tables. Extend it to project sync_entities → entities + sync_relations → relations. UNIQUE constraint conflict on (kind, external_ref) resolved by INSERT OR REPLACE (last-writer-wins per Q5).

5. Multi-machine test harness

Currently the only "fleet member" is zMothership2. To validate sync empirically, need either:

  • A second templedb DB on the same host (different db_path env), with a socket-based sync between them.
  • zMothership3 provisioned with templedb (currently in fleet_machines as target but not deployed).

Concrete first-session checklist

  1. Snapshot the DB first. cp ~/.local/share/templedb/templedb.sqlite /tmp/templedb-backup-2026-09-05.sqlite. CRSql triggers are hard to remove cleanly if something goes wrong.
  2. Iterate on a scratch DB copy. cp .../templedb.sqlite /tmp/scratch.sqlite; export TEMPLEDB_PATH=/tmp/scratch.sqlite. Every experiment runs against the scratch until the pattern's proven.
  3. Add DDLs to SYNC_SHADOW_SCHEMA in src/sync_engine.py. Two entries: sync_entities and sync_relations. Column set matches main tables minus UNIQUE constraints.
  4. Extend _populate_shadow_tables with the two new INSERT OR IGNORE queries, filtered by sync_scope='fleet'.
  5. Run templedb sync init against the scratch DB. Verify: 12 new tables created (2 shadows × 6 companion tables each), row counts match the fleet-scope filter, no errors.
  6. Test one write cycle end-to-end. Insert a Machine entity manually, check it landed in sync_entities. Verify __crsql_clock got a row.
  7. Add write-through trigger. New migration 100 or 101 creating AFTER INSERT/UPDATE ON entities WHEN NEW.sync_scope='fleet' → shadow write. Same for relations. Test again: adapter writes propagate.
  8. Extend reconcile_to_main for the shadow→main direction. Test: pretend a peer's changes arrived (INSERT into shadow), reconcile, verify main table has the row.
  9. Two-instance test. Create a second scratch DB, exchange changes via get_changes/apply_changes in a script, verify convergence.
  10. Only after all of the above works on scratch: apply migration to production DB. Snapshot again just in case.

Known gotchas

CRSql constraint: no UNIQUE

entities has UNIQUE(kind, external_ref). relations has UNIQUE(from_entity_id, kind, to_entity_id). The shadow tables cannot carry these. Uniqueness in shadows is enforced by CRSql's PK tracking + last-writer-wins semantics. Confirmed pattern by inspecting sync_projects (main has UNIQUE(slug), shadow doesn't).

FK cascade + CRSql delete propagation

relations.from_entity_id/to_entity_id reference entities.id with ON DELETE CASCADE. CRSql's delete propagation is separate from SQLite's cascade. Deleting an entity on machine A cascades to its relations on A immediately, but on B the entity delete arrives via CRSql while the relations are still-there until they get their own delete events. Order-of-arrival edge case. May need to disable FK checks during apply_changes and re-run a cleanup pass after.

attributes_json as opaque TEXT

entities.attributes_json (mig 098) is TEXT. CRSql treats it as opaque — no field-level merge; last full JSON blob wins. Fine for most cases. If per-field merge ever needed, that's a much bigger change (custom CRSql column types).

Symbol churn is machine-local for a reason

Don't accidentally flag Symbol as fleet-scope during any refactor. 16,960 rows here now, and re-ingest churns them (ADD/DELETE cycles on every python or SCIP run). Syncing that thrash across machines would be pointless — each machine can re-derive from source.
