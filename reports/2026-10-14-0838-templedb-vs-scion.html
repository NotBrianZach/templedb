TempleDB vs Scion

Anthropic's Redesigning source control describes Scion, a version control system built because git stopped scaling at 30,000 merges a day. TempleDB arrived at four of Scion's six design principles independently and from the opposite direction — normalization, not throughput — and the convergence is sharpest exactly where it matters: commits are changesets against a parent, content is addressed by hash in a shared blob table, merges run where the data lives, and working copies are optional. TempleDB then deliberately inverts Scion's first principle (clients are always online) by building CRDT sync for offline peers. The genuine gaps are concurrency — SQLite's single writer is the exact opposite of "lock-free commits" — and derived data: the entity graph is a richer derivation layer than anything Scion describes, but there is still no blame index or path-history structure.

The two systems, stated plainly

Scion is a client-server VCS that replaced git at Anthropic in five months, built by seven engineers while merge volume grew tenfold. Its forcing function was agent scale: by September 2026 nearly 100 GB of history, a 25 GB compressed working copy, 25 million CI checkouts a day, and a naive-fetch bill of 600 petabytes of daily traffic. Several hundred internal git mirrors were the stopgap, and they "became harder to operate as our merge rate increased."

TempleDB is a database-native project manager whose VCS is one subsystem among deploy, nix, config-AST, agent runtime and entity graph. Its forcing function was stated in docs/DESIGN_PHILOSOPHY.md in March 2026 and has nothing to do with throughput:

Normalization is not just a database principle — it's the key to maintaining truth in complex systems.

The thesis there is that git treats code as duplicated text files, so the same Button.jsx lives in four repos and no one can say which is true. Store content once, address it by hash, reference it from everywhere. That is a deduplication argument. It produces, as a side effect, most of Scion's storage model.

Anthropic merges a TempleDB-lifetime of commits roughly once an hour. This is worth stating up front because it means every performance claim in the article is irrelevant here, and every structural claim may not be. The article is explicit that Scion is "by no means a suitable replacement for git for general use" and lists the preconditions: tens of thousands of code-writing agents, tolerance for massive token expenditure, willingness to migrate the whole development lifecycle. TempleDB meets none of them. So this is not a "should we build Scion" report. It is a report on which of Scion's six principles TempleDB already satisfies, which it rejected on purpose, and which two are real unclaimed wins.

Where TempleDB already converged

The changeset model is the same decision

Scion's fundamental unit is a changeset that "stores changed files relative to first parent rather than full tree pointers," pointing at content-addressed compressed blobs. TempleDB's vcs_file_states is that table:

vcs_file_states(commit_id, file_id, file_path,
                change_type CHECK(IN ('added','modified','deleted',
                                      'renamed','unmodified')),
                content_hash, old_content_hash, previous_path, ...)
                UNIQUE(commit_id, file_id)

One row per changed file per commit, carrying both the new and old content hash and an explicit rename with previous_path. 1,260 commits produce 6,355 file-state rows — about 5 changed files per commit, not 2,464 tree entries per commit, which is what a git-style snapshot model would have cost. Content lives in content_blobs, keyed by hash_sha256 as the primary key, with reference_count, compression IN ('zstd','gzip') and storage_location IN ('inline','external','remote'). That is Scion's storage tier description almost line for line.

Two caveats on that last point. All 4,265 blobs on this install are inline with no compression — the external and remote paths exist in the schema and in docs/BLOB_STORAGE.md (S3, R2, Backblaze) but nothing has exercised them. And TempleDB has no packfiles for the same reason Scion has none: there was never a packfile. Neither system needs repository maintenance; TempleDB needs database maintenance instead, which is a real cost the article's architecture doesn't have an analogue for.

Merges happen where the data is

Scion's asymmetry principle puts history queries, merges, rebases and blame on the server so clients stay thin. TempleDB gets this for free by construction: there is no client. vcs merge, vcs cherry-pick (a three-way merge of a single commit) and the --strategy ours/theirs auto-resolution all read and write SQLite directly. A merge never requires a materialized tree. The config-AST subsystem goes further than Scion describes — ConfigCompilerService.resolve() deep-merges typed config nodes with documented semantics per docs/AST_MERGE_SEMANTICS.md (attrset recursion, list concat in priority order, with-unwrap-merge-rewrap), which is a structural merge over an AST rather than a textual three-way merge. Scion resolves conflicts by handing them to Claude; TempleDB resolves a narrow class of them by type.

Sparse, optional working copies were the original point

Scion's principle 6 lets a CI job request a diff or compute an operation via API without materializing files. TempleDB's equivalents are more numerous than Scion's:

  • source snapshot --rev — read one file at one revision with no checkout at all. This is exactly the API-first history read the article argues for, and it is already how agents read code here.
  • file cat / file ls / file get — single-path reads against the DB, materializing nothing. file ls <slug> src/ -l answers "what is in this directory" without constructing the directory.
  • templedb edit — provision a writable workspace per session, diff it against the DB on commit, discard it after.
  • Git mirrors — publish run materializes to a git remote for the tools that still require one, which is the inverse of Anthropic's "several hundred git mirrors" problem: the DB is authoritative and git is the export format.

There was a fifth, and its removal is the most direct evidence for Scion's principle 6 in this whole comparison. TempleDB ran a FUSE mount at ~/temple/<project>/ with project@branch/ views that reconstructed trees on demand from the vcs_file_states chain plus a vcs_working_state overlay. It is now deprecated and gone — there is no templedb fuse command, no mount, and no ~/temple/ directory. A filesystem projection is still a projection into tree shape, with a cache to invalidate and a kernel boundary to cross; the API reads above do the same job without either. Anthropic argues the same thing prospectively, letting CI jobs "request diffs or compute operations via API without materializing files." TempleDB built the mount, used it, and arrived at the conclusion by subtraction.

Derived data — where TempleDB is ahead

Scion computes "derived data" recursively from the changeset log: blame indices, path history, skip lists for commit graphs, with the stated benefit that new optimizations land without client changes. TempleDB has the same architecture and a much wider derivation surface: the entity graph currently holds 64,737 entities and 73,754 relations across git, nix, agent-runtime, deployment and author authorities — 21,442 Symbols, 17,813 ToolCalls, 13,443 StorePaths, 1,259 Commits — plus an FTS5 index over file contents, import-graph hygiene snapshots, and provenance walks that answer "what motivated the code running on this machine." Scion derives facts about code history. TempleDB derives facts about code history, the nix closure that got built from it, the deployment that shipped it, and the agent session that wrote it.

The honest asymmetry: TempleDB's derivations are richer but weaker. ingest git reads vcs_commits, not git — so a fresh ingest means "the graph matches the tables," not "the graph matches reality." Scion's derived data is computed from the write-ahead log that is reality. TempleDB needs doctor and reconcile to close that loop; Scion needs nothing because there is no second authority to drift from.

Where TempleDB chose differently, and was right to

Offline-first is a deliberate inversion

Principle 1 — "clients are always online" — is the one Scion leans on hardest, and TempleDB spent real effort going the other way. templedb sync initializes cr-sqlite CRDTs on the database and replicates sync_projects, sync_vcs_commits, sync_vcs_branches, sync_entities, sync_relations, sync_environment_variables and sync_system_config across Tailscale peers, each with its __crsql_clock table. That is a conflict-free replicated merge for machines that were apart.

Both choices follow from the deployment model. Anthropic's clients are datacenter jobs with a network. TempleDB's "clients" are five NixOS hosts — zMothership2, zMothership3, zStation, WilliamZacharyAbelTheZeroth, zachMothership — that are sometimes on, sometimes not, and sometimes being reinstalled. A system whose premise is constant connectivity to an authoritative server would be unusable for the exact job TempleDB does. Scion's principle is correct for Scion and wrong here.

No merge queue, for a different reason

The article argues "a proper merge queue... doesn't make much sense at agent scale," and replaces global repository locks with post-merge automated testing, pre-deploy conflict testing, and Claude's automated conflict resolution. TempleDB also has no merge queue, trivially — there is no contention at 1,260 lifetime commits. But it does have the replacement half built: templedb test <project> is a DB-backed QA runner with auto-detection and per-project test definitions, and templedb validate runs env/nixos/deploy validators. The structure Anthropic needed at 30,000 merges/day — test after the merge, not before it — is the structure that already exists here because there was never a gate to begin with.

What is actually worth taking

Four things, ordered by value per unit of effort. The first two are small and self-contained. The third is the only one that matters architecturally, and it turns out to be half-built already. The fourth is a precondition, not a project.

1. Path history — one index and one flag

Start here, because it is the smallest change on the list and the other items depend on it. vcs_file_states.previous_path already records renames, and change_type already has a 'renamed' value, but nothing indexes either — so "show me this file's history" means scanning every commit's changeset, and following a file across a rename means noticing the rename by eye. Two pieces:

-- migration 138 (137 is current head)
CREATE INDEX idx_file_states_path
  ON vcs_file_states(file_path, commit_id);
CREATE INDEX idx_file_states_prev
  ON vcs_file_states(previous_path)
  WHERE previous_path IS NOT NULL;

Then a --path filter on vcs log, which currently accepts only -n, --branch, --published, --session and --all-sessions. The query is a join from vcs_commits to vcs_file_states on commit_id, filtered on file_path, following previous_path when change_type = 'renamed' to continue the walk under the old name. That is the whole feature. It is worth doing first because rename-following is exactly the part of blame that is annoying to retrofit afterwards.

2. Blame as a lazily-materialized cache

Scion lists file blame indices first among its derived structures, and TempleDB has nothing: no blame command, and source revisions lists a file's revisions while attributing nothing to a line. The input is already in the right shape — each vcs_file_states row carries both content_hash and old_content_hash, so the two versions of a changed file are both addressable in content_blobs without reconstructing a tree.

The implementation is a fold, not a tree walk. Python already depends on stdlib difflib (it is what vcs diff and vcs show render through, and what the Rust port's difflib.rs exists to match byte for byte), so SequenceMatcher(...).get_opcodes() over the two blobs gives equal / replace / insert / delete ranges per commit. Carry a line→origin-commit vector forward along the chain: on equal copy the attribution across, on replace and insert stamp the current commit_id, on delete drop the entries.

Do not store that vector for every (file, commit) pair — that is O(lines × commits) and would dwarf the 127 MB of actual content. Cache it at the revisions someone asks about, and replay forward from the nearest cached ancestor:

-- migration 139
CREATE TABLE vcs_blame_cache (
  file_id      INTEGER NOT NULL REFERENCES project_files(id) ON DELETE CASCADE,
  commit_id    INTEGER NOT NULL REFERENCES vcs_commits(id) ON DELETE CASCADE,
  -- line_no (1-based) -> origin commit_id, JSON array
  blame_json   TEXT NOT NULL,
  line_count   INTEGER NOT NULL,
  computed_at  TEXT NOT NULL DEFAULT (datetime('now')),
  PRIMARY KEY (file_id, commit_id)
);

This is cache, not truth — it is derivable from vcs_file_states at any time, so it can be dropped and rebuilt, which is the property that makes Scion's derived tier safe to iterate on without touching clients. CLI surface: templedb vcs blame <slug> <path> [--rev COMMIT], matching source snapshot's existing --rev spelling.

Why this is worth more here than it is at Anthropic. vcs_commits carries a session_id FK into vcs_sessions, and the entity graph already holds Session (755), AgentSession (326), Report (54) and EditIntent (1,107) entities wired by from-commit, applied-to, motivated and proposed relations — which is what provenance commit and provenance report walk. All of that resolves at commit granularity today. Blame drops it to line granularity, which makes "which agent session wrote this line, under which EditIntent, motivated by which report" a single query. Scion's blame answers who; TempleDB's would answer what was being attempted. That chain is the thing this database has that git does not, and blame is the missing join.

Validate it the way the project validates everything else — a named invariant in doctor entities, alongside the fourteen that run now (entity_counts_match_source_tables and friends), asserting that a cached vector's line_count matches the line_count on the corresponding vcs_file_states row. Results persist to invariant_checks, so drift shows up in doctor history without new plumbing.

Register the surfaces up front. The dead-imports feature is the cautionary tale: its bridge-relation set has to be edited in four places in sync — cli/commands/entity.py, cli/commands/summary.py, cli/commands/hygiene.py and gui_pages/entities.py. A new derived structure should name its consumers in one place on day one, or it acquires the same tax.

3. Lock-free commits: the Rust port is already the path

Principle 5 is where TempleDB is genuinely at odds with the article, and the evidence is all in the project's own operating notes: busy_timeout at 30s, _retry_on_lock() with exponential backoff on agent hot paths, streaming writes batched at 0.25s, every agent write funnelled through a single-writer agent/store.py, and admin db check / admin db repair for when it goes wrong anyway. SQLite gives one writer; each of those is a workaround for the thing Scion designed away.

The obvious reading is "nothing to do at this scale," and for throughput that is correct — 1,260 lifetime commits will never strain a write lock. But the load pattern that breaks this design is not volume, it is parallel agents, and that is already present: 14 active sessions, and a vcs_sessions table whose 755 rows exist because concurrent agents collide hard enough to need per-session staging isolation. The 2026-08-29 incident where a bash loop of 259 file rm calls spawned 258 orphan sessions is the same root cause.

Three concrete moves, in order:

(a) Route reads away from the writer. The templedb-rust project — restarted 2026-10-04, 31 files, binary templedb-rs — is a deliberately read-only subset verified byte-for-byte against the Python implementation across file cat, file ls, vcs log, vcs show, vcs diff, vcs branch, source snapshot, source revisions, entity explore, entity trace, entity paths, entity dead-imports and more. That read-only invariant is not a limitation to escape — it is Scion's principle 2. A thin, always-connected reader that never contends for the write lock is exactly the client half of the asymmetry. Pointing agent read traffic at templedb-rs is the cheapest available concurrency win and needs no schema change at all.

(b) The Postgres backend already exists. crates/templedb-db/src/backend/pg.rs sits behind a Store / Dialect abstraction next to backend/sqlite.rs, with value_from_pg narrowing Postgres's static types into SQLite's five storage classes in one place and erroring on an unmapped type rather than silently nulling. The port reads either engine today. Whatever the original motivation, this is the escape hatch from single-writer, and it is further along than any other item in this report.

(c) The schema change that actually unblocks it. Swapping engines is not sufficient, because two UNIQUE constraints make currency a mutable pointer and therefore a serialization point:

file_contents     UNIQUE(file_id, is_current)
vcs_working_state UNIQUE(project_id, branch_id, file_id)

The first is already a known sharp edge — the project's own notes say you must DELETE the old row rather than SET is_current = 0, or the update collides with itself. That is the signature of a design where "which version is current" is stored rather than derived. Scion has no such pointer: currency is a property of the branch head, read out of the changeset log. TempleDB can do the same thing, because vcs_file_states plus vcs_branches.head_commit_id already determine the current content of every file — that is precisely what the retired FUSE branch views reconstructed. Deriving is_current from the commit chain instead of storing it is the single change that most moves TempleDB toward principle 5, and it is worth doing on its own merits even if the engine never changes: content_blobs and vcs_file_states are append-only already, so once the mutable-current pointer is gone, the write path is almost entirely insert-only.

Sequence it (a) → (b) → (c) and each step is independently useful. Note that (c) interacts with the ghost-record failure mode — project_files rows with status='active' and no file_contents row, which present as tracked and return zero bytes. Deriving currency from the chain would make that class of record impossible to represent, which is a second reason to want it.

4. Post-merge testing is already the right shape — wire it up

Anthropic replaced the merge queue with post-merge automated testing, pre-deploy conflict testing, and Claude resolving conflicts. TempleDB has the pieces and no trigger: templedb test <slug> is a DB-backed QA runner with per-project definitions in project_tests and dependencies in project_test_deps, and templedb validate runs the env, nixos and deploy validators. Nothing invokes either on commit. Since DeploymentPipelineService already owns triggers and rollback, the move is to run the project's own test definitions after a commit lands and record the result against the Commit entity — turning "tested" into a queryable fact in the graph rather than something a human remembers doing. That is Anthropic's post-merge posture at 1/20,000th the scale, and it costs a hook rather than an architecture.

5. Directory-level IAM — only if there is ever a second writer

Scion shipped beside Antique (code review with semantic approval constraints), code search, and fine-grained IAM at directory level. TempleDB has code search already (three flavors, which is its own problem) and the skeleton of a review surface in intent — 1,107 EditIntents with create/list/show/apply/cancel, where a proposed edit is inert until applied. Antique's "semantic approval constraints" map onto exactly that: a constraint on which intents may self-apply. There is no access control at all today, which is correct for one operator. It becomes a prerequisite the moment agents should hold write scopes narrower than "the entire database" — and given that file set can silently replace a whole file, "narrower than everything" is already the right default for an autonomous agent. Worth keeping in view, not worth building now.

Finding: a stale design doc

While checking TempleDB's server-side story against Scion's, docs/GIT_SERVER.md turned out to document a database-native git smart-HTTP server driven by tdb gitserver start on port 9418, serving repos from vcs_commits / vcs_branches / content_blobs with on-the-fly git object conversion, intended for Nix flake inputs. templedb gitserver is not a registered command — it returns Unknown command: 'gitserver'. The live path is templedb publish (mirror-add, mirror-list, run), which pushes to external git remotes rather than serving from the DB.

This matters for the comparison because an on-the-fly git protocol server is Scion's principle 3 applied to the existing ecosystem — the article's own closing recommendation is that the git ecosystem adopt "comprehensive server-side RPCs" rather than that anyone reimplement Scion. TempleDB designed that and shipped a mirror-push instead. Whether the service module exists unwired (as happened with nix_store_service.py) or was never built is not established here; the doc should either be marked historical or the command registered. Same shape as the config-ast and ast entries in --help, which at least label themselves INCOMPLETE MIGRATION.

Verdict

TempleDB is not a small Scion, and the article's preconditions make clear it should not try to be. But the two systems independently reached the same four structural conclusions — changesets over snapshots, content-addressed shared blobs, operations where the data lives, working copies as an optional projection — from completely different pressures. Anthropic got there from 600 petabytes a day. TempleDB got there from a Button.jsx copied into four repos. That the storage model is the same either way is the most interesting thing in this comparison: it suggests the changeset-plus-blob-store design is what you get whenever you stop assuming every client needs a full offline replica, regardless of why you stopped.

The two principles TempleDB only half-satisfies are half-satisfied for opposite reasons. Horizontal scalability is absent and should stay absent — one SQLite file is correct for 25 projects and one operator. Lock-free commits are absent and that one is a real liability, because the thing generating write pressure here is the same thing that generated it at Anthropic: agents, in parallel, not waiting their turn. Volume will never be the problem; concurrency already is.

Which makes the most useful finding in this comparison an accident. The templedb-rust port was presumably not undertaken to satisfy a design principle Anthropic published later, but it is simultaneously a thin read-only client (principle 2, verified byte-for-byte against the Python implementation) and a working Postgres backend (the only credible route to principle 5). The structure Scion needed seven engineers and five months to build deliberately is, in miniature and for entirely unrelated reasons, already sitting in this database at 31 files. Finishing it is a smaller job than starting it.
