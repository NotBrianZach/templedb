What I noticed about my process

Parallel-with-isolation worked keep doing

For frecency + nixos reorg, launched the reorg as a background agent instructed to write its finished output to /tmp/nixos_reorg.py without touching the DB. I applied it after frecency landed. The agent hit an API stream timeout at ~48 minutes but had already written the file, so nothing was lost. Reviewing before applying caught a design choice I'd have made differently (Strategy B / dual registration) but that turned out fine.

Pattern to keep When two independent tasks are on the plate, spawn one as a subagent whose only output is a file in /tmp/. Serializing DB writes to the parent keeps SQLite happy; parallel drafting recovers the wall-clock savings. The instruction "don't touch the DB or shared checkout, just write /tmp/output.py" is what makes it safe.

--verify on every file set keep doing

Given the documented FUSE truncation risk, I used templedb file set … --verify on every non-trivial write this session and also byte-count-compared roundtrips (wc -c of input vs file cat | wc -c) for the ~15-20 KB reports. Nothing truncated. Cheap habit, worth continuing on everything larger than a one-line edit.

Wrote to the wrong path in regenerate_index didn't

Passed "index.html" to templedb file set when I meant "reports/index.html". Result: an unwanted index.html at project root pointing at reports as if the whole project were a report index. Caught it two commands later when the extracted view showed 4 entries instead of 3, one of which was a self-link.

Root cause I wrote the CLI's _regenerate_index and the calling regenerate_index method with the string "index.html" hardcoded in two places (the tempfile name and the destination path). The tempfile only needs a leaf name; the destination needs the full path. Muscle memory smeared the two. Fix would be a single INDEX_PATH = f"{REPORT_DIR}/index.html" constant so the two couldn't drift apart.

Verified memory instead of trusting it keep doing

While writing the ontology doc I referenced templedb nix who-uses based on a memory entry. When the user asked about it, I ran templedb nix --help — command doesn't exist. Neither does the equivalent under templedb nixos. Fixed the memory in place with a NEVER SHIPPED flag. The verify-before-cite rule the memory system has caught this one; without it the ontology doc's "distance functions in the CLI" list would have contained a phantom.

Composed queries produced an unexpected finding keep doing

Ran the composed-valuation queries assuming they'd be illustrative. One of them — "for pairs of AST builds on different hosts, do any share an output hash?" — returned zero. All 27 build hashes are host-unique. That's a real architectural finding (content-addressed identity is not being exploited at the AST emit layer) that neither the ontology essay nor the usual grep-around workflow would have surfaced. The pattern: composed queries against structural data often produce useful negative results. "Nothing shares" is signal too.

Wrote a lot of prose today notice

Three ~15-20 KB HTML docs plus this recap. Prose-to-code ratio was unusually high because the work was analysis-heavy. That's a legitimate mode — the doc arguing that TempleDB is an ontology in disguise is where the "AST builds have no cross-host reuse" observation eventually came from. But it's worth noticing that four hours of writing produced roughly one followable insight (the AST reuse finding), whereas the earlier bug fix produced a shipped, verified behavior change in about 20 minutes. Both are worthwhile; neither substitutes for the other. Recognizing which mode I'm in matters.

Resisted scope creep on the phantom cleanup keep doing

After the claude_code fix committed, the 29 phantom modified rows were still there. I asked before sweeping them into the same or the next commit. User confirmed a separate cleanup; that got its own explicit SQL step with a diagnostic first ("all 29 have NULL content, safe to clear"). The alternative — quietly cleaning them during commit — would have buried the diagnostic. Small choice, but the transparent version was worth the extra round trip.

Bug I introduced would have shipped without the smoke test notice

The regenerate_index path bug wasn't caught by any syntax check or unit test — it required actually running the CLI end-to-end and eyeballing the output. Habitual smoke-tests-after-write is what saved it. Without them, a broken index page would have quietly sat in the DB until someone opened it in a browser. This is a general property: my Python edits pass parse checks and roundtrip successfully into the DB, but neither of those catches a logically-wrong string constant. End-to-end runs are the safety net.

Didn't fix the parent-level candidate hint didn't

When I made templedb graph <sub> [POSITIONAL] print candidates on missing arg, I only helped users who typed the subcommand. templedb graph alone still prints an argparse error because subparsers is required=True. Same UX gap I set out to fix, one level up. Would take another 20 lines. Not urgent, but I set the bar and didn't clear it fully.

Meta-meta: what this format wants to become

This is the first session recap. As they accumulate, patterns should emerge that don't fit in a single report — recurring bug shapes ("I write to wrong path" happened at least twice), recurring wins ("--verify saved me"), drifts in scope. Some options for making that legible:

  • Tag each observation with a controlled vocabulary (path-bug, trust-verified, scope-creep, parallel-agent-worked) and grep across recaps to see frequencies.
  • Have templedb reports produce a "meta index" that groups observations across recaps by tag.
  • At the end of each recap, explicitly ask "does anything here contradict a previous recap's assertion?" as a self-check for drift.

For now, one recap is not a series. But writing this made me notice at least three things I would not have surfaced otherwise (the parent-level candidate gap, the "prose-heavy sessions produce fewer discrete wins per hour" observation, and the wrong-path-constant bug pattern). If future recaps produce even one non-obvious observation each, the format earns its keep.
