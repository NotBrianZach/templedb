Workflows before and after: what the observer/integrator model changes in daily use

Companion to the from observer to integrator implementation plan. That report argued for the shift in the abstract; this one grounds it in concrete daily workflows — starting with the editing session that produced this report itself, then walking through five other everyday scenarios (multi-agent refactor, deploy archaeology, cross-project impact analysis, broken-deploy investigation, new contributor onboarding, report/decision archaeology). The theme is boring in a good way: fewer failures at the boundaries, new queries the graph now supports, and no upheaval on the paths that already worked. Most commands stay the same. The changes are concentrated in authoring and querying; everything in between is untouched.

Our current session, before and after

This session shipped three design reports and one Emacs cursor fix. Walk-through of what actually happened, and what would have been different under the proposed architecture.

The session as it went

Today
  1. Cursor hijack reported. Diagnosed at templedb-agent.el:1573.
  2. templedb edit templedb --no-editor for a writable workspace.
  3. Edited the file; ran ERT + pytest.
  4. templedb commit templedb <workspace> to record a DB commit.
  5. templedb project checkout templedb <checkouts> --writable --force to publish to the git-repo view.
  6. git commit in the checkout to update the git ref.
  7. templedb nixos update-input system_config templedb. This also re-materialized system_config’s own checkout, and the materialize step deleted .authinfo.gpg from the working tree because it wasn’t in the DB.
  8. Rebuild failed. Fifteen minutes of investigation. Force-added .authinfo.gpg back to git.
  9. Rebuild again. Success.
  10. Wrote three design reports; repeated mini-versions of steps 2–8 for each.
  11. Reports GUI showed a stale list until a hard-refresh.
Under the proposed architecture
  1. Same diagnosis; nothing about debugging changes.
  2. templedb edit templedb still gives you a workspace, but the workspace is a normal git checkout, not a materialized DB projection. git status, git diff, git log work as usual. Any editor opens it without templedb knowing.
  3. You edit the file. On save, a filesystem watcher fires templedb ingest git templedb --incremental, which re-parses the changed file and updates the entity/relation graph. file_contents snapshots the new state automatically; you don’t call file set.
  4. templedb intent create --from-workspace collects your local changes as an EditIntent. templedb intent apply <id> runs git commit inside the workspace and records applied_at.
  5. No separate publish step. The git checkout IS the source. Nix reads from it directly (same flake input path).
  6. templedb nixos update-input system_config templedb still bumps flake.lock. But there’s no materialize sweep — system_config’s checkout is already the authoritative git tree, nothing to overwrite. The .authinfo.gpg incident is impossible by construction.
  7. Rebuild proceeds normally.
  8. Reports get reindexed automatically on ingest; GUI reflects it on next request.

Net difference: four fewer commands, one fewer failure mode, one fewer 15-minute debug session. Same output. And every state change (edit → commit → deploy) is a chain of typed entities in the graph, queryable as “who wrote this, when, in which session, to fix what, and where did it land.”

Workflow A — multi-agent parallel refactor

Three agents in three sessions, each renaming foo_bar → foo_baz across templedb, bza, and woofsledger.

Today Each agent gets a separate TEMPLEDB_SESSION_ID and edits files via templedb file set. Session-scoped VCS staging protects them from clobbering each other, but there’s no unified view of “what has each agent proposed so far” without dropping to SQL. Conflicts between agents on the same file are silent races — whoever commits last wins.
Proposed Each agent creates EditIntent rows tagged with their session. You run templedb intent list --outstanding and see one row per agent per file. templedb intent dry-run <id> shows the effect without touching the workspace. templedb intent apply <id> applies one at a time; you can cherry-pick, reorder, or reject before final commit. If two agents propose conflicting changes to the same file, the second apply fails cleanly with a rebase-style conflict message.

Bonus: templedb graph query "AgentSession → EditIntent → FileSnapshot" gives you “which files did agent X propose changes to?” as a first-class query.

Workflow B — deploy archaeology

“Was this bug in the currently deployed version?” The question surfaces after every regression report.

Today git log in the checkout, eyeball the commit, cross-reference the deployment table by hand. Fine for a familiar codebase; hostile for anything you haven’t touched in months. If the deployment history isn’t in the DB (fleet deploys sometimes are, ad-hoc deploys usually aren’t), the question becomes unanswerable.
Proposed templedb graph explain deployment/42 walks the graph: Deployment 42 → StorePath xyz → Derivation → Commit abc123 → FileSnapshot foo.py@abc123 → defines-function handle_request. Then templedb graph diff deployment/42 deployment/45 diffs the two source snapshots directly. Every fact in the chain carries observed_by and observed_at, so you can see whether any hop is stale.

Workflow C — cross-project impact analysis

Renaming a function in the templedb agent’s public interface. Which projects call it?

Today templedb graph who-uses <function> if it works for your language; otherwise grep -r across every project directory. Coverage depends on templedb’s scanner, which currently handles Python moderately and Nix via the AST-deploy work.
Proposed Same query, but backed by SCIP facts ingested from language-specific indexers (scip-python, scip-typescript, scip-nix). Coverage grows with the SCIP ecosystem, not templedb’s parser budget. Every project registered with templedb gets uniform semantic search over its symbols, imports, references, and callers. The answer is one query no matter how many languages the target codebase spans.

Workflow D — broken deploy investigation

A deploy went sideways at 3am; you’re trying to figure out where reality diverged from what the DB thinks.

Today SSH to the machine, nixos-rebuild switch --rollback, journalctl -xeu whatever.service, guess. If templedb has stale deployment records, you’re fighting phantom information.
Proposed templedb doctor entities --host zMothership3 runs the reconcile: for every entity claiming to be about zMothership3, asks the machine (via SSH) whether it’s still current. Output tells you: “DB thinks generation 47 is running; machine reports generation 45. Drift of ~4 hours. DB last observed at 03:12; machine last modified at 06:47.” You now know which side is wrong, which is stale, and by how much. Same reconcile catches “DB thinks store path X exists in nix store; nix store says missing” from garbage collection.

Workflow E — new contributor onboarding

Someone (or some future you on a new machine) wants to work on templedb from scratch.

Today Clone the system_config repo. Try to build. Hit .authinfo.gpg does not exist. Get told about the secret handling story. Clone templedb separately (or accept that browsing it means jumping through nix-store hoops). Learn about TEMPLEDB_DEV_MODE=1 for the CLI. Discover the FUSE mount is gone. Discover materialize sweeps. Discover the write-path history in CLAUDE.md. Two-day onboarding.
Proposed Templedb is a normal git repo. git clone, nix build, done. No secret required at eval time (home.nix source references move to sops-nix or age-encrypted paths that don’t exist at eval time). Contributor cds into templedb’s flake input and reads/edits like any other project. CLAUDE.md becomes a short document about the entity graph and the ingestion algebras, not a survival guide for the write-path bugs.

Workflow F — report and decision archaeology

“Which of these design reports actually got implemented?”

Today templedb reports list, grep titles, hope the implementation commit references the report by name in its message. Half the time it doesn’t. You end up scrolling through the HTML in a browser tab.
Proposed templedb graph query "Report → motivated → Decision → implemented-in → Commit" gives you “which reports have been acted on?” The complementary query, Decision → ~implemented-in, gives you “which decisions have no code trace?” That second one is genuinely useful for finding half-shipped design work. Reports become first-class graph entities linked to their implementation, not just HTML files sitting in a directory.

What stays exactly the same

Important honest note: most daily commands don’t change. All of these keep working identically:

Command familyBehavior
templedb file cat / lsUnchanged. Reads snapshots.
templedb graph search / who-uses / callersSame interface; backing store gets richer under the hood.
templedb vcs log / diff / branchUnchanged. Reads commit facts from the graph.
templedb reports listUnchanged. Reports get new optional Decision links.
templedb guiUnchanged endpoints; new graph pages available.
templedb ai vibe / agent / chatUnchanged. Agent runtime stays DB-native.
templedb project list / show / registerUnchanged.
templedb deploy fleetUnchanged. Deploy records get new StorePath → Commit provenance edges.
templedb config-astUnchanged. AST-deploy work is already observer-shaped.

The changes are concentrated in the authoring surface (edit workflow, deployment prep, materialize) and the querying surface (new graph queries that couldn’t be asked before). Everything in between keeps working as-is.

Summary: the shape of the shift

Where the improvement lives Fewer failures at the boundaries. No more materialize sweeps. No more edit-the-wrong-copy. No more “which mirror is stale?” The classes of bug we’ve been hitting close by construction, not by policing.
Where the new capability lives Cross-authority provenance queries. “What did this deployment run, from which commit, from which agent’s intent, motivated by which report?” is now a five-hop graph query. Freshness telemetry per fact makes drift measurable, not just detectable. Multi-agent staging becomes trivially safe.
Where nothing changes The daily shell. Read commands, agent commands, deploy commands, config commands — all unchanged. The philosophical shift (“observer of source, owner of intents”) is invisible to most workflows most of the time. It shows up where it should: at the boundaries that were breaking, and in the queries you couldn’t previously ask.

That’s the honest before/after. Less friction on paths that were breaking. More capability on queries you couldn’t previously make. And no upheaval on paths that were already working. The design is good in the specific sense that most of it doesn’t look like a design at all — it looks like the friction quietly going away.
