Session recap 3: code-intelligence hygiene

What we shipped after the context-window compaction on 2026-09-04: entity paths, entity dead-imports, the __module__ synthetic symbol trick, cross-file inherits edges, decorator tracking, and an ambient hygiene digest in templedb summary. Five commits, five backups.

What existed at the start of this stretch

The observer/integrator plan was done through Phase 5. Six ingest adapters, ten doctor invariants, three preset workflow queries, systemd timers on hourly + daily cadences, and the entities table full of ~16k nodes across git / agent / intent / reports / nix / deploy / python authorities.

What we didn't have was a way to ask questions the graph should be trivially able to answer. Namely:

  • "How is X connected to Y?" — entity trace walks outward from one node; it can't home in on a target.
  • "Which of my imports are dead?" — the raw call graph exists but no CLI surfaces it.
  • "Is this project's import hygiene getting worse over time?" — no ambient signal; you had to remember to look.

What shipped

CommandAnswersUnder the hood
entity paths FROM TO How does X reach Y in the graph? BFS from FROM with parent pointers; undirected by default; prints reconstructed chain with entity labels.
entity dead-imports [--slug S] Which imports have no calls, inherits, or decorator bridge? SQL CTE: for each File→imports→File, LEFT JOIN the defines→calls|inherits→defines chain; keep those with zero bridging edges.
summary hygiene block Is any project's import hygiene drifting? Same SQL grouped by slug, top 5. Green/yellow/red on % dead.

1.9 was flat, which was surprising until you look at the shape of templedb's own code — nearly all decorators here are stdlib (@classmethod, @property, @staticmethod) which aren't project-Symbol targets. Codebases with FastAPI-style @app.get or @dataclass-heavy modules would see much bigger drops.

The remaining 21%

Diminishing returns. The candidates still flagged are mostly:

  • Type annotations: from t import UserSpec; def f(x: UserSpec) — the Name is used in an annotation, never called. Would need to scan annotation subtrees and emit a uses relation.
  • Attribute chains: from mod import svc; svc.method() — the call is Attribute(Name('svc'), 'method'), which the resolver doesn't chase.
  • Reflection: getattr(mod, name), dynamic dispatch — no static analysis will catch these.
  • Genuinely dead imports: the actual value the tool exists to find, buried in the noise.
Decision We stopped at 21%. The tool works for eyeballing per-project — a human can distinguish real dead imports from annotation-uses by reading the file. Making the tool auto-suppress every case would require going deep into type-annotation scanning and would risk hiding real signal.

The categorical bit worth noting

The observer/integrator design put a lot of weight on entities as objects and relations as morphisms. What this stretch showed is that the useful queries are about the category, not the objects:

  • entity paths asks about morphism composition.
  • entity dead-imports asks about the presence of any composition-chain bridging two Files — regardless of whether the bridge is a calls or inherits or any future kind.

When we added inherits in 1.8, dead-imports absorbed it via a two-character SQL diff: cr.kind IN ('calls', 'inherits'). Adding uses or references later would be the same size change. That's the payoff of a uniform graph over domain-specific tables.

Bug we ate our own dogfood on

When 1.7 landed and I ran the first live dead-imports, my test helpfully failed on: 

assert 'used_lib.py' not in out

...because unused_lib.py contains used_lib.py as a substring. Trivial fix — anchor to the full path testproj/src/used_lib.py — but a nice reminder that string containment is not string equality.

What's still on the table

  • Type annotation tracking — uses relations from annotation subtrees. Would probably drop dead-imports another 5–10 pp on templedb.
  • Attribute-chain call resolution — svc.method() where svc is an instance/module of a known type. Big lift; would benefit from SCIP or type inference.
  • GUI page for hygiene — /hygiene mirroring the CLI. Ambient visibility for browser users.
  • Historical hygiene tracking — record dead-import counts into a table, plot over time. Would let the doctor flag "candidates jumped +30 this week".
  • CRSql for fleet — still deferred; sync of the entity graph across machines is the natural next Big Rock after code-intelligence is settled.

Shipping cadence

Five publish cycles this stretch, all following the same recipe the session has used ~35 times total: 

templedb commit templedb $EDIT_WORKSPACE -m "..."
templedb project checkout templedb $CHECKOUT --writable --force
cd $CHECKOUT && git add -A && git commit -m "..."
cd $SYSTEM_CONFIG && nix flake lock --update-input templedb
templedb nixos system-switch system_config --yes
cd $CHECKOUT && git push github master
templedb storage backup gcs

A macro. This is worth its own polish someday — templedb publish run templedb -m "..." already handles part of it; a templedb ship alias that also triggers the nix switch + gh push + backup would compress this to one command. Explicitly not doing that now — the visibility of the individual steps is worth the typing.
