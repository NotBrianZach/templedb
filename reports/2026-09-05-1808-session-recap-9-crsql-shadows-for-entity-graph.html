What actually got done

1. Two shadow tables + full CRR trigger machinery

sync_entities and sync_relations follow the standard 7-object CRSql layout (shadow + __crsql_clock + __crsql_pks + _itrig/_utrig/_dtrig). UNIQUE, FK, and CHECK constraints from the main tables are dropped, since CRSql prohibits UNIQUE on CRRs.

2. Scope-filtered population

_populate_shadow_tables in sync_engine.py gained two INSERT queries. Entities filter by sync_scope='fleet' directly. Relations derive scope from endpoints, because migration 099 landed relations.sync_scope as a column but no ingest adapter populates it. A relation enters the CRR iff both endpoints are fleet-scope. Result: 3,022 of 30k entities and 3,191 of 40k relations enter the CRR — roughly 10% of the graph, same ballpark the prep report projected.

3. Write-through triggers (migration 101)

Six triggers on the main tables propagate fleet-scope writes to the shadows automatically: 

entities_sync_fleet_ins    AFTER INSERT ... WHEN NEW.sync_scope = 'fleet'
entities_sync_fleet_upd    AFTER UPDATE ... WHEN NEW.sync_scope = 'fleet'
entities_sync_unfleet      AFTER UPDATE ... WHEN OLD.sync_scope = 'fleet'
                                          AND NEW.sync_scope IS NOT 'fleet'
entities_sync_del          AFTER DELETE ...

relations_sync_fleet_ins   AFTER INSERT ... (endpoint-derived scope via subquery)
relations_sync_fleet_upd   AFTER UPDATE ... (same)
relations_sync_del         AFTER DELETE ...

All six use INSERT ... ON CONFLICT(id) DO UPDATE rather than INSERT OR REPLACE. The REPLACE path is DELETE+INSERT internally, which fires CRSql's dtrig before its itrig and causes a UNIQUE-on-id failure during reconcile-fed cascades. On-conflict-do-update sidesteps that.

4. Reconcile extensions

reconcile_to_main() now projects shadow rows into entities/relations using the natural key (kind, external_ref) for entities and translating endpoint IDs through the same natural key for relations. Local IDs are preserved; peer IDs never bleed into local main. Rows whose endpoints don't resolve are silently skipped — the entity reconcile runs first, so the normal case is the endpoint has already landed by the time its relation is projected.

5. Wired the orphaned templedb sync CLI

src/cli/commands/sync.py has always defined register(cli) with seven subcommands, but nothing in src/cli/__init__.py called it — so templedb sync init printed Unknown command. Same pattern as the templedb ast orphan fixed in F95251D8. Added the import and the sync.register(cli) line.

The collision that stopped step 10

Design gap

Two-instance convergence works only when the two DBs' shadow IDs don't collide. In real fleet use, they will.

The two-instance test spun up /tmp/scratch.sqlite and /tmp/scratch2.sqlite (both copies of prod, with the scratch2 crsql_site_id reset so CRSql regenerated a distinct site). A on scratch inserts an entity — SQLite assigns ROWID 30460. B on scratch2 independently inserts a different entity — SQLite also assigns 30460, because the two databases' ROWID counters advanced independently from the same starting point.

When A's changes ship over and land in B's sync_entities, CRSql's last-writer-wins collapses the two id=30460 shadow rows into one. The losing row is silently dropped — its entity never reaches B's main table. Post-sync, A has both entities, B has only its own. Test result: 

A: [('conv-A', 'from-A'), ('conv-B', 'from-B')]
B: [('conv-B', 'from-B')]

Repeating the test with explicit non-colliding IDs (INSERT ... (id, ...) VALUES (900001, ...) on A and 900002 on B) produced full convergence: 

A: [('conv-A-2', 'from-A'), ('conv-B-2', 'from-B')]
B: [('conv-A-2', 'from-A'), ('conv-B-2', 'from-B')]

So the CRSql plumbing, migration, write-through triggers, and reconcile all work correctly. The problem is upstream of any of that: SQLite ROWID allocation is per-DB, and any two machines making concurrent inserts on the same table will collide on the shadow's PK.

Options for fixing (deferred to next session)

  • Site-prefixed IDs. Reserve the top bits of the 64-bit ROWID for a per-machine site index. Requires either an AFTER INSERT trigger that rewrites the ROWID (SQLite doesn't allow that) or an explicit INSERT (id, …) pattern in every writer with a globally-coordinated site index. Would need adapter changes.
  • UUID-based IDs on the shadows. Add a uuid TEXT column to sync_entities and use that as the CRSql PK instead of id. Populate on write-through trigger with hex(randomblob(16)). Doesn't require adapter changes since the write-through trigger owns shadow inserts. Adds a 16-byte column per shadow row (~50KB overhead across all shadows, negligible).
  • Drop id as PK on the shadows entirely — use (kind, external_ref) for entities and (from_kind, from_ref, kind, to_kind, to_ref) for relations. CRSql allows composite PKs. Most natural semantically, since the whole reconcile logic already treats natural keys as authoritative. Requires refactoring the shadow DDLs and the write-through triggers to source natural-key values from JOINed entities.

My inclination: option 3 (natural keys). It eliminates the whole class of ID-space coordination problems and matches the design intent of the observer model — surrogate id columns are local implementation details, not shared truth. Costs a moderate refactor of the write-through triggers.

Metacognition

What I got right: starting with the safe steps (snapshot, scratch DB, iterate on scratch) before touching anything live. Trusting the prep notes' current-state summary was empirically accurate — it saved me from re-verifying six shadow tables' worth of infrastructure. Catching the CLI orphan pattern from the recent ast fix — same shape of bug, would have been another 30-min mystery without pattern recognition. Testing the INSERT OR REPLACE vs ON CONFLICT DO UPDATE distinction before assuming the trigger was right.

What I should watch for next time: I ran the two-instance test with the same starting DB — should have realized ROWID collision was structurally guaranteed the moment I set that up. If I had gone through the design implications of "same DB, two independent ROWID allocators" before writing code, I would have flagged the ID collision issue during checklist planning, not at step 9. Ordering: think about the design invariants before the tests, not through the tests.

Discipline held: stopped before applying to production, even though the checklist explicitly listed step 10. The pickup notes assumed no material risk from the migration itself — accurate — but the test result changed the risk picture for enabling sync afterward. Better to surface that to the user than to ship and hope.
