Multi-resolution assessment: templedb from 40,000 feet to the millimetre

A six-magnification pass over templedb as it stands on 2026-10-03: the thesis, the architecture, the subsystems, the code, the conventions, and finally four specific lines. The short version is that this is a system whose central bet — model every authority as a graph and check that the diagram commutes — has paid off well enough that its remaining failures are nearly all of one kind: a true statement stored somewhere nobody is standing. The deepest finding is that templedb has already catalogued 47 of its own decayed columns in a baseline table, which means this report's methodology is one the system runs on itself hourly.

Predecessor. This builds on reports/2026-09-24-1442-templedb-assessment-abstractions-tooling-and-a-10-day-silent.html, which diagnosed a 151-run silent ingest outage and the three-tools-one-name search problem. Both are resolved or unchanged and are not re-litigated here. What is new is the checkout-roles tranche (phases 0–4, 2026-09-27 → 2026-10-03), which that report predates entirely.
40,000 feet — the thesis

TempleDB is a SQLite database that claims to know things about 30 software projects, and a CLI with 45 top-level verbs for asking. The interesting claim is narrower than "database-native project management," which is how the README sells it. The real thesis is in docs/ENTITY_GRAPH_DESIGN.md: facts about software live in mutually ignorant authorities — git knows commits, Nix knows store paths, systemd knows deployments, the agent log knows tool calls — and no authority can answer a question that spans two of them. TempleDB does not try to replace any of them. It observes each, projects what it saw into one typed graph, and then asserts that the projection must agree with its sources.

That last move is the whole system. 34,717 entities across 14 kinds and 28,918 relations are derived state, rebuildable by nine adapters in 17.8 seconds measured. Because it is derived, it can be checked; 23 invariants check it; and because it is cheap to rebuild, the standard response to any graph anomaly is to rebuild rather than to investigate.

Assessment The thesis is sound and the evidence is that the system's failures have changed character. A year-one tool fails by losing data. This one fails by knowing something correct and not surfacing it where the reader is — which is a strictly later-stage problem and the one this report keeps rediscovering at every magnification.

1,000 feet — the subsystems

What works, with evidence

Ingest is boringly reliable now. Excluding the crsqlite outage the prior report diagnosed, every adapter is at a perfect record: agent 251/251, nix 252/252, python 274/274, deploy / intent / reports 248/248 each. The git adapter's 234 failures all terminate at 2026-09-24 21:40:31 — the moment that outage was fixed.

The invariants are actionable, not decorative. 23 checks, and the valuable property is that violations name their own repair. Every one encountered while writing this report told the reader what to run, and in one case told them what not to run: "`ingest all` will NOT fix this; it never deletes." That sentence saves a wasted cycle, and it exists because someone burned the cycle.

The checkout-roles tranche solved a genuinely hard problem. When the canonical checkout, several edit workspaces, and the DB all disagree, which tree is authoritative? Phases 0–4 answer it with a blob-age guard, a purpose-scoped resolve(purpose), and migration 122's partial unique indexes. The deployed result is strict in the right direction: vcs add now refuses rather than silently falling back to the published tree, with an error that explains both failure modes it is preventing.

Where it is weak

1. The deployed build lags the database, and nothing says so. This is the highest-leverage defect in the system. On 2026-10-04, src/cli/commands/checkout.py was 874 lines in the DB and 766 in ~/.nix-profile. The entire Phase 4 prune was committed, published, and inert. Running project checkout-cleanup printed neither of its two verdict branches — it skipped the whole stage in silence, because the deployed binary had no such code. The command did not fail. It succeeded at doing nothing.

2. Dev mode runs the wrong tree, by design, silently. TEMPLEDB_DEV_MODE=1 reads as "run what is in the DB." It does not. resolve_dev_checkout() prefers an edit workspace over the canonical tree — reasonably, since dev mode exists to run the code you are editing — but it will happily choose another session's workspace, and its validity check is existence-only. Its own docstring concedes that "a tree holding stale contents of every file still passes and merely runs slightly old code."

Observed: a parser change written to the DB kept being rejected, because dev mode was loading claude-code-agent-3528/src, whose project.py was 626 lines against the canonical 629 — while its checkout.py was current at 874. A half-stale tree is the confusing case, and nothing printed which tree had been chosen. This is the recency-wins bug the checkout tranche was built to kill, reappearing one layer below the layer that was fixed.

3. Cleanup cascades across subsystem boundaries. admin checkout-gc deletes checkout rows whose directory is gone, and the delete CASCADEs to snapshot rows. The graph does not follow, because ingest never deletes. Removing six dead workspaces therefore orphaned 1,969 File entities and turned entity_counts_match_source_tables red — including orphans in trig-navigator and woofs_projects, projects the cleanup never touched. Correct behaviour from both halves; nobody owns the seam.

4. Documentation drifts faster than it is read. The most load-bearing paragraph in the repository — CLAUDE.md's "TL;DR for agents," the first thing any agent reads — instructed readers to run templedb vcs session start --pin --name … and vcs session unpin. Neither flag has existed for weeks, in the deployed build or the DB source. A second section documented a pin file at $XDG_STATE_HOME/templedb/session.pin and claimed vcs session current reports pin status; that path appears nowhere in the tree except CLAUDE.md and a migration 103 comment, and an orphaned pin file pointing at ended session #889 was sitting on disk being ignored. Meanwhile the copy of CLAUDE.md that agents actually loaded was a 134-line file from 2026-08-12 in an orphaned clone with no row in the checkouts registry. All three are fixed as of this report.

100 feet — the code

Two numbers characterise the codebase. src/cli/commands/entity.py is 5,048 lines — it holds all 23 invariants plus the entity query surface, and it is nearly twice the next largest (nixos.py, 2,616). The three largest files are all CLI command modules; the fourth is src/mcp_server.py at 1,648. Logic accretes at the surface, where it is cheapest to add and hardest to test.

Against that, the comment density is extraordinary and the comments are the good kind. A representative sample, in checkout_repository.py, explaining why a prune refuses to touch unowned rows: 

Requires an owner. A session_id IS NULL row is NOT a candidate,
even though resolve() treats it as equally adoptable: migration
113's backfill left the column NULL rather than matching leaf
names against vcs_sessions, so "no owner" means "nobody recorded
one", not "the owner finished". Retiring those on content alone
would be inferring the thing the backfill deliberately refused to
guess. They stay for a human.

That is a comment explaining a deliberate refusal to act, with its historical cause and the reason the safer-looking alternative is wrong. Commit messages carry the same discipline: they state what was believed, what was measured, and frequently that a fix was "verified a no-op rather than assumed." One system_config commit records reproducing a Nix derivation by hand and diffing the result against the live layer before deleting a file.

Assessment The prose in this repository is better than the structure. Where the code is confusing there is almost always a comment admitting it and explaining why. The failure mode is not ignorance — it is that the knowledge sits in a docstring 4,000 lines into a CLI module instead of in the output of the command that needs it.
10 feet — the conventions

The project has two opposite CLI conventions for destructive operations, and the split is deliberate rather than sloppy. Most commands are destructive-by-default with a --dry-run opt-out. entity prune-orphans inverts it — dry-run is the default, --apply is the opt-in — and the parser carries the reason: 

# Dry-run is the default and --apply is the opt-in, rather than the
# usual --dry-run opt-out. These rows accumulate precisely because
# nobody looks at them, so the first run of an unfamiliar command
# should show its work instead of deleting graph rows.

It is implemented as dest='dry_run', action='store_false', default=True, so every handler reads one uniform field and only the user-facing surface differs. That is the right way to disagree with your own convention. The asymmetry is load-bearing: safe-by-default where the data is invisible, destructive-by-default where the user is already looking at it.

The cost showed up anyway. The entity_counts_match_source_tables invariant ended its message by telling the reader to run entity prune-orphans --kind File --dry-run — a flag that subcommand deliberately does not have. The tool emitted a command the tool then rejected. An audit of the other five command strings doctor emits (doctor entities --check, ingest history --limit, entity search --kind, ingest scip --project, graph explore) found all of them correct, so this was one stale hint and not systemic rot. Fixed in 3D380B12ED06A2FC by correcting the hint rather than adding a no-op alias, on the grounds that an alias would imply the preview needs asking for.

1 millimetre — four lines

The best line in the system

CREATE UNIQUE INDEX checkouts_one_edit_per_session
    ON checkouts(project_id, session_id)
 WHERE kind = 'edit' AND is_active = 1

Migration 122. A partial unique index that encodes "one edit tree per session per project" directly in the schema instead of in five readers' heuristics. It is also, precisely, the system's sharpest open gap: SQLite treats NULLs as distinct in a unique index, so this constrains every row except the unowned ones — which are exactly the ambiguous rows it was written to constrain. The design report predicted this in writing before it was built: the NULL set "only becomes meaningful once sessions populate the column."

The gap is worse than documented

CLAUDE.md says an agent "that exports neither var" creates unowned trees. Measured, it is sharper than that — exporting the variable is not sufficient either: 

$ TEMPLEDB_SESSION=zz-probe2 templedb edit regr-test
  Workspace:  …/edit-workspaces/regr-test/zz-probe2
  → checkouts.session_id IS NULL

Correct directory name, no owner. _resolve_workspace_session_name() reads the env var directly to name the directory, while current_session_id() only matches an existing live row and deliberately never creates one — so if edit is the first call after setting the variable, ownership is lost while every visible signal looks right. Opening the session first yields an owned row. The remedy is one command of ordering, and it is now documented in AA22A3D74D3626E6.

The line that invalidates a lazy reading

Read-only: this reports drift. A future reconcile handler will
apply each session's declared reap_policy.

_check_no_expired_active_sessions, entity.py:3691. Worth quoting because during this very session it was asserted — wrongly — that doctor entities ends sessions as a side effect, on the evidence that two sessions ended at a timestamp near a doctor run. The invariant is a pure SELECT; entity.py contains no session mutation at all; and reap_stale_sessions is reachable only from vcs session gc, which no timer runs. The separation the critique asked for already exists. Correlation in a timestamp is not a caller, and the file was three greps away.

The 47 columns that already knew

The deepest thing in the codebase is no_new_unmaintained_columns, and it reframes this entire report. It measures every column for two failure shapes:

ShapeCountHow it misleads
all_null30 Reader gets None and silently falls back to a hardcoded default.
constant17 Worse — the value is plausible, so nothing about the read looks broken.

Measuring on 2026-10-02 found 47, seeded into unmaintained_columns_baseline by migration 123 so the invariant reports regressions rather than the backlog — because 47 red issues on day one "trains people to skip the whole surface." Among the catalogued 47: vcs_commits.lines_removed is 0 across all 567 commits, so any diffstat rendered from it is confidently wrong; git_commit_hash is NULL on all 567, which is why no templedb-commit → git-rev mapping exists.

And the docstring names vcs_sessions.reap_policy and expected_lifetime_seconds as all-NULL while session gc prints "lifetime 86400s, policy=orphan_stages" for every row — "from code, not from the column." That is exactly the observation this session arrived at independently, mis-diagnosed as "gc is structurally broken," and had to retract: the reaper COALESCEs the same 86400s default, so it works fine — its criterion is simply age, not process liveness. The correct version of the finding was already written down, in the invariant that guards it.
Assessment A system that has catalogued 47 instances of its own most insidious decay pattern, and automated the detection of the 48th, is doing something most mature codebases never attempt. That it is still possible to spend an hour rediscovering one of the 47 is not a contradiction — it is the thesis of this report. The knowledge exists. It is not where the reader is standing.
The through-line

At every magnification the same defect recurs, and it is never a missing fact:

  • 40,000 ft — failures have shifted from data loss to unsurfaced knowledge.
  • 1,000 ft — Phase 4 was committed, published, and inert; the command skipped it in silence.
  • 1,000 ft — the first paragraph agents read described a flag removed weeks earlier.
  • 100 ft — the explanation is in a docstring 4,000 lines into a CLI module.
  • 10 ft — doctor emitted a command doctor's own parser rejects.
  • 1 mm — reap_policy's true behaviour was documented in the invariant that guards it, and still cost an hour.

The system is good at knowing and weak at telling. Its invariants are the counter-example that proves the point: they work precisely because they push a fact and a repair command into the one place someone is already looking. Every defect above is a place where that pattern was not applied.

Which makes the highest-value next work unglamorous and small. Print the resolved tree when dev mode picks a non-canonical one. Make a deployed-build-behind-DB check a startup warning rather than a thing you discover by watching a command do nothing. Have checkout-gc name the graph rows its cascade just orphaned. None of these is an abstraction; all three convert something the system already knows into something it says.
