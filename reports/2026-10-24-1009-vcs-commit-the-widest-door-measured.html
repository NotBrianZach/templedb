vcs commit: the widest door, measured

The write-path document called vcs commit "the widest door in the system" and left it at that. This measures the door. It is seven tables, nine guards, one trigger the port has no equivalent for, and one dependency — the checkout — that is not a translation problem but a question about what the port is for. The conclusion is that commit should be split: the three-quarters that is database work can be ported and verified now, and the quarter that reconciles a filesystem should be refused outright rather than ported badly.

Why this document exists

The sessions report (2026-10-23) listed vcs commit as its step 6 and said it wanted "its own document. Six remaining guards, four tables, and the parent-chain bug". Both numbers were low, and one of them was low in an interesting way.

Since that was written, commit also acquired scope. Porting file set --stage turned up that --stage is message-only in Python — the auto-stage is unconditional — and that vcs_working_state has no reader in the port because its only consumer is commit. So the auto-stage moved here, and with it the table and the checkout mirror that keeps it honest.

So four new mirrored tables, not the document's "four tables" total — and project_files is the one to notice. Commit is the only path in the system that hard-deletes a project_files row. Everything else soft-deletes by flipping status, which is why file set needed an un-delete guard at all.

The trigger, which is the sharpest porting problem

update_branch_head_on_commit is an AFTER INSERT trigger on vcs_commits that sets vcs_branches.head_commit_id = NEW.id. The port's Postgres subset has no triggers at all — 61 live triggers, none translated — so the branch head would simply never advance.

The obvious fix is to do the UPDATE in application code instead, and Python's own comment says why that is a trap: 

-- Branch head is auto-advanced by the `update_branch_head_on_commit`
-- trigger ... so no manual UPDATE is required here. The previous
-- app-level compare-and-swap was buggy: it always fired a
-- false-positive HEAD_RACE error because the trigger had already set
-- head_commit_id to the new commit id by the time the CAS's
-- WHERE head_commit_id IS <old> ran.

That is a bug caused by the trigger existing. A port with no trigger can do the compare-and-swap correctly — it is the only implementation that can, because nothing has moved the column underneath it. So this is the first place the port can be better rather than merely faithful, and the first place "reproduce Python" and "reproduce Python's behaviour" come apart: reproducing the code gives a head that never advances, and reproducing the behaviour gives a CAS that Python cannot have.

It also means the cross-backend digest stops being free. Every measurement so far has compared SQLite against Postgres after a copy; this would be the first table whose contents are produced by different mechanisms on the two sides.

Guard 9 the port cannot hit, because session.rs never creates. Guards 4, 5, 6 and 8 are all filesystem guards: they compare a workspace against the database. Guards 1 and 2 are preconditions. Only 3 and 7 are about the database alone.

The dependency that is not a translation problem

Five of the nine guards exist to reconcile a filesystem against the database. The port has no concept of a checkout, by design: it reads a database and prints. Porting those guards means porting the workspace scanner, the checkout-role resolver, and the mirror-to-disk step — which is a different project, not a harder version of this one.

The mirror-to-disk step is the one that should settle it. Python writes every file set into the active checkout, and its comment records what a miss costs: the refresh classifies a staged file with no file on disk as deleted, and the next commit hard-deletes the project_files row. On 2026-09-24 a commit "announced Files: 2 and committed one". A port that writes vcs_working_state without the disk half has built exactly the state that produces that.

Recommendation: split the door

Do not port vcs commit. Port the half that is a database operation, under a name that does not promise the other half, and refuse the other half explicitly.

portrefuse
Committing already-staged rows: the seven-table write, the parent edge, the CAS on the branch head, guards 3 and 7Workspace scanning — there is no workspace
Guard 9's shape, which file set already follows: session resolved at the edge, passed in, never createdGuards 4, 5, 6, 8 — all of them compare against a tree the port does not have
Guard 2, the orphan reap, which is pure SQL--strategy and its resolution strategies, which exist to settle conflicts the port cannot detect

Concretely: templedb-rs vcs commit <proj> -m <msg> --session <id> commits what the session has staged and refuses if anything would require consulting a tree. That is not a reduced vcs commit; it is the operation publish already performs — its guard is COUNT(*) … WHERE staged_by_session_id IS NOT NULL, and it commits without scanning anything.

Which means the auto-stage question answers itself in the other direction too. file set --stage can land with this reduced commit, because then vcs_working_state has a reader and the pair is verifiable end to end by cross-read: set, stage, commit, then vcs log and vcs show — both already byte-identical — read the result back.

Two things this document does not decide

Whether the reduced command may be called vcs commit. It accepts a narrower input than Python's and refuses where Python scans. The flag-surface stage in parity-sweep.sh will report every absent flag, which is the right outcome — but a command that shares a name and refuses a workflow is the --no-fts argument again, and it should be settled before the name is used rather than after.

What vcs_file_states should hold for the 124 historical sentinel rows. The port mirrors them today and source snapshot already errors on the dangling blob where Python printed nothing and exited 0 — so the port is already more honest about them than Python. Whether a ported commit should refuse to mirror them, or carry them as the archaeology they are, is a question about what the mirror means and not about commit.
