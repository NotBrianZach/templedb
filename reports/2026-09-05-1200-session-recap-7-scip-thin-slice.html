4. writeShellApplication over buildNpmPackage

buildNpmPackage failed: scip-typescript uses yarn, not npm (no package-lock.json). Considered mkYarnPackage (correct but adds two more hashes to hunt); shipped writeShellApplication wrapping npx --yes @sourcegraph/scip-typescript@0.4.0. Trade-off documented at the top of the file: not fully hermetic (first run fetches from npm cache), but zero hash management, deterministic version pin, works today. If hermeticity matters later, migrate to mkYarnPackage — upstream source hash sha256-VKzNiazF+TtlvmXNCIEJbhsuNfnL2c8FslnVFvydXs8= is preserved in the file's header comment.

Two mid-session pivots that changed the shape

Pivot 1: system_config → templedb flake

User redirect (mid-run) "also since templedb depends on scip can we make it a templedb flake thing? as opposed to system wide?"

Cleaner ownership: templedb is the consumer, templedb packages the dependency. Anyone with templedb installed gets scip capability by default; no system_config edits required for other users. Undid the initial scip addition to configuration.nix's systemPackages and staged deletion of system_config/scip-typescript.nix.

Pivot 2: buildNpmPackage → writeShellApplication

Discovered upstream uses yarn only after the first nix-build attempt. buildNpmPackage needs package-lock.json; the yarn.lock is what actually ships. mkYarnPackage would work but adds complexity. Chose the smallest solution that unblocks today (writeShellApplication + npx) with a clear escape hatch for later hermetic packaging.

Debugging highlights

SCIP JSON uses snake_case, not camelCase

First bza/frontend ingest reported +0 symbols, 154 untracked. Diagnosis: scip print --json emits relative_path, display_name, symbol_roles. Adapter was looking for camelCase (relativePath, displayName). Fixed in the field. Next run: +12,428 symbols.

display_name is empty for every scip-typescript@0.4.0 symbol

After fixing the snake_case bug, verified that display_name is populated for 0 of 12,398 emitted symbols. Labels all come from the fallback scip_sym.rsplit('/', 1)[-1] path. So the labels look like createSupabaseServerClient(). (with the trailing SCIP descriptor suffix) instead of the cleaner createSupabaseServerClient. Cosmetic; refine in v1.1 by stripping trailing (). and .. No data-integrity impact.

FUSE default view vs. checkout diverge silently

Reflection templedb file set --verify writes to vcs_working_state and mirrors to the checkout dir. The FUSE mount's default view uses file_contents.is_current, which doesn't update on file set. Wasted a minute chasing "why is nix-build seeing my old buildNpmPackage code?" — because the FUSE view served the old current blob while the checkout had the new working blob.

Corollary for tool-driven work: read the checkout, not the FUSE mount, when validating in-session file set edits.

Session forking defeats intent tracking

templedb vcs status at end-of-session showed my edits as "Staged in other sessions" — each Bash tool subprocess forked a new session leader, so my file sets scattered across ~5 sessions. Known issue per recap 6 (added vcs session gc as mitigation). Downstream effect: I couldn't cleanly stage just my SCIP-related files via vcs add because they're owned by other sessions. Worked around by testing via dev-mode + in-memory checkout paths, deferring the git publish.
