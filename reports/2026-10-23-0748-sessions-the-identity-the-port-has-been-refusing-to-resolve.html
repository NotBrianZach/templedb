Sessions: the identity the port has been refusing to resolve

Everything substantive left in templedb-rust sits behind one question. Three of file set's seven guards, the last read-layer divergence, edit_intents provenance and vcs commit all wait on the same thing: what "the current session" means to a port that must not create one. This is the precondition document the porting order asks for before any of them. Its conclusion is that the port should resolve sessions never, accept them always, and that this is a smaller change than it sounds — but it closes one command permanently.

Why this blocks so much

The port is at fifty invocations byte-identical against Python, a write path with four of seven guards, and three sweep stages for what a byte diff cannot reach. What remains is not a backlog of translation. It is five items, and they are the same item:

Twelve tables in the live database carry a VCS session reference, and four of them are ones the port already mirrors or will need to: vcs_commits.session_id (1,414 rows), vcs_working_state.staged_by_session_id (1,930), edit_intents.session_id (1,202) and vcs_session_heads (29). A further ten are the agent tables, which are a different notion of session entirely and are out of scope here.

What Python actually does

VcsService.get_current_session() resolves through seven steps, in order, and the last one inserts a row.

#SourceBehaviour
0--session <id|name>Explicit pin. Outranks both env vars; when set, the environment is not consulted at all
1TEMPLEDB_SESSION_IDMust reference a row with ended_at IS NULL. Raises if not
2instance cacheself._current_session — per-process memoisation
3TEMPLEDB_SESSIONA declared name. Looks up (author, host, name); creates if absent
4os.getsid(0)Session-leader PID, (author, host, pid), started within 24 hours
5os.getppid()Same lookup on the parent PID — backwards compatibility with pre-SID rows
6—Creates <host>-<sid>-<short-ts>

Two of the seven write. That is the whole difficulty: a read command calling this can mutate the database, which is the one thing the port's architecture has been built to make impossible — Store has no execute, and the SQLite handle carries SQLITE_OPEN_READ_ONLY as a flag specifically so the restriction is visible in the type.

The SID choice is not incidental, and it is instructive

Step 4 keys on os.getsid(0) rather than os.getppid(), and the reason is written into the docstring: os.getppid() returns the immediate parent, which for x=$(templedb ...) is a bash-forked subshell with a fresh PID. A loop doing command substitution would fan out into one session per iteration. The session leader is inherited from the controlling terminal and is stable across $(...), pipelines and nested subshells.

And step 3 exists because even that is not enough for agents: Claude Code and similar wrappers spawn each tool call under its own SID and do not propagate environment variables, so a per-turn shell fans out anyway. TEMPLEDB_SESSION=<name> in the launcher env pins identity across those shells.

The lesson for the port: every automatic step here is a heuristic for "same human, same terminal, recently", and each one was added because the previous one fanned out. A port that reimplements the heuristics inherits a tuning problem it has no way to validate — there is no byte diff for "did these two invocations agree about which session they were in".

The recommendation

Resolve never. Accept always. The port reads TEMPLEDB_SESSION_ID and validates it against a live row; it accepts --session <id> as an explicit pin; and it does nothing else. No SID lookup, no name lookup, no creation. With no session identified, every session-scoped behaviour falls back to the published view and says so.

That is steps 0 and 1 of the seven, and only the non-writing halves of them. It is a deliberate decision to be less capable than Python at the thing Python works hardest at, and the argument is that the hard work is all heuristic:

StepPorted?Why
0 — --session <id>yesAn explicit integer naming a live row. No inference, no write
0 — --session <name>noThe name path creates when absent. Accepting a name that resolves and refusing one that does not would be a flag that works or writes depending on data
1 — TEMPLEDB_SESSION_IDyesSame: explicit, validated, read-only
2 — instance cachen/aA CLI that exits after one command has nothing to memoise
3 — TEMPLEDB_SESSIONnoCreates. And a port that read the name without creating would silently disagree with Python about which session a wrapper is in
4 — SID lookupnoHeuristic, unverifiable, and the one most likely to drift as Python tunes it
5 — PPID lookupnoExplicitly labelled backwards compatibility for rows predating the SID switch
6 — createneverA read command that inserts a row is the thing this port exists not to do

Why not resolve read-only — steps 4 and 5 without step 6

This is the obvious middle option and it should be rejected explicitly, because it looks free. Doing the SID and PPID lookups without the creation fallback means the port finds the session when one happens to exist and finds none when it does not — so the same command, in the same terminal, returns a different view depending on whether Python has run there in the last 24 hours. The behaviour would be correct, unpredictable, and impossible to test. Refusing to resolve at all is worse in capability and better in every property the port is trying to hold.

What this costs, stated plainly

The honest version of that last row: this closes --session <name> permanently, not until later. Supporting it requires creating rows, and if the port ever creates session rows then the read-only guarantee is gone and so is the argument for the whole architecture. If name support turns out to be load-bearing for how agents actually use the tool, that is an argument for revisiting this document, not for quietly adding the write.

The guard the design document already named

The write-path document lists seven guards for commit, each dated to an incident. One is specifically about sessions and it is a warning for how this gets implemented, not whether:

Session resolution outside the transaction. Session creation inserts into vcs_sessions with commit=True. Called from inside the transaction, its commit ended the caller's — so a later per-file failure rolled back the file states but could not undo the already-committed commit row. Result: a commit with zero vcs_file_states, listed in the log, breaking the parent chain. Reproduced on demand 2026-10-03.

Under this recommendation the port cannot hit that bug, because it never creates. But the shape of the fix survives and is worth keeping: resolve the session before opening the transaction, pass it in. That is the same rule the clock seam established — the instant and the identity are arguments threaded from the entry point, not ambient reads — and file set already follows it for the clock.

What already works, and what it proves

summary's handoff-inbox pane is session-scoped and has been ported since 2026-10-21. It takes the session identity as a &str argument, resolved at the CLI entry point from TEMPLEDB_SESSION_ID or (gethostname, getppid), and handoff_inbox(store, session_id) reads no environment.

That pane is byte-identical with Python's on live data. It is a small case — one query, two counts — but it is evidence for the shape: the identity threaded as a parameter, resolved once at the edge, with the query layer staying a function. The recommendation here is that pane's arrangement applied to the write path, with the edge resolution narrowed from "guess like Python" to "accept or decline".

One inconsistency to fix while doing this: that pane's fallback constructs <hostname>-<getppid>, reproducing Python's handoff identity, which is a different scheme from vcs_sessions entirely — handoff notes address a string, VCS sessions have integer ids. The two should not share a resolver, and today they nearly do.

Item 3 is the one to do first after the plumbing, and not because it is next in the porting order. It is the only session-dependent behaviour that is byte-diffable: pin TEMPLEDB_SESSION_ID on both implementations, run vcs log, compare. Every other item on the list is a write and falls back to cross-read. Doing the verifiable one first means the session plumbing is pinned against Python before anything depends on it — the same reasoning that put the clock seam behind summary rather than behind the write path.

Open questions

Two, and both are decisions rather than research.

Does an unpinned file set --stage refuse, or stage with a NULL session? The column is staged_by_session_id and the staging model assumes ownership, so a NULL-owned staged row may be a state nothing else knows how to read. Refusing is safer and narrower; staging with NULL is more useful and might corrupt a concept. This needs a look at what reads vcs_working_state before it is decided.

Should the port refuse to run at all when TEMPLEDB_SESSION (the name variable) is set? It is the agent wrapper's variable, so a port running under an agent will routinely see it — and will ignore it, meaning it silently disagrees with Python about which session it is in. Ignoring a variable that changes the answer is the failure mode rule 3 of the decisions report warns about. Erroring is loud and correct and would make the port unusable in exactly the environment it is developed in, which is an argument for a warning rather than a refusal.

What this document commits to

Nothing is implemented. The claim is the precondition the porting order asks for: the blocker is not SQL and not the seven steps, it is that two of them write and the other four are unverifiable heuristics. The port should take the two explicit steps, decline the rest, and say so in its output rather than guessing. One capability — --session <name> — closes permanently as a result, and that is the price of the read-only guarantee rather than an oversight to fix later.
