The CLI as a surface: 432 commands and who reads them

An audit of TempleDB's command-line surface, measured 2026-10-08 from templedb admin schema and the argparse registrations themselves. 432 commands, 1153 parameters, ~44k lines. The headline is not the size: it is that the interface built specifically so agents could discover the CLI described nothing — 422 of 432 commands serialised an empty help string — while a dead reference on the main deploy path made every successful deployment report failure. Both now fixed. What remains is a shape problem: 34 of those 432 names are aliases of other commands, and the surface has no mechanism that would have told anyone. Reference companion: docs/CLI_SURFACE.md.

2. Two audiences, two channels

The surface is read through two independent channels, and until today only one of them worked:

Human channelAgent channel
Mechanism--help, rendered by argparseadmin schema, JSON
Source of command helpparent's _choices_actionswas parser.description
Coverage beforecomplete10 of 432
Short aliasesshowndiscarded by design

That divergence is the report's organising fact. vcs add has always been registered add_parser('add', help='Stage files for commit') and templedb vcs --help has always rendered it. But argparse stores the help= given to add_parser() on the parent's _choices_actions list, never on the subparser object; a subparser's own .description is populated only when description= is also passed. Ten commands do that — the deploy hooks family. The other 422 serialised help: "".

An agent pointed at admin schema for capability discovery received 270 KB of JSON describing 432 commands and explaining none of them. The command's own help text says it exists "for agent/scripting use."

Fixed by carrying the parent's recorded help down the recursion. A second pass handles aliases=[…] registrations, which put both names in .choices pointing at one parser while recording a single pseudo-action under the canonical name — those 15 (ls, rm, gen) now inherit by parser identity. Empty help went 422 → 15 → 0.

3. The deploy path was reporting false failures

src/cli/help_utils.py is a stub — its header says so — and has been in every recorded commit. CommandHelp and CommandExamples define only __init__ and print. Five call sites referenced attributes that therefore never existed:

SiteReferenceReachable when
deploy.pyCommandExamples.DEPLOY_RUN--examples
deploy_ops.pyCommandExamples.DEPLOY_EXEC--examples
deploy_script.pyCommandExamples.DEPLOY_HOOKS--examples
deploy.pyRelatedCommands.AFTER_DEPLOY_RUNevery successful non-dry-run deploy run
deploy_script.pyRelatedCommands.AFTER_HOOK_REGISTERevery successful deploy hooks register

The fourth is the one that mattered. It ran after the deployment had already succeeded, inside a try whose except Exception logged Deployment failed: type object 'RelatedCommands' has no attribute 'AFTER_DEPLOY_RUN' and returned 1. So a successful deploy printed a failure message and exited non-zero, and anything gating on exit status — CI, a wrapper script, a scheduled job — saw every deployment as broken. The error text was not merely unhelpful, it was false.

Removed rather than repaired: with no example data anywhere in history, "repair" would have meant authoring content for three deploy commands, which is a writing task and not this pass's business. --examples now gets a plain argparse rejection.

4. Duplicate names: 15 are proper aliases, 19 are real duplication

Corrected. An earlier revision of this report claimed "34 redundant names" and recommended collapsing them with argparse aliases=. Both halves were wrong. 15 of those names are already proper aliases, and the remaining duplicates cannot be expressed as aliases at all. The figure came from a grep over cli.commands assignments, which cannot establish handler identity: the variable name cmd is reused in every module, so unrelated functions look shared, and id() on a bound method is meaningless because attribute access mints a fresh object each time. Re-measured by introspecting the live parser tree and grouping on (__func__, __self__). 
cli.commands entries                            420
leaf command names                              428
distinct leaf parsers                           413
handlers with >1 dispatch key                    34
  ├─ sharing ONE parser (proper argparse alias)  15   <- correct, keep
  └─ via DISTINCT parsers (duplicate surface)    19   -> 25 redundant names

The 15 are not a problem. config list/config ls, domain remove/domain rm and the rest are registered with add_parser(…, aliases=['ls']): one parser, two names. Their duplicate cli.commands keys are required for dispatch, so what looked like redundancy is the mechanism working.

The 19 are real, and almost entirely nixos — a flat hyphenated spelling beside a nested noun form: 

nixos config-get       &  nixos config get
nixos dotfiles-add     &  nixos dotfiles add
nixos add-package      &  nixos packages add
nixos system-rollback  &  nixos system rollback
nixos rebuild  &  nixos system-rebuild  &  nixos system rebuild   (3 names)

Why they cannot become aliases

The two spellings sit at different subparser depths: nixos config-get is a child of nixos, while nixos config get is a grandchild under a config group. argparse's aliases= applies only within one subparser, so there is no way to declare that these two names are one command. Collapsing them means removing a spelling — a user-facing break, not a refactor.

Nor is either spelling dead. Both appear in this repository's own documentation (nixos config-get 6 hits against nixos config get 2; nixos system-rebuild 3 against nixos system rebuild 3), and CLAUDE.md plus the operational memory use the flat form — a weak argument for flat as canonical, and the only argument available.

So this pass stops at measurement. Choosing a spelling and retiring 25 names is a product decision about an interface people have muscle memory for, and nothing in the analysis settles it.

5. Naming collisions the schema used to hide

admin schema deliberately dropped short option forms, preferring the long name. One consequence is that a consumer cannot learn -p means --project. The sharper consequence is that collisions were invisible to tooling:

FlagMeaningsSeverity
-a--all on vcs add/vcs reset; --author on vcs commitsilent wrong behaviour
-s--session, --stage, --statuscross-noun, low

-a was the dangerous one: vcs commit has no --all, so someone who learned -a from vcs add set an author string instead of getting an error. Removed, so it now fails with unrecognized arguments: -a. A deliberate compatibility break — failing loudly beats silently recording the wrong author.

admin schema now emits an aliases array (120 params gained one), so the next collision is detectable without reading argparse calls.

6. Destructive posture

MeasureCount
Commands offering --dry-run31

The raw 50-of-53 figure overstates the exposure. Most unguarded prompts are unreachable without opting in: commit.py's eleven fire only under --interactive. The risk concentrates in prompts reachable on a default invocation, and admin checkout-gc had two of them — a plain templedb admin checkout-gc from any agent tool call died with EOFError: EOF when reading a line and a traceback. Both now decline and name the flag that resolves it.

The model to copy is nixos.py:279-295, which short-circuits on --yes and catches EOFError with an actionable message. templedb commit states the same stance in its --strategy help: "no-TTY invocations auto-abort by default."

A correction this pass had to make about itself. The first draft of the companion document named nixos.py:287 as the known-bad EOF case and claimed --yes did not cover it. That came from a note written 2026-10-01 and was repeated without reading the enclosing block — which shows the opposite. The site is one of the three that already handled this correctly. Verifying the line and trusting a memory for the behaviour around it is the same error as citing documentation from recollection, and it happened twice in one session.

7. Guards added, and why they belong in a CLI report

Three guards landed earlier the same day. They are CLI-surface facts, not just library-internal ones, because each converts a silent catastrophe into a refusal with a message:

  • commit refuses when ≥50% of tracked files are missing from the given workspace (floor 10), overridable with --allow-mass-delete. The diff is taken against whatever path is handed in, and a wrong one used to commit the project away as deletions.
  • project checkout --force refuses a target that strictly encloses any registered checkout. Its stray-purge walks recursively and unlinks anything absent from the project's file list; the previous guard skipped same-slug rows, which is the common shape.
  • admin checkout-forget <path> is new, and closes a gap rather than adding a guard: no command could deregister a checkout row whose directory still existed. It refuses active rows, rows owned by a live session, and trees holding unstored content, and never touches the filesystem.

8. The discoverability class

The --session flag added earlier today fixed one instance of a general pattern: behaviour that decides whether your command does anything at all, documented nowhere in --help. Staging is session-scoped; identity was steerable only by environment variables; neither vcs add --help nor vcs commit --help mentioned sessions. No changes staged for commit in this session was unreachable from the CLI.

Load-bearing factIn --help?

The test for membership: if a user gets a surprising no-op or a silent revert, could --help alone have told them why?

Why phase 1 is worth doing before anything else

A doctor invariant asserting "no command serialises empty help" would have caught the 422-command gap the day it appeared, and would keep catching it. The same check generalises to parameters. The 115 undocumented params are the next tranche of the same defect, and they are genuine absence rather than an extraction bug — nothing can be inferred for them automatically.

10. The question this audit does not settle

Is 432 the right number? Minus aliases it is ~398 distinct operations across 42 top-level nouns, with deploy at 73 and nixos at 54. Nothing in this pass establishes whether that is an honest reflection of the problem domain — a tool that really does own version control, nix config generation, fleet deploy, secrets, domains and an agent runtime — or accumulated surface that nobody has had reason to remove.

Two observations that bear on it without resolving it. First, the duplicate names are evidence of growth by accretion rather than design: nobody adds nixos rebuild, nixos system-rebuild and nixos system rebuild deliberately. Second, the noun boundaries leak — checkout operations live under project, under admin, and as the top-level edit, which is why the gap that checkout-forget fills went unnoticed: no single noun owns the concept, so no single --help listing shows the hole.
