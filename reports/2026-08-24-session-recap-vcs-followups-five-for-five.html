The five followups

#1: Fix Migrator fresh-DB bug — pivoted to regenerate schema.sql landed

Original plan: rewrite Migrator to actually run numbered migrations after applying schema.sql on fresh installs, tolerating “already exists” errors for shapes schema.sql already had. Implemented that, hit whack-a-mole with error patterns (added no such table, duplicate column, no such column, no such view, has no column named, table renamed), then realized the truly right fix was upstream: schema.sql itself was stale. Regenerating it from the live DB made the numbered- migration re-run unnecessary, since every migration’s effects are now present in the endpoint schema.

Kept the tolerant-migrate scaffolding’s spirit as a _verify_critical_tables safety net: after fresh install, assert that seven post-schema.sql tables exist. If they don’t, RuntimeError with a pointer to “schema.sql drift.” Next time the schema goes stale, the failure is loud instead of silent.

#2: Regenerate schema.sql landed

Python script dumps sqlite_master in creation order, adds IF NOT EXISTS, excludes FTS5 shadow tables (they get auto-created by CREATE VIRTUAL TABLE). Result: 3441 lines vs the old 4177, but complete relative to migrations 075-083 — 140 tables, 217 indexes, 45 views, 45 triggers, matching the live DB exactly.

#3: Drop staged BOOLEAN — three commits and a lot of surface area landed

Bigger than expected. Grep found 17 read sites in 7 files plus 10+ write sites in 4 more. The compat mirror was keeping staged BOOLEAN in sync with staged_by_session_id IS NOT NULL, but only the service code maintained that mirror. FUSE auto-stage, GUI stage/unstage, file rm, file set —stage, and merge conflict INSERT all wrote the boolean directly without setting staged_by_session_id. That meant those rows were invisible to my Phase 1 session-scoped commit because commit queries by session_id. A latent isolation hole hiding behind the mirror.

Fixed in three commits:

  • Part 1 (4215BE16): switch every reader to staged_by_session_id IS NOT NULL; give every writer an attributed session (FUSE gets a per-host fuse-auto-<host> named session, GUI gets gui-<host>, CLI writers resolve via get_current_session()).
  • Part 2 (3D30FE3A): migration 083 drops the column. Required a view rebuild (vcs_current_files_view referenced it, so SQLite refused the drop until the view was recreated). Regenerated schema.sql post-drop.
Rule to keep When a “compat mirror” is maintained only by some writers, it’s not a compat mirror — it’s a coincidence that happens to work most of the time. The FUSE and GUI writers set the boolean without the new column, meaning their staged rows never showed up in my Phase 1 session-scoped commit path. This is exactly the subtle isolation hole the “let's drop the mirror” audit was designed to surface.

#5: vcs session prune landed

templedb vcs session prune [--older-than DAYS] [--dry-run]. Deletes ended sessions past the threshold whose staged_by_session_id rows are all cleared. Preserves sessions with lingering staged rows and lists them separately. Default 30 days. Small feature, one commit.

Caught a classic Python bug in myself: getattr(args, 'older_than', None) or 30 replaces 0 with 30 (because 0 is falsy). Fixed to a proper if days is None.

What I noticed about my process

Whack-a-mole is a signal to stop and rethink keep doing

The Migrator fix started as “tolerate this specific error,” then “tolerate these seven,” then still failed on migration 077’s partial rollback. Each layer of tolerance made the code uglier. When I stepped back and asked why is this hard, the answer was “because schema.sql is stale.” Fixing the upstream (regenerate) collapsed the whole problem. Cost: 20 minutes of chasing before pivoting. Could have been faster if I’d asked the “why is this hard” question after the second tolerance addition.

Rule to keep If a fix requires more than two special-case exceptions, the abstraction is wrong. Stop adding exceptions and re-examine the invariant.

Full-refactor felt scary, then wasn’t keep doing

When I saw 17 read sites and 10 write sites for the staged column, my first reaction was “this is genuinely too big for one session, should defer.” But I asked the user, they picked full refactor as “recommended,” and I did it in maybe 45 minutes of focused edits. The scariness was overestimation, not real complexity. The reads were all “does this row have any staging” and the writes all needed the same “attribute to a session” pattern; both were repeated 20+ times with minor variations.

Discovered latent bug during audit keep doing

The whole reason for the full refactor emerged from actually looking: FUSE/GUI/file.py writes were setting the boolean without the session_id, meaning session-scoped commit didn’t see them. That’s a functional bug in Phase 1 that was hiding behind the compat mirror — you’d never notice unless you tried to isolate two agents where one used vcs add and the other used file set --stage. Naming this in the recap so the next agent knows: Phase 1 had a real hole in it that only got closed by #3.

Bash tool spawns fresh shells — still tripping me up notice

Repeatedly this session I’d run templedb vcs add X in one Bash call and templedb vcs commit in another, and the second would report “no changes staged in this session.” Because each Bash tool call spawns a fresh shell with a different PID, so the ppid-based session reuse doesn’t apply. Every time I hit this, the workaround was to combine into one bash -c or use TEMPLEDB_SESSION_ID=<id> explicitly. Fine but worth calling out: the shell-workflow reuse from Phase 3.5 works for real users but not for my harness’s testing model.

Committed under wrong session by accident, twice didn’t

Because of the shell-variance issue above, I twice ended up with files staged in session A and trying to commit from session B. Fallback was vcs status --all to find the right session ID, then TEMPLEDB_SESSION_ID=A templedb vcs commit. This worked but wasted a minute each time. Better default for the harness: always eval $(templedb vcs session start --name X | grep export) at the top of a bash-c so all invocations inside share a session by env var. Should adopt this pattern next time.

The “0 is falsy” Python gotcha notice

days = getattr(args, 'older_than', None) or 30 is Python 101 wrong but I still wrote it. Caught it in the first smoke test (--older-than 0 silently became 30). Fixed. Only wasted 30 seconds, but the fact I still make this class of error is worth noticing.
