Mobile agentic development: the client already exists

The ask was "integrate Android into TempleDB, or at minimum let me do agentic development from my phone." Measuring what is already built changes the shape of the answer twice. First: the mobile client is mostly written — a FastAPI + HTMX GUI with twenty-six registered page modules is running right now, one of which already answers an agent's blocking question from a browser in 200 ms, and templedb ai agent fleet already prints the exact triage screen a phone wants. Three small, specific facts block it. Second, and less obvious: enumerating what full framework participation would actually buy shows that nearly all of it is offline origination rather than merge — which needs an append-only outbox, not a CRDT replica. The one application that genuinely needs replication is the one this architecture already argues against.

The two questions, separated

The request contains two asks that look adjacent and are not:

  1. Agentic development from the phone. Start, steer, unblock and review agent work on the projects, from a handset, wherever it is. The phone is a client; the work happens on a mothership.
  2. Android inside the framework. The phone becomes a participant — a machine TempleDB knows about, deploys to, syncs with, and perhaps ingests from.

Ask 1 is nearly free, because the substrate is built. Ask 2 is where the interesting speculation lives, and it splits cleanly once its applications are written down. This report measures what exists, names the three obstacles, lays out four tiers, and then spends its second half on what the top tier would be for — because a recommendation against building something is worthless without that.

The headline. The mobile client is mostly written. It is a server-rendered HTMX app — no build step, no JS framework, no app store — which is the easiest possible thing to put on a phone. The reason it is not on a phone today is three specific, small facts, not a missing component.

The three obstacles, in the order they bite

1. The GUI has no authentication, and that governs everything

There is no auth in the GUI. Not a weak scheme — none. It also exposes POST /config/set, POST /db/migrate, POST /backup/gcs and the woofs Supabase sync routes. On 127.0.0.1 that is a reasonable design: the trust boundary is "has a shell on this box", and anyone with a shell can run templedb anyway. The moment the bind address changes, that reasoning expires.

So the first decision is not "how do we make a mobile UI" but what is the authentication boundary. Three candidates, and they are not equal:

  • The tailnet is the boundary. Bind to the Tailscale interface only, leave 8420 out of the LAN firewall, and let device authorisation in the tailnet be the auth. This is the cheapest honest answer and it is genuinely defensible: the tailnet already gates SSH to this machine. The cost is that every device on the tailnet is fully privileged, so a compromised or careless peer is a compromised TempleDB. There is already one Windows peer on it.
  • Tailscale Serve with its identity headers. Serve terminates TLS and passes the authenticated tailnet identity to the app, so the GUI can check which device and user rather than merely "someone on the tailnet". Slightly more work, materially better, and it removes the certificate problem from the phone.
  • App-level auth in the GUI. A token or a session cookie. The most work, the most to get wrong, and it duplicates something the network layer already does properly. Worth doing only if the GUI ever needs to be reachable from off-tailnet, which is not the ask.

Recommendation: the tailnet boundary to start, Tailscale Serve as the first upgrade. Do not add 8420 to allowedTCPPorts — that opens it to the whole LAN, which is a different and much larger set of devices than the tailnet, and the existing firewall block already carries a comment about an edit that "said the opposite of what the let block reads like."

2. The sync layer carries no file content

If the plan were "put TempleDB on the phone", this is the wall. The eight cr-sqlite shadow tables replicate metadata: project rows, env vars, commit and branch rows, entities and relations. A phone holding a full replica of that still could not display a single line of any file, because content_blobs and file_contents are not in the set — and they are the overwhelming majority of the bytes (the Rust port measures the live database at 776 MB, with content_blobs alone at 104 MB in its Postgres mirror).

There is a second, sharper reason not to go that way, and the Rust port found it independently: 58 of the live database's 61 triggers are cr-sqlite's own, calling into an extension that has to be loaded for the schema to behave correctly. A replica is not a file you copy; it is a participant in a replication protocol with a loadable extension, a site id, and a merge semantics. Putting that on Android means an Android build of cr-sqlite and a reconciliation step (reconcile_to_main) that today only ever runs on a desktop.

And crsql_tracked_peers is empty. The replication layer has never completed an exchange with another machine. Making a phone the first peer means debugging the protocol and the mobile platform at the same time, which is the kind of coupling this codebase's own reports keep concluding against.

3. The GUI can answer an agent, but cannot start or steer one

This is the real functional gap for ask 1, and it is the smallest of the three. The agent-session pages are three GET routes. What is missing is a way to send a message into a session.

The method already exists: AgentService.queue_message(session_id, content, context=None) in src/agent/service.py, which is what the Emacs client calls. So the work is a POST /agent-sessions/{sid}/message that calls it, plus a textarea in the existing detail template. The same pattern pending_asks.py already demonstrates end to end, including the redirect-back.

Worth stating plainly because it inverts the intuition: the hard-looking part (a mobile agent console) is one route and a textarea. The easy-looking part (exposing a web app) is the one with a security decision in it.

Four tiers

Tier 0 — SSH from the phone. Today, zero code.

Termux plus the Tailscale Android client plus an SSH key. The tailnet exists, sshd is up and key-only, and tmux is already installed and configured from the TempleDB flake (config/tmux.conf, also used by templedb ai vibe start --tmux). Once there, the entire system is available, because the agentic loop is a CLI: 

templedb ai agent fleet                    # triage roster
templedb ai agent ask list                 # what is blocking
templedb ai agent ask respond <id> "..."   # unblock it
templedb ai agent resume <id>              # restart an interrupted run
templedb ai agent log                      # what it did
templedb ai vibe                           # launch Claude Code with project context
templedb ai agent notify decide <id> approve

What this buys: everything, immediately, with no new attack surface and nothing to maintain. A tmux session on the mothership survives the phone losing signal, which matters more on a handset than anywhere else.

What it costs: typing on a phone keyboard into a TUI. This is a real cost and should not be minimised — it is fine for "unblock, approve, check" and unpleasant for composing a paragraph of instructions. No mosh is installed, so a dropped connection means reconnecting and reattaching rather than resuming mid-keystroke; adding mosh to the system config and opening its UDP range would help, and is a two-line change.

Do this first regardless of what else gets built. It is the fallback for every other tier, and it is the thing that makes the phone useful this week.

Tier 1 — the existing GUI, reachable over the tailnet

Bind the GUI to the Tailscale interface instead of localhost and decide the auth boundary (above). Today templedb gui takes --port and nothing else, so this needs a --host flag or a system_config key — a small change in one place.

What this buys, with no further work, on a phone browser:

  • The pending-asks page — answering a blocked agent from the phone, which is the single highest-value mobile action in the system, because it is the one where latency is the whole cost.
  • Agent sessions, runs, and the event timeline — reading what an agent did.
  • The agent work log and session sections (findings / todos / questions).
  • Projects, code browsing, entities, graph, handoffs, deploy status, nix store, audit — twenty-six pages of read surface.

The honest caveat: those pages were laid out for a desktop. HTMX and server-rendered HTML degrade gracefully, so they will be usable rather than good on a 390 px viewport. Wide tables are the main offender. The report you are reading has <meta name="viewport"> and the GUI's _base should get the same, which is a one-line fix with an outsized effect.

Tier 2 — make it a console, not a dashboard

Three pieces of work, in value order:

  1. POST /agent-sessions/{sid}/message over the existing queue_message. This is the line between "I can watch and unblock" and "I can direct work." Highest value of anything in this report.
  2. A mobile-first roster route. templedb ai agent fleet's four buckets, rendered as cards with a tap target per session. The query behind it already exists; this is a presentation of data the CLI already assembles.
  3. Push instead of polling. The notification channel already models everything needed — agent_notifications with pending_until and decision_default — and currently delivers over SMTP. Email to a phone is already a working push channel and may be sufficient. If it is not, a web-push subscription against the same table is the natural second drain alongside notify drain, not a new mechanism.

Note what is not on this list: a native app, a React client, an API layer. The GUI is HTMX; adding a JSON API and a separate client would be building a second front end for the sake of being an app. A PWA manifest over the existing pages gets the home-screen icon and offline shell for a fraction of the cost.

Tier 3 — Android as a framework participant

This is ask 2. The first version of this report dismissed it in a paragraph, which was a bad argument: a recommendation against building something is worthless without an account of what it would do. The next section is that account, and it changes the recommendation from "no" to "yes to half of it, and the half is separable."

The mechanical cost, stated first so the applications can be weighed against it:

  • A fleet_machines row. The cheap part, and partly dishonest: the table's columns are target_host/target_user/target_port, system_type, nixos_version, system_profile, boot_id, deployment_status. They describe a machine TempleDB deploys NixOS to over SSH. A handset is none of that, so it would be a row whose every interesting column is NULL — the shape the Rust port's README calls out as worse than an absent row.
  • A cr-sqlite peer. An Android build of the extension, a site id, the reconcile step, and the distinction of being the first peer the replication layer has ever had.
  • Content access. Not in the sync set. The phone would need the git daemon (9419 is already open and exportAll) or the GUI to read any code — at which point it is a client again, which is Tier 1.

What Tier 3 would actually be for

Six applications, ordered by whether they survive contact with the cost above. The ordering is the argument.

1. A declared phone environment

The literal reading of Tier 3 and the best entry point, because it compounds with Tier 0 rather than competing with it. TempleDB already declares machine configs, dotfile mappings (POST /dotfiles/add, and home.nix already sources .config/tmux/tmux.conf from the TempleDB flake) and environment_variables scoped by (scope_type, scope_id, var_name).

nix-on-droid exists. A handset whose shell environment is declared in TempleDB and materialized on the device gets the same tmux config, the same templedb binary and the same per-project env vars as every other machine. Tier 0's real weakness is that the phone shell is hand-configured and silently drifts from everything else; this is the fix for exactly that, and it needs no replication at all — materialization is a one-way push, which is the direction the architecture already supports.

2. Offline-originated direction

The one application that genuinely wants replication's core property. No signal — subway, plane, dead zone. You queue four prompts into different sessions, mark three todos done, write a handoff note, and approve a pending decision. It all lands locally and merges on reconnect; the sessions pick up the queued messages and the pending_until clock on the decision has not expired.

A thin client does not degrade gracefully here, it simply fails: no network, no action, and the thought is gone. This is the strongest argument for the whole tier — and see the reframe below, because it turns out not to need a merge engine.

3. Voice capture into the graph

The phone's actual advantage over a laptop is not the screen; it is that it is always on you and has a microphone. Walking, a thought arrives: "the auto-stage should refuse without a session." Today that is either lost or it goes into a notes app TempleDB knows nothing about, which is its own kind of drift.

A participating phone writes it straight into handoff_notes — which summary already has an inbox pane for, and which currently holds 22 rows — or into a session's todo section via the same mechanism the agent-section MCP tools use. This is probably the highest daily-use item in this list, and it is almost entirely orthogonal to code: it is capture, not development.

4. Physical-world provenance in the entity graph

The most interesting one, and the measurement makes the case better than argument does. The graph holds 80,308 entities across 18 kinds: 

AgentSession  AstBuild  Checkout  Claim  Commit  Deployment
Derivation  EditIntent  File  Generation  InvariantCheck  Machine
MirrorLocation  Report  Session  StorePath  Symbol  ToolCall

Every one of the eighteen is a software artifact. Not one node in 80,308 is a place, a person, a moment, or anything that exists outside the machine. The graph has an elaborate account of what the code did and no account whatsoever of where you were when you decided it.

That is the gap a phone is uniquely able to fill, and the schema is already shaped for it: every entity carries source_authority and observed_at, so "the phone" is a source authority that fits without schema invention, and observations_archive (30,709 rows) already models superseded observations of a changing world. Add Place, Trip, Person, and the relations get strange and good: 

Commit --authored_at--> Place
AgentSession --ran_while--> Trip
Report --drafted_at--> Place

Then entity paths and entity trace — which already do multi-hop BFS over this graph — can answer questions nothing in the system can answer today. "Which commits did I write at the coffee shop?" "What was I doing the week the bza mojibake bug shipped?" "Show me every report drafted away from home." The query engine exists; it has no physical-world nodes to point at.

This is speculative and it is the one item here that could justify the whole tier on interest alone. It is also, notably, an ingest problem rather than a replication problem — see below.

5. The phone as a signing approval device

This one quietly answers the report's own open question. agent_notifications already models decisions with pending_until, decision_default, decision and decided_at. If the handset holds a key and signs approvals, an approval becomes attributable to a device rather than to "whoever could reach the GUI" — which is a better answer to obstacle 1 than either tailnet-as-boundary or Tailscale Serve, arrived at from a completely different direction.

The riskiest operations are the natural gate: publish, db/migrate, a NixOS deploy, anything that writes the live SQLite. The write-path design document's instinct — that a guard is only real if a refusal is distinguishable from a crash — extends cleanly to "an approval is only real if it is attributable to a device."

6. Fleet witness

Small, cheap and real. The phone is the one machine that is always on and always networked, which makes it the natural prober rather than probe target. fleet_machines.last_health_check_at and health_status exist and are NULL on five of six rows. A handset noticing that zMothership2 is down is worth more than TempleDB deploying NixOS to a handset — and it inverts the relationship the table was designed around, which is why it is interesting rather than merely useful.

Considered and dismissed

  • Opportunistic agent compute. Eight idle cores on a charger overnight. No: the work is overwhelmingly LLM round trips, so it is network-bound rather than CPU-bound, and thermal throttling on a handset makes it the worst node in the fleet for the one thing it would contribute.
  • Geofenced triggers. Arriving home starts the nightly sweep; leaving pauses autonomous runs. The scheduler exists, so this is cheap — but it is automation looking for a problem, and a misfire pauses work you wanted running.
  • NFC or QR stickers on machines. Tap zMothership3's case, the phone opens that machine's fleet page. Genuinely pleasant in a multi-machine house, genuinely trivial, and it needs Tier 1 and nothing else — a URL is a URL.
  • Multi-device authorship with real merge. Two desktops and a phone all editing content and merging. This is the one thing only full replication delivers, and it is in direct conflict with the one-writer discipline the Rust port spent four steps defending. Flag as attractive and dangerous; do not build it by accident while building something else.

The reframe: origination, not merge

Writing those six out exposes something that strengthens the earlier recommendation rather than contradicting it.

Almost all the value is offline origination, not merge. That needs an append-only outbox, not a CRDT replica.

Applications 2, 3, 5 and 6 all have the same shape: capture something on the phone, possibly while disconnected, deliver it when connected. One-way, append-only, no concurrent edits to the same row, no conflict to resolve. A local queue that drains over HTTP covers every one of them. No cr-sqlite on Android, no site id, no reconcile_to_main, no being the first peer a never-exercised replication layer has ever had.

Application 1 needs no sync whatsoever — materialization is a one-way push. Application 4 is an ingest adapter, which is the shape nine adapters in ingestion_runs already have.

So the merge engine earns its cost only for the dismissed item: concurrent editing of the same state from several devices. Which the architecture already argues against.

There is a practical obstacle that makes the outbox look better still. agent_messages and handoff_notes are not in the sync set — the eight shadow tables are config, projects, env vars, commits, branches, nixos config, entities and relations. So even a fully working CRDT phone could not queue a prompt or a handoff note today without extending that set, with all the shadow-table and reconciliation work that implies. An outbox does not care: it holds an intent and replays it against whatever API or CLI eventually accepts it, and the set it writes to is a detail of the drain rather than a property of the device.

This is the same conclusion the Rust port reached about Store and the write path, one layer out: when a general mechanism has exactly one real use and a specific mechanism covers the rest, build the specific one and say why.

Note that 3a is four separable pieces, none of which blocks another, and that the ingest adapter has no dependency on the phone being a participant in any deeper sense than "a thing that can POST".

What to refuse, and why

  • The phone is never a write authority. It is a client that asks a mothership to write, or an outbox that replays intents. This is the same boundary the Rust port defends — one writer owns the live SQLite — and a handset with intermittent connectivity is the worst possible candidate for a second one. It also means there is no local database to lose with the device.
  • Do not add 8420 to the LAN firewall. The tailnet and the LAN are different trust sets. With no auth in the GUI, LAN exposure hands POST /config/set and POST /db/migrate to anything on the network.
  • Do not build a JSON API and a native client. It duplicates a working server-rendered surface to gain an app icon that a PWA manifest provides.
  • Do not make the phone the first cr-sqlite peer. If replication is worth exercising, exercise it between two desktops first — crsql_tracked_peers is empty and the Windows peer on the tailnet already shows "no sync". Debugging a protocol and a new platform simultaneously is how both get blamed for the other's faults.
  • Do not let the outbox grow into a replica. It is append-only and one-way by design. The first feature that wants it to reconcile is the signal to stop and reread this section.

Recommended sequence

StepWorkBuys
1 Termux + Tailscale + SSH key on the handset. No code. The entire CLI loop, today. The permanent fallback.
2 <meta viewport> in gui_helpers._base. One line. Every one of the 26 GUI pages stops rendering at desktop width on the phone.
3 --host for templedb gui; bind the Tailscale interface; decide the auth boundary. Pending-asks, sessions, runs, work log, projects — read and unblock from the phone browser.
4 POST /agent-sessions/{sid}/message over the existing queue_message. Directing work, not just watching it. The actual ask.
5 Mobile-first roster route mirroring ai agent fleet's four buckets. One screen that answers "what needs me".
6 Tailscale Serve for TLS + per-device identity; PWA manifest. Real auth rather than network-perimeter auth; home-screen icon.
7 The append-only outbox (3a), starting with voice capture into handoff_notes. Offline origination. The thing a thin client cannot do at all.
8 Declared phone environment via nix-on-droid. Tier 0 stops drifting; the handset becomes a declared machine without pretending to be a deploy target.
9 Physical-world ingest adapter: Place, Trip, Person. The first entities in the graph that exist outside a computer, and the joins that follow.

Steps 1 and 2 are same-day. Step 3 is the one with a decision in it and should not be rushed past. Steps 4 and 5 are the actual feature and are small because the substrate is there. Steps 7–9 are 3a, in the order that delivers value soonest, and each is independently abandonable.

Open questions

  • Which auth boundary? Tailnet-only is cheapest and defensible; Serve-with-identity is better and not much more work; application 5 suggests a third answer that is better than both and further away. This is a decision, not a research task, and step 3 is blocked on it.
  • Is email already the push channel? agent_notifications delivers over SMTP today and a phone already receives mail with a notification. If that is good enough, web push is unnecessary and step 4's third piece disappears. Worth trying before building anything: templedb ai agent notify test.
  • Does ai agent serve need a non-stdio transport? It is stdio-only, which is why the agent protocol is reachable from Emacs and from a shell but not from a browser. The GUI reaches agent state through the database instead (agent_pending_asks, agent_events), which is why the ask-answering route works without touching the protocol. If the GUI only ever needs to queue messages and read events, the database is a sufficient transport and the protocol does not need to change — queue_message writes a row. Worth confirming before anyone designs a websocket.
  • What is the outbox's replay semantics on partial failure? The one genuinely hard question in 3a. If three queued prompts drain and the fourth is rejected, the device needs to know whether to retry, drop, or surface it — and this is the same refusal-parity problem the write path solved with exit codes. Reuse that answer rather than inventing one.
  • Does mosh earn its firewall ports? Only measurable by using Tier 0 on a real commute.
