Mobile agentic development: the client already exists

The ask was "integrate Android into TempleDB, or at minimum let me do agentic development from my phone." Measuring what is already built changes the shape of the answer: there is a FastAPI + HTMX web GUI with twenty-six pages running right now, one of which already answers an agent's blocking question from a browser in 200 ms, and templedb ai agent fleet already prints the exact triage screen a phone wants. Nothing needs to be built to see the fleet from a phone. Three things block it: the GUI binds 127.0.0.1, it has no authentication at all, and its agent-session pages are read-only. The first two are a config change and a decision; the third is one route over a method that already exists. Full Android participation in the framework — a phone as a fleet_machines row and a cr-sqlite peer — is a different and much larger project, and this argues against it.

The two questions, separated

The request contains two asks that look adjacent and are not:

  1. Agentic development from the phone. Start, steer, unblock and review agent work on the projects, from a handset, wherever it is. The phone is a client; the work happens on a mothership.
  2. Android inside the framework. The phone becomes a participant — a machine TempleDB knows about, deploys to, syncs with, and perhaps ingests from.

Ask 1 is nearly free, because the substrate is built. Ask 2 is a project on the scale of the Rust port, and most of what it would buy is already available from ask 1. The rest of this report measures what exists, names the three obstacles, and lays out four tiers with honest costs.

The headline. The mobile client is mostly written. It is a server-rendered HTMX app — no build step, no JS framework, no app store — which is the easiest possible thing to put on a phone. The reason it is not on a phone today is three specific, small facts, not a missing component.

The three obstacles, in the order they bite

1. The GUI has no authentication, and that governs everything

There is no auth in the GUI. Not a weak scheme — none. It also exposes POST /config/set, POST /db/migrate, POST /backup/gcs and the woofs Supabase sync routes. On 127.0.0.1 that is a reasonable design: the trust boundary is "has a shell on this box", and anyone with a shell can run templedb anyway. The moment the bind address changes, that reasoning expires.

So the first decision is not "how do we make a mobile UI" but what is the authentication boundary. Three candidates, and they are not equal:

  • The tailnet is the boundary. Bind to the Tailscale interface only, leave 8420 out of the LAN firewall, and let device authorisation in the tailnet be the auth. This is the cheapest honest answer and it is genuinely defensible: the tailnet already gates SSH to this machine. The cost is that every device on the tailnet is fully privileged, so a compromised or careless peer is a compromised TempleDB. There is already one Windows peer on it.
  • Tailscale Serve with its identity headers. Serve terminates TLS and passes the authenticated tailnet identity to the app, so the GUI can check which device and user rather than merely "someone on the tailnet". Slightly more work, materially better, and it removes the certificate problem from the phone.
  • App-level auth in the GUI. A token or a session cookie. The most work, the most to get wrong, and it duplicates something the network layer already does properly. Worth doing only if the GUI ever needs to be reachable from off-tailnet, which is not the ask.

Recommendation: the tailnet boundary to start, Tailscale Serve as the first upgrade. Do not add 8420 to allowedTCPPorts — that opens it to the whole LAN, which is a different and much larger set of devices than the tailnet, and the existing firewall block already carries a comment about an edit that "said the opposite of what the let block reads like."

2. The sync layer carries no file content

If the plan were "put TempleDB on the phone", this is the wall. The eight cr-sqlite shadow tables replicate metadata: project rows, env vars, commit and branch rows, entities and relations. A phone holding a full replica of that still could not display a single line of any file, because content_blobs and file_contents are not in the set — and they are the overwhelming majority of the bytes (the Rust port measures the live database at 776 MB, with content_blobs alone at 104 MB in its Postgres mirror).

There is a second, sharper reason not to go that way, and the Rust port found it independently: 58 of the live database's 61 triggers are cr-sqlite's own, calling into an extension that has to be loaded for the schema to behave correctly. A replica is not a file you copy; it is a participant in a replication protocol with a loadable extension, a site id, and a merge semantics. Putting that on Android means an Android build of cr-sqlite and a reconciliation step (reconcile_to_main) that today only ever runs on a desktop.

And crsql_tracked_peers is empty. The replication layer has never completed an exchange with another machine. Making a phone the first peer means debugging the protocol and the mobile platform at the same time, which is the kind of coupling this codebase's own reports keep concluding against.

3. The GUI can answer an agent, but cannot start or steer one

This is the real functional gap for ask 1, and it is the smallest of the three. The agent-session pages are three GET routes. What is missing is a way to send a message into a session.

The method already exists: AgentService.queue_message(session_id, content, context=None) in src/agent/service.py, which is what the Emacs client calls. So the work is a POST /agent-sessions/{sid}/message that calls it, plus a textarea in the existing detail template. The same pattern pending_asks.py already demonstrates end to end, including the redirect-back.

Worth stating plainly because it inverts the intuition: the hard-looking part (a mobile agent console) is one route and a textarea. The easy-looking part (exposing a web app) is the one with a security decision in it.

Four tiers

Tier 0 — SSH from the phone. Today, zero code.

Termux plus the Tailscale Android client plus an SSH key. The tailnet exists, sshd is up and key-only, and tmux is already installed and configured from the TempleDB flake (config/tmux.conf, also used by templedb ai vibe start --tmux). Once there, the entire system is available, because the agentic loop is a CLI: 

templedb ai agent fleet                    # triage roster
templedb ai agent ask list                 # what is blocking
templedb ai agent ask respond <id> "..."   # unblock it
templedb ai agent resume <id>              # restart an interrupted run
templedb ai agent log                      # what it did
templedb ai vibe                           # launch Claude Code with project context
templedb ai agent notify decide <id> approve

What this buys: everything, immediately, with no new attack surface and nothing to maintain. A tmux session on the mothership survives the phone losing signal, which matters more on a handset than anywhere else.

What it costs: typing on a phone keyboard into a TUI. This is a real cost and should not be minimised — it is fine for "unblock, approve, check" and unpleasant for composing a paragraph of instructions. No mosh is installed, so a dropped connection means reconnecting and reattaching rather than resuming mid-keystroke; adding mosh to the system config and opening its UDP range would help, and is a two-line change.

Do this first regardless of what else gets built. It is the fallback for every other tier, and it is the thing that makes the phone useful this week.

Tier 1 — the existing GUI, reachable over the tailnet

Bind the GUI to the Tailscale interface instead of localhost and decide the auth boundary (above). Today templedb gui takes --port and nothing else, so this needs a --host flag or a system_config key — a small change in one place.

What this buys, with no further work, on a phone browser:

  • The pending-asks page — answering a blocked agent from the phone, which is the single highest-value mobile action in the system, because it is the one where latency is the whole cost.
  • Agent sessions, runs, and the event timeline — reading what an agent did.
  • The agent work log and session sections (findings / todos / questions).
  • Projects, code browsing, entities, graph, handoffs, deploy status, nix store, audit — twenty-six pages of read surface.

The honest caveat: those pages were laid out for a desktop. HTMX and server-rendered HTML degrade gracefully, so they will be usable rather than good on a 390 px viewport. Wide tables are the main offender. The report you are reading has <meta name="viewport"> and the GUI's _base should get the same, which is a one-line fix with an outsized effect.

Tier 2 — make it a console, not a dashboard

Three pieces of work, in value order:

  1. POST /agent-sessions/{sid}/message over the existing queue_message. This is the line between "I can watch and unblock" and "I can direct work." Highest value of anything in this report.
  2. A mobile-first roster route. templedb ai agent fleet's four buckets, rendered as cards with a tap target per session. The query behind it already exists; this is a presentation of data the CLI already assembles.
  3. Push instead of polling. The notification channel already models everything needed — agent_notifications with pending_until and decision_default — and currently delivers over SMTP. Email to a phone is already a working push channel and may be sufficient. If it is not, a web-push subscription against the same table is the natural second drain alongside notify drain, not a new mechanism.

Note what is not on this list: a native app, a React client, an API layer. The GUI is HTMX; adding a JSON API and a separate client would be building a second front end for the sake of being an app. A PWA manifest over the existing pages gets the home-screen icon and offline shell for a fraction of the cost.

Tier 3 — Android as a framework participant

This is ask 2, and it is worth being concrete about what it would mean so the cost is visible:

  • A fleet_machines row. The cheap part, and partly dishonest: the table's columns are target_host/target_user/target_port, system_type, nixos_version, system_profile, boot_id, deployment_status. They describe a machine TempleDB deploys NixOS to over SSH. An Android handset is none of that. It would be a row whose every interesting column is NULL, which is the shape the Rust port's README calls out as worse than an absent row.
  • A cr-sqlite peer. Requires an Android build of the extension, a site id, and the reconcile step; and it would be the first peer the replication layer has ever had. See obstacle 2.
  • Content access. Not in the sync set. The phone would need the git daemon (port 9419 is already open and exportAll) or the GUI to read any code — at which point it is a client again, which is Tier 1.
  • Ingest from the phone. The one genuinely new capability a participating handset would add: photos, location, notes, health data as entities in the graph. This is interesting and is completely orthogonal to agentic development. It should be its own project with its own report, and it does not need a replica — an ingest adapter posting to an endpoint is the shape every other adapter already has (ingestion_runs records nine distinct adapters).

Recommendation: do not pursue Tier 3 for the stated goal. Every capability it would deliver for agentic development is delivered by Tiers 0–2 at a small fraction of the cost. Keep it on the list only as "phone as an ingest source", which is a different feature wearing the same word.

What to refuse, and why

  • The phone is never a write authority. It is a client that asks a mothership to write. This is the same boundary the Rust port defends — one writer owns the live SQLite — and a handset with intermittent connectivity is the worst possible candidate for a second one. It also means no local database to lose with the device.
  • Do not add 8420 to the LAN firewall. The tailnet and the LAN are different trust sets. With no auth in the GUI, LAN exposure hands POST /config/set and POST /db/migrate to anything on the network.
  • Do not build a JSON API and a native client. It duplicates a working server-rendered surface to gain an app icon that a PWA manifest provides.
  • Do not make the phone the first cr-sqlite peer. If replication is worth exercising, exercise it between two desktops first — crsql_tracked_peers is empty and the Windows peer on the tailnet already shows "no sync".

Recommended sequence

StepWorkBuys
1 Termux + Tailscale + SSH key on the handset. No code. The entire CLI loop, today. The permanent fallback.
2 <meta viewport> in gui_helpers._base. One line. Every one of the 26 GUI pages stops rendering at desktop width on the phone.
3 --host for templedb gui; bind the Tailscale interface; decide the auth boundary. Pending-asks, sessions, runs, work log, projects — read and unblock from the phone browser.
4 POST /agent-sessions/{sid}/message over the existing queue_message. Directing work, not just watching it. The actual ask.
5 Mobile-first roster route mirroring ai agent fleet's four buckets. One screen that answers "what needs me".
6 Tailscale Serve for TLS + per-device identity; PWA manifest. Real auth rather than network-perimeter auth; home-screen icon.

Steps 1 and 2 are same-day. Step 3 is the one with a decision in it and should not be rushed past. Steps 4 and 5 are the actual feature and are small because the substrate is there.

Open questions

  • Which auth boundary? Tailnet-only is cheapest and defensible; Serve-with-identity is better and not much more work. This is a decision, not a research task, and step 3 is blocked on it.
  • Is email already the push channel? agent_notifications delivers over SMTP today and a phone already receives mail with a notification. If that is good enough, web push is unnecessary and step 4's third piece disappears. Worth trying before building anything: templedb ai agent notify test.
  • Does ai agent serve need a non-stdio transport? It is stdio-only, which is why the agent protocol is reachable from Emacs and from a shell but not from a browser. The GUI reaches agent state through the database instead (agent_pending_asks, agent_events), which is why the ask-answering route works without touching the protocol. If the GUI only ever needs to queue messages and read events, the database is a sufficient transport and the protocol does not need to change — queue_message writes a row. Worth confirming before anyone designs a websocket.
  • Does mosh earn its firewall ports? Only measurable by using Tier 0 on a real commute.
