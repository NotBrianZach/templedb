A roster for the agent fleet

Claude Code grew a dispatch surface: agents bucketed into needs-input / working / completed, with a chat per agent. TempleDB already recorded every fact that view needs and had no view — ai agent sessions was a flat list sorted by updated_at. This is the roster that now exists, the five buckets it uses instead of three and why, the four defects switching it on exposed (one of which had been quietly eating questions for 27 days), and a dozen concrete ways the flow could go further than the thing it copies.

The shape being copied

The dispatch interface is three lists and a chat. Agents you started sit in one of three states — blocked on you, working, finished — and you move between them without thinking about processes. The value is not the chat; Temple Agent has had a better chat than a terminal pane for months. The value is that one place answers "who is waiting on me?" That question is cheap to answer per session and expensive to answer across twenty.

TempleDB had twenty. At the moment the roster was first run there were 34 sessions inside the last fortnight across six projects, and the only way to triage them was to read a table sorted by recency and open things.

The data was already there

Nothing in this change required a migration. Every signal a triage view wants was already being written by someone:

SignalWhere it already livedWritten by
Is the agent running?agent_sessions.statusservice.py on each run transition
Is it blocked on a question?agent_pending_asks (status pending)MCP templedb_ask_user
Is it blocked on an approval?agent_notifications (kind='decision', decided_at IS NULL)MCP templedb_agent_notify_email
Did it produce anything?agent_session_sections — findings / todos / open questionsthe agent, mid-run
Why did it stop?agent_runs.status, error_textservice.py
Is it actually alive?agent_events.created_at for the newest runevery streamed event
What has it cost?agent_work_log.cost_usdrun completion

So the work was classification, not collection — and classification is where a view like this either tells the truth or flatters you.

Five buckets, not three

Three buckets do not survive contact with this data. Two extra states are load-bearing:

BucketRuleWhy it is its own bucket
needs_input a live ask, or an undecided decision the only bucket where the agent is stopped and the clock is running
working status='running', with a stalled flag when the newest event is >180s old status='running' is a claim, not an observation — see below
attention failed, cancelled, interrupted an interrupted run is resumable; filing it under "completed" loses the work silently
done waiting / completed "the agent finished its turn" and "it is your move" are the same row
idle done older than 2 days, or created with no messages without it, done becomes an archive and stops being a to-do list

Why working needs a heartbeat

A session's status is set to running when a run starts and rewritten when it ends. If the ending never happens — the Emacs buffer was killed, stop-stale reaped the serve process, claude died without a terminal event — the row says running forever. Nothing in the system ever corrects it. A naive three-bucket view would show phantom work indefinitely and, worse, show it in the bucket you are least likely to interrogate.

The honest signal is MAX(agent_events.created_at) for the newest run. updated_at will not do: it only moves on status transitions, so it looks frozen for the entire duration of a legitimate twenty-minute run. The roster therefore keeps stalled sessions in working — they are still claimed as work — but marks them ⚠ stalled with the age of the silence.

What switching it on exposed

1. Sixteen questions nobody could ever answer

First run of the bucketed query put six sessions in NEEDS INPUT, aged six to twelve days. That looked like a damning backlog until the ask rows were read directly: 

ask_id        session  created_at           age
d1ee40209647    316     2026-10-07 18:06:46   7.8d
af58010a6f15    315     2026-10-07 18:06:10   7.8d
880cb9da2d0c    307     2026-10-04 16:53:33  10.8d
...
dc5480bf4271    282     2026-09-08 ...       36.0d     (16 rows)

templedb_ask_user inserts a row, then polls it for 600 seconds and returns an error to Claude if no answer arrives. Nothing marks the row afterwards. So a pending ask older than ten minutes has no reader left: the handler gave up, the provider subprocess is gone, and an answer written into that row goes nowhere. Sixteen such rows had accumulated since 8 September, every one of them counted as outstanding work by anything that trusted status='pending'.

A needs-input queue is only as good as its liveness check. The fix is a split: live_asks (inside the deadline, blocking, actionable) and dead_asks (annotation only — "the agent asked and carried on without you"). After the split, NEEDS INPUT was correctly empty and the six sessions moved to their honest buckets with a note. There is now an ai agent ask expire sweeper so the rows stop being counted forever, and ask respond refuses an expired ask unless forced, rather than silently writing into the void.

2. SESSION_COMPLETED is defined and never written

events.py declares seven session statuses and validates against the set. service.py writes five. completed and created-after-first-message are dead vocabulary: a successful run lands in waiting, which means "no run in flight" and nothing about whether the task is finished. The roster's done bucket is therefore inferred rather than asserted — see idea 5.

3. close_session does not close the session

AgentService.close_session pops in-memory provider state and never touches the DB row. The Emacs client papered over this by shelling out to sqlite3 with a hand-written UPDATE agent_sessions SET status='interrupted' — a raw write from the editor into the one table that is supposed to have a single writer. The roster preserves that behaviour (it is load-bearing for killing a session with no live buffer) but it should be a protocol method.

4. One failure mode is 40% of the attention bucket

Of 15 sessions in attention, six failed with idle_timeout; open_tools=['toolu_…'] — the same provider fault, across three projects, over four days. Nine more were interrupted. A per-session view shows you one of these at a time and it reads as bad luck; the roster shows all fifteen at once and it reads as a bug report. (That column also had to learn to truncate: the raw error pushes everything else off the line, and the tool id in it is noise.)

Asks are answerable from anywhere — the useful accident

The MCP bridge round-trips through the database because it has to: the tool handler runs in the MCP server process, a grandchild of the serve process, with no access to the event callback. templedb_ask_user writes a row and polls that row for an answer.

Which means the answer only has to land in the table. It does not have to travel back through the session that asked. Any process — the roster, the CLI, a cron job, a phone over SSH — can unblock a waiting agent by writing one row. That is what makes a single cross-session inbox possible at all, and it is a property of the design rather than something that had to be built. The 600s deadline is the only constraint, and it is the thing worth surfacing in the UI (idea 4).

What shipped

CLI

templedb ai agent fleet [--project SLUG] [--bucket B] [--recent-days N]
                        [--stale-seconds N] [--idle-days N] [--json]
templedb ai agent ask list [--session ID] [--questions-only] [--live]
templedb ai agent ask respond <ask-id-or-prefix> --answer TEXT [--force]
templedb ai agent ask expire [--dry-run]

Bucket rules live in store.classify_fleet_row, which is pure — no DB access — so the rules are unit-testable without fixtures and the CLI, the Emacs buffer and (next) the GUI cannot drift into three different opinions about what "needs input" means. 33 tests cover the classifier, the query and the CLI responder; the agent suite is 121 passing.

Emacs

M-x templedb-agent-roster (and SPC a T A l, which used to show the flat list — templedb-agent-list is now an alias). The roster is a reader: it shells out to ai agent fleet --json and needs no ai agent serve process of its own. Only the actions that talk to a session spawn or reuse one.

KeyAction
RETopen the session in its own buffer
creply without leaving the roster — reuses a live buffer, else opens one; message.queue if the agent is still working, so this doubles as mid-run guidance
aanswer a live question inline (options offered via completing-read)
ddispatch: pick a project, state a task, it lands in WORKING — with its own vcs session and edit workspace (idea 1); C-u d to opt out
r / k / Kresume · kill · reap orphaned serve processes
Xexpire undeliverable asks
P / / / TABfilter by project · by substring · fold a bucket
g / Grefresh · toggle the 5s auto-refresh

Two details that matter more than they look. The refresh timer does nothing unless the buffer is in a window, so a buried roster is free, and it skips any tick with an open minibuffer — otherwise a re-render moves point out from under your own completing-read. And point is restored by session id, not by line number: rows crossing between buckets while you watch is the entire point of the view.

The roster calls the installed templedb. Until the next publish run + nixos system-switch, the fleet subcommand does not exist in the deployed binary and the buffer will say so rather than appearing empty. Run Emacs with TEMPLEDB_DEV_MODE=1 and a pinned TEMPLEDB_DEV_SRC to use it before the rebuild.

Ideas: where this flow should go next

The copied interface is a triage surface. Everything below treats that as the floor rather than the ceiling, roughly in order of payoff per unit of work.

1. Dispatch provisions isolation, not just a session shipped

Dispatch is the one genuinely new capability, and it is also the one that breaks things. Two agents dispatched onto the same project would share an edit workspace, and TempleDB's documented hazards are nearly all collision hazards: unpinned sessions adopt whatever edit tree is newest, a materialise elsewhere can move it mid-run, file set reverts a whole file to a stale copy.

So d now does what a careful human does: vcs session start --name agent-<slug>-<stamp>, export it, then templedb edit. The order is not interchangeable and this is the one place the sequence is enforced in code rather than in prose — the function that stamps the checkouts row deliberately never creates a session, so an edit that runs first yields session_id IS NULL: a tree checkout-gc cannot clean and that makes checkout_matches_db go red. Verified by provisioning one and reading the row back: session_id set, retired cleanly by vcs session end.

Two details carry the isolation the rest of the way. The session id is exported into the serve process, because the agent's own Bash calls are its grandchildren and each gets a fresh shell with a fresh session-leader PID — without an inherited id, vcs add in one call and vcs commit in the next stage into different sessions. And the workspace is passed as the context cwd, which _resolve_cwd honours ahead of the project's repo path, so a dispatched agent stands in its own tree rather than in the shared checkout it is told not to edit. C-u d opts out.

2. Show what each agent touched, not just whether it stopped

agent_work_log already stores files_modified, commands_run and tools_used per run. The real triage question for a done row is not "is it finished" but "what did it change, and do I believe it". A files_modified count in the row (expanding on TAB) turns the roster from a status list into a review queue — and a row that modified 30 files is a different object from one that modified none.

3. Make needs-input push, with escalation fixes a real loss

The 600-second deadline is the whole ballgame and nothing surfaces it. If you are not looking at the right buffer when an ask lands, the agent waits ten minutes and then proceeds on an assumption — which is exactly what happened sixteen times. The roster helps only if it is on screen.

The pieces for a real escalation chain already exist: agent_pending_asks for the ask, agent_notifications with pending_until / decision_default for the timeout semantics, and ai agent notify drain for email. Wire them: ask lands → mode-line alert and desktop notification immediately → at T+5min email it → at T+10min record the agent's declared default and say so in the transcript. A timeout then becomes a decision with an audit trail instead of a silent assumption.

4. Put the deadline in the UI

Live asks should show time remaining — #316 · 4m left — and NEEDS INPUT should sort by it, not by recency. It is the only queue in the system with a hard expiry, and currently the view that exists to drain it does not show the clock.

5. Let the agent assert "done" instead of inferring it

waiting conflates "task complete" with "turn over, awaiting instructions". SESSION_COMPLETED already exists in the vocabulary, validated and unwritten. Give the agent a way to claim it — an MCP templedb_agent_done taking a one-line outcome, or simply treat the existing suggest_next_prompts call as the signal — and done becomes agent-asserted with a summary, while turn-over-but-unfinished gets its own bucket. The roster would then be able to show what finished, not just that something stopped.

6. Bulk actions, because the buckets arrive full

Day one: 15 in attention, 13 in idle, 16 expired asks. One-key-per-row does not drain that. Mark region → resume all; "resume all interrupted in this project"; "archive everything idle >7d". Grouping identical failure reasons would also have made the idle_timeout cluster visible as one item instead of six — and a single "retry all six" is the action you actually want.

7. Make the fleet cooperative via handoffs

templedb handoff already does cross-session messaging with read/ack state, and the roster is the first place where you can see two sessions that should be talking. A roster action "forward this finding to that session" (or "broadcast to every session on this project") turns N parallel monologues into something that shares work. The agent that just discovered the WAL was pinned by its own session should be able to tell the other five.

8. A fleet budget line

cost_usd is recorded per run and summed per session but shown nowhere. Dispatch makes it trivial to have six agents running; the roster header should carry today's fleet spend and the cost of the session at point. Cheap to add, and it is the number that makes "dispatch another one" an informed choice.

9. One classifier, three surfaces

src/gui_pages/agent_sessions.py renders the same data in the web GUI with its own opinions about what matters. It should call store.fleet(). The whole reason the bucket rules are a pure function is so that the CLI, Emacs and the GUI cannot disagree about whether a session needs you — three independently-drifting definitions of "needs input" would be worse than none.

10. A fleet counter in the global mode line

The per-session modeline badge [F:7 T:3 Q:1] is the quietest good idea in the existing client: state without unfolding anything. The fleet equivalent — [!2 W1 A15], globally — means you never need the roster buffer open to know whether anything is blocked on you. Pair it with templedb-agent-answer-next: a minibuffer walk through every live ask across all sessions, like n in a mail reader, with no buffer at all.

11. Stop trusting status; reconcile it consistency

The heartbeat flag is a read-time patch over a write-time problem. There is prior art for the honest fix in this codebase: doctor for passive invariants, reconcile for active probes. A doctor agents check — "no session claims running with no live serve process", "no pending ask past its deadline", "no session has status='running' with a terminal latest run" — would turn three of the four defects in this report into a red line rather than something a new view happens to notice.

12. Bound the roster, or say that you did

It defaults to 14 days and 200 rows. Those are reasonable and they are also invisible: a roster showing nothing because everything is older than the window looks identical to a quiet fleet. The header should state the window, and say how many rows fell outside it.

The one thing to carry forward from the exercise: the view was easy and the classification was not. Three of the four defects above are cases where a column records an intention (status='running', status='pending') that no one is obliged to retract, and a dashboard that reads such a column literally will report work that nobody is doing and queue questions that nobody can answer. Every bucket rule here is really a liveness check wearing a label.
