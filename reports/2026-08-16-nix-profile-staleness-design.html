Nix-profile staleness: how to stop being surprised by which templedb ran

Two consecutive session recaps flagged the same pattern: I edit templedb source, test it via templedb ..., see stale behavior, spend 10 minutes tracing before realizing the running binary is from the last time I built the nix profile — not from what I just wrote to the DB. This report explores the design space for fixing that: nine options across three axes (awareness / freshness / packaging), a recommended phased path, and the smaller nuances that decided it.

The failure mode, precisely

What breaks isn't "I forgot to rebuild after a change." That framing implies a discipline problem. The actual break happens inside a loop: 

1.  Edit src/cli/commands/xxx.py via `templedb file set`
2.  Refresh the checkout so the DB and disk match
3.  Run `templedb xxx --help` to verify the flag lands
4.  Flag not there. Assume typo. Reread source.
5.  Source is correct. Assume caching. Clear __pycache__.
6.  Still not there. Trace. Discover /home/zach/.nix-profile/bin/templedb
    predates the edit.
7.  Realize: `-m cli` under a frozen PYTHONPATH ignores everything
    in the checkout.

Steps 4–6 are the wasted time. The user's problem isn't that the code didn't rebuild — it's that they got no signal that they were about to fail. Any good fix has to attack step 3 or 4: either make the running code fresh, or make the staleness visible immediately.

Two axes, not one There are actually two possible sources of staleness in play, and confusing them leads to bad fixes:
  1. Package staleness — the nix-profile-installed templedb is older than what's in the DB.
  2. Checkout staleness — the materialized checkout at ~/.config/templedb/checkouts/templedb/src is older than the DB.
Fixes that route around package staleness by preferring the checkout still fail if the checkout itself is stale. Any awareness mechanism should watch both.

The design space

Nine options, grouped by what they attack:

# Option Attacks Effort Behavior change
0 Discipline (do nothing) nothing 0 LOC no
1 Startup staleness banner awareness ~40 LOC warning only
2 Env-var checkout-priority (TEMPLEDB_DEV_MODE) freshness ~30 LOC + PYTHONPATH tweak opt-in only
3 Per-invocation flag (templedb --dev …) freshness ~50 LOC opt-in only
4 Two-tier CLI (templedb + templedb-dev) freshness ~100 LOC + nix package change additive
5 direnv .envrc in the repo freshness ~10 LOC + direnv zero (per-shell)
6 Auto-rebuild on staleness freshness ~150 LOC invasive
7 Systemd watcher rebuilds on HEAD change freshness ~200 LOC + systemd unit invasive
8 Launcher-as-entrypoint (nix package uses templedb_launcher.py) freshness ~50 LOC + nix package change changes semantics

Deeper on each

0. Discipline skip

The only option that requires no engineering. It's also the one that provably doesn't work — this pattern showed up in two consecutive session recaps despite each recap flagging it as important to remember. If discipline worked, we wouldn't be having this conversation. Ruling it out isn't laziness; it's honesty about how the failure actually manifests.

1. Startup staleness banner phase 1

On each templedb invocation, before dispatching: 

# In cli/__init__.py:main(), before command dispatch
if os.environ.get("TEMPLEDB_DEV_MODE"):
    banner = _check_staleness()
    if banner: print(banner, file=sys.stderr)

def _check_staleness():
    """Return a one-line warning if package or checkout is behind DB HEAD."""
    installed_ver = _installed_package_version()   # from setup.py or a stamp file
    db_head = _db_head_commit("templedb")           # SELECT head_commit_id ...
    if installed_ver != db_head:
        n = _commits_between(installed_ver, db_head)
        return f"⚠  templedb pkg is {n} commit(s) behind DB HEAD " \
               f"(run `templedb build && nix profile upgrade templedb`)"
    return None
  • Where — cli/__init__.py's main(), before argparse. Runs on every invocation regardless of subcommand.
  • What to check — package version (stamp file baked in at nix build time), and checkout HEAD if the checkout is referenced. Both axes.
  • When to suppress — --json, --quiet, or when TEMPLEDB_DEV_MODE is unset. Opt-in avoids nagging users who don't develop templedb itself.
  • Cost — one SQLite query (~1ms), one file stat. Negligible per invocation.
Why start here Doesn't fix the problem, but eliminates the 10-minute diagnosis step. That was the actual pain. And it composes with every other option below — even with launcher-as-entrypoint (option 8), the banner still helps by flagging checkout staleness.

2. Env-var checkout-priority phase 1

When TEMPLEDB_DEV_MODE=1, prepend the checkout src to sys.path so newer code wins. Implementation is subtle because it has to happen before any from cli.* import — once a module is imported, changing sys.path doesn't unload it.

Cleanest path: modify the wrapper (or the very first line of cli/__init__.py) to check the env var and manipulate sys.path or PYTHONPATH before further imports: 

# cli/__init__.py — must be the first executable statement
import os, sys
from pathlib import Path
if os.environ.get("TEMPLEDB_DEV_MODE"):
    checkout = Path.home() / ".config/templedb/checkouts/templedb/src"
    if checkout.exists() and str(checkout) not in sys.path:
        sys.path.insert(0, str(checkout))
        # Wipe any already-cached cli.* submodules so re-imports come from checkout
        for mod in list(sys.modules):
            if mod == "cli" or mod.startswith("cli."):
                del sys.modules[mod]

Subtle bit: because we're modifying sys.path inside cli/__init__.py, the containing module (cli) is already loaded from the profile package. The wipe-and-reimport dance handles that. Alternative: set PYTHONPATH in your shell rc when TEMPLEDB_DEV_MODE=1, and Python does the priority ordering naturally at import time — no re-import trickery needed.

3. Per-invocation flag optional

templedb --dev ai vibe start --tmux. Same mechanism as option 2 but explicit per call. Advantages: no hidden state across invocations; scripts can pin behavior. Disadvantages: verbose, and if you forget the flag you're back to the staleness problem — so it doesn't reduce the awareness gap, just gives you a lever to pull once you know you need it. Complements option 1 (banner tells you to add --dev).

4. Two-tier CLI later

Ship templedb (frozen, reproducible) and templedb-dev (checkout-priority) as separate binaries in the nix package. Users pick per invocation. Cleanest UX in one respect — behavior is fully determined by the binary name — but doubles the home-manager surface, and users who forget which they invoked have the same problem in a different clothes.

Basically option 2 with visibility bought via binary duplication. Worth considering only if the env-var approach turns out to be confusing in practice.

5. direnv .envrc nice add-on

A .envrc at the repo root (well, wherever your templedb checkout lives — for you it's likely ~/templeDB) that activates dev mode when you cd in: 

# .envrc
export TEMPLEDB_DEV_MODE=1

Requires direnv installed and hooked into your shell (it is, or can be — one home-manager line). Composes perfectly with option 2: the env var mechanism is already there, direnv just automates when it's set. Great "I don't want to think about it" layer for people who work on templedb in a specific directory.

6 & 7. Auto-rebuild / systemd watcher skip

Both fully automate the rebuild step, at real UX cost. A nix rebuild takes 30 seconds to several minutes; running one mid-CLI-invocation is intolerable. A background watcher hides the rebuild from you but adds race conditions (nix-profile mid-upgrade while another templedb is running) and failure modes (rebuild fails silently, you don't notice). Overkill for a solo-dev machine. Would revisit if the fleet grows and multiple humans are pushing templedb changes.

8. Launcher-as-entrypoint phase 2

The nix package already ships a Python program that does exactly what we want: templedb_launcher.py. It:

  1. Checks if ~/.config/templedb/checkouts/templedb/src exists.
  2. If so, prepends it to sys.path — checkout wins.
  3. Then imports cli and dispatches.

Right now that launcher only runs when you invoke /home/zach/templeDB/templedb (the local dev wrapper). The nix-profile-installed templedb uses python3 -m cli directly, bypassing the launcher entirely.

The fix: bundle a copy of templedb_launcher.py inside the nix package and change the wrapper to invoke it. 

# Current nix wrapper (bin/templedb):
exec python3 -m cli "$@"

# Proposed:
exec python3 /nix/store/xxx/lib/python3.13/site-packages/_launcher.py "$@"

With this change, the checkout automatically wins whenever it exists — no env var required, no per-invocation flag, no discipline. Everyone with a checkout gets fresh code by default; everyone without a checkout still gets the frozen nix package. The launcher's fallback logic handles both cases without branching from the user's side.

The semantics shift Today: templedb is reproducible; running it on any machine with the same nix generation gives the same behavior. After option 8: templedb is checkout-dependent; two machines with the same nix generation give different behavior if one has a stale checkout and the other doesn't. This is a real trade-off.

Mitigation: gate the checkout-preference on TEMPLEDB_DEV_MODE=1 even in the launcher, so reproducibility is the default and dev mode is opt-in. That collapses option 8 into "option 2, but bundled with the package instead of requiring per-user sys.path setup." Still an improvement because the wire-up work is done once at package time, not per user.

Alternatively, keep option 8 unconditional (checkout always wins if present) and rely on the banner (option 1) to remind you when the checkout is stale. Two-check awareness, single-source freshness.

What actually solves the pattern

The failure was step 4 of the loop above — assuming a typo when the real cause was staleness. Every option below can be evaluated by how well it attacks that exact moment:

OptionWhat happens at step 4?
0 DisciplineSame loop.
1 Banner Banner is already visible from step 3. You read it, run the rebuild, done. 30-second recovery instead of 10-minute.
2 Env-var If dev mode was set, step 4 never happens — checkout was preferred at step 3.
3 Per-invocation flag Only helps if you remembered to pass --dev at step 3. If you forgot, back to the same loop.
4 Two-tier Only helps if you invoked templedb-dev at step 3. Otherwise same loop.
5 direnv If you're in the repo directory, dev mode is already on. Step 4 never happens.
6/7 Auto-rebuild Prevents step 4 but at the cost of an unpredictable latency at step 3.
8 Launcher-as-entrypoint Checkout wins by default; step 4 never happens on any machine with a checkout.

Recommendation: a three-phase path

Phase 1 — cheap and immediate Ship option 1 (banner) and option 2 (env-var checkout-priority) in the same commit. Roughly 70 LOC total, no packaging changes. Behavior:

• Default: unchanged. templedb uses the frozen nix package, prints nothing extra.
• With TEMPLEDB_DEV_MODE=1: checkout is preferred; a warning prints to stderr if the checkout is behind DB HEAD.
• With TEMPLEDB_DEV_MODE=1 and no checkout: banner warns that dev mode is on but no checkout exists.
Phase 2 — after Phase 1 has been used for a couple weeks Add option 8 (launcher-as-entrypoint) — bundle templedb_launcher.py in the nix package and switch the wrapper to invoke it. Keep the TEMPLEDB_DEV_MODE gate so reproducibility remains the default. This collapses phase 1's env-var setup into "just works," and the banner still watches for checkout staleness. Requires touching flake.nix in templedb; scoped to the packaging derivation, no runtime code changes.
Phase 3 — nice-to-have, low cost Drop an option 5 (direnv .envrc) in the templedb repo root. Anyone with direnv gets dev-mode auto-activation when they cd in. Optional; pure convenience layer over phase 1/2.

Non-goals

  • Automatic rebuilds. Options 6 and 7 both hide the rebuild cost from you at real UX cost. Don't do this. The banner tells you when to rebuild; humans decide when to pay the latency.
  • Making the frozen package behavior go away. Nix's reproducibility guarantee is why the profile-installed templedb is trustable in the first place. Anything that breaks reproducibility for non-dev users would be net negative.
  • Solving this on other people's machines. The pattern hits me because I develop templedb on the machine that runs it. Users who only consume templedb (fresh install, no checkout) will never see the staleness problem, and the phase 1/2 changes are silent for them.

Implementation notes to future-me

Where to get the "installed package version"

For the banner to compare "installed" vs "HEAD," it needs to know its own version. Options:

  • Nix package stamp file — write a _version.py at build time containing the templedb git revision the package was built from. Read it in the banner check. Clean; requires modifying flake.nix.
  • File mtime — compare datetime.fromtimestamp(Path(sys.modules['cli'].__file__).stat().st_mtime) against the newest vcs_commits.commit_timestamp. Approximate but requires no packaging change.
  • Nix store hash — walk Path(sys.executable).parent.parent to get the store path, diff against the current profile generation's templedb store path. Fragile.

Recommend the stamp file for phase 1 (small addition to flake.nix), or the mtime approach if we want to ship without touching the packaging.

Where to put the sys.path manipulation

The env-var check needs to run before any cli.commands.* import happens. The absolute earliest place is the top of cli/__init__.py. Second-earliest is a sitecustomize.py in the nix-installed site-packages — runs before any user code but harder to maintain because it's a package-level concern hidden in a Python startup hook.

Path of least surprise: top of cli/__init__.py, before the from cli.commands import ... line. If the env var is set, wipe already-loaded cli.* from sys.modules and re-import. Ten lines.

Banner throttling

Even at ~1ms per invocation, printing the banner every time is noisy in scripts. Cheap throttle: cache the last-seen "no staleness" state to ~/.cache/templedb/staleness_ok with a 5-minute mtime; if fresh, skip the check entirely. On staleness, always print. Costs one stat per invocation.

What this means for the next few days

If phase 1 ships (roughly one focused session), the exact loop that showed up in the last two recaps stops showing up. That's the specific followup this report is proposing to close, not to add. If phase 2 ships (another session, with a packaging change and a nix rebuild), templedb becomes correctly reactive to the checkout without any env-var setup — a step toward "the CLI just works" as a baseline.

If neither ships and a third recap flags the same pattern, that's a signal the problem isn't cost-of-implementation, it's priority. In which case the honest move is to either commit to fixing it or stop pretending I care by mentioning it in every recap.

Nine options, three phases, one recommendation. Banner + env-var first (cheap, no packaging change), launcher-as-entrypoint second (real fix, small packaging change). Everything above phase 2 is diminishing returns or actively worse UX. If phase 1 doesn't ship by the third recap that flags this pattern, the problem is priority, not design.
