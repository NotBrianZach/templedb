Why the sweep-preservation fix needed two commits

git check-ignore semantics

git check-ignore by default treats tracked files as "not subject to exclude rules" — so a file added with git add -f (which is how .authinfo.gpg lands in the tree) returns exit 1 (not ignored) even though .gitignore would match it. That was masking my whole preservation mechanism: sweep called check-ignore, got no matches, deleted the file.

--no-index evaluates .gitignore against filesystem paths without consulting the index, so tracked-and- gitignored files come back as ignored. Applied in system_service.py. In hindsight I should have looked at check-ignore's tracked-file semantics before trusting the "gitignored → preserve" branch in the sweep code — that would have saved a rebuild cycle.

The one that got away: bza better-sqlite3

bza's default.nix uses buildNpmPackage, which after fetching npm deps runs npm rebuild to compile any native modules against the nix-provided nodejs. bza depends on better-sqlite3, which ships its own binding.gyp. That gyp file targets a nodejs version where v8::ObjectTemplate::SetAccessor had a signature including v8::AccessControl; current nodejs (nodejs_22 in the build graph) has dropped that parameter. The compile fails: 

note: candidate: 'void v8::ObjectTemplate::SetAccessor(
    v8::Local<v8::String>, v8::AccessorGetterCallback,
    v8::AccessorSetterCallback, v8::Local<v8::Value>,
    v8::PropertyAttribute, ...)'
note: no known conversion for argument 5 from
    'v8::AccessControl' to 'v8::PropertyAttribute'

Two ways forward, both out-of-scope for this session:

  • Bump better-sqlite3 in bza's package-lock.json to a version whose bindings match current nodejs.
  • Pin bza's build to nodejs_20 explicitly (bza's default.nix already has nodejs = pkgs.nodejs_20 for buildNpmPackage, but the transitive node-gyp ended up picking nodejs_22-source headers from the templedb build graph — that mismatch is what the error is complaining about).

Filed as task #21. Meanwhile bza stays dropped from home.packages; the ~/.local/bin/bza wrapper (which nix-shells its own deps at runtime) continues to work.

Metacognition

Two dev-mode-vs-installed-binary gotchas cost time. Both #17 and #18 needed multiple attempts before the fix was in the right place at the right time:

  1. Edited in edit-workspace, ran command, wondered why nothing changed — because dev-mode reads from CHECKOUT, not workspace, so the fix has to publish through before the tools see it.
  2. Published the fix, then ran a subcommand — but the subcommand is invoked via the installed nix templedb, which was BUILT pre-fix, so TEMPLEDB_DEV_MODE=1 is required to pick up the checkout version until the next NixOS rebuild bakes it in.

A mnemonic for future me: every templedb-source fix has three visibility gates (edit-workspace → checkout via publish → nix package via NixOS switch), and the reproduction command has to be routed through whichever gate you're testing.

What went well: testing #17 by soft-deleting a real file (reports/CLAUDE.md) proved the behavior end-to-end, and having it archived via vcs_file_states meant the overwrite was recoverable. The debug loop for #18 kept getting shorter each iteration because the --no-index mnemonic came from reading the man page carefully instead of guessing.

What I'd do differently: for #19, I should have tried actually building bza standalone (nix build .#pkgs.bza from an eval expression, or a targeted nix build against the overlay) instead of running the full nixos-rebuild switch as the probe. Each rebuild took 2-3 minutes and I did 6+ of them across recaps 11 and 12. A tighter probe would have surfaced the v8 issue in 30 seconds.
