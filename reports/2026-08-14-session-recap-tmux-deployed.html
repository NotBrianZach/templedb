What I noticed about my process

Proactive NixOS-gotcha fix keep doing

User flagged "there is an error with trying to use /bin/sh it should use nix friendly bash path" mid-session. I added set -g default-command "$SHELL" to the tmux config immediately, before it could bite in production. This is the pattern I want to keep: when a user's report matches a known-shape NixOS gotcha (missing /bin/sh, hard-coded interpreter paths, $PATH assumptions), fix it in the config rather than triage the specific report. The fix is right regardless of what exact error they saw.

The nix-profile vs. checkout split bit me again recurring pattern

Same pattern as the previous recap. I edited src/cli/commands/ai.py, ran templedb ai vibe start --help to confirm the new flag showed up, and it didn't. Ten minutes of tracing revealed the running templedb binary was from ~/.nix-profile/bin/templedb (built Aug 12), and my edits landed in the checkout but not in the profile-installed package. To reach the profile-installed binary, my changes needed publish run + nix flake update + nixos-rebuild.

This is now a two-recap pattern Both this session and the last hit the same "why isn't my code running" moment. The recipe: edit → refresh checkout → expect it to work → be surprised → trace → discover the binary you're invoking isn't the one that reads the checkout. Two options for actually solving it:

(a) Make the profile-installed templedb read the checkout at runtime — replicate templedb_launcher.py's sys.path-prepend inside the nix-profile wrapper. Trades reproducibility for developer ergonomics.

(b) A conspicuous status line — templedb prints a one-line stderr banner when the running package hash differs from HEAD-of-templedb, e.g. "⚠ running Aug 12 build; DB has 3 newer templedb commits — templedb build; nix profile upgrade to refresh". Doesn't fix the split but stops me tracing.

Discovering the update-input bug during real work paid off keep doing

templedb nixos update-input system_config templedb failed with AttributeError: 'SystemService' object has no attribute 'update_flake_input'. I could have ignored the CLI, run nix flake update manually, and moved on. Instead I did both — worked around it to unblock the deploy, then implemented the missing method (commit CC7C691E) so the next person doesn't hit the same wall. The fix took ~15 minutes; the reward is the CLI's advertised behavior actually working.

Rule to keep When an advertised CLI feature crashes with an AttributeError or NotImplementedError, that's a small, well-scoped fix that's easy to defer forever. Fix it in the session, even if it wasn't the ask. The cost of context-switching now is much lower than reconstructing the context later.

Dry-run before real rebuild was worth it keep doing

User picked "dry-run first" for the rebuild step. It succeeded, so the real rebuild had no surprises — but if the dry-run had shown a stray derivation failure or a missing input, we'd have caught it before activating a broken system. The 45-second cost of dry-run is dominated by the cost of a single bad activation.

Discovered but didn't fix: deploy fleet CLI dispatch didn't

templedb deploy fleet network list failed with "Unknown command 'deploy'" — the dispatcher misinterpreted list as the top-level command. Similarly templedb publish mirror-list templedb errored on the positional; mirror-list takes no project arg and always shows all. Both are one-line argparse fixes but I logged them and moved on. Next session should sweep these up if nothing bigger is on the plate.

The "fleet" abstraction doesn't fit personal machines notice

User asked to deploy "to all personal machines." The fleet_machines table has app-project targets (web1, vultr-woofs) but none of the personal hosts (zMothership2/3, zStation, zachMothership, WilliamZacharyAbelTheZeroth). So templedb deploy fleet deploy system_config can't reach them. This is a real gap: the "fleet" concept as built is for applications, not for the machines that run TempleDB itself. Registering personal hosts as fleet targets would collapse "SSH into each box and rebuild" into one command.

End-to-end publish → rebuild path works cleanly keep doing

From templedb file set config/tmux.conf to activated ~/.config/tmux/tmux.conf took about 12 minutes and 5 discrete steps (edit → publish → flake update → publish → rebuild). No hidden state, each step's output was interpretable, and the failure modes (missing method in update-input) were obvious. The pipeline is legible.
