session recap — agent login-required + write-path hazards + publish auto-pin

Started with "my temple agent emacs sessions r dying" and sprawled into a whole class of write-path and deploy-chain hazards. Nine commits, five rebuild cycles, one pre-existing latent bug caught by accident. This recap is mostly about what the sprawl exposed and what I'd do differently, not the fixes themselves — the fixes are in the code.

What triggered the session

User asked: "my temple agent emacs sessions r dying" — and immediately offered a diagnosis: "i think its cuz i needed to log into claude but there wasnt a mechanism from within the emacs agent to transmit that to me or if there was it didnt work." The diagnosis turned out to be correct, and also incomplete — the "silent death" was actually a two-layer bug (provider + elisp handler) that both had to be fixed for the auth-required flow to surface cleanly.

From there the session branched into fixing the "other sessions" cross-shell stage hiccup, then the flake.lock rebuild trap, then a pre-existing file set --stage revert bug I stumbled on while dogfooding the pin flow, then diff/show semantics, then file where nix-store probe. Each layer surfaced during the previous layer's testing.

What I noticed about my process

Keep Diagnosed both sides before writing either. The Emacs death had a Python-side cause (missing terminal event) and an Elisp-side cause (anemic handler) — I read both files and found both bugs before touching either. Both fixes worked on first try. Contrast with the file where nix-store probe, where I wrote three versions before it worked. Reading first pays.

Keep Session-pinned before doing agent work. templedb vcs session start --pin --name claude-agent at the start of the "let's fix the hiccups" phase. Every subsequent file set --commit reported the same session (#887 (claude-agent)) and the "other sessions" footer correctly excluded unrelated stages. Dogfooded the fix I was documenting.

Keep Verified memory against source when it mattered. Memory said the vcs commit revert bug was "retracted" (2026-09-01 probe). I trusted that but then hit a structurally similar revert via file set --stage. Reading the code (specifically stage_files() + _refresh_ws_row_from_disk) is what found it — not memory. Memory tells you where to look; source tells you what's true now.

Missed Shipped --pin-input before understanding stage_files(). The first publish --pin-input run wrote the pinned URL to DB, and then the write silently reverted. Diagnosed it as "flake.lock got reverted" for ~10 minutes before finding the actual mechanism (the --stage path double-stages and refreshes from stale disk). Cost one full rebuild cycle. If I'd read _write_content_to_db and stage_files end-to-end before writing the feature, would have seen the redundant stage immediately.

Missed Iterated file where against the deployed binary instead of a local Python script. Wrote v1 (probed stale user hm-profile symlink → found nothing), rebuilt, tested, wrote v2 (probed ~/.emacs.d with rglob → still nothing because rglob doesn't descend into symlinked dirs), rebuilt, tested, wrote v3 (os.walk(followlinks=True) → works). Each iteration was a ~90-second rebuild. Total wasted: ~4 minutes of wall time and 3 nix generations. A five-line scratch script would have caught both v1 and v2 in seconds.

Missed Confused a working-as-designed command for a bug. "vcs diff <commit> returned 'No differences' for a commit that changed 129 lines" — I filed this as a bug in the top picks I offered the user. When I finally read the code, it was correct: vcs diff <commit> compares commit vs current worktree, exactly like git diff <commit>. The bug was UX (misleading), not correctness. Should have read the code before labeling it a bug.

Notice The "other sessions" mechanic re-bit me three times. First when publish said "0 changes staged for commit in this session, 21 in other sessions" during templedb publish. Second when the same happened for system_config. Third when my pin flow's fc.set() call staged in the parent process's session. Each time I re-derived what was happening from the output. Would have saved five minutes just to look at CLAUDE.md first — the pin mechanism was already documented at line 180. I only realized this while writing the CLAUDE.md addendum.

Notice Every stage of the deploy chain has a silent no-op path. publish quietly skips the VCS-commit step when nothing is staged in this session. materialize's git-commit is skipped when disk content matches HEAD. nix flake update writes to a gitignored file that nixos-rebuild ignores. nixos-rebuild can pin to a stale rev if the daemon HEAD hadn't advanced by the time nix's fetcher runs. Any single one misfiring produces "everything says it worked but nothing changed." Chain observability is bad; each stage should print its outcome hash so a downstream stage can assert.

Notice "Multiple copies of files" isn't a fact, it's a UX crisis. For templedb-agent.el alone: DB → checkout → edit-workspace → materialized system_config layer → templedb project's overlay copy → home-manager-files nix-store output → symlinked layer store path → symlink from ~/.emacs.d/private/local-layers. Seven hops from source of truth to what Emacs loads. The file where extension surfaces one hop (the last). The other five remain invisible. This is a structural fragility, not a tooling gap — fewer hops is the real fix.

The one that got away

Total rebuild cycles this session: five. Cost ~10 minutes wall time. Root cause of most of them: the flake.lock gitignored + local-daemon-URL combo. Every rebuild re-locks; every re-lock races with the git daemon reflecting the just-pushed commit. --pin-input fixes the class, but I discovered it mid-session, not upfront. If --pin-input had been the default all along (which the user asked about at the end), zero of those rebuild cycles would have been needed — the first pin publish would have inlined the exact rev, nothing else to race.

  2. vcs session gc to reap orphans. Small. The "N files staged in other sessions" footer will keep growing without it.
  3. file where "overlay drift" vs "checkout drift" classification. Small doc/UX polish; makes the exit-code story sensible.
  4. Deploy-chain hash logging. Each of publish, materialize, git commit, flake fetch should print the input and output hash. Cross-stage assertions become trivial.
  5. Emacs SPC , a L for claude auth login. Small elisp, closes the loop on the original bug.

Meta-meta — patterns across recaps

Personal-use bug reports have the highest signal-to-word ratio of any input. The user's "my emacs is dying" sentence produced this whole tree — two direct fixes, one latent-bug catch, one full class of deploy hazards documented. Every substantial recap I've written seems to start this way. Sessions triggered by pure refactor or feature requests don't branch nearly as much.

The deploy chain touches everything, no matter how narrow the fix. This is the third session in a row where a "surgical" change ended with a publish + rebuild loop. The chain is the biggest cost driver. Any improvement to templedb's dev-mode / in-place reload paths pays back multiplicatively.

Memory is a starting point, not an authority. Two memory entries were slightly wrong this session (both were "fix claim retracted / retracted-but-not-really"). Neither was actively harmful, but both encouraged me to skip verification I should have done anyway. The pattern is: memory says "X was fixed," I don't check, X is still partly broken. Always verify claims of "shipped" or "fixed" against source.
