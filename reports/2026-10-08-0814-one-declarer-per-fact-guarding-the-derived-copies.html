One declarer per fact: guarding the derived copies

A session that began as a complaint about an undiscoverable environment variable and ended as an audit of the boundary the whole codebase rests on: exactly one place declares each fact, and every copy downstream is derived and must prove its standing before it may overwrite anything. Seven of this project's sharpest edges turn out to be a single confusion about that boundary wearing different costumes — and the session's own worst moment, committing 818 deletions against the live project, was that same confusion committed by the author of the guard meant to prevent it. Ships a --session flag, three default-on guards, two analysis documents, and a 607 → 336 line rewrite of CLAUDE.md.

2. The boundary

TempleDB's stance is already written down — observer of source, owner of the graph — but the operational rule underneath it was not. State it plainly:

Exactly one place declares each fact. Every copy downstream is derived, is recomputed from the declaration, and is never trusted on its own. A derived copy that wants to overwrite a declaration must first prove it is still current.

git declares source bytes; file_contents is a snapshot whose is_current=1 row is the most recent observation, not the truth of the file. nix declares store paths. The entity graph is derived from the relational tables, which are themselves derived from — or authoritative for — their authority. NixOS makes the identical move with the system closure, which is why a home-manager profile is re-derived at boot and anything activated out of band simply vanishes: it left no mark on the thing that generates reality.

The reason to name it is that it is generative of the bug list. Each of these was previously filed as its own footgun:

Seven places where the tooling lets you forget which side you are standing on. Every guard this session adds is the same shape: make the derived copy prove its standing.

3. The incident: 818 deletions, self-inflicted

Worth recording in full, because the failure mode is instructive and the guard that would have caught it was written minutes earlier by the same hand.

Having implemented and tested the mass-deletion guard under TEMPLEDB_DEV_MODE=1, the next question was whether the deployed binary carried it. The method chosen was to run the guarded command against the real project with dev mode unset: 

env -u TEMPLEDB_DEV_MODE templedb commit templedb /tmp/frozen-probe -m "x"

The deployed build predated the fix, so there was no guard. Instead of being refused, the probe committed 818 deletions as ed5de8b0 and tombstoned every file in the project. templedb file ls templedb returned “No files found”.

Nothing was lost. Content survived in the canonical checkout, 19 edit workspaces, the git object store and the GitHub mirror, and ed5de8b0 was never published — the mirror went from f4ae0cd straight to b39ad29 and never saw the deletion. Recovery was a full-tree re-commit from the session workspace (7b162dfc), verified exact: 818 paths restored, zero missing, zero extra, against the pre-incident git tree. The old UNIQUE failure on re-adding status='deleted' rows did not reappear.

The lesson is narrow and worth obeying. A guard exists only in the tree you just edited. Testing “is the guard deployed?” by invoking the dangerous command is a coin flip whose tails destroys the project — and since the deployed build routinely lags the DB until a rebuild, tails is the likely branch. Verify guard presence by reading the deployed code: 
SP=$(templedb admin which | awk '/importing from/{print $3}')
grep -c MARKER "$SP/cli/commands/commit.py"
If a destructive path must be exercised, point it at a throwaway slug. -p templedb on a probe is the mistake.

4. What shipped

4.1 --session <id|name>

Staging is session-scoped, and each agent tool call gets a fresh shell with a fresh session-leader PID and no inherited environment. Session identity was steerable only by TEMPLEDB_SESSION / TEMPLEDB_SESSION_ID — and neither vcs add --help nor vcs commit --help mentioned sessions at all, so No changes staged for commit in this session was unreachable from the CLI.

The flag outranks both environment variables and carries no persistent state, unlike the session.pin file removed in #907. Two details that emerged from testing and changed the design:

  • The override had to reach checkout-role resolution. vcs status --session claude-agent resolved staging correctly while still warning that no edit tree belonged to it, because CheckoutRepository.current_session_id() reads environment variables only. Six files read those variables independently, so rather than thread an override through all of them the flag resolves once and exports TEMPLEDB_SESSION_ID into the process environment.
  • Read-only commands must not create sessions. The first version opened a session from a misspelled probe name, violating the invariant that asking where a tree lives must not open one. Write commands now create a named session; vcs status resolves strictly and errors on a typo.

4.2 Three default-on guards

project checkout --force runs a stray-purge that walks the target recursively and unlinks every scanner-recognized file whose relative path is absent from the project's file list. A refusal guard existed, but skipped same-slug rows — and same-project nesting is the common shape, since edit workspaces live at edit-workspaces/<slug>/<session>/. Pointing --force at edit-workspaces/templedb would therefore have purged all 19 nested session trees, 11 of them live. Now refuses on strict enclosure regardless of slug, while still permitting the checkout that is the target.

commit computed its diff against whatever directory it was handed and marked every absent tracked path as deleted, with no threshold. Now refuses at ≥50% of tracked files missing (floor of 10 so small projects do not trip), overridable with --allow-mass-delete. Deletions are the worst half to get wrong: they tombstone paths, and re-adding a tombstoned path later hits a UNIQUE constraint.

get_current_session() accepted an ended session, contradicting both its own error message and CheckoutRepository.current_session_id(), which has always required ended_at IS NULL. The split let staging adopt a dead session that checkout-role resolution then refused.

5. Ingest: two layers, not one

Full detail in docs/INGEST_ADAPTERS.md. The finding that matters:

templedb ingest git does not run git. It projects vcs_commits rows that an earlier observation step wrote. A green ingest history means the graph matches the relational tables, not that it matches git.

Seven of nine adapters are such projections; only nix (probes nix-store) and scip (reads .scip files) touch a foreign authority. The observation for git is GitHistoryImporter, invoked by vcs import-history — not by ingest. Only doctor entities and reconcile interrogate an authority.

A second asymmetry: agent and intent are originators, reading agent_sessions and edit_intents, for which no upstream authority exists. For those the DB is the declaration, and loss is not recoverable by re-ingest. That is a backup-policy distinction, not a philosophical one.

Two README claims were corrected as measured: adapters are not all under 500 LOC (python is 1005) and not file-isolated — all nine share a 6597-line entity.py, the same file two file set writes clobbered on 2026-10-04. Also recorded: git's 234 error runs are a closed outage, every one between 2026-09-06 and 2026-09-24, the cr-sqlite window. ingestion_runs counts are cumulative; bound them by date before calling an adapter broken.

6. CLI: 432 commands, and the agent-facing surface is empty

Full detail in docs/CLI_SURFACE.md. 432 commands, 1153 parameters, ~44k LOC under src/cli/commands/.

admin schema exists specifically “for agent/scripting use” and serialises help: "" for 422 of 432 commands. The help is not missing from the CLI — vcs add is registered add_parser('add', help='Stage files for commit') and --help renders it. But schema.py:63 reads parser.description, and argparse keeps the help= from add_parser() on the parent's _choices_actions, never on the subparser. Only the ten commands that also pass description= survive.

--examples, which CLI_DISCOVERABILITY_IMPROVEMENTS.md marks “Implemented ✓”, raises AttributeError on every invocation: CommandHelp defines only __init__ and print, while three call sites still invoke the removed show_examples. Reproduced on the deployed build, so it is a live regression.

Also found: -a means --all on vcs add but --author on vcs commit, and since vcs commit has no --all the mistake is silent rather than an error. 53 input() prompts exist of which only 3 handle EOFError, so under automation the rest produce an uncaught traceback.

Correction, same day. An earlier revision of this report named nixos.py:287 as the EOF trap and claimed --yes did not cover it. Reading the enclosing block rather than the single line shows the opposite: nixos.py:279-295 short-circuits on --yes and catches EOFError with a message naming the flag that resolves it. It is one of the three sites that get this right, and is the model the others should copy. The claim came from a note written 2026-10-01 and was repeated without checking — the same failure as the home-manager documentation claim elsewhere in this session.

8. Open, not addressed here

  • checkout-gc never reclaims directories. checkout.py:620 states it outright — retiring a row leaves the tree, deliberately, since a tree may hold work the DB never saw. Nothing completes the job, so trees accumulate; 16 were removed by hand this session. A --prune-dirs that re-verifies classify_edit_tree at delete time would finish it.
  • The flat edit-workspaces/templedb row (#251) is unreachable. is_active=0, session_id NULL, directory still present — so checkout-gc cannot see it and no command can deregister it. Item 6 addresses this.
  • scip has 22 runs and mirrors has 2, ever. Neither is on the hourly timer. A dormant adapter still publishes entities under its source_authority, so its stale rows look as trustworthy as fresh ones; only observed_at distinguishes them. Drive them or retire them.
  • The two commits of the deletion/restore pair remain in the DB log. No tooling rewrites DB-native history, and it is cosmetic: publish materialises current state, so git never recorded the pair at all.

The root cause item 6 exposed

checkout-forget initially refused row #251, reporting that the tree held content the DB had never stored. That was a false positive of the same kind as the project checkout --force bug fixed earlier in the session: classify_edit_tree walked the tree without excluding nested registered checkouts, so the three live session workspaces beneath the flat parent were counted as its untracked work. Any parent-of-workspaces path was therefore permanently unprunable and permanently unforgettable.

Fixed in checkout_repository.py: classify_edit_tree now collects strictly-enclosed checkout paths and _untracked_in_tree prunes those subtrees during the walk, reporting them as nested_checkouts. The lesson generalises — any code that walks a checkout recursively has to know that other checkouts live inside it, which is now true of the purge guard, the prune, and forget.

With that fixed, #251 was still refused, and correctly: the flat tree holds 12 genuinely untracked files. None was work — flake.lock (transient, gitignored), the duplicate migrations/106_project_files_edit_mode.sql superseded by migration 120, src/cli/commands/nixops4.py (deleted on purpose in fcbabea, content recoverable from 7776c31), three _reprotest_*.py scratch files, and six test artifacts. Forgotten with --force on that evidence; the files remain on disk.
