From observer to integrator: TempleDB implementation plan

Sharpens yesterday’s observer proposal against a strong external critique and lands on a concrete phased implementation. The critique makes three moves that reshape the recommendation without invalidating any of its steps: (1) reframe the problem as authority per fact rather than authority per system; (2) replace the CAP analogy with a bidirectional-lens / view-maintenance framing that names the real defect (materialize is a poorly-lawed lens); (3) introduce EditIntent as a first-class abstraction so agent-mediated writes survive the retreat from authority-over-bytes. The refined vision: TempleDB is not a static analyzer plus agent state, but the semantic and provenance fabric connecting several authoritative worlds. Five phases, ~4 months of incremental work, no phase breaks a consumer.

What survives from the observer proposal

Everything concrete. The engineering recommendations from yesterday still land unchanged:

  • templedb file where as a drift diagnostic
  • Materialize made gitignore-aware and incremental (fixes yesterday’s .authinfo.gpg sweep at the root)
  • Emacs layer symlink escape hatch (TEMPLEDB_DEV_MODE_EMACS=1)
  • Watcher via inotify triggering incremental graph build-deps
  • SourceSnapshot reframing of file_contents
  • SCIP for language-agnostic code facts

What the critique does is reshape the framing and add two structural pieces the observer proposal was missing. Those pieces (EditIntent and the entity/relation model) turn the recommendation from “retreat to a well-known pattern” into “occupy a more interesting position no other tool holds.”

The theoretical refinement: authority per fact

“Source of truth” is a scalar phrasing for a per-fact property. Every candidate authority in our stack is authoritative for some facts and not others:

FactNatural authority
Bytes of foo.nix at rev abcGit
Which symbols foo.nix definesTempleDB (derived, computed by parser)
Which symbols foo.nix imports from bar.nixTempleDB (derived)
Agent 17 is editing foo.nix in session STempleDB (agent runtime)
Deployment 42 was built from commit abcTempleDB (deployment history)
Nix store path /nix/store/xyz is a build outputNix (produced it)
Store path /nix/store/xyz came from deployment 42TempleDB (provenance)
Machine zMothership3 is running store path /nix/store/xyzNixOS on the machine (running state) + TempleDB (recorded observation)
Report R motivated decision DTempleDB (authored, stored)

The right question is not “who owns source?” It is “which fact needs which authority?” TempleDB’s job is to hold the facts with no natural home elsewhere, and to record the graph across facts stored by different authorities. That last piece — the graph across authorities — is what makes TempleDB not-Sourcegraph and not-a-metastore.

Lenses, not CAP

The CAP framing yesterday was technically wrong. CAP is about distributed replicated systems under network partitions with a particular meaning of consistency. Three co-located representations of source on one machine are not CAP-relevant. The honest framework is bidirectional synchronization / view maintenance / cache coherence, and specifically the theory of lenses.

A lens between structure S and view V is a pair:

get : S → V
put : S × V → S

with laws that make the round-trip well-behaved:

put-get : get(put(s, v)) = v
get-put : put(s, get(s)) = s

The put-get law says “if I write v back through the lens, reading it should give v.” The get-put law says “if I read out what’s there and write it back unchanged, nothing changes.” These sound trivial. In practice they are hard.

This names TempleDB’s defect precisely. templedb project checkout is a put: it takes DB state and produces filesystem state. templedb project scan is a get: it reads filesystem state back into DB. Every observed materialize bug is a violated lens law:

  • .authinfo.gpg deletion: the working tree had an untracked file the DB didn’t know about. put deleted it. Then get observed “file missing” and recorded it. put-get violated: writing the DB state didn’t round-trip through the observation.
  • Comment / whitespace drift when re-emitting Nix from AST: get(source) = ast, but put(source, ast) produces different bytes. get-put violated.
  • Gitignored file handling: gitignore rules are part of the checkout’s reality but not part of the DB’s state. Any lens that ignores gitignore is fighting the working tree constantly.
The mathematical heart of the fix The observer pattern deletes put. What remains is a view (a get-only lens, or in more general terms a fold). Views have no laws to violate. This is not a retreat — it’s picking the safest, best-understood shape from lens theory.

There are richer lens theories (aligned lenses, symmetric lenses, edit lenses) that handle more complex round-trips. They come with more complex laws and correspondingly more implementation subtlety. The observer position picks the trivially-lawed shape and gets much of the benefit without any of the maintenance tax.

EditIntent: the missing structural piece

Yesterday’s proposal demoted templedb file set to “internal shortcut.” That’s wrong, and the critique caught it. Agent-mediated editing is not a corner case; it’s a first-class use case that deserves a first-class abstraction. But the thing TempleDB owns should be the edit transaction, not the resulting bytes.

Concretely, introduce a new entity:

EditIntent = (id, session, base_revision, patch, author, timestamp, status)

and one operation:

apply : GitCheckout × EditIntent → GitCheckout'

After which the normal observer chain resumes:

GitCheckout' → SourceSnapshot' → SemanticGraph'

This is CQRS + event sourcing applied to source editing. It has three concrete wins:

  1. Session-scoped staging preserved. Parallel agents each own their intent queue. No agent’s intent is applied until it commits, and no commit sweeps another’s uncommitted intents. The current vcs_working_state table is already almost this, just under a different name and coupled to raw file content.
  2. Provenance is trivial. A deployment can point at the exact chain of intents that produced its source tree. “Which agent’s edit ended up in production?” becomes a graph query.
  3. Undo and dry-run become natural. Cancel an intent before apply. Preview an intent’s effect without touching the checkout. Reverse an applied intent by applying its inverse patch.

My addition to this piece: TempleDB already partially does this. vcs_working_state is essentially an intent queue keyed on session. templedb file set is essentially intent create && intent apply immediately. Formalizing the pattern isn’t inventing something new — it’s naming a shape that already exists and rebuilding the surface API around it.

TempleDB as semantic integration layer

The most interesting refinement in the critique is the entity/relation model. TempleDB’s ambition should not be to absorb Git and Nix and Emacs and the filesystem, but to be the graph that knows how their objects correspond.

Fundamental object: Entity. Kinds include:

Repository   Commit          File            FileSnapshot
ASTNode      Symbol          Package         Import
Derivation   StorePath       BuildOutput
Machine      Deployment      Generation
Session      Agent           EditIntent      ToolCall
Report       Decision        Secret          Config

Fundamental relation: typed edges between entities:

File             defines           Symbol
Symbol           calls             Symbol
Symbol           references        Symbol
Commit           contains          FileSnapshot
Commit           parent-of         Commit
Derivation       built-from        Commit
Derivation       produces          StorePath
Deployment       installed         StorePath
Deployment       targets           Machine
Session          proposed          EditIntent
EditIntent       applied-to        Commit
Report           motivated         Decision
Decision         implemented-in    Commit

Every entity carries a source_authority field indicating which system is canonical for its bytes/state. Every relation carries an observed_at timestamp and an observed_by field indicating which ingestion algebra recorded it. This gives you two things nothing else in the stack has:

  1. Cross-authority provenance. “Which store path is running on this machine, from which deployment, from which commit, from which agent-session-and-intent-chain, motivated by which report?” is a five-hop graph query.
  2. Freshness telemetry. Every fact’s observed_at tells you how stale it is relative to its authority. Drift becomes measurable, not just detectable.

Industry analogs and their failure modes

The role “coordinator/integrator holding metadata about foreign systems” is well-known:

SystemOwnsDefers toFailure mode
Hive / Iceberg / Unity CatalogTable metadata, schemas, partitionsS3 / HDFS for dataMetastore staleness silently breaks queries
Istio / LinkerdRouting / policy / observabilityThe services themselvesControl-plane outage takes down the mesh
Terraform / Pulumi stateInfrastructure modelThe cloudsState-vs-reality drift; state locks; state corruption
dbt / Cube semantic layerMetric definitionsWarehouses for dataSemantic-layer divergence from raw table changes

Every one of these systems succeeded by being disciplined about what it owns. Every one has been bitten by staleness relative to underlying authorities. The universal lesson: a coordinator needs a reconcile story from day one. Not “we’ll add it later.” The reconcile story is core.

Concretely for TempleDB: a templedb doctor entities command that walks the graph and, for every entity claiming to have an external authority, asks that authority whether the fact is still current. Git for commit facts, nix-store for store-path facts, machine SSH for running-generation facts. Anything stale is flagged; anything missing is flagged. This is not an addon — it’s the equivalent of terraform refresh and it’s load-bearing.

SCIP as one ingestion algebra, not the ingestion algebra

The critique reframed SCIP as “one ingestion algebra into a larger knowledge graph” rather than merely an interop format. That’s the right elevation. It also implies a design principle: every authority publishes into TempleDB via a well-defined ingestion algebra. Candidates:

AuthorityIngestion algebraFacts published
GitCommit walker + tree diffCommit, FileSnapshot, contains, parent-of
Nixnix-store queries + eval traceDerivation, StorePath, built-from, produces, closure-refs
NixOS on a machineSSH probe of /run/current-systemGeneration, running-on, deployed-at
Agent runtimeDirect DB write (native)Session, ToolCall, EditIntent, proposed, applied-to
Language serversSCIP / LSIF exportSymbol, defines, calls, references
Author (human)Report writer + decision markupReport, Decision, motivated, implemented-in

Each row is a distinct implementation of the same shape: read from an authority, translate to the TempleDB entity/relation model, upsert. Each shape needs its own freshness policy: git is cheap to re-scan, SSH probes are expensive, SCIP files can be large. The design principle: keep ingestion adapters small and swap-able, so upstream schema changes hurt one adapter at a time.

The implementation plan

Five phases, sequential but each a coherent stand-alone deliverable. Total ~4 months. Every phase ships something usable. No phase requires the AST parser to be complete. No phase breaks existing consumers.

Phase 0 — acute pain (weeks 1–2)

Not architectural, but load-bearing for daily work. Ships as three PRs.

  • templedb file where <slug> <path> — walks the static mirror list, prints hashes with drift/immutable/match color coding.
  • Materialize made gitignore-aware. Untracked-but-gitignored files in the checkout are preserved. Yesterday’s .authinfo.gpg sweep becomes structurally impossible.
  • TEMPLEDB_DEV_MODE_EMACS=1 symlink swap for the Spacemacs layer path, mirroring the existing dev-mode for the CLI.

Ships: daily friction drops by roughly an order of magnitude.

Phase 1 — SourceSnapshot (weeks 3–4)

Reframe file_contents as immutable historical observation, not authoring surface.

  • Migration: add a view source_snapshots over file_contents exposing (repo, revision, path, hash, content, observed_at, source_authority).
  • Document: “file_contents is a snapshot table. The current row for a path is the most recent observation, not authoritative bytes.”
  • New query surface: templedb source snapshot at <slug> <path> --rev <commit>.
  • Add store_path → source_snapshot relation for build provenance.

Ships: the vocabulary shift, plus one immediately-useful query (“what did this file look like when the currently-deployed system was built?”).

Phase 2 — EditIntent (weeks 5–6)

Formalize CQRS for source edits.

  • New table: edit_intents (id, session_id, base_revision, patch_content, author, created_at, applied_at, status).
  • New CLI: templedb intent {create, list, apply, cancel, dry-run, describe}.
  • Update templedb file set to be a thin wrapper: creates an intent, applies it immediately, and prints the intent id for later reference.
  • Update the agent MCP tools to produce intents rather than direct writes. Session-scoped by construction.
  • Wire vcs_working_state to reference intents rather than store raw content (backward-compatible via view).
  • Undo command: templedb intent revert <id> applies the inverse patch.

Ships: every agent edit is now trace-able and reversible. Parallel-agent staging remains uncorrupted by construction.

Phase 3 — entity/relation model (weeks 7–10)

Move toward the semantic integration layer.

  • New tables: entities (id, kind, external_ref, source_authority, observed_at) and relations (from_id, kind, to_id, source_authority, observed_at).
  • Migration: existing typed tables (agent_sessions, project_files, vcs_commits, config_nodes, nix_store_paths, deployments) become materialized views over the entity graph. Zero-downtime; old queries keep working.
  • templedb graph explore <entity> — walk relations outward. templedb graph query — ad-hoc traversal.
  • Ingestion algebras registered explicitly: templedb ingest {git, nix, ssh-probe, scip, agent, report}.
  • templedb doctor entities — the reconcile story. Walks each entity, asks its authority whether the fact is still current, flags drift.

Ships: cross-authority provenance queries. The five-hop “what motivated the code running on this machine” query becomes real.

Phase 4 — SCIP + ingestion discipline (weeks 11–13)

Externalize the code-facts ingestion algebra.

  • Adopt SCIP schema for code facts across languages.
  • Wire scip-python, scip-typescript, scip-nix (via existing tree-sitter-nix) as adapters.
  • graph search / who-uses / callers / importers become SCIP queries; templedb-native tables remain for what SCIP doesn’t cover.
  • Document each ingestion algebra’s freshness policy explicitly: git = cheap to re-scan on commit; SCIP = expensive, run on push; SSH probe = manual or scheduled.

Ships: external tools can consume TempleDB code queries via SCIP. Language coverage grows with the SCIP ecosystem, not with our parser budget.

Phase 5 — retire authority-over-source (weeks 14–16)

The final vocabulary shift.

  • FUSE mount permanently retired (already de facto).
  • file_contents for source rows becomes optional. If SourceSnapshot has provenance, we don’t always need the bytes; we can re-obtain them from git.
  • Documentation and CLAUDE.md updated: “TempleDB observes source, owns intents, holds the graph.”
  • The templedb write path broken-class memories become historical curiosities.

Ships: the ownership question is settled. The drift-bug family is closed by construction.

Risks I want to name explicitly

Coordinator becomes a bottleneck Every metastore / mesh / config coordinator becomes a critical path. When TempleDB is stale, users get confused. When it’s inconsistent with underlying authorities, users get burned. Mitigation: the reconcile story (templedb doctor entities) has to ship in Phase 3, not later, and it has to be cheap enough to run frequently.
Ingestion algebra explosion Every new authority (a new build tool, a new VCS backend, a new language server) needs an adapter. Adapters rot when upstream schemas change. Mitigation: adapters are small, isolated, and can be updated one at a time. Budget maintenance time per adapter as a first-class expense.
The EditIntent + apply loop is still a lens The observer pattern for source deletes put. But apply(checkout, intent) is a form of put, and its round-trip get(apply(checkout, intent)) has to produce the observed effect we predicted. Mitigation: property-based tests on the intent-apply-observe cycle. For any intent, apply-then-scan should produce a snapshot that matches the intent’s declared effect.
Two-step intent workflow adds latency for agents Currently templedb file set is one call. Under Phase 2 it becomes create + apply. On the fast path this doesn’t matter (single-call convenience wrapper). On the slow path (multi-agent coordination, review workflows) the two-step is a feature. Design the API so the fast path is one call and the slow path composes.
Storage cost of the entity graph If we register every symbol, every relation, every observation with a timestamp, the graph grows fast. Mitigation: partition by domain (code facts vs deployment facts vs report facts), garbage-collect superseded observations aggressively, and offer opt-in retention policies per ingestion algebra.

What TempleDB becomes

Refined from the critique:

The one-sentence vision TempleDB is the semantic and provenance fabric connecting several authoritative worlds — git for source, nix for artifacts, agents for intent, machines for running state, humans for decisions — with a knowledge graph that traces every fact back to its ingesting authority and every derived answer back to its source snapshot.

This is more ambitious than “static analyzer plus agent state” and more disciplined than “database as universal source of truth.” It has industry precedent (metastores, meshes, semantic layers) and known failure modes (staleness, coordinator bottleneck, adapter rot). The failure modes are budget-able; the elegance-and-hostility of the DB-as-truth model is not.

What I’m taking from the critique, credited

Three moves in the critique that I’m incorporating wholesale:

  1. Authority per fact. Replaces “source of truth” as the framing concept. Cleaner, and it dissolves the “identity crisis” framing into something more precise.
  2. Lenses replace CAP. Names the defect (poorly-lawed put), justifies the observer position (deletes put, no laws to break), and points at the extension (EditIntent’s apply is a new put whose laws we must test).
  3. EditIntent as first-class abstraction. Fixes yesterday’s under-service of the agent-writes use case without re-introducing DB-owns-bytes.

My additions on top:

  1. The observer pattern is the “get-only lens” — naming which shape from lens theory we’re picking makes the choice defensible in terms other than aesthetics.
  2. vcs_working_state is already an intent queue in disguise. Phase 2 is less “introduce a new pattern” and more “name the pattern we accidentally built.”
  3. The reconcile story is load-bearing from day one. Every industry coordinator that skipped this became a source of subtle bugs. templedb doctor entities ships in Phase 3, not later.
  4. Ingestion algebras multiply and rot. This is a real ongoing cost that needs a budget, not a footnote.

What’s next

If accepted: Phase 0 in the next two weeks. templedb file where, gitignore-aware materialize, and the Emacs symlink escape hatch. Those three ship independently, buy most of the daily-life improvement, and don’t commit us to the larger direction until we’ve seen how Phase 0 lands.

The rest is a quarter of incremental work. Nothing in it is urgent, nothing blocks any other improvement, and the direction survives being paused. That’s the mark of a plan that fits the complexity budget rather than fights it.
