§1 · Auto-pin agent context

Auto-write session pin when the context looks agent-y

files: src/services/vcs_service.py cost: medium touches: session resolution path (careful)

Problem. Every Claude Code Bash tool invocation runs in a fresh shell with a fresh session-leader PID and no inherited env. Without a filesystem pin, each templedb call resolves to its own new session. Stages from earlier calls become invisible to later commits. The workaround (vcs session start --pin) exists but requires human awareness.

Design. In VCSService.get_current_session(), after step 3 (filesystem pin lookup) fails but before step 4 (SID lookup), insert an auto-pin step:

  1. If TEMPLEDB_AUTO_PIN=0 is set, skip. (Env-var opt-out.)
  2. Detect "agent context" via one of:
    • CLAUDECODE=1 or CLAUDE_CODE_ENTRYPOINT in env (Claude Code sets these), or
    • controlling terminal absent (os.isatty(0) is false AND stdin is a pipe), or
    • an env var flag opts in explicitly: TEMPLEDB_AUTO_PIN=1.
  3. If agent context detected AND no existing pin file, create a session with name auto-agent-<host> and write the pin. Log a single INFO line the first time.
  4. Subsequent calls in the same context read the pin normally.

Guardrails.

  • Auto-pin creates a session with a distinct name prefix (auto-agent-*) so it's obvious in session list.
  • Auto-pins expire after 4 hours (shorter than the 24h manual pin TTL) to reduce collision blast radius.
  • If two auto-pin candidates race, the first-writer-wins (via O_EXCL on the pin file). Second one just adopts the first's session.
  • templedb doctor gets a check: "You have N stale auto-agent sessions; consider vcs session gc."

Risk. If a real human runs templedb in a shell that happens to trigger the agent-context heuristic (e.g. tmux on a non-TTY), they get an auto-pin they didn't ask for. Mitigation: the log line ("auto-pinned session for agent context — unpin with…") is loud enough to notice, and unpin is one command.

Ready-to-write test. Set CLAUDECODE=1, run templedb file set in one subprocess, vcs commit in another — they must share the session. Set CLAUDECODE=1, run vcs session current; expect an auto-agent-* session identity.

§2 · vcs session gc

Reap orphaned sessions and their working-state rows

files: src/services/vcs_service.py, src/cli/commands/vcs.py cost: medium touches: vcs_sessions, vcs_working_state

Problem. Every publish output ends with (N file(s) staged in other sessions were not included). That N grew from 21 to 23 during this session as I created new auto-shell sessions. Most of those rows are orphaned — their session was a one-shot shell that ended hours ago.

Design. New subcommand:

templedb vcs session gc [--dry-run] [--older-than DURATION] [--force]

Behavior:

  • Find sessions where ended_at IS NULL AND started_at < now - DURATION (default: 24h) AND pid is no longer alive (probe with os.kill(pid, 0) under the same author). If any of those conditions fail, session is "possibly still active" — skip.
  • For each reap candidate: SET ended_at = datetime('now'), end_reason = 'gc'. Do NOT delete vcs_working_state rows staged by them — those are user data. Instead, orphan them (SET staged_by_session_id = NULL, state = 'modified'). The user's next vcs status then correctly shows them as unstaged modifications.
  • --dry-run reports the plan without executing.
  • --force bypasses the "pid still alive" check (for cleaning up after a crashed process where the PID has been reused).

Guardrail. Never touch a session that has an active pin file pointing at it. And never touch vcs_working_state rows in a way that loses content — only rewrite their session ownership.

UX addition. templedb doctor reports "You have N staged rows from ended sessions; run vcs session gc --dry-run to see them." Nudges without acting.

§3 · --expect-rev assertion on publish

Fast-fail when the flake fetcher resolves to an unexpected rev

files: src/cli/commands/publish.py, src/services/system_service.py cost: small (~15 LOC) touches: no schema, no data

Problem. The rebuild race we hit five times this session: publish materializes and pushes, but if the local git daemon hasn't reflected the new commit by the time nixos-rebuild --flake . runs its flake fetch, nix locks to the previous rev. Everything says "OK." Nothing changed.

Design. Two touch points.

Emit new rev after publish

Modify PublishCommands.publish() to capture the git HEAD hash of the target's checkout after the materialize step succeeds. Print it:

Published to 1 mirror(s)
  git HEAD: 04558face5873ad946f041723776dd8accfd77d7

Also emit a machine-readable JSON line when --json is passed:

{"slug": "templedb", "head": "04558face5...", "materialized": 751, "committed": true}

Add --expect-templedb-rev <hash> (or generalized: --expect-input <name>=<hash>)

New flag on publish run. If passed, after the publish completes, run nix flake metadata --refresh against the resulting checkout and assert that the named input resolves to the expected hash. Exit 3 (distinct from other errors) on mismatch.

templedb publish run system_config \
    --pin-input templedb \
    --expect-input templedb=04558face5873ad946f041723776dd8accfd77d7

Combined with --pin-input, this guarantees: (a) the rev is pinned in flake.nix, and (b) nix's resolver actually picks up the pin. If the daemon isn't serving that rev yet, we fail loud instead of building silently against a stale one.

Usage pattern. A scripted "publish + rebuild" loop becomes:

NEWREV=$(templedb publish run templedb --json | jq -r .head)
templedb publish run system_config \
    --pin-input templedb \
    --expect-input templedb=$NEWREV
templedb nixos system-switch system_config --yes

§4 · Stage outcome-hash logging

Every deploy-chain stage prints its input+output hash

files: publish.py, system_service.py, nix_deploy_backend.py cost: medium (~30 LOC across 4 files) touches: log output only

Problem. Each stage optimizes its own idempotency (skip if unchanged) and reports success either way. Cross-stage, that means "everything says it worked" is compatible with "nothing changed at any stage." No way to tell which stage no-op'd.

Design. Introduce a consistent log format at each boundary. Even on no-op, emit a line with the pre/post hash.

StageFormat
file set set <slug>/<path>: db=<pre12> → <post12> (post=pre if content unchanged)
vcs commit commit <slug>: HEAD=<pre12> → <commit_hash12> (N files)
publish materialize materialize <slug>: db_state=<12> disk_pre=<12> disk_post=<12> (N files written, git-commit=<hash|noop>)
publish git push push <mirror>: local=<12> remote_pre=<12> → remote_post=<12>
nixos-rebuild flake fetch flake: input <name> resolved to rev=<40> (one line per non-follows input)

Implementation. Each stage has an existing "success" print — extend it. The hash is already computed internally in almost every case (content_blob hash, git rev-parse, etc.). Just print it.

Depends on. Enables §3 --expect-rev assertions in a scripted pipeline (parseable output) and §5 file trace (relies on stages to record their hashes durably somewhere queryable).

§5 · templedb file trace <slug> <path>

Print every copy of a file across the full deploy chain

files: src/cli/commands/file.py cost: medium (~80 LOC) touches: adds a new subcommand, no schema

Problem. file where now surfaces one hop (the live overlay). But the actual chain from DB to the running binary is up to 7 hops. When a change fails to land, you need to know which hop is stuck.

Design. New subcommand:

templedb file trace <slug> <path> [--verbose]

Walks the chain and prints every copy with its hash and how it was derived:

trace: templedb/src/agent/providers/claude_code.py

  01. DB              hash=fed7e5fd6f98  is_current=1
      ↳ blob_size=4748  updated=2026-09-19 13:47:30

  02. checkout        hash=fed7e5fd6f98  ✓ matches DB
      /home/zach/.config/templedb/checkouts/templedb/src/agent/providers/claude_code.py

  03. edit-workspace  hash=ed9e9b9ba231  ✗ drift (older DB rev)
      /home/zach/.config/templedb/edit-workspaces/templedb/src/agent/providers/claude_code.py

  04. git HEAD        hash=fed7e5fd6f98  ✓ matches DB
      commit=04558face5  msg="fix(file where): use os.walk..."

  05. git daemon HEAD hash=fed7e5fd6f98  ✓ matches git HEAD
      served at git://localhost:9419/templedb

  06. flake.lock pin  rev=04558face5873a  (via ?rev= in flake.nix)
      /home/zach/.config/templedb/checkouts/system_config/flake.nix

  07. nix store       hash=fed7e5fd6f98  ✓ matches DB
      /nix/store/7h5jyhb19142mvp7nv8dq3vlrblimcd7-templedb-0.1.0/lib/python3.13/site-packages/agent/providers/claude_code.py

  08. live binary     ✓ resolves to step 07
      /home/zach/.nix-profile/bin/templedb → same store path

verdict: ✓ end-to-end match, current DB content is what's running

For a file with drift, the verdict changes:

verdict: ✗ drift at step 6 (flake pin) — nix store still holds an older rev.
Recommended: templedb publish run system_config --pin-input <slug>

Implementation notes.

  • Steps 1–3 reuse file where's existing probes.
  • Step 4: git rev-parse HEAD + git show HEAD:<path> under the target's checkout.
  • Step 5: git ls-remote git://localhost:9419/<slug> HEAD (skip if daemon not local).
  • Step 6: parse the consuming project's flake.lock (find any node whose original.url is git://localhost:9419/<slug>). Cross-project — need to know which consumer(s) to check. Take --consumer <slug> to disambiguate; default to system_config.
  • Step 7: for known projects, follow the mapping to a nix store path. For templedb specifically: readlink -f $(which templedb) → /nix/store/<hash>-templedb-*/bin/…. For arbitrary slugs, walk ~/.local/state/nix/profiles/* (already partial coverage in file where).
  • Step 8: symlink/binary chain resolution.

Follow-up ideas.

  • --fix: for each drift, offer the exact command to re-sync that hop.
  • --json: machine-readable trace, so CI can assert the chain is clean.
  • templedb doctor runs trace for a canary file per project (e.g. flake.nix for system_config, templedb binary for templedb) and reports any drift.

§6 · Dev-mode symlink for editable overlays

Skip the 7-hop chain for files under active development

files: home.nix, src/services/system_service.py, possibly Emacs layer packages.el cost: larger — design work touches: home-manager module structure

Problem. Currently every edit to templedb-agent.el requires: DB write → publish → git push → flake update → home-manager rebuild. ~90 seconds and a nix generation per iteration. For files edited during active development, this is unbearable friction.

Design. Add an opt-in dev-mode symlink pattern to home.nix for specifically enumerated files. When enabled:

home.file.".emacs.d/private/local-layers/templedb/local/templedb-agent/templedb-agent.el" = {
  source = if config.templedb.devMode
    then config.lib.file.mkOutOfStoreSymlink
      "/home/zach/temple/templedb/integrations/emacs/templedb-agent.el"
    else ;
};

When templedb.devMode = true: the file is a symlink to the FUSE mount. Edits via templedb file set reflect immediately in Emacs (after M-x load-file). No rebuild needed.

When false (default, deploy mode): current chain unchanged. Reproducible builds, signed deployments, etc.

Enable list. Should be a small, explicit whitelist of files that receive dev-mode treatment. Candidates:

  • templedb-agent.el and other integrations/emacs/*.el
  • Config files that don't affect the nix closure (documentation, systemd unit descriptions, etc.)

Cost / open questions.

  • FUSE mount is a runtime dependency. If it's not mounted, dev-mode Emacs is broken. Need a startup check.
  • Introduces a per-file exception to "everything through nix," which is a real invariant break. Worth it only if the friction savings materially exceed the cognitive tax.
  • Doesn't help for files that affect the nix closure (e.g. Python source, Nix modules). Only helps for interpreted / read-at-use files.
  • Might be simpler to just teach agents to run templedb file checkout <slug> <path> -o <target> after every edit, to a well-known dev-mode target. Less nix design, more shell scripting.

Recommendation. Do §5 (file trace) first. It'll tell us quantitatively how often the 7-hop chain matters vs. is fine. If most edits go end-to-end cleanly, this spec is unnecessary. If many drift, then dev-mode symlink pays back.

How these compose

The specs interlock more than the ranking suggests. In order of dependency:

  1. §4 stage hash logging is the substrate. Every other spec assumes stages emit their outcome hashes.
  2. §3 --expect-rev uses §4's output for scripts to assert against.
  3. §5 file trace queries §4's records (or re-derives them) to walk the chain.
  4. §1 auto-pin and §2 gc are session-side concerns; they don't depend on §3–§5 but do interact (auto-pin creates sessions that gc must handle correctly).
  5. §6 dev-mode symlink is orthogonal — a shortcut around the chain for specific files rather than a chain improvement.

What NOT to do

  • Don't remove session isolation. The "other sessions" mechanic is the right default for concurrent human work. The fix is to auto-share for agent contexts, not to remove isolation.
  • Don't try to reduce the 7-hop chain by rewriting the architecture. Each hop encodes a real requirement (DB source-of-truth, git-for-nix, nix content-addressing, home- manager overlays). Trying to unify them would produce a worse version of both nix and templedb. Make the chain observable (§5), not shorter.
  • Don't add "empty commits so materialize always emits one." Considered and rejected. The no-op skip is correct; it's the invisibility of the skip that's the problem, and §4 fixes visibility without breaking idempotency.

Meta

This is a "we noticed patterns" spec, not a bug list. Each item addresses a class rather than an incident. If half of these land, the next agent session should hit exactly zero of the frictions this session hit.
