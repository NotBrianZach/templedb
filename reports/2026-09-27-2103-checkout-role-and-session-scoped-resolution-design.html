Checkout role and session-scoped resolution design

templedb vcs commit silently reverted a file set write that --verify had just confirmed. The cause is not a race or a typo: checkouts.is_active is 1 on all 61 rows and 0 on none, so "the active checkout" actually resolves to whichever directory was written to most recently. Four of seven projects have more than one candidate; templedb has 43. This is the design for replacing that rule with an explicit role plus session ownership, and the measurement showing why the role column alone is not enough.

The incident

Commit FA20845EE25BD208 to system_config was supposed to record two files. It recorded the corrected flake.nix (b3d734a99778) and the stale hosts/zachgigamothers.nix (3dee653f6abd) — discarding DB content that file set --verify had confirmed as fd190b8c2437 moments earlier. The tree then claimed hostName = "zachgigamothers" while the file that had been verified against the running machine said "nixos".

The chain, all in one direction:

vcs add <file>
  → VCSService.stage_files
  → _refresh_ws_row_from_disk          # re-hash the file from disk
  → SyncManager.get_checkout_path()
  → CheckoutRepository.get_active_for_project()
  → "newest is_active=1 row whose directory still exists"

Staging deliberately re-reads from disk. That exists for a good reason — without it, vcs add stages whatever hash the last scanner pass recorded, so an editor write that postdates the scan gets committed with a message describing a different diff. The bug is not that it reads disk. The bug is which disk it reads.

What made it fire: earlier in the same session I had run project checkout system_config …/checkouts/system_config to refresh the canonical tree. That made the canonical row the newest, so it won "active" away from the edit workspace where the real work was. Staging then read pre-correction bytes from it, over a verified DB write.

is_active is not broken, it is empty

The column holds no information. Measured on the live database: 

checkouts total = 61      is_active=1: 61      is_active=0: 0

Nothing has ever set it to 0. The single UPDATE that touches it (vcs_service.py:391) fires only when session reaping rmtrees a workspace. So WHERE is_active = 1 is a no-op filter and the effective rule is recency.

get_active_for_project already carries a comment about this and a mitigation — it prefers the newest row whose directory exists, because 45 rows once pointed at deleted directories. That part works and is not the problem here. The canonical checkout existed. It won legitimately, by a rule that is simply wrong for the question being asked.

Two independent defects in that rule:

  • Recency-based. Any tool that materialises to a different path becomes the staging authority as a side effect. 40 of templedb's 43 candidates are /tmp/tdb-* scratch trees that still exist; each is one project checkout away from owning the next commit.
  • Project-scoped, not session-scoped. Concurrent agents on one project share a single answer. bza currently has two agent workspaces; today's rule hands both agents whichever is newer.

The surface to change is small, which is the one piece of good news: there is one insert point (CheckoutRepository.create_or_update) with one caller (checkout.py:134), and five readers of the resolution.

Schema

ALTER TABLE checkouts ADD COLUMN kind TEXT NOT NULL DEFAULT 'scratch';
ALTER TABLE checkouts ADD COLUMN session_id INTEGER REFERENCES vcs_sessions(id);

DEFAULT 'scratch' is fail-safe on purpose: an unclassified row must never win authority. Defaulting to 'edit' would make every future unlabelled row a candidate, which is the current bug with extra steps.

Backfill is pure path shape. No inference:

UPDATE checkouts SET kind='canonical'
 WHERE checkout_path LIKE '%/.config/templedb/checkouts/%';
UPDATE checkouts SET kind='edit'
 WHERE checkout_path LIKE '%/.config/templedb/edit-workspaces/%';
UPDATE checkouts SET is_active=0 WHERE kind='scratch';   -- retires 47 rows

session_id is left NULL by the backfill. The leaf names could be matched against vcs_sessions.name, but historical attribution has no consumer and a wrong guess is worse than an honest NULL. Only new checkouts get an owner.

Resolution

get_active_for_project(project_id) becomes resolve(project_id, purpose), with the old name kept as a deprecated shim mapping to purpose=EDIT so the five readers can be migrated one at a time. 

BUILD | MATERIALIZE | PUBLISH  →  the canonical row. Full stop.

EDIT | STAGE | COMMIT | STATUS →
  1. this session's edit workspace (kind=edit, session_id=me, dir exists)
  2. adoptable edit workspaces (session_id IS NULL, or session.ended_at set):
       exactly one   → use it
       more than one → raise AmbiguousCheckout(candidates)
  3. none → refuse, naming `templedb edit <slug>`

scratch is never returned. A scratch tree is used only when named
explicitly, e.g. `templedb commit <slug> <dir>`.

The load-bearing property is in step 1: another live session's workspace is never silently used. Different purposes also stop fighting over one answer — a build genuinely wants the canonical tree while a commit genuinely wants the edit tree, and no single "active" flag can express both.

Session-scoping compatibility

This is where the sharp edges are, and one of them invalidates the simple version of the plan.

1. Reaping must not orphan a tree

On session end, set session_id = NULL — making the row adoptable via step 2 — rather than deleting it. Set is_active = 0 only if the directory was actually removed. That keeps the existing vcs_service.py:391 behaviour coherent instead of competing with it.

2. No session behaves exactly as today

With TEMPLEDB_SESSION unset, step 1 cannot match and step 2 applies. A project with one workspace resolves as it does now. That is the backward-compatibility guarantee, and it is why step 2 cannot be dropped in favour of pure session ownership.

3. The raw-sqlite duplicate becomes a correctness coupling

src/cli/__init__.py resolves the dev-mode source tree before the templedb packages are importable, so it reimplements the rule in stdlib sqlite3. It has to learn the same rule. Until it does, TEMPLEDB_DEV_MODE=1 can run different code than the tree you just edited — which its own comment says already happened once. Mitigation: port the rule and add a test asserting both implementations agree against the live database.

4. Ended-session ambiguity is real, and the role column does not fix it

The measurement that changes the plan. After classifying by path shape and deactivating all 47 scratch rows, 3 of 4 projects are still ambiguous, because each has several live edit workspaces: bza 4, templedb 3, system_config 2. Step 2 would raise for three projects on day one. Session scoping is therefore required, not complementary.

The bare legacy rows have to be retired in the same migration. That also fixes something worse than ambiguity: edit-workspaces/<slug> is the parent of the session-stamped workspaces, so that tree physically contains nested copies of the project. If a bare row ever won resolution, a scan would walk into the session subdirectories and see every file twice. 

UPDATE checkouts SET is_active=0
 WHERE kind='edit'
   AND checkout_path IN ('…/edit-workspaces/bza',
                         '…/edit-workspaces/templedb',
                         '…/edit-workspaces/system_config');

That leaves bza 3, templedb 2, system_config 1. The remaining two are resolved by step 1 once sessions own their workspaces, and by pruning workspaces whose session has ended and whose tree has no uncommitted changes.

Indexes

CREATE UNIQUE INDEX checkouts_one_canonical ON checkouts(project_id)
  WHERE kind='canonical' AND is_active=1;
CREATE UNIQUE INDEX checkouts_one_edit_per_session ON checkouts(project_id, session_id)
  WHERE kind='edit' AND is_active=1;

The canonical index is satisfiable today — verified, 5 rows across 5 projects, zero violations. The per-session index is not enforceable yet: SQLite treats NULLs as distinct in a unique index, so every session_id IS NULL edit row slips through, and that is precisely the set which is still ambiguous. It only becomes meaningful once sessions populate the column, which is why it lands last rather than first.

Rollout

phasechangeverifiable by
0blob-age guard in _refresh_ws_row_from_disk reproduces this incident; independent of everything below
1migration: columns, path-shape backfill, retire scratch + bare legacy 50 rows deactivated; resolution unchanged
2resolve(purpose) + 5 readers; old name as shim staging picks the session tree, build picks canonical
3canonical unique index + doctor invariant for >1 adoptable edit tree index applies cleanly
4session_id populated on create; AmbiguousCheckout becomes fatal per-session index applies

Phases 0 and 1 are independently useful and carry no behavioural risk — phase 1 is pure bookkeeping, and phase 0 is the part that actually stops data loss.

Phase 0 in more detail, since it ships first

Refuse the disk overwrite when the disk content resolves to a content_blobs row older than the one the working-state row already holds. This is the same discriminator already shipped for the checkout_matches_db invariant in 5584E0DF1B9559E3, so the two agree by construction rather than by coincidence.

Do not use mtime for this. It is the obvious choice and it would not have caught this incident: project checkout writes stale content with a fresh mtime, so the stale copy looks newer than the verified write. Blob age is the signal that holds.

One open question

Step 3 above refuses when no edit tree exists. The alternative is to return the canonical tree flagged read-only, which is friendlier — but it means vcs status on such a project reports against the materialised copy, and DB-versus-checkout confusion is the root of this entire class of bug. The design as written refuses and names templedb edit <slug>. That is a judgement call, not a derivation, and it is the one decision here worth disagreeing with.

Wider point

is_active was a boolean that no code ever cleared, so it decayed into a constant while still looking like state. Every reader then layered a heuristic on top of it — newest-first here, directory-exists there — and the heuristics diverged. The same shape has now appeared three times in this codebase: project_files.lines_of_code written at import and never refreshed, project_files.status read by some queries and ignored by others, and this. A column that nothing maintains is worse than a missing column, because a missing column cannot be trusted by mistake.
