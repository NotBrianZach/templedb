VCS commit revert regression — investigation

A memory note dated 2026-08-20 says “vcs commit -p again reverts file set writes in deployed 0.7.0 binary. Use templedb commit <slug> <fresh-checkout> workflow.” I attempted four increasingly-adversarial repros against both my patched dev-mode code and the deployed 0.7.0 binary. None reverted. Content survived vcs commit in every scenario. This report characterizes the investigation, suggests possible reasons the note doesn’t currently repro, and lists what would still be worth verifying.

Repro attempts

All against a fresh scratch project regr-test. Each row is one full setup: initialize state, do file set, do vcs commit, then file get to see what landed.

Baseline: file set → vcs add → vcs commit Dev-mode (Phase 1+2) v2 v2 PASS
file set auto-staged → vcs commit Deployed 0.7.0 v3 v3 PASS

Why my hypothesis didn’t bite

Going into this I expected the failure mode to be:

  1. file set writes file_contents.is_current with new hash Hnew.
  2. WorkingStateDetector refreshes from checkout (which still has Hold), sets vcs_working_state.content_hash = H_old.
  3. vcs commit reads ws.content_hash = H_old and writes file_contents.is_current = H_old. Original write is lost.

In practice, the fourth repro was specifically designed to trigger this and didn’t. Reading the deployed vcs commit code, the actual behavior is: when vcs_working_state has a stale content_hash that doesn’t match a known blob, commit falls back to the file-on-disk read. My scratch project’s WorkingStateDetector was scanning the project repo_url path, not the checkout, so it reported “Deleted: 1” and the stale checkout content never made it into working state.

Working hypothesis, deprecated “Commit re-reads working state from the checkout filesystem rather than the DB.” Wrong. Commit reads ws.content_hash, and refresh populates that from disk only when the project has a valid repo_url pointing at real files. My scratch project had neither, so the buggy path was never exercised.

What’s still worth verifying before ruling out

  • The templedb project itself. It has a real repo_url at /home/zach/templeDB, so WorkingStateDetector actually reads files there. If a prior agent’s file set wrote content that doesn’t match the checkout, and a refresh runs, and then a commit runs — the stale checkout could theoretically win. Rerunning today with my Phase 1+2 code active, my four commits (04856C82, D29C1D0B, A6615A35, E6DCDE39, C032F453) all preserved intended content. But those all used --verify on file set, which fails loudly if the write didn’t stick — a possibly-relevant guard.
  • Non---verify writes. The memory predates the --verify flag’s widespread use. A worth-doing test: on templedb, do a file set without --verify, refresh, commit, verify. If content reverts silently there, --verify successfully guards against the bug rather than fixing it.
  • FUSE mount interaction. The memory note mentions “Use templedb commit <slug> <fresh-checkout> workflow.” That suggests the mount / checkout interaction is part of the failure surface. My repro attempts all used the editable checkout at ~/.config/templedb/checkouts/regr-test; haven’t tried the FUSE mount path. If the bug lives in the FUSE-write path, I wouldn’t see it via checkout writes.
  • Concurrent access. If two agents (or one agent and the FUSE server) both hold the DB and race a file set against a commit, isolation could fail. Not testable with a single-shell script.

Related discovery: shell-workflow session bug

While setting up the repro I found a real bug my own Phase 1+2 introduced. Sequential shell invocations (templedb vcs add X then templedb vcs commit) each create their own implicit session, because get_current_session()’s fallback creates a fresh session every process. add’s file lands in session A; commit runs in session B and doesn’t see it. The fix is straightforward — make implicit-session resolution find an existing active session for (author, host, ppid) instead of always creating — but it’s substantial enough to warrant its own scoped change.

Recorded as Phase 3.5 Real regression I ship-blocked myself with. Users can work around by export TEMPLEDB_SESSION_ID=$(templedb vcs session start --name X), but that’s not a fine default. Real fix: implicit session lookup keyed on (author, host, ppid).

Recommendation

  1. Update the memory note to soften the “regressed” language: characterize as “possible under specific conditions not currently reproducible in a controlled scratch project.” Keep the --verify guidance because it’s useful regardless of whether the underlying bug still exists.
  2. Do the templedb-live non---verify test at some point when it’s safe to do so on a real project. That’s the highest-value remaining diagnostic.
  3. Fix the shell-workflow session bug (implicit session ppid-scoping) before Phase 5 recap, or explicitly ship Phase 1+2 with a “always export TEMPLEDB_SESSION_ID” caveat in the docs. The former is preferable.
