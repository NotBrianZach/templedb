TempleDB assessment: abstractions, tooling, and a 10-day silent ingest outage

A hands-on walkthrough of TempleDB 0.7.0 across 30 tracked projects, exercising the real workflows rather than reading the code. The entity-graph and invariant layer is the strongest idea in the system and proved it by making a 10-day silent data outage recoverable in eleven seconds. Most weaknesses sit at the edges: environment discovery is Nix-store-fragile, scheduled failures never escalate, and three differently-behaved search commands share one mental model — with the project's own CLAUDE.md pointing at the wrong one. One does not: committing this report deleted it from the database and exited 0, which the postscript documents.

The headline: 151 consecutive silent failures

templedb summary showed most ingest adapters last succeeding on 2026-09-14. templedb ingest history explained why: 

✗ #827  git  v1.1  2026-09-24 17:00:50  error  +0e +0r +0x
        — no such function: crsql_internal_sync_bit

The same line, 151 times, once per hour, from 2026-09-14 15:01 through 2026-09-24. The last successful git ingest was run #670 at 2026-09-14 14:06:15. The failure reproduced interactively, so this was never a systemd-environment quirk — it was broken for every caller.

Root cause

src/sync_engine.py:143 — _find_crsqlite() probes four hardcoded Nix profile paths for crsqlite.so, then falls back to the bare name "crsqlite" and hopes the dynamic loader finds it. On this machine all four miss: 

False  ~/.local/state/nix/profiles/home-manager/home-path/lib/crsqlite.so
False  ~/.nix-profile/lib/crsqlite.so
False  /run/current-system/sw/lib/crsqlite.so
False  /nix/var/nix/profiles/default/lib/crsqlite.so

The library does exist in the store, but only in a superseded generation. The current home-manager generation (yahyl1qk8bvaa4yvw7wjsmiqrvp2m90d-home-manager-path, activated 2026-09-15) ships no crsqlite.so at all; the prior generation (2j741x3gx8f0…) did. A rebuild dropped the package and nothing noticed.

The diagnosability failure is the real bug. src/db_utils.py:83 wraps the extension load in a try/except by design — the comment reads "Fresh installs without the extension still work for non-sync writes." But every subsequent write touching a sync_* table hits a CRDT trigger that calls crsql_internal_sync_bit. So a clean, knowable startup condition ("cr-sqlite extension not found") is swallowed, then resurfaces hours later as an internal symbol name from inside a trigger. The error names a function nobody wrote and cannot act on.

What the abstractions get right

The entity graph as a commuting diagram

This is the best idea in the system. TempleDB models source tables and the derived entity graph as two paths that must agree, and doctor entities checks the square commutes. Crucially, every violation names its own repair command: 

✗ every_tool_call_has_entity  200 issue(s)
    - ToolCall#2391 not in entities table (run `templedb ingest agent`)

That property is why a ten-day outage was an eleven-second recovery rather than a forensic project. Because the graph is derived, it is rebuildable; because the invariants are named, the damage was measurable; because the errors are actionable, the repair needed no investigation. Most homegrown tooling gets none of these three. The counter-example is instructive: the one piece of state that isn't derived — the Nix store path — is exactly the piece that broke and stayed broken.

Ingest is idempotent and fast

Nine adapters, ~5,400 entities, 11.3 seconds, safely re-runnable. Cheap enough that "just rebuild it" is a legitimate first response to any graph anomaly.

The write path has been hardened

file set --verify round-tripped a file cleanly and emitted an EditIntent (#438) as a side effect — real auditability on writes. The historical "vcs commit silently reverts file set" bug documented in CLAUDE.md stayed dead under testing.

Where it's weak

1. Search is three tools wearing one name

The most consequential abstraction problem, because it makes you draw false conclusions:

CommandActually searchesStatus
graph search Xfile paths + commit messagesno content at all
graph who-uses Xfile contents, cross-projectcorrect, ~1.5s over 30 projects
search content XFTS5 indexstale / partial

apply_standard_pragmas is defined and used in four files. graph search returned a single commit message and no files — who-uses found all four. Meanwhile the FTS index is badly under-populated: search content "def" matched 39 files across a 197k-line Python corpus.

CLAUDE.md instructs: "Do NOT use grep -r or find for code search — use templedb graph search." Followed literally, that leads an agent to conclude code doesn't exist when it does. The guidance should name graph who-uses.

2. Failures never escalate

151 failed timer runs produced no notification, no email, no handoff entry — only a red timestamp inside templedb summary. The single place the system admits it is broken requires you to already suspect it is broken. For a tool whose entire value proposition is derived state staying fresh, silent staleness is the worst available failure mode.

3. The dashboard misreports broken checks as failing checks

summary says 
✗ no_expired_active_sessions   389 issue(s)
doctor says 
! no_expired_active_sessions   error: no such column: context

The invariant references a column dropped by the in-flight migrations (082_vcs_sessions.sql, 083_drop_staged_boolean.sql). It cannot run — yet summary renders a stale persisted count as a live violation. "Broken" and "failing" must be visually distinct; a check that cannot execute is an unknown, not a number. (For the record: 938 sessions exist, 50 are open, none have a TTL set.)

4. CLI surface sprawl

44 top-level subcommands with genuine overlap — commit / vcs commit / project commit, push / publish run --force, build / deploy nix build, search / graph search, and five separate health surfaces (doctor, reconcile, summary, hygiene, status). Argparse errors compound it: omitting a subcommand yields 

$ templedb search "apply_standard_pragmas"
❌ Unknown command: 'apply_standard_pragmas'

which reads as "your term was searched and not found" rather than "you omitted a subcommand."

5. The docs' own verification recipe fails

CLAUDE.md's "belt-and-suspenders SQL check" shells out to sqlite3, which is not on PATH on this machine. Every documented invocation exits 127.

Postscript: committing this report destroyed it

Everything above was written before the report was committed. Committing it surfaced two further defects — one of them the most serious in this document — so they are recorded here rather than rewritten into the sections above.

6. file set on a new path is silently discarded by commit

The report was authored with templedb reports new, written with piped file set --verify, and read back byte-identical (sha a0d37ae7…, 353 lines). Every check passed. Then: 

$ templedb vcs add -p templedb reports/2026-09-24-1442-….html reports/index.html
✓ Staged 2 file(s)

$ templedb vcs commit -p templedb -m "reports: …"
Created commit 7A3BF285566D7D87
  Files: 2                      <-- claims two

$ templedb vcs show templedb 7A3BF285 --no-diff
Changed files (1):              <-- committed one
  📝 modified reports/index.html

$ templedb file cat templedb reports/2026-09-24-1442-….html
ERROR  File not found in project 'templedb'

The commit did not merely skip the file — it deleted it from the database, and exited 0 while reporting twice the number of files it wrote.

The cause: file set on a path with no existing project_files row writes the blob and logs an EditIntent, but creates no tracking row and never mirrors the file into the edit workspace. vcs add then stages a path that exists nowhere on disk, and vcs commit reconciles staged paths against the workspace, finds it absent, and drops it. The blob survived orphaned at reference_count = 0 — intact, but eligible for the next GC.

--verify offers no protection here. It confirms the blob hash round-trips, which it does — it cannot see that the file is untracked. The only check that catches this is re-reading after the commit. Note also that this fails exclusively on new paths, and therefore fails exclusively in the CLI-first authoring workflow CLAUDE.md recommends; updates to already-tracked files are unaffected.

Mechanism, confirmed by reproduction

file set mirrors its write to ~/.config/templedb/checkouts/<slug> — but when a project is in edit mode the live tree is ~/.config/templedb/edit-workspaces/<slug>/<stamp>/, and the refresh scans that. The mirror therefore lands in a tree nobody reads, the refresh finds nothing on disk, and the commit hard-deletes the project_files row.

The explicit vcs add is a required ingredient — a bare file set plus commit survives, because the auto-stage keeps the DB-side hash. Reduced to a two-line reproduction: 

$ echo x | templedb file set templedb tmp/repro.txt   # + remove from workspace
$ templedb vcs add -p templedb tmp/repro.txt
$ templedb vcs commit -p templedb -m "..."   -->  Files: 1
$ templedb file cat templedb tmp/repro.txt   -->  ERROR: No file matches

Fixed

file set now resolves the mirror target from the active checkout record (SyncManager.get_checkout_path()) instead of the hardcoded path, and a failed mirror warns rather than logging at debug. With the fix the same sequence round-trips intact. Landed in 0633046C, together with the cr-sqlite diagnostics below. The lost report was recovered and recommitted as E10498F6.

Worth noting the near-miss: the first attempt to characterise this bug used file set without vcs add, did not reproduce, and very nearly produced a confident retraction of a real defect. The reproduction is what settled it.

7. Two parallel tables for "files in a commit"

Noticed while confirming the above: commit_files is empty for every recent commit. The first reading — a regression after #911 — was wrong, and the truth is more structural. There are two tables recording the same concept, written by different code paths: 

commit  hash       vcs_file_states  commit_files   written by
  921   534C4DFF         2               0         vcs commit
  917   E10498F6         2               0         vcs commit
  916   7A3BF285         1               0         vcs commit  (dropped a file)
  911   1c63ab50         4               4         git-history importer

vcs commit writes vcs_file_states and never touches commit_files; record_file_change() — the only writer of commit_files — is called solely from cli/commands/commit.py and importer/git_history.py. Commit #911's lowercase 40-char hash marks it as git-imported, which is why it has both. Nothing regressed; the schema simply has two homes for one fact, and which one gets filled depends on how the commit was made.

The practical hazard is that any query written against commit_files silently misses every natively-made commit, and any query against vcs_file_states misses every imported one. Note also the useful diagnostic this afforded: commit 7A3BF285 has exactly one vcs_file_states row, independently confirming the dropped file.

8. Generator output reverts on commit

A third instance of the same underlying split: templedb reports reindex reads and writes the database, while vcs commit reconciles from the workspace. Running reindex then committing silently reverted index.html to its pre-reindex state. The regenerated file must be copied into the workspace before staging.

All three defects are the same architectural fault: the database and the edit workspace are two sources of truth, and different commands trust different ones. file set, reports reindex and file cat speak to the DB; vcs commit and vcs status --refresh speak to the workspace. Wherever a write path and the commit path disagree about which is authoritative, data is lost silently and the CLI reports success.

Recommendations

  • [critical] Make file set on a new path create the project_files row and mirror to the workspace — or make vcs add refuse a path with no workspace presence. Today the sequence write → add → commit discards the file and reports success.
  • [critical] Find why commit_files stopped populating after #911 and backfill what is reconstructable.
  • [high] Resolve crsqlite.so from the current home-manager generation (realpath the live profile) rather than a hardcoded candidate list — or restore it to programs.templedb.extraPackages.
  • [high] Fail loudly at startup when the extension is missing. The swallow-and-defer pattern converted a one-line startup diagnostic into ten days of silence.
  • [high] Alert on ingest timer failure — email via agent_notifications, or a handoff entry after N consecutive errors.
  • [medium] Fix the no_expired_active_sessions invariant and render errored checks as ! in summary, never as a count.
  • [medium] Collapse the three search paths into one command with documented semantics; rebuild the FTS index; correct the CLAUDE.md guidance.
  • [low] Replace the catch-all argparse error with a missing-subcommand message, and drop sqlite3 from CLAUDE.md in favour of a templedb-native check.

Verdict

The core is sound and the central bet — model everything as entities, derive aggressively, verify with named invariants — is paying off. It turned a serious outage into a footnote, and that is not a small thing.

One class of gap is that this rigor stops at the process boundary. Inside the database, state is derived, checked, and repairable. Outside it — Nix store paths, systemd timers, the FTS index, the docs — state is assumed, unchecked, and silently wrong. Those defects need no data-model change; they need the same invariant discipline extended outward to the system's own dependencies.

The postscript is a harder problem, and it revises the assessment above. The database and the edit workspace are two sources of truth, and the write commands and the commit command trust different ones. That is not an edge; it sits directly under the primary authoring path, and its failure mode is the worst available — silent deletion reported as success. An entity graph that can prove its own consistency is of limited comfort when the layer beneath it can drop a file and exit 0.

The recommendation that follows from a day's use is therefore narrower than "extend the invariants outward": point the invariant machinery at the write path first. The tooling already knows how to detect drift between two representations and name the repair — doctor entities does exactly this for the graph. The same check does not yet exist for the pair that matters most, DB versus workspace. It should, and it would have caught all three postscript defects before they reached a commit.

Assessed 2026-09-24 against TempleDB 0.7.0, 30 projects, 32k entities. The ingest all run described above was executed during assessment and wrote ~5,400 entities to the live database — additive repair explicitly prescribed by the doctor output, but a mutation nonetheless.
