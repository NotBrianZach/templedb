Project initialization and per-machine tracking

Companion to the proposed schema map. Once FUSE is retired and git is authoritative for source bytes, “initializing a project into TempleDB” and “bootstrapping TempleDB on a new machine” both change shape. This report specifies the initialization surface (import, attach, ingest), the per-machine vs cross-machine split of what gets tracked, and takes a position on the three open design questions from yesterday’s discussion: canonical-remote model, project identity across forks, and per-machine ingestion cadence.

Framing: what “initialize” means under the observer model

Under the DB-as-truth model, importing a project meant “copy every file into content_blobs, materialize a checkout on demand.” The DB was the master; the filesystem was a projection.

Under the observer model the vocabulary inverts. Git holds the bytes. Import means:

  1. Register the project as an entity (kind Project) with a canonical git URL, an identity key, and metadata.
  2. Attach a checkout on the current machine if there is one, recording its path in project_checkouts.
  3. Ingest observations via the git adapter: walk commits, populate Commit/FileSnapshot/Symbol entities with source_authority='git', observed_at=now, observed_by=<machine>.

None of these copies bytes into the DB as authoritative content. content_blobs may hold cached bytes (for cross-project queries and offline reads), but git is the truth — if a hash cache-misses, we fetch from git.

The three CLI verbs

templedb project import <git-url>         # register + clone canonical + attach + ingest
templedb project import <local-path>      # register from existing local git repo + attach + ingest
templedb project attach <slug> <path>     # this machine now has a checkout at path
templedb project detach <slug> [--path]   # this machine no longer tracks that checkout
templedb ingest git <slug>                # re-run observation from this machine's checkout

project import <git-url>

New project, no local checkout yet. Steps:

  1. Compute an identity key: hash of the initial-commit sha (see § project identity below).
  2. Upsert a Project entity with external_ref = <identity-key>, attributes_json.canonical_url = <git-url>.
  3. Clone to a default location (~/.config/templedb/checkouts/<slug> by convention, overridable by --to).
  4. Register the clone in project_checkouts (project_id, machine_id, path, current_branch).
  5. Run templedb ingest git <slug>: emit Commit, FileSnapshot, contains, parent-of observations for the full history (or --depth N).

project import <local-path>

The path already contains a git repo; TempleDB attaches to it instead of cloning. Steps 1–5 as above, minus the clone step. Uses git remote get-url origin to fill in canonical_url if a remote exists; otherwise canonical_url = null and the project is machine-local until a remote is added.

project attach <slug> <path>

Project already known to the DB (synced from another machine); this machine wants a checkout. Steps:

  1. Look up the Project entity.
  2. If path doesn’t exist and canonical_url is set, clone there.
  3. If path exists as a git repo, verify its git remote get-url origin matches canonical_url (warn on mismatch).
  4. Upsert into project_checkouts for this machine.
  5. Run templedb ingest git <slug>.

ingest git <slug>

Idempotent re-scan of this machine’s checkout. Walks commits since last_scanned_at (or all commits with --full), upserts Commit/FileSnapshot/relations, updates project_checkouts.last_scanned_at and project_checkouts.current_branch, appends a row to ingestion_runs with the count of facts emitted.

Per-machine vs cross-machine: the split

Cross-machine facts are synced via CRSql. Per-machine facts stay local and describe this-machine’s view of the world. Every ingested fact carries observed_by=<machine_id> to make the split queryable.

The design principle Anything that describes the project is shared. Anything that describes this machine’s current view of the project is local. Observation metadata is shared-row-with-per-machine-tag. This is the same split Kubernetes uses for cluster-vs-node facts, and the same split Terraform uses for shared-state-vs-local-plan.

Schema addition: project_checkouts

CREATE TABLE project_checkouts (
    id              INTEGER PRIMARY KEY,
    project_id      INTEGER NOT NULL REFERENCES projects(id) ON DELETE CASCADE,
    machine_id      INTEGER NOT NULL REFERENCES fleet_machines(id),
    path            TEXT NOT NULL,
    current_branch  TEXT,
    current_commit  TEXT,             -- last-observed HEAD
    is_writable     BOOLEAN DEFAULT 1,
    is_bare         BOOLEAN DEFAULT 0,  -- true for the canonical mirror
    last_scanned_at TEXT,
    created_at      TEXT NOT NULL DEFAULT (datetime('now')),
    UNIQUE(machine_id, path)
);
CREATE INDEX project_checkouts_project ON project_checkouts(project_id);

A stub table already exists in the current schema (checkouts + checkout_snapshots) that predates the fleet-machines shape; the proposal is to migrate that data into project_checkouts with a machine_id column so it’s addressable in the new topology.

Open question 1: canonical-remote model

Options

A. Hub-mirrored. One machine (or a designated TempleDB server) hosts a bare mirror at ~/.config/templedb/git/<slug>.git. All other machines’ checkouts have that as an additional remote (or the primary origin). TempleDB’s ingestion adapter walks the hub mirror as the authoritative commit history.

B. Federated. No hub. Each machine has its own origin pointing at whatever git remote it uses (GitHub, self-hosted forge, etc.). canonical_url on the Project entity is a convention, not enforced. Ingestion walks each machine’s local checkout independently.

C. Hybrid. canonical_url points at the actual public remote (GitHub / forge). Each machine may optionally maintain a local bare mirror as a fetch cache. Ingestion prefers the local mirror if present, falls back to the checkout’s history.

Recommendation: C (hybrid)

Reasoning:

  • A hub makes provenance neat (“which commit was ingested” has one answer) but adds an availability concern: if the hub is offline, all other machines are stale. Also creates a bootstrap chicken-and-egg (a fresh machine needs the hub to know about the hub).
  • Pure federation is what most projects already are (GitHub is the hub). No new machinery needed, but ingestion runs may see slightly different histories on machines that haven’t fetched recently.
  • The hybrid keeps GitHub / forge as the real canonical remote (matches how the world already works), lets us cache locally for speed and offline queries, and doesn’t require a hub role. Provenance still resolves because observed_by + observed_at tags each observation.

templedb project mirror <slug> is an optional command that creates the local bare mirror; without it, ingestion walks the working-tree’s git history directly.

Open question 2: project identity across forks

The question

Machine A has origin = git@github.com:foo/templedb.git. Machine B has origin = git@my-fork:bar/templedb.git (a personal fork). Both are on branch main, both share the same initial commit. Are they one Project entity or two?

Options

A. Same entity if shared initial commit. Identity key = hash of the initial commit sha. Forks and mirrors of the same repo collapse into one Project. Simple, correct for the common case.

B. Distinct entities per canonical URL. If the URLs differ, the projects differ. Explicit, but wrong for the “my fork of upstream” case where they should reference the same thing.

C. User-declared identity. Every project has a stable project_id the user picks; forks share it if the user says so. Most flexible, but pushes complexity onto the user.

Recommendation: A with an override

Default identity = SHA-256 of the initial commit hash. Two checkouts with the same initial commit are the same project. This handles forks, mirrors, and re-clones correctly. Users can override with --identity <key> at import time for the edge cases (e.g. two projects that happened to start from the same commit but are unrelated).

Rationale: git already uses initial-commit as the closest thing to canonical repo identity. Anything more clever (canonical URL matching, remote name comparison) breaks on renames and forks. Anything less clever (arbitrary user id) creates duplication.

What about a rewritten history?

If someone force-pushes a new initial commit (rare but possible — git-filter-repo, rebase-of-root), the identity changes. This is technically a “new project” from TempleDB’s perspective. Reasonable behavior: warn on ingest, offer a project migrate-identity <old> <new> command to reconcile. Rare enough to not need automation.

Open question 3: per-machine ingestion cadence

The question

Different adapters have wildly different costs. Git is cheap (a diff since last_scanned_at). SSH probes are expensive (network round-trip per machine). SCIP indexing is expensive per language. When does each adapter run?

Adapter-by-adapter recommendation

AdapterCostCadenceTrigger
git (this machine)cheapon-demand + on-committempledb ingest git, git post-commit hook, or filesystem watcher (inotify)
SCIP (per language)expensiveon-push + nightlygit push hook, cron; skipped by default on local edits
SSH probe (per host)expensive (network)manual + on-deploytempledb doctor entities --host X, deploy pipeline hook
Nix store scan (this machine)moderateon-generation-changeNixOS activation hook, or manual templedb ingest nix

Report authoringzero (native)on writereports new / reports reindex

Design principle: each adapter carries its own freshness policy in attributes_json on its ingestion_runs row. templedb doctor entities uses that policy to decide whether a fact is stale enough to warrant a re-scan. Cheap adapters can be run eagerly; expensive ones defer to explicit triggers.

Freshness telemetry

Every entity carries observed_at. Every relation carries observed_at. A single query answers “how fresh is our view of this machine?”:

SELECT machine, MAX(observed_at) AS last_observation, adapter
FROM (
  SELECT e.attributes_json->>'machine' AS machine,
         e.observed_at,
         e.source_authority AS adapter
  FROM entities e WHERE e.kind = 'Generation'
)
GROUP BY machine, adapter;

Under the observer model, staleness stops being a mystery. Any user or agent can ask “is this fact still authoritative?” and get a timestamp answer.

Bootstrap flow on a new machine

Puts the pieces together. Fresh Linux install; user wants their TempleDB world available.

  1. Install templedb. Nix, or via a bootstrap script that fetches the tarball. Same as today.
  2. Sync the DB. templedb bootstrap --from <peer-host> pulls a WAL-checkpointed copy of another machine’s templedb.sqlite via SSH. All shared entities (projects, commits, symbols, decisions) arrive instantly.
  3. Register this machine. Auto-insert into fleet_machines with hostname / arch. Assign machine_id.
  4. Attach projects incrementally. templedb project attach <slug> per project you want a local checkout for. Clones from canonical_url, registers in project_checkouts, kicks off git ingestion tagged with this machine’s observed_by.
  5. Restore per-machine state. If the source machine had nix_generations or SSH-probe observations for this new host (unlikely; usually not), they’re already synced. Otherwise the first templedb doctor entities populates them.

Total time to productive: minutes for the DB sync, plus one project attach per project you want. No FUSE, no materialize, no scaffolded working trees TempleDB has to keep in sync — the user has normal git checkouts.

Interaction with EditIntent and the agent write path

EditIntents (Phase 2) are session-scoped and machine-scoped by construction: the vcs_sessions row carries the machine (via ppid resolution today, explicit machine_id under the new model). An intent created on machine A cannot accidentally apply on machine B because apply needs a checkout path from project_checkouts, and only this-machine’s checkouts are addressable locally.

When intents are synced across machines (Phase 3+), an intent from machine A becomes visible on machine B but not automatically applied. The user or agent on B can templedb intent apply <id> to apply it to their own checkout. This is exactly the shape you want for multi-machine collaborative refactor.

Risks and things still to decide

Machine identity is currently loose fleet_machines rows exist per host but the machine_id a session picks up is derived from hostname / SSH probe. If two machines have colliding hostnames (VMs, dev containers), observations get cross-attributed. Need a stable machine key beyond hostname — possibly the machine-id from /etc/machine-id, or a UUID generated at bootstrap.
Migrating existing projects to the new identity scheme Every existing project needs its initial-commit hash computed and stored as external_ref. Not hard, but the migration must run on a machine that has each project’s git checkout attached (otherwise there’s no way to compute the hash). Consider making it lazy: Project.external_ref starts NULL, gets populated on first ingest git after Phase 3 lands.
Ingestion determinism vs performance If two machines run ingest git against the same commit, they should produce the same entities (idempotent upsert). But if one is running an older TempleDB with a different parser, they emit different symbol facts. Version the ingestion algebra explicitly on ingestion_runs.adapter_version so drift between machines is visible.
What happens to today's ~/temple/templedb/ mount Users have muscle memory for that path. The observer/integrator plan retires FUSE in Phase 5, but before then the mount coexists. Recommend: at Phase 1, add a soft warning banner in the FUSE mount’s directory listing (via a synthetic README.md) explaining the retirement and pointing at templedb edit. No hard break until Phase 5.

Summary

Under the observer model, initializing a project is three verbs: import (register + attach + ingest), attach (this-machine gets a checkout), ingest (re-observe). Per-machine tracking layers on top of a shared entity graph: the project is one entity everyone sees; the checkout is a per-machine row; observations carry observed_by and observed_at tags. Canonical remote is whatever the world already treats as canonical (GitHub, forge), with an optional local bare mirror as a fetch cache. Project identity keys on initial-commit hash. Ingestion cadence is per-adapter and captured in ingestion_runs so freshness is queryable, not mysterious.

Everything above is a Phase 1 or Phase 3 deliverable in the existing plan; nothing here is on the critical path for the immediate acute-pain work in Phase 0. The three open questions (canonical-remote model, identity across forks, ingestion cadence) now have named recommendations to disagree with rather than aspirational hand-waves.
