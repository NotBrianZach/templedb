The Emacs agent interface — one buffer, owned sections, and a database that outlives the render

A design-philosophy pass over integrations/emacs/templedb-agent.el, written the same day the multi-pane layout was removed from it. The interface rests on three commitments: a session is exactly one Org buffer, every section of that buffer has exactly one owner, and the buffer is a view whose authority lives in SQLite. Usage data across 104 real sessions says two of the three are carrying the design and the third is mostly unused — and that the most-praised feature in the docs has never once been touched by a human.

Why this report exists

Prompted by removing something. templedb-agent-layout (C-c C-3) showed a session as three windows — state in a sidebar, conversation top right, Next Prompt underneath — built from indirect buffers each narrowed to a span of the base. It was clever and it worked. It is now deleted, along with templedb-open-layout in the spacemacs layer, which did the analogous thing one level up: a T:<slug> perspective holding VCS status, a dired pane and a vterm.

Deleting two features in one afternoon is a good moment to ask what the interface is actually for, because the answer is what makes one removal obvious and another a mistake. There is already a reference document — docs/TEMPLE_AGENT_EMACS.md — that says what each moving part does. This is the other half: what the parts are for, which of them earn their keep, and how to work with the thing.

The thesis: the buffer is a view

The single most load-bearing sentence in the client is a comment on its rendering: Emacs holds no authoritative state. The buffer is rebuilt from the database on , g. Everything the interface does follows from taking that seriously.

That is a stronger claim than it sounds. It means the Org document is not a transcript that happens to be saved — it is a projection, and the session is the rows. A terminal-based agent client has the opposite property: the scrollback is the session, and when it is gone the session is gone. Here you can kill the buffer mid-run, restart Emacs, reopen by id, and the conversation reassembles from agent_events — 37,399 of them across 1,209 runs at the time of writing.

Three consequences fall out, and they are the whole design:

  • Other readers are free. The same rows render as web pages (src/gui_pages/agent_{sections,sessions,work_log}.py), as CLI output (templedb ai agent fleet --json), and as the roster triage buffer. None of them is a second implementation of the session; they are second queries.
  • The agent can write into your document. If the buffer were the truth, a tool running in a sibling process could not touch it. Because the truth is a table, it can — see the MCP bridge.
  • Render code is disposable. Which is exactly why the pane layout could go without a migration, a deprecation window or a single lost byte of anyone's session.

Commitment 1 — a session is one buffer

This was the implicit default for most of the client's life and became an explicit rule today. The case against panes is instructive, because none of it is about taste.

An indirect buffer shares the base's text and its text properties, which is why panes were attractive: the section anchors, the ewoc's in-place rendering and the save path all kept working untouched. What it does not share is narrowing, point, window and buffer-read-only — precisely the list a pane needs to differ on. The design was correct. The cost was that it created a second rendering contract that every write had to honour:

ObligationImposed on
Re-narrow every pane, because a narrowing's bounds move when text inside them changes sizeevery section re-render, every agent event, every new exchange
Repair every pane's restriction, which a full erase collapses to nothing--render-buffer
Accept that the fresh-write highlight is invisible — overlays are the one thing indirect buffers do not shareevery agent-owned section write
Maintain a parallel keymap of view-* wrappers that re-enter the base; the , major-mode leader did not work in a pane at allevery binding
Rename the session's panes, including ones orphaned when re-running the major mode wiped the alist that tracked themevery retitle

Five ongoing obligations, paid on every write, so that a window could be split in a way C-x 3 already splits it. The removal was −549 lines in the client and −286 in its test file. The one capability panes had that plain windows do not — "put point where I actually type" — survived as templedb-agent-focus-prompt on C-c C-n, which is 10 lines.

The principle, stated generally. A feature that adds an invariant every unrelated write must maintain is not priced at its own line count. It is priced at the sum of all the places that now have to remember it. The pane layout cost about 460 lines to have and five standing obligations to keep, and only the first number was visible when it was written.

Commitment 2 — every section has exactly one owner

The Org document is not a chat log with extra headings. It is eleven fixed sections in a fixed order, and the order encodes who may write where. templedb-agent--section-order:

Two details make the ownership real rather than documentary.

Anchors, not regexes. Sections are located by text properties. The old --section-heading-regex survives only for legacy callers and is marked deprecated, because regex matching breaks the first time a tool result contains a line starting with * — which, in a tool that reads Org files and shell output, is immediately.

A one-way persistence firewall. templedb-agent-save-user-sections is the only path that writes user sections back to the DB. It fires on C-c C-s, on 3 seconds of idle with the buffer modified, and on kill-buffer-hook — and deliberately not from run-completion handlers. That coupling used to exist, and on 2026-08-28 a rendering bug let it persist tool-bucket garbage into the user's Scratch. The fix was both to decouple it and to add --scratch-is-polluted-p, which refuses to save Scratch text containing :TOOL_ID: or **** RUNNING/DONE/FAILED and says so. Note the asymmetry: user sections are saved by an explicit guarded path; agent sections are written by the agent's own tools and read back as rows. Neither side's writer can reach the other's storage.

Commitment 3 — the agent writes into your document mid-run

This is the part of the design that is genuinely surprising, and it is the thing a terminal cannot do at all.

When Claude calls templedb_agent_note_finding, that tool executes in the MCP server process, which is a child of the claude subprocess — not in AgentService. It has no access to the event callback that would push a line to Emacs. The bridge is a table:

MCP tool handler  ──writes row──▶  agent_pending_events   (one-way)
                                   agent_pending_asks     (round-trip)
                                            │
AgentService._ask_poll_loop ──polls 300ms───┘
                                            │
                                     re-emits as events ──▶ Emacs

One poll loop serves both transports per session, marking rows dispatched so they fire once. The directions differ: pending events are fire-and-forget (a finding, a todo), while pending asks are a round trip — templedb_ask_user blocks until a human answers, and the answer travels back by ask_id.

Because the ask polls its own row, the answer only has to land in the table. It does not have to come back through the session that asked. That single fact is why you can answer a question from the roster without opening the session, or from any shell with templedb ai agent ask respond. It is also why a stale ai agent serve process is actively harmful rather than merely idle: two pollers race the same rows.

What the data says about which parts earn their keep

Three readings, in increasing order of how much they should change what gets built next.

The agent-writes-your-document bet paid off. 961 findings and 631 todos, in roughly 70% of all real sessions, is not a feature being politely tolerated. It is the main thing the interface does that a terminal does not, and it is used accordingly. The [F:n T:n Q:n] modeline badge is the quiet companion win — you can see that seven findings have accumulated without unfolding anything.

Goal is the sleeper. 63% adoption for a section whose entire mechanism is "this text is re-sent with every message." It is the cheapest anti-drift device in the system and it competes with nothing.

Notes and Scratch have never been used once. Zero of 104 real sessions. The reference doc describes Notes as persisted-to-DB and Scratch as "genuinely local", both in the tone of features. They are, in practice, two headings that exist to be scrolled past — and they cost more than nothing: they are half the surface of the persistence firewall, the reason --scratch-is-polluted-p exists, and the subject of the one data-loss incident the save path has had (2026-08-28). A feature with no users and a dedicated guard against its own failure mode is a feature worth retiring.

dynamic:* is the interesting near-miss: 8 entries across 6 distinct names, including a dynamic:Next Prompt and a dynamic:Suggested Next Prompts that are plainly an agent reaching for a section that already exists. Arbitrary agent-named sections are more generality than the problem needed.

Suggested workflows

Keyed to what the data says actually works, rather than to the full feature surface.

The default loop: Goal, then let findings accumulate

SPC a T A n → , x a to add the project → write the standing constraints into Goal → ask the question in Next Prompt → C-c C-c.

The thing to internalise is that Goal is re-sent every message, so it is where "don't touch the migrations", "this is a read-only investigation" or "the acceptance test is X" belongs. Putting that in a message instead means it decays with distance. Then let the agent file findings as it goes rather than asking for a summary at the end: a finding written at the moment of discovery survives buffer refresh, /compact, and you closing the buffer, because it is a row.

Steering without cancelling — and what it actually does

, i (templedb-agent-guide) is the chord worth memorising: it gets a correction to the agent without cancelling and re-prompting, which is what a terminal client forces. It is the difference between watching an agent go the wrong direction for four minutes and redirecting it in ten seconds.

The mechanism is worth stating precisely, because the reference doc calls it "mid-run steering" and that is slightly generous. There are two different send paths:

C-c C-c (send), i (guide)
While idlemessage.send + full context payloadmessage.send, content only
While a run is activeswitches to message.queue — drained when the turn endsstill message.send, immediately
Carries Goal and the context basketyesno

So guide does not interleave text into the turn in flight. send_message creates a new run, and because the provider passes --resume <external_session_id>, that run continues the same Claude conversation. Your guidance therefore reaches the right thread without losing the run — which is the useful property — but as another turn rather than an injection. Two practical consequences: guidance does not re-send your Goal, so it should be self-contained; and it is the one path that can put two runs on one session (see open questions).

Long investigations: hand off to yourself

Work the problem, let Findings and Open Questions fill, then walk away. Coming back, , s s into the session rebuilds the buffer from stored events and the open-question count tells you where you stopped. For anything genuinely durable, promote the findings into a report in reports/ — the session is a view, but it is not a document, and nobody greps 37,000 event rows for a conclusion.

Fleet work: triage from the roster, not the buffer list

SPC a T A l buckets every session by who is blocked — NEEDS INPUT, WORKING, NEEDS ATTENTION, DONE · your turn, IDLE — and auto-refreshes while on screen. Use a to answer a live question inline and c to reply without leaving it. C opens an overseer session seeded with a fleet snapshot: chat about the agents rather than with one. Press ? rather than memorising keys — the guide is generated with substitute-command-keys against the live keymaps, so it prints your config's actual bindings, which matters because evil's motion state steals six of the plain ones.

Read-only reconnaissance is a deliberate act

Permission mode defaults to bypassPermissions. , P (plan mode) is therefore a narrowing, not a default you can forget to turn off. Use it before pointing an agent at anything you do not want edited.

Walk away, but arm the alerts

The event stream only reaches whoever launched the run, so a finished run in a hidden buffer gets an echo-area message that the next message erases. The durable channel is on disk: six event types drop a pre-rendered JSON file into ~/.local/share/templedb/alerts, and templedb-agent-alerts-mode turns each into a desktop notification. Enable it from your init file rather than letting it self-start on first agent buffer, or you miss everything that finished before you opened one.

The last row generalises into the most repeated lesson in this codebase: order of operations across two subsystems is a design decision, not an implementation detail. Session-before-edit, write-then-rename for alert files, enter-the-layout-before-creating-the-buffer — same shape three times.

The philosophy, stated as rules

  1. The database is the session; the buffer is a query. Anything that makes the render authoritative is a regression, however convenient.
  2. One session, one buffer. Splitting is the window manager's job. A view layer inside the application has to be maintained by every writer in the application.
  3. Every region of the document has exactly one owner. Shared-write regions are where corruption lives. The ewoc owns Conversation outright and the source says so in a warning.
  4. Price a feature at the invariants it imposes, not the lines it adds. The pane layout's five standing obligations were the real cost and were invisible at authoring time.
  5. Cross-process writes go through a table, never a callback. It is why the agent can annotate your document mid-run and why an ask is answerable from anywhere.
  6. Degrade, never block. Every persp call is wrapped and falls back to a message; alert writes never raise into the event path; the provider abstraction has a fake so the stack is testable without tokens. A convenience must never be able to stop a session opening.
  7. One list, many readers. --fleet-tools is rendered for the human in the guide window and handed to the overseer agent in its brief, so the two cannot drift into different accounts of how to manage a fleet. Same instinct as bucket rules living in store.classify_fleet_row and being consumed by CLI, Emacs and GUI alike.
  8. Generality is a cost until it has users. dynamic:* at 5% adoption, and Notes/ Scratch at 0%, are the standing counter-examples to rules 2–7 being followed everywhere.

What I would change next

In rough order of value over effort.

  • Retire Notes and Scratch. Zero real users, two of the eleven fixed sections, half the persistence firewall's surface, and the site of its only data-loss incident. The rows (agent_session_notes.notes_org, scratch_org) can stay; the headings do not need to. Goal keeps the one part of that table that is used.
  • Collapse dynamic:* into something narrower. The observed uses are an agent reaching for "suggested next prompts" and "discoveries" — both of which want to be first-class sections or nothing. Arbitrary names bought flexibility nobody spent.
  • Decide what templedb-agent-perspectives is for. It defaults to project and is live here (persp-mode is on), so every session buffer is claimed by an @<project> layout and the frame follows it there. That is a different axis from the pane layout — it is about which frame-level buffer set the one buffer belongs to, not about splitting it — and the removal half (taking the buffer out of every other layout) is the part that earns its keep. The switch half (templedb-agent-perspective-switch, default t) is the part that rearranges your frame without being asked.
  • Add a doctor check for the deployed-vs-DB gap. The client is nix-store-backed: ~/.emacs.d/private/local-layers/templedb is a symlink into /nix/store, assembled from both system_config (layer scaffolding, leader keys) and templedb (the agent client itself). A committed change to templedb-agent.el is inert in the running Emacs until a home-rebuild or an explicit load-file — as of this writing the live layer is still the 5,453-line pre-removal build, panes and all. Nothing warns about that.

Open questions

Things this pass surfaced but did not settle. Each is a real question about the code, not a rhetorical one.

  • Can , i start a concurrent run? templedb-agent-send checks --status and switches to message.queue while a run is active; templedb-agent-guide has no such check and calls message.send unconditionally. Server-side, send_message creates a run and overwrites self._active_run[session_id]. Whether anything upstream refuses the second run, or whether two runs genuinely stream into one session, I did not verify. If it is unguarded, the fix is the same status check send already does — but the point of guide is immediacy, so queueing it would defeat it, and the right answer is probably a provider-level injection path that does not exist yet.
  • Should guide carry Goal? It currently sends content only. Given Goal's whole purpose is surviving distance, omitting it from the one message you send because the agent drifted is at least ironic.
  • Is the 600s ask deadline the right number? The record is 58 responded, 16 expired, 8 pending out of 82. A 20% expiry rate on questions the agent considered blocking is either a human-latency problem or a deadline problem, and the data does not distinguish them.
