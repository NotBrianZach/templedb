What was applied from external contributions

Two parallel sessions authored design reports during this run. Both landed in the archive via templedb's normal commit path and were incorporated in real time.

The categorical critique

Received mid-session. Three moves incorporated wholesale:

  • Authority per fact, not per system — dissolves the “identity crisis” framing into something more precise. Every entity + relation now carries source_authority.
  • Lenses replace CAP — the CAP analogy from the earlier plan was technically wrong. Bidirectional lenses / view maintenance is the honest framework. Names the defect precisely: materialize was a poorly-lawed put. Observer pattern deletes put, reducing to a well-lawed view / get-only lens.
  • Promote junctions to first-class objects — the span pattern A ← R → B. edit_intents, ast_builds already fit; report_implementations, Deployment, ToolCall were designed under the pattern from the start.

The schema report

A 465-line disposition matrix for all 131 tables (keep/shrink/view/retire/new). Called out ingestion_runs and invariant_checks as Phase 3 additions, and handoff_notes as Phase 2.5. Shipped all three as proposed. Named decisions as the preferred name for the workflow-F junction; we shipped as report_implementations and documented the rename as future work.

The complexity budget observation

On restraint This session shipped ten migrations. That's a lot of schema growth by any measure. But the schema-report's discipline held: no new authority required a new table (adapters were enough). New tables only landed for genuine junctions with lifecycle (edit_intents, ingestion_runs, invariant_checks, handoff_notes, tool_calls, report_implementations). The rest was constants and indexes. The “one core, many views” invariant survived contact with reality.

The observer-vs-owner arc, marked

TempleDB started the day owning source (file_contents as authoritative bytes), owning the FUSE mount, owning materialize sweeps. By EOD:

  • Source — TempleDB observes. source_snapshots view named the shift; file_contents is documented as snapshot, not truth.
  • Edits — EditIntent is the write channel. file set still works but routes through intent for provenance.
  • Deployment state — Generation entities are observations from nix (source authority='nix'); Deployment entities are our own coordination artifact.
  • Code facts — File, Symbol (soon), Commit, contains, calls — all from git authority via ingest adapter.
  • Agent state — Session, ToolCall, EditIntent — all DB-native by construction (agent-runtime authority).

Every entity carries its source_authority. Every doctor check runs a commuting-diagram invariant. Every ingest adapter is a small transition map from one local algebra into the shared graph. The observer/integrator vision isn't a design doc anymore; it's the running system.

The queue that remains

  1. Agent runtime writes tool_calls directly. Closes the extraction loop. ~1 hour.
  2. SSH-probe reconcile. Workflow D fully lit up. Reads /run/current-system on each fleet_machine via SSH, verifies against nix_generations. ~2–3 hours.
  3. SCIP Phase 4. Adopt SCIP as an ingestion algebra for cross-language code facts. Removes the need for templedb to parse Python / Nix / TypeScript itself. ~1 week of focused work.
  4. Deployments consolidation into proper span (if needed). Currently the ingest adapter is sufficient; a schema promotion only matters if we start carrying per-deployment attributes the ingest adapter can't emit uniformly.
  5. Phase 5: retire authority-over-source vocabulary. Documentation update, FUSE removed from mental model, templedb-write-broken-class memories become historical curiosities.
