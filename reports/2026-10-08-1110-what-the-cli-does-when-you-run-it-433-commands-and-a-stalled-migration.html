What the CLI does when you run it

A command-by-command pass over all 433 leaf commands, 2026-10-08, plus an attempt to finish the AST config migration. Companion to the morning's surface report, which measured the CLI's shape; this one runs it. Eight commands are broken and every one of them passes --help cleanly, which is the whole argument for executing rather than reading. The migration attempt ends in a verdict rather than a completion, for a reason worth more than the completion would have been: a generated file became the place where declarations were made, so the generator can no longer be run. Detail lives in CLI_COMMAND_AUDIT.md and CLI_SEMANTICS.md; this is the narrative and the verdicts.

2. Why execution, not documentation

--help proves a command is registered. It says nothing about whether the handler works. Every finding in section 3 renders a clean help string and then fails on invocation, so a documentation pass — however careful — would have found none of them.

Each safely-runnable command was therefore executed against the deployed binary with dev mode unset, and its exit code and stderr recorded. 130 commands were skipped for carrying a destructive verb (deploy, rm, gc, switch, push); 166 need an argument that is not a project slug.

The 296 unexecuted commands are not cleared. A command absent from the broken list has either passed or not been tried. This is the honest limit of the pass and the reason section 6 argues for a smoke-test suite rather than another audit.

3. Eight broken commands, five root causes

NameError ts_info — 3 commands

network.py reads ts_info at lines 95, 138 and 178 and never assigns it: four uses, zero assignments. The name is a copy-paste remnant from sync.py:88, where ts_info = probe_peer(peer["ip"]) does exist.

commandfails when
sync network status≥1 online peer — prints its header, then raises
sync network setup≥1 online peer, inside the if online > 0 branch
sync network sync-allimmediately, on the first peer

sync-all is the one that matters: for peer in peers: if not ts_info: raises before any sync is attempted, so the command whose entire purpose is syncing peers has never been able to do it. Only sync network connect escapes.

Stale table names — 2 commands and one silent lie

Two code paths query tables that do not exist, and the columns differ too, so this is not a rename a search-and-replace could fix:

queriedactual tablecolumn drift
nixos_packagesnixos_managed_packagesproject_slug→project_id, name→package_name, scope→install_scope
nix_servicesnix_service_metadataopens_port→opens_ports

nixos packages list and its alias fail outright. The worse case is templedb validate, which reports PASS and exits 0 while logging no such table: nix_services to stderr. A validator passing while one of its own checks errored is worse than a crash: the crash would have been noticed in August.

Two AttributeErrors

  • nixos system status and its alias — 'SystemService' object has no attribute 'get_system_status'. Python prints the fix in the error: Did you mean get_system_config?
  • admin cache list — 'DeploymentCacheService' object has no attribute 'db_utils': a module reached for as an instance attribute.

Slow, not broken

graph overview (42s) and sync status (31s) both exit 0. Both exceed the ~20s an agent tool call allows, so they present as hangs. graph overview is pure local query work, which makes it a performance defect rather than an unavoidable cost.

4. The biggest blind spot is deploy

73 commands — the largest noun — with zero executed coverage, because every leaf mutates or needs live infrastructure. It is also where this session found the bug that made successful deploys report failure: RelatedCommands.AFTER_DEPLOY_RUN ran after a completed deploy, the enclosing except Exception logged Deployment failed: … and returned 1, so anything gating on exit status saw every deploy as broken.

That combination — largest noun, zero coverage, a latent exit-code lie — is the CLI's main risk concentration. The fix is structural: if every deploy leaf honoured --dry-run as a guaranteed no-side-effect path, the sweep above would extend to it. Four of the nine sub-domains already have one.

5. The config models, and a correction

The morning's semantics pass claimed config-ast was the successor to nixos config, reasoning from the existence of config-ast seed ("Seed config_nodes from existing system_config keys"). Measuring inverted it:

nixos status reads system_config and reports the live rebuild. seed is the bridge that was built, not evidence the migration completed — and the timestamps show it did not. Published before checking, which would have led a reader to deprecate the live system.

The practical hazard is sharper than "two models": 21 commands are presented as current while writing to a dormant store. config-ast set succeeds, changes config_nodes, and has no effect on the machine. Both groups now carry INCOMPLETE MIGRATION in their help.

6. The migration cannot complete as conceived

Attempted, and the failure is instructive.

Two AST builds were promoted, 2026-08-02 and 08-04 — which is why configuration.nix:2 reads # Generated by TempleDB configuration compiler. Since then 162 lines were hand-added to that generated file, and config_nodes was never updated.

A derived file became the place where declarations were made. That is the same boundary error as file set reverting work, a stale workspace reading as committable, and a home-manager profile evicted at boot — here applied to the project's own config pipeline, and it is why the generator can no longer be run.

Measured rather than assumed:

  • ast build --host zMothership2 reproduces August's hash 330c53e69c4e byte-for-byte and still passes nix build
  • ast diff against live: 687 lines across all three files
  • promoting it would delete 316 lines of live config
  • the 162 hand-added lines are 86 comments + 76 config

The only real blocker — comments

The emitter knows 20 node types (AttrSet, FnCall, With, LetIn, MultilineString, Interpolation, …) and none is a comment. There is no comment emission anywhere in config_compiler.py, and config_nodes.description is populated on 0 of 1254 rows. So 86 lines of rationale — including a 20-line explanation of why kernel.sysrq is 1 and not 244 — are dropped. In a codebase whose comments are its institutional memory, that is not a rounding error.

But capture is nearly free. The parser is tree-sitter-based and tree-sitter already emits comment nodes; nix_ast_parser.py deliberately discards them at four sites (:197, :351, :375 — pass # skip comments — and :581). The expensive part is anchoring, not acquisition: one field per node cannot express a block that explains a group of settings, paragraph breaks, trailing inline comments, or a file header. That needs trivia-with-anchors.

Measured addendum, same day — the structure round-trips at 98.8%. An in-memory round trip of the live 593-line configuration.nix (parse → ConfigNode → emit_nix, no DB writes) gives: 451 nodes, zero RawNix fallbacks — the parser understood every construct, including the embedded shell script — and 98.8% line similarity against the comment-stripped original. The only two differences are semantically neutral: lambda headers joined onto one line, and kernel.sysctl."kernel.sysrq" = 1; expanded into nested attrsets, which in Nix is the same thing written differently.

So the AST represents the entire live config faithfully, including the voiceAIEnvRenderer block — a 15-line shell script embedded via pkgs.writeShellScript with interpolation and a makeBinPath call, which parses into MultilineString + Interpolation + FnCall with no fallback. Earlier revisions of this report treated that block as a second blocker. It is not one for representation; it remains an argument about where it is pleasant to edit.

Which means the 687-line diff was measuring the wrong thing. It compared live against the August AST state — two months of stale config_nodes — not against what a fresh import would produce. Re-import the live file and the AST holds current config faithfully, minus comments.

And re-seeding does not help

config-ast seed --dry-run would rewrite all 158 nixos.* keys and close none of the gap. kernel.sysrq, lib.mkDefault and brightnessctl are keys in neither model — the hand-edits exist only in the derived file. AST_MERGE_SEMANTICS.md does not cover it either: it merges multiple AST inputs by host-chain priority, not AST output into an edited file.

Three ways forward

#optioncost
1Capture comments and re-import: stop discarding comment nodes at the four parser sites, add a Comment node type with an anchor, then re-import the live file over the stale August nodesanchoring + whitespace fidelity; the structure already works
2Scope boundary — AST owns structured settings, authored Nix stays in files, generate merges rather than replacesa design project; the merge it needs does not exist
3Retire the AST pathdiscards a working, nix-verified build pipeline

Recommended: 1 — reversing the recommendation this report first carried. With the structure round-tripping at 98.8% and zero unparsed fragments, comments are the single gap, and tree-sitter already hands them over. Option 1 is a bounded change to one parser and one emitter; option 2 is an open-ended design project whose merge semantics do not exist yet.

Note what this does to the "hostile authorship" objection the earlier draft raised: if import round-trips, authorship never has to move into the database. You keep editing configuration.nix as Nix, re-import, and the AST mirrors it — the model becomes a lossless index over the file rather than a replacement for it. The hostility was a property of a DB-as-author implementation, not of the migration.

The residual judgement call is formatting. The emitter normalises — joining lambda headers, expanding dotted attribute paths — so a round trip is semantically faithful but not byte-identical. Either the emitter learns to preserve those choices, or the project accepts that generated output is canonically formatted and stops hand-formatting it. That is a smaller question than it looks, and `nixfmt` already implies an answer.

Whichever is chosen, the invariant worth adding first would have caught this the week it happened: a generated file must not diverge from what its generator produces. Same shape as checkout_matches_db, pointed at config-ast.

Nothing was promoted. The destructive step was available and declined.

7. Smaller findings worth keeping

  • ~170 lines of dead code. env.py:175-345 holds its own var_set / var_get / var_list / var_delete / var_export, registered nowhere and called nowhere — superseded when var.py took over. Anyone reading env.py to understand env var set reads the wrong code.
  • env var * and var * are one implementation, deliberately exposed under two nouns via a prefix parameter in var.py. Not accidental duplication — worth knowing before someone "fixes" it.
  • Three nouns begin with "config" and mean three different things: config (file links), nixos config (system values), config-ast (AST nodes).
  • Some concepts have no owning noun. checkout lives under project (6), admin (3) and top-level edit — which is precisely why the deregister gap survived until this week: no single --help listing could show the hole.
  • Under-advertised commands that answer real questions: file where (which derived copies disagree with the declaration), entity observations (the graph's own audit trail), vcs export (the only bridge from the DB commit log to git).
  • Patterns worth copying: storage blob gc is dry-run by default and paired with blob deletions as a standing record of what it collected; env key revoke requires multi-key quorum on an irreversible act; intent create/apply makes writes two-phase; report confirm/reject records the negative when a human overrules inference.
