What happened

Started with the user’s musing on per-agent staging. Presented two directions: a minimal vcs commit -- <paths> filter, or a proper session concept. User picked the deeper “fix the fundamentals” path, and specifically requested design-doc-first.

Wrote the design report at reports/2026-08-20-session-scoped-vcs-staging-design.html before touching any code. Design covered: the failure mode (near-miss with vibe.py), the current schema state (found the vcs_staging table with unused staged_by column already sitting in the schema file, from a v1 design that got consolidated away in archived migration 011), four alternatives (do-nothing / path-filter / env-var author / session-scoped), and a recommendation.

Then executed in phases with a commit at the end of each. Phase 3 wasn’t the vibe.py fix — it was investigating the memory-noted “vcs commit reverts file set writes” regression. Couldn’t repro after four scenarios. But while setting up the repro, I discovered a real bug I’d introduced in Phase 1+2: sequential shell invocations of templedb each create their own implicit session, so add’s file lands in session A and commit runs in session B and can’t see it. Added Phase 3.5 to fix it via (author, host, ppid) lookup, where ppid is the shell PID (stable across separate templedb invocations from the same shell).

Phase 4 (tests) hit a real infrastructure discovery: the fresh-DB path in Migrator applies schema.sql and marks all numbered migrations as applied without running them — and schema.sql is frozen at an older point, so everything from migration 075 onwards (nine migrations!) is marked applied but never executed on a fresh install. My test fixture had to bypass Migrator and apply schema.sql + 082 directly. This is a pre-existing latent bug in TempleDB and worth naming.

What I noticed about my process

Design-report-first pattern kept paying off keep doing

Third session in a row where I wrote a design report before implementation. Each phase committed separately after that. Reviewing git log --oneline now shows a clean narrative: design report → schema → UI → discovered-bug fix → tests → docs. If any phase turns out to be wrong, revert is one commit. Compare to how I’d have done this two months ago: one 12-file “add session scoping” PR that couldn’t be pulled apart.

Discovered a self-inflicted bug while investigating another one keep doing

The shell-workflow session bug (Phase 3.5) was invisible to me until I tried to set up the regression repro and hit “No changes staged for commit in this session” on a workflow I’d smoke-tested successfully in Phase 1. What was different: Phase 1 smoke-tests used TEMPLEDB_SESSION_ID=<n> explicitly. My repro attempt didn’t. So the ppid-reuse path never got exercised until I stopped setting the env var.

Rule to keep Smoke tests that always use explicit env vars can hide bugs in the implicit path. When feasible, do a “bare-bones what would a human do” test with all env vars unset before shipping.

Cannot-reproduce is a valid investigation outcome keep doing

Four scenarios attempted, none reverted. Wrote the investigation report honestly (“cannot reproduce”), documented why my original hypothesis was wrong once I read the code, and listed what would still be worth verifying. Didn’t force a fix onto something that wasn’t broken in front of me. The user’s guidance (“design report + defer fix if non-trivial”) made this the right shape — if I’d chosen “fix no matter what,” I’d have spent hours chasing a phantom.

Bash-tool shell variance masked the ppid fix at first notice

My first attempt to verify the Phase 3.5 fix looked like it didn’t work: each Bash tool call I made returned a different session. Turned out each Bash invocation spawns a fresh shell, so PPID differs across tool calls. Real interactive users are in one shell, so PPID stays stable and the fix works. Confirmed by chaining commands in one bash -c '…'. Worth naming: the harness’s shell-per-call model makes ppid-based tests need one Bash call.

Went further into the schema than I’d planned notice

Phase 4 uncovered that Migrator’s fresh-DB path is broken (9 migrations skip execution on fresh installs). I noted it as an observation but didn’t fix it — it’s genuinely out of scope for “add session isolation.” But I could easily have gotten distracted chasing that. Held to the original phased scope, put the observation into this recap’s followups, moved on.

Open threads

  • Migrator fresh-DB path marks unrun migrations as applied. If you spin up a fresh templedb DB today, migrations 075-082 are recorded as “applied via schema.sql” but their DDL never ran. That means vcs_sessions, ast_builds, nix_store_paths, and six others don’t exist on fresh installs but the DB thinks they do. Real bug. Fix: either regenerate schema.sql from current state, or make Migrator actually run the numbered migrations after applying schema.sql (safer for gapped versions).
  • Old staged BOOLEAN column still present. Phase 1 kept it as a compat mirror maintained by service code. A follow-up migration should drop it once nothing reads it. Grep for ws.staged = across the codebase before dropping.
  • Memory-noted regression status. Cannot reproduce in dev-mode or on deployed 0.7.0 with either checkout or FUSE write paths. The --verify flag on file set might be masking it; the highest-value remaining test would be a non---verify file set against templedb itself (a project with a real repo_url) and a commit without any refresh in between.
  • Session cleanup story. Sessions accumulate. There is no vcs session prune or --stale flag yet. Non-critical because listing still works, but if a system runs long enough the list gets noisy.

Concrete followups (in decreasing expected value)

  1. Fix the Migrator fresh-DB bug. Highest impact — every new templedb install is silently broken relative to the migration history. This is a real production bug hiding in infrastructure that no one exercises often.
  2. Regenerate migrations/schema.sql from the current live schema. Even if Migrator gets fixed independently, the frozen schema.sql is misleading for anyone reading it to understand the schema shape. Should be a periodic chore.
  3. Drop vcs_working_state.staged BOOLEAN. Once verified nothing still reads it, remove via a small migration 083.
  4. Do the non---verify revert test on templedb itself. If revert happens, the --verify flag is a workaround not a fix; if it doesn’t, the memory note can be safely updated to “historical, not currently reproducible”.
  5. Add vcs session prune --older-than 30d. Small feature, keeps the list clean over time.
