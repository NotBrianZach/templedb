TempleDB as an ontology in disguise

A response to the ChatGPT essay on ontological trees, typed knowledge graphs, and p-adic-style semantic distance — considered in the specific context of what TempleDB already is and what it could productively become.

The thesis in one sentence

The essay describes an architecture — typed nodes, partial orders for subsumption, ultrametric distances for similarity, multiple projections over one underlying graph — that TempleDB has already built about 60% of, without ever calling it an ontology. The remaining 40% is worth doing only where it powers a query someone actually runs, not as a standalone "knowledge graph" feature.

The reframing Git isn't an ontology: it types nothing above "file." Nix is halfway there — it types derivations and their inputs but not what those derivations mean. TempleDB types everything: projects, files, commits, config nodes, hosts, generations, closures, tests, deploys, and the relations between them. The ontology is emergent from the schema, not designed as a separate layer. That's the interesting property, and it's a feature, not a bug.

Where the essay's model already lives in TempleDB

1. Typed entities with typed relations

The AST config compiler is the clearest example. Every NixOS system config is stored as a graph of typed nodes — 26 node types covering the full Nix language (AttrSet, LetIn, FnDef, With, RawNix, etc.). Ownership goes through config_node_owners. Host inheritance goes through config_hosts.parent_id. That's exactly the essay's move from a filesystem tree to a typed graph. 

-- Not "here's a file with 40kb of Nix in it"
-- but a graph you can query, merge, and re-emit.
config_nodes (id, type, position_in_parent, ...)
config_node_owners (node_id, project_id)
config_hosts (id, name, parent_id, ...)  -- partial order

2. A partial order for subsumption

Host inheritance through config_hosts.parent_id is a genuine partial order — zMothership2 ≤ shared, zStation ≤ shared, etc. The deep-merge resolver walks this order to produce the final config, with priority going shared → host chain root → leaf. That's a lattice traversal in everything but name, and it's what makes the same DB state deterministically produce different per-host outputs.

3. An ultrametric for identity, everywhere

Content-addressed hashing is what makes the p-adic geometry natural in TempleDB. Two things with the same SHA-256 hash are identical. Two things with different hashes are different, in a way that admits no partial credit at the point of identity but supports a real distance function one level up:

DomainDistance functionWhere it lives
File content Hamming-ish over lines (via vcs diff) vcs_file_states.content_hash
VCS commits Depth to lowest common ancestor vcs_commit_parents
Nix closures Symmetric difference of store paths nix_closures, nix_closure_diffs
Nix generations Path-set overlap between generations nix_generation_history
AST builds Hash equality (identical) or full re-build ast_builds.output_hash
Config subtrees Structural overlap under the deep-merge resolver config_nodes

The ultrametric property — "every triangle isosceles with the two largest sides equal" — approximately holds for the closure and commit-ancestry distances, because the natural structure is a DAG of derivations or commits, and shared ancestry is the shared-prefix that p-adic geometry rewards.

The interesting bit The essay observes that under p-adic geometry, two things are close iff their descriptions share a long prefix. In a content-addressed world, this is literally true: two Nix closures are close iff they share a long list of identical /nix/store/ paths, because each path is a hash of its derivation inputs, which is a hash of their derivation inputs, all the way down. Shared-prefix-in-a-Merkle-DAG is the ultrametric.

4. Multiple valuations over the same graph

The essay's strongest single point is that there is no universal semantic metric — concepts are close under one valuation and far under another. TempleDB already ships four or five distance functions over the same underlying graph:

  • templedb graph search — lexical similarity
  • templedb graph who-uses — reverse-import distance
  • templedb graph callers — call-graph distance
  • templedb graph importers — import-graph distance
  • templedb graph build-deps — Nix-input-graph distance
  • templedb nix who-uses — reverse dependency in the store

These are exactly the essay's dtaxonomic, dcausal, dfunctional, dlinguistic — separate valuations that reveal different truths about the same entities. A file is "close to" different neighbors depending on which one you ask.

Where the model would meaningfully extend TempleDB

Cross-project semantic equivalence

The essay's data integration section is the biggest concrete win. Right now the graph is intra-project or file-to-file; there's no way to state that services.woofsledger.dbPath in system_config and DB_PATH in the woofsledger project are the same fact in two forms. Typed cross-project relations (SAME_AS, SPECIALIZES, INSTANCE_OF) would let graph who-uses follow meaning across project boundaries instead of stopping at each project's edge.

Epistemic status on derived facts

The essay's insistence that "water boils at 100°C" and "democracy improves X" don't belong in the same epistemic bucket applies directly. TempleDB has:

  • Ground-truth: test_runs (pass/fail), fleet deploy status (SSH-verified activation), nix build success.
  • Inferred: config_node_owners assignments (some auto-inferred from file imports), project.category, graph edges derived from static analysis.

A confidence or evidence_source column on the derived tables would let you sort "known good" from "best guess," and would surface in the GUI as e.g. dim-vs-bright edges in the graph view.

Typed relations, not just adjacency

The import graph currently says "file A imports file B." An ontology-typed graph would say how: EXTENDS, OVERRIDES, USES_TYPE_FROM, INSTANCES. That's not free — it takes richer static analysis — but it's the difference between a graph you can search and a graph you can reason over.

Formalize distance as a first-class query

If you already have five valuations, you might as well expose them symmetrically: 

templedb distance src/gui.py src/gui_pages/dashboard.py --via imports
templedb distance zMothership2 zMothership3 --via config-ast
templedb distance generation-421 generation-422 --via nix-closure

This would make it explicit that TempleDB has a real distance geometry on its entities, and that different queries pick different valuations. It's a small surface-area move that reifies something already true.

Where I'd resist the model's pull

Don't build an "ontology" as its own subsystem

Building a generic ontology_nodes / ontology_relations layer is a classic tarpit: a year of schema design, no queries anyone actually runs. The reason the AST config compiler works is that it's tightly coupled to a concrete downstream mechanism (emit → build → promote → deploy). Every ontology feature in TempleDB should be attached to a specific query, tool, or transformation, or it will rot.

Don't materialize distances you can compute

The nix closure distance, commit-ancestry distance, and config-subtree overlap can all be computed from existing tables on demand. Caching them into a semantic_distances table would create a synchronization problem bigger than the queries save.

Don't confuse structural types with semantic types

The 26 AST node types (AttrSet, LetIn, etc.) are syntactic: they describe Nix's grammar, not what any particular config means. A separate layer of semantic types (NetworkInterface, SystemService, UserAccount) could be layered on top, but conflating them would poison both. The AST is the wrong place to encode "this is a firewall rule."

Don't over-generalize what's already working

The config_hosts parent chain is a partial order because it needs to be; deep-merge resolves priorities exactly as the essay describes. But generalizing that to "partial orders on everything" (projects, files, tests) buys nothing until there's a mechanism that needs the ordering to resolve something.

The one weird corner worth pursuing

The essay's most seductive line is "the notion of size or closeness depends on a chosen valuation." In TempleDB, the choice of valuation is currently implicit in which command you type. What if the choice were explicit — a --via flag on graph queries, a valuation-picker in the GUI's graph view, a scriptable API where you can define new distance functions in terms of existing ones?

Composed valuations ("close under imports AND close under commit-ancestry") would let you ask questions like "which files are frequently co-modified AND import each other?" — a natural candidate for extraction into a module. Or "which Nix closures differ by only a single derivation with a single input hash change?" — a natural candidate for a targeted rebuild rather than a full system rebuild.

That's the version of the ontology idea I'd actually build: not a schema, but a small algebra of distance functions over the entities TempleDB already types.

What to take from the essay's closing frame

Ontology: what can exist · Statechart: how it can change · Effects: how changes interact with the world

TempleDB has all three:

  • Ontology: the schema, the AST config compiler, the typed entities.
  • Statechart: the deploy pipeline (build → hash → diff → promote → activate → magic-rollback), VCS branch states, agent session states.
  • Effects: the FUSE mount, nixos-rebuild, nix build, fleet SSH activation, git materialization.

What makes this list interesting is not that any one of them is novel, but that they're all in one database with content-addressed identity across all three layers. That's rarer than it sounds, and it's what the essay would call a "formal world model" — with the important caveat that "formal" here means executable and content-addressed, not philosophically complete.

Short version: TempleDB is already an ontology in the essay's sense; it just doesn't advertise itself as one. The productive additions are cross-project semantic linking, epistemic tagging on derived facts, and reifying distance as a first-class query. The unproductive additions are anything called "ontology_*" that isn't wired to a concrete mechanism.
