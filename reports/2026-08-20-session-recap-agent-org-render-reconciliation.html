Deleted the server-side agent/org_renderer.py and made the Emacs client the single source of truth for session Org rendering. Fixed two complementary latent bugs the drift was hiding: server-render reopens overwrote the client's Guide/Pinned/Context scaffold, and the "fallback" path called --restore-messages which turned out to be dead code with zero callers. What I noticed about my process

Post-edit grep found a third callsite keep doing

Original plan named two callsites (--do-open-session, templedb-agent-refresh). After editing both I ran grep -n 'org-text\|--restore-messages' before pushing and found --wait-and-open-session using the same pattern. Two minutes to fix. Without the grep pass it would have been a latent bug in the async retry path — the exact kind of path that gets hit intermittently and is annoying to diagnose.

Rule to keep When removing a code shape (a field, a helper, a pattern), grep for all references after each edit, not just the ones the plan named. Plans list what you thought about; grep lists what’s there.

Caught dead code mid-implementation, updated the story keep doing

I’d framed the client-fallback path as "also broken but in a different way." When I actually opened --restore-messages to edit it, grep for callers returned zero. That reframes the bug: fallback wasn’t "broken differently," it was silently no-op. Corrected the situation description to the user before continuing. Small thing but the honest framing shapes what the fix needs to cover.

Paused on unfamiliar staged state keep doing

templedb vcs status before commit showed src/cli/commands/vibe.py staged — I didn’t touch it. Also 21 unstaged modifications from prior work. Since templedb vcs commit has no per-file scoping, hitting commit would have swept vibe.py in. Surfaced instead of guessing; user replied "a different agent is staging that vibe.py." So: reset it, commit only my 4 files. If I’d assumed "probably a leftover from my session" I’d have committed another agent’s in-progress work under my message.

Rule to keep In a shared repo where multiple agents may be staging, always diff the staging area against what you actually edited before committing. The safety cost of pausing is one AskUserQuestion; the cost of a wrong sweep is that the other agent’s work has your commit message on it.

Search index tokenizer wasted a step notice

templedb search content 'render_session' returned zero results even though render_session exists in two files I’d just read. FTS5’s default tokenizer splits on underscores, so snake_case symbols are effectively unfindable via the built-in search. I noticed after wasting a couple of queries, fell back to grep, and moved on — but this is a real usability gap in templedb search that will bite the next agent (or me) doing symbol lookups.

Fired off a background scan I didn’t need didn’t

Kicked off an xargs | grep scan across 672 files to double-verify no consumer of org_renderer existed. I already had the answer from directly reading protocol.py’s imports and had confirmed via a smaller grep -c inside the module. The xargs job would have taken minutes; killed it after the smaller checks came back conclusive. Should have skipped it from the start — direct-read on 2 files beat background-scan on 672.

Went thicker on analysis than the user needed notice

The 4-column comparison table of "which path loses what" was useful to me for scoping the fix, but the user only needed a directional answer. A one-liner ("server render overwrites scaffold; client fallback is silently no-op") plus the three options would have been enough. Table added maybe 30 seconds of reading with no directional payoff. Notice for next time: after I finish an analysis, ask what fraction of it actually informs the user’s next decision.

Open threads

  • No live UI verification. Test-green ≠ render-correct-in-Emacs. Next open should confirm Guide + Pinned scaffold survive and past tool events appear as *** RUNNING/DONE/FAILED <summary> under each exchange.
  • Rich tool blocks not replayed on reload. Deliberate scope cut — we don’t persist enough arg-buffer state to reconstruct them. Past runs get simple STATUS/summary headings; live runs still get rich blocks. If someone opens a completed session hoping to inspect prior tool args/output, they’ll be surprised. Fixing this needs a data-model change (capture tool.completed args in the event row, not just summary).
  • templedb search content FTS5 tokenizer can’t match snake_case symbols. Real gap; agents will keep hitting it. Options: switch tokenizer to trigram, or document "use plain grep for code symbols" in the top-level CLAUDE.md.
  • 21 unstaged modifications in the templedb project from prior work — not mine, not touched, but they’re someone’s in-flight state. If I’d re-checked out any of those files to sync my checkout for testing, I would have blown their changes away. Didn’t; used narrow file checkout for just my 2 test-relevant files. Worth noting the pattern: always use file checkout <path> -o <path> for sync, never project checkout --force, when other agents may have working changes.
