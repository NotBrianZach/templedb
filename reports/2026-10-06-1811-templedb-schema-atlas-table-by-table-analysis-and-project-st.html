TempleDB schema atlas: table-by-table analysis and project status

A full pass over the live TempleDB database as of 2026-10-06: 165 tables, 47 views, 369 indexes, 62 triggers, 776 MB on disk. The schema is read here as a stratigraphy — five distinct eras of design intent laid down on top of each other, each with its own theory of what the database is for, and only the top two still load-bearing. The report walks every subsystem table by table, names the semantics the schema actually enforces (as opposed to the semantics the column comments claim), and ends with the four concrete defects this pass turned up — the largest of which is that 54% of the database file is unreachable blob garbage with no collector.

1. Status at a glance

The project is in a stable operating regime. The observer/integrator model landed (Phases 0–3, Sep 2026); the checkout-role tranche landed (Phases 0–4, Sep 27 – Oct 3); nine ingest adapters run hourly; 29 doctor invariants run daily. What is left on the declared roadmap is Phase 5 — retire the "authority-over-source" vocabulary — plus a decision on whether SCIP stays.

2. How to read this schema

The 126 application tables were not designed at once. They are five strata, and the most useful single act of orientation is to learn which stratum a table belongs to, because that predicts whether it is maintained, whether its comments are true, and whether you should write to it.

StratumTheory of the databaseRepresentative tablesStatus
I — Catalogue"A database of facts about code"project_files.purpose/owner/description, file_metadata, file_types, code_clustersVestigial. Columns are all-NULL.
II — Code intelligence"A symbol graph with embeddings and impact analysis"code_symbols, code_symbol_dependencies, code_search_index, impact_transitive_cacheSuperseded by the entity graph; 12 rows survive
III — Database-native VCS"The DB is authoritative for source; git is an export format"content_blobs, file_contents, vcs_*Demoted but load-bearing
IV — Deployment/fleet platform"TempleDB deploys to a fleet of machines"fleet_*, deployment_*, blue_green_state, edge_function_deploymentsMostly empty; the real deploy path is nix_generations + system_deployments
V — Observer / entity graph"Git is authoritative; TempleDB observes and relates"entities, relations, ingestion_runs, invariant_checks, claimsCurrent. Where all new design goes.

The characteristic signature of stratum V, and the thing that makes this schema genuinely interesting, is that it writes its own epistemics into the DDL. Stratum III tables say what a thing is. Stratum V tables say when the thing was last observed, by which authority, and with what warrant — entities.observed_at, entities.source_authority, claims.warrant_kind, claim_evidence.role IN ('supports','undercuts'). That is a deliberate and unusual commitment: the database is designed to be wrong in legible ways rather than right in silent ones.

3. The content spine

Five tables carry every byte of source TempleDB knows about. Everything else hangs off them. 

projects ──1:N──> project_files ──1:1──> file_contents ──N:1──> content_blobs
                        │                                            ▲
                        └──N:M (via vcs_file_states) ── vcs_commits ─┘

projects — 30 rows

The root. slug is the universal external key; nearly every CLI verb takes one. Carries a lot of accreted classification: project_type, project_category, is_nix_project, service_type, flake_check_status, nix_build_status. Four of those six are CHECK-constrained enums added by separate ALTERs, which is why the DDL reads as a run-on sentence. project_type and project_category overlap almost entirely — 'service' is a legal value of both — and nothing reconciles them. Trade-off: wide denormalised classification on the root table makes WHERE is_nix_project = 1 cheap and avoids a join for the most common filter, at the cost of a root table that no longer has a single coherent meaning. Future: collapse the two enums, or move classification into entities.attributes_json where the rest of the typed-fact work now lives. Nine of the 30 rows (proj_a, proj_b, proj_sess, proj_ctx, proj_missing, …) are test fixtures with zero files.

project_files — 2,369 rows

Path identity, UNIQUE(project_id, file_path). This is the stable integer handle a path gets, and the thing File entities point at. It is also the clearest fossil of stratum I: of its 18 columns, seven — description, purpose, owner, documentation_url, inline_documentation, complexity_score, edit_mode — are 100% NULL across all 2,369 rows and are formally accepted as such in unmaintained_columns_baseline. Semantics worth knowing: status = 'active' is a real filter — source_snapshots and the FTS triggers both honour it, so a file whose status drifts silently disappears from search without disappearing from the table. Future: the seven dead columns are the cheapest DROP in the schema and the baseline table already licenses it.

content_blobs — 12,512 rows, 489 MB, 70% of the database

Content-addressed store keyed on hash_sha256, with content_text for UTF-8 and content_blob for binary (only 105 blobs are binary). This is the single best design decision in the schema: dedup is free, identity is content, and --if-match hash-guarded writes are possible because the hash is the primary key.

It is also where the schema's largest live defect lives. Seven of its columns — storage_location, external_path, chunk_count, compression, remote_url, fetch_count, last_fetched_at — describe a tiered-storage design (inline / external / remote, zstd-compressed, chunked) that was never implemented; all blobs are 'inline', and three views (external_blobs_view, migratable_inline_blobs, blob_storage_stats) plus a storage blob migrate subcommand exist to operate a tier system with nothing in it. Meanwhile reference_count, the field that would make collection possible, is maintained by two triggers that fire only on INSERT and DELETE of file_contents — never on UPDATE. Since file_contents holds exactly one row per file and is updated in place, the counter drifts monotonically upward: declared total 4,263 against an actual 2,051, wrong on 2,073 blobs. Consequence: §7.1.

file_contents — 2,051 rows, all is_current = 1

The current-snapshot map: file → blob. Since migration 086 this is explicitly a snapshot table, not an authoritative store — the row records the most recent observation of a file, and git owns the truth. The vocabulary change was the whole point of Phase 1 and it is worth taking literally.

The interesting artefact here is UNIQUE(file_id, is_current). The intent is "at most one current version per file", and it achieves that. But because SQLite treats 0 as an ordinary value in a unique index, the same constraint also permits at most one non-current row per file — which makes the version column and the is_current flag structurally unusable as a history mechanism. The table has silently become single-valued, which is in fact the correct Phase-1 semantics; the constraint arrived at the right answer for the wrong reason, and is_current is now recorded as a constant in the unmaintained-columns baseline. Future: drop is_current and version, make file_id the primary key, and let vcs_file_states own history outright — which is already true in practice.

file_contents_fts — FTS5, ~97 MB

Porter-stemmed full-text index over current text contents, kept in sync by five triggers (three on file_contents, two on project_files for path renames and deletes). Migration 110 added the INSERT trigger that had been missing — before that the index silently stopped growing and matched 39 files across a 197k-line corpus, the worst class of bug this schema can have because a search that returns nothing looks identical to code that does not exist.

Trade-off, unexamined: this is a contentless-by-default FTS5 table, meaning it keeps its own full copy of every indexed document in file_contents_fts_content (37 MB) alongside the inverted index (61 MB). The text already exists in content_blobs. Declaring content='current_file_contents_view' would eliminate the duplicate at the cost of a join per snippet. 37 MB is 5% of the database — not urgent, but it is pure duplication.

file_types — 66 rows

A lookup table project_files joins through on every read, with a mandatory non-null FK. Sixty-six rows of ('javascript','frontend')-style pairs that could be a derived function of the file extension. Trade-off: a normalised type table buys you category rollups (ft.category appears in three views) at the price of a required join on the hottest path in the schema. Defensible, but it is the only hard FK a file row cannot live without.

4. Version control

Twelve tables implementing a git-shaped VCS inside SQLite. Under the observer model this layer is demoted — git is authoritative for source — but it is not dead: it is how TempleDB records its own write path, and vcs_commits is the join target for provenance queries from deployments, generations, claims and intents.

vcs_commits — 1,118 rows

The hub. Note the dual identity introduced by migration 126 (126_separate_git_shas_from_commit_ids.sql): commit_hash is now strictly a TempleDB-native identifier, and git_commit_hash holds the imported SHA when there is one. The 262-row commit_hash_migration_126 table is the audit trail of that split, recording per-commit whether the old value moved to git_commit_hash (kind='git-sha') or was merely a case normalisation (kind='case-only'). Keeping the mapping table as a permanent artefact rather than a throwaway is good practice and pays for itself the first time someone finds an old hash in a report.

Constraint oddity: commit_hash TEXT NOT NULL UNIQUE and UNIQUE(project_id, commit_hash) are both declared. The second is redundant given the first, and the first is stronger than it should be — it makes commit hashes a global namespace across all 30 projects, which is fine for native IDs but would collide the moment two projects import the same upstream commit. Two indexes are maintained for one guarantee.

Four columns are formally dead: committer, committer_email, git_branch, and — notably — merge_parent_commit_id, because there are no merge commits yet and merges are tracked in vcs_commit_parents anyway. That is two competing representations of parentage (parent_commit_id + merge_parent_commit_id on the row, versus the vcs_commit_parents junction with parent_order), and the junction won. Future: drop both scalar parent columns.

vcs_file_states — 4,230 rows

The per-commit tree delta: (commit_id, file_id) unique, with change_type CHECK-constrained to the five git verbs. Migration 118 normalised this out of an earlier commit_files table, which now survives as a view that reconstructs the old column shape (old_file_path / new_file_path switched on change_type = 'deleted', with lines_added and lines_removed hardcoded to 0). That is a clean way to retire a table without breaking callers, and the hardcoded zeros are an honest signal that the old columns were never populated either.

This table plus file_contents is what source_snapshots unions to give the "read any file at any revision" surface. previous_path is all-NULL — rename detection is declared in the change_type enum but not implemented.

vcs_sessions — 709 rows, 2 active

The most consequential small table in the schema. A session is the unit that scopes staging, so that two agents writing to the same project do not sweep each other's work into one commit. Identity is (author, host, name) with a 24-hour expiry; resolution is by TEMPLEDB_SESSION_ID (exact, must be live) or TEMPLEDB_SESSION (name, validated against author+host+active).

The asymmetry that causes all the trouble: VCSService.get_current_session() may create a session for an unknown name; CheckoutRepository.current_session_id() deliberately may not, because resolving a path should not have the side effect of opening a session. The consequence is visible in the data: of 72 checkout rows, 54 have session_id IS NULL — including all 8 canonical trees (correctly, they are nobody's) and 3 of 21 edit trees (incorrectly, those are unowned workspaces). Migration 122's partial unique index is supposed to constrain exactly the ambiguous rows, but SQLite treats NULLs as distinct in a unique index, so the constraint does not bind precisely where it is needed. This is the documented open gap in the checkout-role tranche and it is a schema-shaped problem, not a code-shaped one.

expected_lifetime_seconds and reap_policy are all-NULL — a configurable-reaping design that never shipped. Reaping is age-based with a COALESCE default of 86,400s and works correctly.

vcs_working_state — 1,738 rows

The staging area: (project, branch, file) → working content, plus staged_by_session_id and intent_id. Note it stores content_text/content_blob inline rather than referencing content_blobs — the one place in the schema that breaks the content-addressed discipline. It also carries content_hash, so the hash is computed but the dedup is not taken. Future: point this at content_blobs like everything else; it is the same change that would make blob GC tractable.

Migration 083 dropped the boolean staged column in favour of staged_by_session_id IS NOT NULL, and vcs_current_files_view re-derives the boolean for compatibility. Good: one source of truth, one derived convenience.

vcs_commit_metadata — 233 rows / 1,118 commits

Twenty-five columns of optional commit annotation: intent, change_type, breaking-change notes, impact and risk levels, review status, test-coverage delta, and an ai_assisted / ai_tool / confidence_level triple. Five views read it. It is populated on 21% of commits. Trade-off: this is a sidecar table rather than columns on vcs_commits, which is the right call — it keeps the hot table narrow and makes the optionality explicit in the join. But none of the 25 columns is CHECK-constrained despite every one of them being a small enum in the comments, so impact_level can be anything. Cheap, high-value hardening.

vcs_branches / vcs_commit_parents / vcs_session_heads — 22 / 857 / 5

vcs_branches.head_commit_id is advanced by an AFTER INSERT trigger on vcs_commits — the only write-path trigger in the VCS layer, and a nice one: it makes "the branch head" unforgeable from the application side. vcs_session_heads is the per-session view of a branch head (head_commit_id + base_commit_id, the latter NULL when the branch was empty at session start), which is what lets concurrent sessions commit onto the same branch without a lock. Five rows: it is used, lightly.

Empty VCS tables

vcs_tags (0), vcs_commit_tags (0), vcs_file_change_metadata (0). Tagging was built twice — once project-scoped with annotated-tag support, once commit-scoped with categories — and neither is used. vcs_file_change_metadata is the per-file analogue of vcs_commit_metadata and has never received a row.

5. Workspaces, intents and the write path

This is the newest substantial subsystem and the one with the most careful semantics. The problem it solves: when the canonical checkout, several agent edit workspaces, and the DB all disagree about a file's contents, which one is authoritative — and for whom?

checkouts — 72 rows (8 canonical / 21 edit / 43 scratch)

The answer is kind plus session_id, both added by migration 113. A role (not a path) determines authority, and resolve(purpose) picks a tree by what the caller intends to do — so a writer never reconciles against the published copy. Migration 122 added partial unique indexes to make roles unambiguous. The design is right; the NULL-session gap in §4 is what keeps checkout_roles_are_unambiguous occasionally red. Note that admin checkout-gc cannot fix it: those trees are live, not stale.

checkout_snapshots — 36,198 rows, 3.8 MB

Per-checkout record of which blob each file was at materialise time. This is the blob-age guard's evidence base — the mechanism that stops a stale disk from overwriting a newer blob. It is the second-largest row count in the schema after nix_closure_paths, and it grows as O(checkouts × files): 72 checkouts × ~500 files. ON DELETE CASCADE from checkouts keeps it bounded when checkout-gc runs, but that cascade is also what orphans File entities and requires a follow-up entity prune-orphans.

edit_intents — 978 rows

Phase 2's core object: a proposed edit as a first-class row, with base_revision, new_content_hash, a lifecycle (proposed → applied | cancelled) and a link to the commit that recorded it. Every file set creates one. This is the schema taking seriously that an edit is a speech act with an author and a basis, not just a mutation.

Two columns undercut it, though one is already half-repaired. base_revision was the literal string 'current' on every row until 2026-10-04 — so the intent did not pin what it was computed against, which is precisely the information that would make the --if-match stale-write class of bug structurally detectable rather than opt-in. The write path was fixed that afternoon and the 93 intents created since carry a real base hash or the explicit 'new-file' sentinel; the remaining 888 are legacy. The unmaintained_columns_baseline row calling the column constant was recorded the day before the fix and is now stale, which is worth noting as a limitation of the ratchet: it suppresses reporting on a column that has since started being written.

applied_commit_id is the one still entirely unwritten — 100% NULL, so no intent is ever linked to the commit that landed it, even though 978 of them are marked applied. This is the highest-value repair in the schema: populating it would turn the intent table from a log into a span, and would let provenance intent answer the question it was built for.

sync_cache — 1,555 rows

Despite the prefix, this is not a CRDT table — no cr-sqlite clock. It is the "hash at last sync" record used to detect disk drift. Name collision with the eight real sync_* tables is a genuine readability hazard.

edit_sessions / editor_sessions — 0 / 0

Two abandoned designs. edit_sessions has UNIQUE(project_id) — one edit session per project, a global lock — which is exactly the model the checkout-role tranche replaced with per-session trees. Its companion stale_edit_sessions view is likewise dead. editor_sessions would have persisted Emacs buffer layout per host.

6. The entity graph

Stratum V. Two generic tables plus a ring of telemetry and invariant tables around them. The design doc frames it categorically — entities as objects, relations as morphisms, span tables as first-class arrows with duration, doctor checks as commuting-diagram invariants — and the DDL is unusually faithful to that framing.

entities — 53,050 rows, 8.8 MB

UNIQUE(kind, external_ref)
kind              TEXT   -- conventional, NOT enforced
external_ref      TEXT   -- heterogeneous IDs coexist as text
source_authority  TEXT   -- git | nix | agent-runtime | author | templedb | machine | scip-typescript | python
observed_at       TEXT   -- freshness per fact
sync_scope        TEXT CHECK (IN ('fleet','machine-local','none'))

Trade-off, deliberate and correct: kind is a free-text convention rather than a FK to a kinds table or a CHECK enum. The cost is that a typo creates a new kind silently. The benefit is that an ingest adapter can be added without a migration — and nine adapters have been. Given that the whole point of the graph is to absorb facts from authorities TempleDB does not control, soft-typing the kind is the right call. The invariant layer (entity_counts_match_source_tables, every_commit_has_entity, …) is what buys back the safety a CHECK would have given, and it buys it at observation time rather than write time, which is the only place it can be bought for foreign facts.

The one real namespace problem: Symbol entities are produced by two authorities — python (5,095) and scip-typescript (15,821) — into a single UNIQUE(kind, external_ref) namespace. Nothing in the schema prevents a Python symbol ref and a TypeScript symbol ref from colliding; the unique constraint does not include source_authority. Deliberately excluding it is defensible (the same commit observed by two adapters should be one entity, not two) but it means authorities must agree on a ref-encoding discipline that the schema does not enforce. The 8,133-row bulk Symbol deletion earlier today is a symptom of that churn.

relations — 62,373 rows

UNIQUE(from, kind, to) with ON DELETE CASCADE both ways. The comment on attributes_json states the governing rule explicitly: "if a relation grows more than 2–3 attributes or a lifecycle, promote it to a span with its own table." That is a schema-evolution policy written into the DDL, and the codebase follows it — edit_intents, tool_calls, report_implementations, ast_builds, deployment_history and nix_generations are all spans that were promoted rather than crammed into JSON. attributes_json is consequently all-NULL, which here is a success signal rather than a dead column.

Relation-kind distribution shows where the graph's mass is: defines 20,894 / uses 17,530 / invoked 11,850 / calls 4,680 / contains 3,091 / built-by 2,355 — i.e. 93% of edges come from two adapters (python/scip and agent). The cross-authority edges that justify the whole design — motivated (2), targets (1), from-commit (29) — are three orders of magnitude rarer. That is the honest state of the graph: an excellent intra-authority index, and a thin cross-authority one.

observations_archive — 26,275 rows, 4.8 MB

Append-only history of entity mutations, written by trg_entities_archive_on_update. The trigger is scoped tightly — AFTER UPDATE OF label, source_authority … WHEN OLD IS NOT NEW — so the hourly re-observation that only bumps observed_at does not archive. That scoping is what keeps this table at 26k rows instead of millions. Worth noting because it is easy to get wrong and expensive when you do.

entity_deletions — 8,133 rows

Added by migration 124 to answer a specific forensic question. Its comment is the clearest statement of intent in the schema: "A gap in this table next to a drop in entity counts therefore means 'not deleted through the CLI', which is the single most useful thing to know when counts move unexpectedly." It records relations_removed because the cascade leaves no trace of its own. All 8,133 current rows are from a single bulk_sql event today.

ingestion_runs / invariant_checks / reconcile_runs / hygiene_snapshots — 2,496 / 3,250 / 11 / 102

The telemetry ring. Each records a process rather than a fact, which is what makes "is this number stale?" answerable. Two details worth calling out:

  • invariant_checks.sample_issues_json stores only the first N issues, with the rationale written in the comment — "Freshness > completeness for a history log." A bounded-growth decision made explicitly rather than discovered later.
  • hygiene_snapshots.adapter_version exists so that a step-change in dead_candidates can be attributed to an adapter upgrade rather than to real code change — the comment cites the 1.6→1.7 bump that dropped false positives ~40pp. This is versioned-measurement discipline, and it is rare.
  • invariant_checks.ingestion_run_id is all-NULL: the intended link from a violated invariant back to the ingest run that caused the drift was never wired.

claims / claim_evidence — 2 / 2 rows

The most ambitious and least populated part of the schema, added by migration 116. A claim is a proposition scoped to (project, commit, host, inputs) with a warrant_kind naming the inference rule rather than the conclusion, and 'asserted' as an explicit value meaning "an agent's say-so, recorded as such so it is distinguishable from a checked claim." Evidence can be attached with role = 'undercuts' so a claim carries its own contrary evidence rather than the author silently omitting it. evidence_hash is captured at assertion time so that evidence moving under a claim fails loudly.

Phase 2 — the actual warrant checkers keyed on warrant_kind — has not landed, so evidence_hash is currently decorative and the table holds two rows. Assessment: this is the schema's best idea and its biggest unrealised asset. The epistemics are already correct in the DDL; what is missing is a handful of predicate functions and a test_runs / ast_builds integration that would make every green test run auto-assert a warranted claim. The UNIQUE(project_id, commit_id, statement) constraint already encodes the right semantics — re-running the same work at the same revision is a re-observation, not a second claim.

unmaintained_columns_baseline — 47 rows

A meta-table listing columns known to be all-NULL or constant, with the shape recorded (not just the name) so that a column changing shape is still visible. The no_new_unmaintained_columns doctor check uses it as a ratchet. This is an unusually mature answer to schema rot: rather than pretending dead columns do not exist or churning migrations to drop them, it accepts the current set and prevents growth. Of the 47, 24 are honestly labelled "pre-existing at baseline; not triaged"; the rest carry real reasons ("single-user install", "no merge commits yet", "blob chunking is not in use").

tool_calls — 11,872 rows

A span extracted from agent_events. Three of its columns — finished_at, args_hash, result_hash — are all-NULL, which means the table currently answers "what was called" but not "how long did it take" or "was this the same call as that one". The args_hash comment states the intended query — "same tool + same args across sessions" — which is the memoisation/dedup question an agent platform most wants answered. Unimplemented.

7. Nix, deployment and configuration

The largest subsystem by table count (~35) and the most stratified. Two generations of deployment design coexist with a third that actually runs.

7a. The Nix store model — live

TableRowsRole

nix_closure_paths at 347k rows costs 4.6 MB of table plus 13.3 MB across three indexes (its own autoindex plus one per direction) — the indexes are 2.9× the data. With 146 closures averaging 2,374 paths each and heavy overlap between generations, this is a classic candidate for interning: store the diff against a parent closure rather than the full membership set. nix_closure_diffs already computes exactly that information for display; it is not used for storage. Future direction: if the fleet grows past a handful of machines, this table is the first thing that will hurt.

nix_generations is the genuinely valuable one: it is the join that makes provenance machine <host> work, carrying FKs to fleet_machines, nix_closures, vcs_commits, projects, fleet_deployments, system_deployments and itself (previous_generation_id) — plus denormalised machine_name and commit_hash that deliberately survive deletion of their referents. All seven FKs are ON DELETE SET NULL: history outlives its subjects. That is the right durability model for an audit table and it is applied consistently.

7b. The config AST — live, 1,254 nodes

config_nodes is a Nix AST in a table: a self-referencing tree with a 27-value node_type CHECK covering the Nix grammar (AttrSet, LetIn, With, Inherit, HasAttr, … down to RawNix as the escape hatch), an operator CHECK listing every Nix binary and unary operator, and scope ∈ (system, home, flake). config_roots pins one root per scope; config_hosts is a self-referencing host hierarchy with inheritance; config_node_owners is the project↔node junction.

Trade-off: representing a programming language as rows gives you queryable, diffable, host-parameterised configuration — and ast_builds (27 rows, with nix_buildable and nix_build_error) proves the round-trip works. The cost is that RawNix exists, and every construct that falls into it is opaque to exactly the queries the design was for. UNIQUE(parent_id, name, host_id) is the clever bit: the same attribute path can be specialised per host without a separate tree. description, category and enabled are unmaintained — the human-annotation layer on top of the AST never materialised.

7c. Deployment: three generations

Generation 1 — deployment_* (8 tables). deployment_history (290 rows) and deployment_targets (10) are real and feed the deploy ingest adapter. deployment_cache (4) / deployment_cache_stats (12) / deployment_health_checks (3) / deployment_notifications (4) / deployment_triggers (3) are lightly used. deployment_snapshots (0) and deployment_rollbacks (0) are empty — which means the rollback machinery (a three-way FK between from/to/rollback deployments, carefully modelled) has never executed.

Generation 2 — fleet_* (6 tables). A nixops4-shaped multi-machine deployment model: networks → machines → deployments → per-machine deployments, plus resources and local services. Five networks, five machines, five local services; zero deployments, machine-deployments or resources. Six triggers compute durations and allocate ports for a system that has never run. The summary output confirms it: all five fleet machines are "never deployed via templedb". Assessment: this is the clearest candidate for deletion in the schema — six tables, six triggers, four views, zero operational rows, superseded by 7a.

Generation 3 — what actually runs. system_deployments (251 rows, 2.3 MB — it stores full nixos-rebuild output per row) with an enforce_single_active_deployment trigger, plus nix_generations, plus deploy_stage_runs.

deploy_stage_runs — 1,077 rows

The write-path audit: each stage records input_hash → output_hash so the pipeline file_set → vcs_commit → materialize can be verified end to end. 626 / 261 / 191 runs respectively, zero failures, zero left open — and deploy_stages_have_no_stale_runs is green, which migration 112 earned by closing the orphans. But prev_stage_run_id, the column that would actually chain the stages into a verifiable sequence, is 100% NULL. So the table records three independent stage logs rather than one provenance chain, and no stage after materialize (push, nix build, switch) is instrumented at all. Future: populating the chain pointer and adding a push stage would make "did the bytes I wrote reach the deployed binary?" a single query — the question the deployed_build_matches_db doctor check currently answers by probing the filesystem.

7d. Nix metadata — mostly empty

nix_eval_cache (0), nix_cache_entries (0), nix_project_paths (0), nix_env_sessions (0), nix_environments (1), nix_service_metadata (1), nix_flake_metadata (3), nix_configs (2), nix_flake_validation_history (11). Three substantial designs — a binary-cache server (nix_cache_entries stores pre-rendered .narinfo), an evaluation cache keyed on flake+attr+input hash, and per-project dev environments — are built and unused. The eval cache in particular would be valuable given how often this project rebuilds; it has never recorded a hit.

9. Secrets, variables, and the rest

Three generations of environment variables

environment_variables (60 rows) is current: scoped global | project | nix_env | tag with value_type ∈ (static, compound, secret_ref) and a template column for interpolation. Three views (env_vars_view, project_env_vars_view, compound_values_view) project the old flat APIs out of it — the same retire-a-table-as-a-view pattern used for commit_files, and it works. env_vars (0) and project_env_vars (0) are the superseded originals, still present with live FKs.

Secrets — 52 blobs, 5 keys, 53 assignments

secret_blobs holds age-encrypted bytes; encryption_keys models Yubikey / filesystem / age recipients with PIV slot, physical location, and a revocation lifecycle that is correctly one-way (is_revoked separate from is_active, with revoked_at/revoked_by/reason); secret_key_assignments is the M:N that lets one secret be decryptable by several keys. encryption_key_audit (11 rows) logs every add/remove/test/rotate with a trigger that bumps last_used_at. This subsystem is small, complete, and the only one in the schema with a properly modelled revocation path.

cr-sqlite replication — 8 CRDT tables + 19 shadow tables

Eight sync_* tables are cr-sqlite CRDTs with per-column clocks: sync_entities (4,868), sync_relations (5,803), sync_vcs_commits (871), plus branches, projects, system_config, nixos_config, environment_variables. They are projections of the main tables, kept current by seven hand-written triggers on entities and relations (_sync_fleet_ins, _upd, _del, _unfleet), filtered by sync_scope = 'fleet' so machine-local facts never replicate. The CRDT tables are keyed on (kind, external_ref) rather than integer id — correct, since autoincrement ids cannot merge across sites.

The operational hazard is the one memorialised in the crsqlite_extension_loads doctor check: if the extension fails to load, every write to a CRDT table raises no such function: crsql_internal_sync_bit, and because the triggers sit on entities, git ingest fails entirely. That is the 234-error window in §1. The check now exists. Replication itself has only ever had one peer; sync_scope is constant across the install.

Stratum-II code intelligence — effectively dead

code_symbols (12), code_symbol_dependencies (0), code_search_index (0, with an embedding column for a vector search that was never built), code_search_fts (empty FTS5), impact_transitive_cache (0), code_cluster_members (0), code_cluster_files (0) — but code_clusters itself has 318 rows, i.e. 318 named clusters with no members. The Symbol entities in the graph (20,916) have entirely replaced this layer. file_dependencies (129) and file_metadata (300) are the two survivors of the era and are still read by views.

Odds and ends

audit_log (1,737) — actor constant, single-user install. backup_history (104). graph_query_log (287) — logs which graph queries were run, which is the raw material for learning what the graph should index. prompt_templates (10) / project_prompts (12) with parent-version chains, but prompt_usage_log is empty so the usage-summary view is dead. project_tests (41) is a smoke-test spec (page/post/structure); test_runs has 4 rows and a commit_id FK added by migration 115 that would let a test run warrant a claim — the wiring §6 is waiting on. tags/project_tags: 1 tag, 0 assignments. project_domains (2) / dns_records (6). migration_history (21) tracks application SQL migrations per deploy target and is distinct from schema_version, which tracks TempleDB's own 90 applied migration files.

10. Defects found in this pass

10.1 — 378 MB of unreachable blobs, no collector (critical)

Of 12,512 content blobs totalling 489 MB, 8,741 blobs / 378 MB are referenced by nothing — not file_contents, not vcs_file_states (new or old hash), not vcs_working_state, not checkout_snapshots, not edit_intents, not sync_cache, not deployment_snapshots. That is 77% of blob bytes and 54% of the entire 700 MB database.

The mechanism is clear. file set writes a blob and repoints file_contents in place; the previous blob is only retained if a commit captured it in vcs_file_states. Uncommitted intermediate writes — which, given 978 edit intents against 1,118 commits, are a large fraction of all writes — leave their blobs stranded immediately. content_blobs.reference_count would detect this, except its two triggers fire only on INSERT/DELETE of file_contents and never on UPDATE, so the counter over-reports (4,263 declared vs 2,051 actual, wrong on 2,073 blobs) and cannot be used as a GC predicate. There is no storage blob gc subcommand — status, verify, list and migrate only — and no doctor check covers either the orphan count or the refcount drift.

Fix, in order: (1) add a blob_refcount_is_accurate doctor check computing the true count from the seven referent tables; (2) add an AFTER UPDATE OF content_hash ON file_contents trigger; (3) add storage blob gc with a retention window (blobs younger than N days are spared, since an orphan today may be committed tomorrow). Step 1 alone converts a silent 54% waste into a visible number.

10.2 — edit_intents never records the commit it landed in (high)

applied_commit_id is NULL on all 981 rows, including the 980 marked status='applied', so provenance intent <id> cannot complete the span it was built to traverse. It was never written because nothing could write it at the right time: file set creates the intent and marks it applied immediately (content lands in file_contents without a commit), and the commit that eventually records those bytes happens later, in a different process, through one of seven separate INSERT sites.

Correction. An earlier draft of this section also claimed base_revision was constant on all rows. That was true of the 888 legacy rows but not of the column: the write path was fixed on 2026-10-04 and every intent since carries a real base hash or 'new-file'. What survives from that claim is a smaller point — the unmaintained_columns_baseline row for it predates the fix and now suppresses a column that is maintained.

10.3 — related_readmes is a broken view (fixed, §12)

Migration 121 (121_drop_readme_index.sql) dropped the readme tables but left the related_readmes view behind. It references readme_topics, which does not exist; any query against it errors. SQLite does not validate view bodies at creation or at schema load, so this sat undetected. Fix: DROP VIEW related_readmes, and consider a doctor check that EXPLAINs every view once per run — cheap, and it catches this whole class.

10.4 — The FTS index stores a second copy of every file (low)

file_contents_fts is a default (content-owning) FTS5 table, so file_contents_fts_content holds 37 MB of text that already exists in content_blobs, alongside a 61 MB index. An external-content configuration would recover the 37 MB. Noted rather than urgent.

11. Where this should go next

Reclaim the file. (Tooling done — see §12; the reclaim itself is still pending an operator decision.) §10.1 is 54% of the database and the only item here with an order-of-magnitude payoff. Doctor check first, trigger second, GC third. Do it before the next backup cycle — there is already 1.5 GB of stale .backup_* copies in the data directory carrying the same garbage forward.

Close the intent span. (Done — see §12.) §10.2 converts the write path from "audited" to "verifiable". Combined with populating deploy_stage_runs.prev_stage_run_id, it would make the full chain — intent → commit → materialize → generation → deployed binary — a single recursive query, which is the thing the observer model has been building toward and has not yet reached.

Cash in claims. The epistemics are already correct in the DDL and the table has two rows. A warrant_kind = 'tests_passed_at_revision' checker plus the existing test_runs.commit_id FK would start auto-asserting warranted claims from work that already happens. This is the highest-leverage new capability available, because it is mostly already built.

Delete a stratum. The fleet_* family (6 tables, 6 triggers, 4 views, 0 operational rows) and the stratum-II code-intelligence family (code_symbols, code_symbol_dependencies, code_search_index, code_search_fts, impact_transitive_cache, code_cluster_*) are both superseded by things that work. Removing them would cut the table count by roughly 10% and remove two entire wrong answers to "where do I look for symbols / how do I deploy". The unmaintained_columns_baseline ratchet already demonstrates this project can retire things deliberately; this is the table-level version of the same move.

Resolve the SCIP question. 15,821 of 20,916 Symbol entities come from scip-typescript, sharing a unique namespace with 5,095 Python symbols and no authority discriminator in the key. Either make source_authority part of the Symbol ref encoding and keep the adapter, or retire it. The current state — an adapter that last ran 6 hours ago, owns 75% of a shared namespace, and has no phase doc — is the ambiguity the roadmap already flags.

Harden the cheap things. CHECK constraints on the 25 enum-shaped columns of vcs_commit_metadata; drop the seven dead project_files annotation columns and the two redundant parent columns on vcs_commits; drop the redundant UNIQUE(project_id, commit_hash); reconcile projects.project_type with project_category.

13. Method

Everything above was read from the live database at ~/.local/share/templedb/templedb.sqlite on 2026-10-06, via read-only SQL (sqlite_master for DDL, dbstat for physical sizes, direct counts for row totals) plus templedb summary, templedb reports list and the invariant_checks / ingestion_runs history tables.
