Migration plan: dual-write to log-based projection

Concrete migration for the recommendation in Q1 of the answers report. Today’s entity_counts_match_source_tables invariant (from the session recap that shipped it) catches dual-write drift; this report specifies how to eliminate the drift class entirely by moving to a single-write log-and-project pattern. Four phases (A introduce log, B shadow projection, C cut over, D replay/rebuild), ~2 weeks of focused work, reversible up to Phase C, zero adapter-code churn until then. Uses the existing invariant as the migration-time guardrail.

Where we are and what we’re moving to

Current state: dual-write

Every ingestion adapter writes twice, in one transaction: 

with tx:
    upsert vcs_commits (id=..., message=..., parents=..., ...)
    upsert entities (kind='Commit', external_ref=..., source_authority='git')
    upsert relations (from=commit, kind='parent-of', to=parent)

This works but is exactly the shape of failure that produced the file_contents orphaning bug seen twice this week: same content in multiple places, competing write paths, one path dropping the other’s row. The Q1 invariant catches drift after it happens. Fine as a guardrail; wrong as an architecture.

Target state: log-and-project

Adapters write once, to the typed table: 

with tx:
    upsert vcs_commits (id=..., message=..., parents=..., ...)
    -- AFTER trigger enqueues a projection job automatically

async worker:
    for each job in entity_projection_queue where processed_at is null:
        row = read source_table where id = source_row_id
        upsert entities / relations to match
        mark job processed

Typed table is authoritative. Entities/relations are a projection. Failed projections retry; the queue is durable. New consumers (search index, GUI, audit trail) can be added by draining the same queue without touching adapter code.

The four phases

Phase A — introduce the log alongside dual-write (~1 day)

Adds infrastructure without changing behavior. Fully reversible.

CREATE TABLE entity_projection_queue (
    id            INTEGER PRIMARY KEY,   -- monotonic ordering
    source_table  TEXT NOT NULL,
    source_row_id INTEGER NOT NULL,
    operation     TEXT NOT NULL CHECK(operation IN ('insert','update','delete')),
    enqueued_at   TEXT NOT NULL DEFAULT (datetime('now')),
    processed_at  TEXT,
    error         TEXT
);
CREATE INDEX epq_unprocessed
  ON entity_projection_queue(id) WHERE processed_at IS NULL;

Add AFTER INSERT/UPDATE/DELETE triggers on the typed tables that already have entities counterparts: vcs_commits, edit_intents, ast_builds, deployment_history, agent_sessions, project_files, nix_store_paths, nix_generations, fleet_machines. Each trigger writes one row to the queue.

Nothing else changes. Dual-write continues. But every write also produces an ordered log entry, giving us:

  • An audit trail immediately.
  • A safety net for reconstructing entities/relations if they ever get corrupted.
  • The substrate the next three phases build on.

Reversibility: Fully reversible. Drop the triggers and the queue table; adapters continue working.

Phase B — shadow projection (~1 week)

Build the projection worker; run it in parallel with dual-write; validate by diffing.

CREATE TABLE entities_shadow AS SELECT * FROM entities WHERE 0;
CREATE TABLE relations_shadow AS SELECT * FROM relations WHERE 0;
-- indexes matching entities/relations

The projection worker (src/services/entity_projector.py) reads unprocessed queue rows in id order, dispatches to per-table projection functions, writes to *_shadow. One projector per source table:

def project_vcs_commit(row) -> List[EntityOp | RelationOp]:
    # returns intended operations against the shadow tables
    yield UpsertEntity(kind='Commit', external_ref=row['commit_hash'], ...)
    if row['parent_commit_id']:
        yield UpsertRelation(from_ref=..., kind='parent-of', to_ref=...)
    ...

Run continuously. Every hour, diff entities vs entities_shadow (and relations). Anything that doesn’t match is either:

  • A projection bug — the projector didn’t reproduce what dual-write did. Fix the projector.
  • A dual-write bug — adapters wrote to entities in a way the projector correctly rejected. Fix the adapter. (This is the exercise finding real bugs; we should expect a few.)

The existing Q1 invariant (entity_counts_match_source_tables) is the top-level metric for this diff. Add finer-grained diffs per kind (entities_shadow_diff as a view) so we know which projector is lagging.

Iterate until the diff is empty for N consecutive days (suggest N=7). Longer is safer; the failure mode of “we cut over too early” is worse than the failure mode of “we ran validation longer than needed.”

Reversibility: Fully reversible. Drop the shadow tables and the worker; nothing has changed in the live path.

Phase C — cut over (~1 day)

The one irreversible step. Do it once the shadow diff has been empty for a week.

  1. Rebuild entities/relations from scratch using the Phase D machinery below (which we build first — see next section on ordering). Truncate entities / relations, walk every typed table, enqueue everything, drain. This validates that the projection covers every existing row, not just new writes. Takes ~30 seconds at current 12K entity scale.
  2. Rip entity/relation writes out of every adapter. Adapters now write only to typed tables. This is a mechanical edit — delete the paired upsert entities / upsert relations calls, keep the typed-table upsert and the trigger fires automatically.
  3. Retire the shadow tables. They served their purpose. Drop entities_shadow / relations_shadow.
  4. Keep entities_prev as a snapshot for one week. If a subtle bug surfaces, we can diff against the pre-cutover state to identify what changed.

Reversibility: Only via git revert of the adapter changes. Not truly irreversible — adapters can be reverted to dual-write — but doing so is a real deploy, not a config toggle. Hence the demand for empty diff for a week beforehand.

Phase D — replay/rebuild capability (~2 days, built before Phase C)

The acid test that the projection is truly log-based.

templedb entity rebuild --from-scratch [--kind Commit,Symbol,...] [--dry-run]

Steps:

  1. Truncate entities and relations (or the specified kinds).
  2. Walk each typed table, enqueue every row as an insert operation.
  3. Drain the queue via the projection worker.
  4. Report timing, row counts, any projection errors.

If this command works cleanly and produces the same entities/relations as dual-write did, the projection is complete. If not, we’ve discovered a place where derived state depended on order-of-events beyond what’s captured in the log — fix by encoding that dependency in the projection function itself.

Ships before Phase C because Phase C uses it. Order of implementation is A → B → D → C.

Reversibility: Always available. After Phase C, entity rebuild --from-scratch is also the fastest recovery path if entities/relations ever get corrupted.

Handling the existing 12K entities / 11K relations

Two options for what to do with the graph rows that dual-write built up over the past months:

OptionApproachTrade-off
A. Trust dual-write historyLeave existing rows. Only apply projection to new writes.Fast but you never validate the projection covers what’s already there. Subtle historical bugs stay hidden.
B. Rebuild from scratch at cutoverTruncate and rebuild via Phase D during Phase C. All 12K entities and 11K relations get re-derived from typed tables.Slower (~30 sec) but guarantees the projection is complete. Validates the code path Phase D formalizes. Recommended.
Why B is the right choice Phase D’s entity rebuild --from-scratch has to work anyway — it’s the recovery path for corrupted derived state and the confidence check that the projection is complete. Using it as the cutover mechanism means we exercise it under real conditions before we depend on it in an emergency. Same code, better tested.

Migration-time gotchas

Ordering

If contains(Commit, FileSnapshot) requires both endpoints to already exist as entities, the projection must process events in order. SQLite’s single-writer nature helps: enqueue order = commit order, so a monotonic id PK on the queue is enough. Worker processes strictly ascending.

Edge case: a relation from row R may reference an entity from row R (self-contained), row R−1 (dependency), or row R+1 (forward reference that arrives shortly). If forward references happen, either (a) the projector defers the relation and retries on the next queue drain, or (b) upsert the relation with a placeholder entity ref that gets resolved when the target lands. (a) is simpler; (b) is faster. Start with (a).

Idempotence

Every projection must be safe to apply twice. Use INSERT ... ON CONFLICT (kind, external_ref) DO UPDATE SET ... patterns. Then a crashed worker replaying its last batch is harmless. This is the same pattern the observation adapters already use for typed tables; extend to entities/relations.

Queue growth

Append-only means it grows forever. Retention policy: keep processed rows for 7 days as audit; then move to observations_archive (from Q2 of the answers report). Never delete outright — the queue is also the audit log of every fact-producing event, useful for “when did this entity change?” queries.

Trigger reliability

SQLite triggers fire in the same transaction as the source write. If enqueue fails (schema bug in the queue, disk full, etc.), the source write also fails — good for consistency, bad if it happens unexpectedly. Deploy the queue table well before the triggers; run trigger deployment behind a feature flag so it can be disabled without a code push if it causes problems.

Two adapters producing the same fact

Shouldn’t happen if the fact model is right, but if it does: ON CONFLICT (kind, external_ref) DO UPDATE SET observed_at=excluded.observed_at, source_authority=excluded.source_authority. Last-writer-wins with observation timestamp preserved. Divergence between adapters becomes visible via the adapter_version from Q3 of the answers report.

Long-running projections

Big changes (Phase D full rebuild, or a schema migration that touches many rows) can produce huge queue drains. Worker should process in batches with intermediate commits so it can resume after interruption. LIMIT 1000 per batch, commit, repeat until processed_at IS NULL count is zero.

What this closes and what it opens

Closes

  • The dual-write drift class. Q1’s primary concern. After Phase C, there is exactly one write path for any given fact; drift becomes structurally impossible for entity/relation content.
  • The “how do we add a new consumer” problem. Once the queue is the log, new consumers (search index, GUI, audit trail, external metric publishing) drain the same queue independently. No adapter changes required.
  • The “how do we rebuild if corrupted” problem. Phase D’s entity rebuild --from-scratch means derived state is always recoverable from typed tables. Same command handles corruption recovery, cutover, and validation.
  • The file_contents family of orphaning bugs — not directly, but the pattern is now established. file_contents and its blob layer could adopt the same log-and-project shape in a follow-up.

Opens

  • Projection worker as a new service. Something has to run continuously. Options: cron via systemd timer (simple, adds latency), long-running daemon (low latency, needs process supervision), inline on-request drain (no lag but adds request latency). Start with systemd timer at 1min interval; move to daemon if lag ever becomes user-visible.
  • The freshness telemetry surface. Once projections have observed_at lag, users will want to see it. templedb entity freshness or a widget in the GUI. Small work but worth doing before the lag becomes silently confusing.
  • Applying the pattern to file_contents. If file_contents becomes a projection over content_blobs and adapter observations, the cross-contamination bug family goes away entirely. Separate migration, same pattern.

Total budget and next step

~2 weeks focused development + 1 week monitored validation = 3 weeks calendar. Reversible at every step until Phase C. First concrete next step: land the Phase A migration (queue table + triggers) — it’s a single small PR, ships value immediately (audit trail), and unblocks Phase B without committing to anything downstream.

The Q1 invariant that landed today is the guardrail this migration was waiting for. Building the projection without a way to check it against dual-write would be dangerous; building it after the check is in place is straightforward. Good sequencing.
