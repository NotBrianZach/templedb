Thirty-three decisions: porting summary and the first write

One day of work on templedb-rust, recorded as decisions rather than as a changelog. Five commits took the port from a read-only subset to one with an opt-in write path, and almost none of the interesting work was SQL. It was choosing, repeatedly, between matching an implementation that is sometimes wrong and being right in a way that breaks a diff. Four of the thirty-three were not judgment calls at all — they were mistakes, and they share a cause with a fifth error this report made about itself.

Six rules, not one

An earlier revision of this report opened with a single rule and called it "the rule most of them follow". The rule is right and the claim was not. Checked against the thirty-three, it governs five rows in the tables below and three cases in the prose — the output-fidelity cluster — and on the rest it is either silent or actively wrong. What follows is the corrected account: one rule about bytes, and five more that were doing the work it was being credited for.

1. Output fidelity — and only output

For bytes on stdout: copy Python's behaviour if it is deterministic, defects included. Fix it if copying would mean reproducing a crash or an unspecified result.

This is why the port reproduces a misaligned column, an escape pair wrapping nothing, and idle Noned, but not project show's TypeError. The cost is code that looks wrong on purpose: three times today the deliverable was a test whose only job is to stop a future reader from fixing something.

2. Unspecified is not a behaviour

Part of the first rule as originally written, and it deserves to stand alone because it decided four cases by itself. An ORDER BY with ties and a LIMIT does not have a behaviour to be faithful to — there is nothing there to copy, so "copy it" is not an available option and the only question is which total order to impose. The port adds a tie-break and changes nothing else. entity trace, entity search, invariant_results and the reconciliation listing all went this way.

3. Interface: accept a flag only if the thing it names exists

Nothing to do with output, which is why the first rule could not reach it. vcs log --published is accepted because it selects behaviour the port has; --session is rejected because it promises session inclusion the port cannot produce, and search content --no-fts is rejected for the same reason. A no-op flag is only harmful when the thing it names is absent.

4. On a write, diverge toward safety

Where a reader's mistake costs a second and a writer's overwrites a file, the costs are asymmetric and parity loses. Python's file set fuzzy-matches the project; this one demands an exact slug. The writer is also opt-in and points at a disposable database. Each of those is a deliberate failure to match, and the first rule has no opinion on any of them because none is about bytes.

5. On a write, the refusal is the output

The rule that was missing, and its absence is why the first version of file set shipped with exit 1 for every refusal where Python uses 2 and 3. Exit codes are not stdout, so rule 1 said "do not care" — and for a read command that is nearly true. For a write it is backwards: the command prints almost nothing, so the status and the message carry the whole contract. Ranking them with output rather than below it is the correction.

6. Internal consistency beats external fidelity

When copying Python would make the port inconsistent with itself, do not copy. project list's filters are the clean case: Python runs a separate query under either flag, so its filtered and unfiltered output disagree about the same project's file count. Matching that would have meant importing a contradiction, so the filters add a WHERE and change nothing else. search content is the same rule at larger scale — the two full-text engines disagree on a quarter of the hit set, so there was no single behaviour to be faithful to and matching one backend would have meant diverging from the other.

None of the six covers the NUL escape, and that is worth noticing: it was not a parity question at all. Both implementations read the same SQLite; the conflict was between two storage engines. It was decided on whether the verification instruments survived the choice, which is a seventh consideration that applies only to decisions with no Python side to copy.

Output fidelity, in summary

summary is the first command in the port that is not a pure function of the database — it reads the wall clock, the hostname, getppid(), systemd and TEMPLEDB_SESSION_ID alongside the rows. Its observation layer landed three days earlier; this was the rendering.

The unported-pane decision is the one worth dwelling on, because silence would have been faithful. Python's agent-fleet pane vanishes when its tables are absent, and the port's are. But a missing systemd pane reads as "no failed units" and a missing fleet pane reads as "nothing waiting on you", and a wrong number is better than a confident absence. That is why the port prints two lines the original never emits.

Verification, once the byte diff stops working

The port's method is a byte diff of stdout against the Python implementation, across fifty invocations. That method has a precondition nobody had to state while everything was read-only: both implementations see the same input, and both are functions of it. summary breaks the second half; a write breaks the first. Three new comparison stages came out of that, all the same move — when whole stdout cannot be diffed, diff the sub-unit that carries the meaning.

DecisionChoseOverCost
summary Compare pane by pane One sweep row A bespoke stage
Retry logic Per-pane agreement across attempts All panes must agree before stopping Subtler; and necessary — ingest writes mid-sweep
Flag drift Parse both --help outputs Nothing: the sweep is structurally blind Parsing help text
project list filters Compare slug sets Byte diff — the format diverges A third bespoke stage
Writes Cross-read through the real reader SQL written for the test None — it caught a bug in the test
All three stages Sabotage-test each one Trusting them Time, and it was repaid immediately

The flag-surface stage deserves its own note, because it closed a gap the README had carried for a week as unverifiable. A diff of outputs can only compare flags that both implementations define — a flag one side does not know is never passed to the other — so a missing flag stays invisible until a caller hits it. Comparing the surfaces directly asks a different question: can the same command line be typed at both? It found four undocumented divergences on its first run, across three commands that the sweep was reporting as byte-identical. Three of the four are now closed.

The uncomfortable part: two of the three stages were wrong when first written, and both failed in the direction that blames the port. The filter stage looked for table rows under a dashed rule that only Python prints, so the port's output parsed as empty and six of eight comparisons "failed" against correct code. The summary stage required every pane to agree before it stopped retrying, so one continuously-churning pane consumed the attempts and the rest were judged against whatever the last capture held — it reported a false failure the first time an ingest ran during a sweep. A check that cannot fail on demand is not evidence of anything, and one that fails for its own reasons is worse than nothing.

The decision with no good answer

SQLite TEXT may contain U+0000. Postgres text may not, at the protocol level, and no encoding or cast changes that. One row in the live database has one, and it is not a misclassified binary: bza/frontend/lib/suggest/normalize.ts contains .join('\0'), which is an ordinary thing for a TypeScript file to do. The column really is text. There is nothing upstream to fix. It appeared between two mirror runs on the same afternoon, which is how a copy that had worked all week started failing.

OptionWhat it breaks

I expected to decide this on fidelity. What actually decided it was statediff's cross-backend digest: two of the four options change it, and that does not fail a test so much as destroy the instrument. A digest that needs a special case for a known-accepted difference has stopped being a comparison. Escaping is the only option that keeps it equal, and for a structural reason — the digest hashes rows read through Store, and the unescape happens inside Store's Postgres implementation.

DecisionChoseOverCost
Escape marker U+0001, itself escaped A "rare" character assumed absent None — see below
Scope Escape every text column content_text only None; a rule with exceptions gets one missed

Escaping the introducer is the part that is easy to get wrong, and measurement is what settled it. The tempting shortcut is to pick a character that "never appears" and use it as a marker. In this corpus that would have been false: content_blobs has 1 row containing U+0000, 2 containing U+0001, 2 containing U+0002 and 4 containing U+001F. Control characters are not hypothetical here. Escaping the marker makes the transform injective however often it appears, so the marker's rarity buys small diffs rather than correctness — 4,715 of 4,718 text rows are byte-identical in the mirror, and three are not.

The mirror, and what a write path needed from it

DecisionChoseOverCost
ANALYZE After the commit; failure non-fatal Inside the transaction; fatal Statistics can lag a run
Identity sequences setval inside the transaction After the commit None — stale sequences break the first write
id columns GENERATED BY DEFAULT GENERATED ALWAYS Must setval after every mirror

The two halves of that first pair look inconsistent and are not. Statistics are not part of the copy's atomicity: a mirror that committed is correct whether or not it has been analysed, so a failure there must not report a successful copy as a failed one. Sequences are the opposite — a mirror whose sequences are behind is not merely unoptimised, it is one that the first write breaks on a primary-key collision. Same function, different atomicity requirements.

The id decision exists because the read subset never needed it. The schema was built for mirror, which copies rows that already have ids, so every id is a plain bigint PRIMARY KEY with no default and a writer has nothing to generate one from. BY DEFAULT rather than ALWAYS because mirror must keep supplying explicit ids, and ALWAYS rejects its COPY outright.

--published and --session look symmetrical and are not. --published names behaviour the port has — it is the default — and it is the only one of Python's three views that needs no session, so a script written vcs log --published exiting 2 here was the opposite of compatibility. --session asks for the current session's unpublished commits, which the port cannot produce; accepting it would promise session inclusion and silently deliver none. The test that separates them: a no-op flag is only harmful when the thing it names is absent. That is the same test search content --no-fts fails.

The project list filters are a smaller version of the fidelity question. Python runs an entirely separate query under either flag — COUNT(DISTINCT pf.id) over all files rather than active ones, a different line source, a different sort — so project list and project list --nix-only can report different file counts for the same project, from the same database, in the same second. The port's filters add a WHERE and change nothing else, which is the property that makes a filtered list worth believing. All eight filter combinations select exactly the projects Python selects.

The write path: safety over parity

Every decision here is a deliberate non-parity choice, and each is justified the same way: the cost of being wrong is asymmetric.

DecisionChoseOverCost
Writer shape PgWriter outside Store Widening the trait None; readers keep their guarantee
Target Scratch Postgres The live SQLite Not a drop-in for Python
Configuration A separate TEMPLEDB_WRITE_URL Reusing TEMPLEDB_URL Two variables to set
Default Opt-in environment variable On by default Not a drop-in
Project lookup Exact slug Fuzzy, as Python does Diverges — stricter
Refusal codes Reuse 2 and 3 Invent new numbers Each code means two things (Python's doing)
Mojibake guard Fire on an increase Fire on presence None — corrupt files must stay editable
--verify Fresh transaction after the commit Inside the writing transaction A round trip; inside, it could not fail
Write tests #[ignore] + just write-test Requiring a server for cargo test A gate people can forget
sha2 Pin to the lock file (0.11) Hand-rolling sha256 One declared dependency

Two of these are worth expanding. Exact slug resolution inverts the port's own convention — every read command takes a fuzzy name, and so does Python's file set. But a reader that guesses wrong wastes a second and a writer that guesses wrong overwrites a file, and the scoring function has two known bugs wrapped around it. The slug is also resolved inside the write transaction, against the write target, because the reader and the writer point at different databases; resolving against one while writing to the other would be a genuinely nasty class of bug.

--verify on a fresh transaction is the difference between a check and a ritual. Inside the writing transaction it reads its own uncommitted effect and can only ever agree. The gap the flag actually covers is narrow — the write already reported success, so the only thing left is something else having changed the row — and only a post-commit read can see that. The integration test reverts the row with its own UPDATE before checking, so it is a test that can fail.

The refusal codes, which are the contract

This one started as an error. The first version of file set returned exit 1 for every refusal; Python returns 2 for an --if-match mismatch and 3 for a mojibake refusal. For a read command that would be a nicety. For a write it is the interface: the design document lists refusal parity as one of three techniques replacing the byte diff — "every guard refuses with a specific exit code and message; for a write, the refusals are the contract" — and closing the error-exit gap had been made a precondition for this work. Shipping a writer whose refusals are indistinguishable from a missing database undoes that precondition.

The fix reuses numbers the read commands already use for other meanings, which looks sloppy and is Python's arrangement rather than this port's invention. A malformed --if-match argument still exits 1 — also Python's split: a bad flag is bad input, a mismatched one is a conflict.

Worth revisiting, and when

ItemTrigger
The NUL escape — probably becomes BYTEA Cutover. With no second backend there is no digest to preserve, and the escape would otherwise become how the canonical bytes are stored
Drop the write opt-in When file set carries all seven guards
The --session rejection The least confident call of the day; accept-and-warn is arguable

The first of those is the one that matters. It was taken as a mirror decision, where the cost is three rows looking odd in a psql session and nothing reading through the crate noticing. Postgres-as-primary is decided rather than hypothetical, and at that point the escape stops being a storage detail and becomes the canonical representation, visible to every non-Rust consumer. That is a materially larger commitment than the one actually made, which is why it is recorded with an expiry date instead of being inherited by default.

The pattern in all five is the same: trusted a summary over the source. The README over the design document; an earlier statement of my own over re-reading; a stage's output over checking the stage. The specific remedy was reading the primary document, where the SqliteWriter recommendation in the body had been reversed two sections later by the same report's own 2026-10-16 decision.

The fifth is the most pointed, because this report committed the error it was written to diagnose. One rule was easier to state than six, so it got stated — and nothing checked it against the cases it claimed to govern until someone read the report and asked whether it held. It mostly did not. A summary that has not been tested against its source is a hypothesis, and this one was wrong in the usual direction: too confident, too tidy, and silent about the places it did not reach.

The general remedy is a convention this project already has and which this is a case study in: that report says it will "record what it changes rather than quietly leaving the body of the document wrong." It did exactly that, and the README still quoted the stale half for five days. A document's body goes stale while its conclusions keep getting cited — so a superseded recommendation needs to be struck through where it sits, not only corrected somewhere later.
