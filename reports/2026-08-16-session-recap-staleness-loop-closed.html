What I noticed about my process

Design-before-implementation split paid off keep doing

Writing the design report before touching code meant the implementation arrived with phases pre-scoped and gated. Each phase committed separately, so if any broke, revert would be one commit — not a big refactor. This is the second session (after the tmux one) where a design report preceded the code; both times the implementation went smoother than sessions that started coding immediately.

Rule to keep When a task has more than one plausible design axis (e.g. 9 options for staleness, 3 tiers for read-only viewing), write the design first. It costs one report but produces a shippable plan the user can redirect before implementation cost is sunk.

Bootstrap-loop debugging on Phase 1 notice

Testing Phase 1's dev-mode logic hit a chicken-and-egg: the new code is in the checkout, but the profile-installed templedb loads from nix — so my checkout-priority logic can't kick in without already having checkout-priority. I traced this for a minute, realized the situation, and pivoted to testing via direct Python invocation with PYTHONPATH pointing at the checkout.

Meta-observation The fix I was shipping was exactly the mechanism that would have prevented this loop. So the debugging was inherent — you can't test the fix from within the broken world it's fixing without bootstrapping around it. Naming this explicitly so I don't waste time next time the pattern shows up (which is inevitable — anything that changes invocation behavior has this shape).

Fast-then-real testing pattern keep doing

Verified logic via direct PYTHONPATH="$CHK:$NIX" python3 -c "..." first — fast, three-second turnaround, four scenarios covered. Then did the real deploy + real templedb invocation to prove end-to-end. This split matters: the direct-Python test told me the algorithm was correct before I paid the 90-second rebuild cost. If the direct test had failed, I would have iterated on the algorithm without any rebuilds in between.

Sequential phase commits keep doing

Three commits (design, Phase 1, Phase 2+3), each focused. Contrast with earlier sessions that bundled unrelated changes into "kitchen sink" commits. Reviewability is objectively better and reverts are scoped. Cost: three commit messages instead of one. Worth it.

Meta-meta: what actually made this session ship

The self-referential test worked

Last session's recap ended with: "If neither phase ships and a third recap flags the same pattern, that's a signal the problem isn't cost-of-implementation, it's priority." Reading that line at the start of this session was decisive. Not because it was a rule — I could have ignored it — but because it forced a binary choice: fix it, or accept I don't care. I chose fix. That's a working design pattern for self-generated pressure: give future-me an explicit escalation clause rather than a vague "should probably…".

The user opened the door

I could plausibly have written a design report and then punted on implementation ("here's a plan, want me to build it?"). I did, in fact — the design report ended with "want me to implement or leave standing?" User said "lets do the three phase path". The escalation was invited, not self-taken. Two-sided handshake beats unilateral action for this class of infra change.

Design-report-as-decision-record is composable

The design report is now sitting in reports/ alongside the implementation commits. If someone six months from now asks "why does the wrapper invoke _launcher.py instead of -m cli?", the answer isn't buried in a commit message — it's a 17KB HTML doc explaining the nine options considered, the phasing, and the non-goals. That's better documentation than any commit message could carry.

Two-recap patterns are real signal

Both the last recap and this one had recurring-pattern callouts — the nix-profile issue in the last, "bootstrap loop when testing infra changes" in this. The first is now closed. The second is now named. I'd bet money the second one shows up in the next recap too, because infra-change-testing is inherently bootstrap-loop-shaped. That's fine — naming it is what a recap format is for. What matters is whether naming it three times escalates to fixing it once.
