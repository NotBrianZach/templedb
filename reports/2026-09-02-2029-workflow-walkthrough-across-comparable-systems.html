Workflow walkthrough across comparable systems: where TempleDB earns its keep

Written after Phase 0 shipped (templedb file where + gitignore-aware materialize). Now that the initial observer-plan tranche is proving out, this report pauses to ask the harder question the design docs deferred: does TempleDB actually fill a gap no existing tool occupies, or is it a slightly-different way of doing what already exists? Walks each of the six workflow use cases from the workflows before and after report through nine comparable systems (Backstage, Sourcegraph, Terraform, Fossil, LSP, Nix, Datomic, Obsidian, Bazel) and asks: for this workflow, would that tool solve it, and if not, why not? The honest answer per workflow is different. Some are genuinely novel; some are redundant with tools you might already have; some are combinations that don’t exist together anywhere else. Ends with a matrix, an honest niche statement, and the reiterated next-steps queue.

Redundancy is not necessarily bad — for C we adopt SCIP rather than reinvent, and for E we accept git+nix as the base and layer TempleDB above. The novel four are where TempleDB earns its distinctive keep.

Workflow A — multi-agent parallel refactor

Three agents in three sessions rename foo_bar → foo_baz across templedb, bza, and woofsledger. Need to see each agent’s proposed changes, cherry-pick or reject, apply safely without stomping.

Backstage No editing surface at all. Read-only catalog of what exists.
Sourcegraph Read-only; can help you find the callsites (batch changes exist as an add-on but write back to individual PRs, not multi-agent staging).
Terraform state Single-writer state file with locks. Multi-agent means multi-lock-contention, not multi-intent-queue.
Fossil Has branches like git. Each agent gets its own branch; merge conflicts at commit time. No native concept of “proposed but not yet applied.”
LSP Per-editor, in-process. Refactor lives in one editor session; no cross-session coordination.
Nix Not applicable.
Datomic Could model intents as datoms (transactions), but no UI or CLI ergonomics for it.
Obsidian Not applicable to code editing.
Bazel Not applicable to editing.
TempleDB Session-scoped VCS staging is already implemented; EditIntent abstraction (Phase 2) formalizes the dry-run and cherry-pick surface.
Verdict Genuinely novel. No existing tool has intent-queue semantics for parallel agent-driven edits. The closest thing is git branches + PRs, which introduces significant overhead per agent and has no dry-run/cherry-pick vocabulary at the intent level. This is one of TempleDB’s strongest niches.

Workflow B — deploy archaeology ("was this bug in prod?")

The question surfaces after every regression: given a bug you just found, was it in the deployed build, and if so, since when?

Backstage Partial — if the org configured service→deploy relations in the catalog. Usually manual and stale.
Sourcegraph Knows source but not deployments. Can’t answer.
Terraform state If deployment IS a Terraform resource, history is in state. Rare for app-level deploys.
Fossil Has commit history; nothing about deployments.
LSP Not applicable.
Nix Partial — /run/current-system is a symlink to the running store path; nix-store --query --deriver traces to a derivation; but the derivation-to-source-commit link isn’t automatically preserved.
Datomic If you were disciplined about writing deploy events as datoms, yes.
Obsidian Not applicable.
Bazel Knows build graph; not deploy history.
ArgoCD / Flux (bonus comparable) Yes — GitOps loop records commit→deploy pairs. Requires GitOps workflow adoption.
TempleDB Yes, once Phase 3 lands: Deployment → StorePath → Derivation → Commit → FileSnapshot → function-symbol as one graph query.
Verdict Redundant with a full GitOps setup, novel otherwise. If you already run ArgoCD or Flux and have the discipline to keep the loop clean, deploy archaeology is solved. If you don’t (which is most personal setups and many small teams), no existing tool spans the code→build→deploy→symbol chain cheaply. TempleDB earns its keep for the non-GitOps case, which is most of the world.

Workflow C — cross-project impact analysis

Renaming a function in a shared library. Which projects call it?

Backstage Catalog knows service→service dependencies at the config level, not code level.
Sourcegraph Yes, this is literally its use case. SCIP-backed “Find references” across every indexed repo.
Terraform state Not applicable.
Fossil Not applicable at the semantic level.
LSP Yes but single-project. Multi-project requires either monorepo-aware LSP or manual project-per-project search.
Nix Not applicable.
Datomic Only if you ingested the code facts as datoms.
Obsidian Not applicable to code.
Bazel Partial — knows target-level deps, not symbol-level. “Which binary depends on this library” yes; “which function calls this function” no.
TempleDB Yes via Phase 4 SCIP adoption; already partially via graph who-uses for languages the current scanner handles.
Verdict Redundant with Sourcegraph. If you self-host Sourcegraph or use their SaaS, this is solved. TempleDB’s move here is to adopt SCIP so it consumes the same facts Sourcegraph does, rather than reinvent semantic indexing. The value TempleDB adds on top is combining code facts with deploy/agent/decision facts in one graph — the cross-domain query is what neither tool alone can do.

Workflow D — broken deploy investigation

3am, a deploy went sideways. You’re trying to figure out where reality diverged from what the DB thinks.

Backstage Shows deployment status if the catalog is fresh. No reconcile.
Sourcegraph Not applicable.
Terraform state Yes for infrastructure — terraform refresh is exactly this. Reports drift between recorded state and actual cloud state. Doesn’t extend to app-level (NixOS generation, running processes, secrets on disk).
Fossil Not applicable.
LSP Not applicable.
Nix Partial — nixos-rebuild --rollback reverts, doesn’t explain drift.
Kubernetes controllers (bonus comparable) Reconcile loop is exactly this pattern for pods.
Datomic Not without ingest adapters.
Obsidian Not applicable.
Bazel Not applicable.
TempleDB Yes via templedb doctor entities --host X (Phase 3). Extends the Terraform pattern from infra to NixOS + processes + secrets + generations.
Verdict Novel for the NixOS-personal-server niche. Terraform solves this for cloud infra; Kubernetes solves it for containers. Neither speaks NixOS generations or per-machine on-disk state. TempleDB’s doctor entities is a straight port of the reconcile pattern to a domain nobody else covers. Load-bearing insight: this MUST ship in Phase 3, not later, or TempleDB slips into the “coordinator without reconcile” anti-pattern that has bitten every metastore.

Workflow E — new contributor onboarding

Someone wants to work on templedb from scratch. Or future-you on a new machine.

Backstage Yes, this is a headline feature — Software Templates + Software Catalog + TechDocs = one-stop “here’s our world.”
Sourcegraph Not applicable; assumes you already have the repo.
Terraform state Not applicable.
Fossil Single-file clone is unusually clean.
LSP Not applicable directly; assumes editor + project already exist.
Nix Yes for build environment reproducibility. nix develop gives you every dep pinned. Doesn’t document intent or architecture.
Datomic Not applicable.
Obsidian If the docs are in an Obsidian vault, yes at the docs level.
Bazel Deterministic build; not architecture docs.
TempleDB Would look like Backstage-for-one: templedb project list shows every project; templedb graph explain project/X gives you the entity/relation map; reports/ archive gives you the design history. Currently under-documented, mostly latent.
Verdict Redundant with git+nix in the small case; approaches Backstage territory in the multi-project case. For one project, git clone + nix build wins. For a developer’s whole ambient world (5+ projects, several machines, custom NixOS config), TempleDB is closer to Backstage in spirit and could genuinely be the “here’s the map of everything” onboarding surface no other tool provides at personal scale.

Workflow F — report / decision archaeology

“Which of these design reports actually got implemented?”

Backstage TechDocs feature stores docs but doesn’t link them to commits programmatically.
Sourcegraph Can search across docs and code, but no explicit motivate/implement relation.
Terraform state Not applicable.
Fossil Wiki + commits in one DB; could link by convention but no first-class relation.
LSP Not applicable.
Nix Not applicable.
Datomic If modeled as datoms yes; no product does this out of the box.
Obsidian / Roam Yes, this is what PKM does — bidirectional links let you jump from Decision to referenced Commit note. But the “commit” is a plain-text link, not a live git object.
ADRs (bonus comparable) Filesystem convention (docs/adr/NNNN-title.md). Human-readable, not queryable, no reverse index.
Bazel Not applicable.
TempleDB Yes via Phase 3 entity graph: Report → motivated → Decision → implemented-in → Commit as a first-class query. Combines Obsidian’s link semantics with live-code awareness.
Verdict Genuinely novel. Obsidian gets close for the docs-linked-to-docs case; ADRs get close for the human-readable case; neither is queryable across “code that was written to implement decision X.” TempleDB’s entity graph makes this a two-line CLI query. This is one of the more interesting workflows because it’s something a lot of teams want and no one has really shipped.

Workflow G — this session (meta example)

The workflow that produced this report: agent-driven editing, testing, snapshotting, deploy prep, and report shipping across multiple back-and-forth iterations with a human.

Backstage No editing or agent surface.
Sourcegraph Read-only.
Terraform state Not applicable.
Fossil Provides SCM but no agent runtime, no MCP, no report registry.
LSP Provides editor semantics but no persistence or agent coordination.
Nix Provides build but no editing loop.
Datomic Provides DB but no CLI/agent glue.
Obsidian Provides doc storage but no code awareness.
Bazel Provides build but no editing / reports / agents.
TempleDB The only tool that spans agent + edit + snapshot + deploy prep + report shipping in one integrated surface.
Verdict Uniquely combined. Each individual capability exists in some tool; the specific combination doesn’t exist elsewhere. This is the most defensible thing about TempleDB — not any one capability, but the specific stack of capabilities converging on a single developer’s workflow.

The honest niche

Where TempleDB earns its keep
  • Multi-agent parallel edit coordination — session-scoped staging + intent queue is unique.
  • Report↔code archaeology — design decisions as first-class graph entities, queryable across the code they motivated.
  • NixOS-native drift reconcile — Terraform-refresh-shaped tool for personal NixOS setups.
  • Meta-session workflows — agent + edit + snapshot + deploy prep + report shipping in one surface.
  • Cross-domain graph queries — the “which motivating decision led to the code running on this machine” class of question is TempleDB’s alone.
Where TempleDB is redundant
  • Cross-project semantic code search — Sourcegraph is better if you have it. Phase 4 mitigates by adopting SCIP rather than reinventing.
  • GitOps-shaped deploy archaeology — ArgoCD/Flux solve it if you’re disciplined about the pipeline.
  • Small-team software catalog — Backstage exists and is more polished, if you’re at that scale.
  • Static analysis at the sub-language level — language-specific tools (rust-analyzer, gopls) are deeper and always will be.
The honest scope statement TempleDB is a personal knowledge graph for software engineering, sized for a single developer with several projects, custom NixOS infrastructure, and AI agents in the loop. The specific combination of scope + scale + agent integration doesn’t exist elsewhere. Individual capabilities are redundant with best-of-breed tools; the integration is not.

What Phase 0 changed about this picture

Phase 0 shipped two tiny things (file where, gitignore-aware materialize) and one non-shipped item (TEMPLEDB_DEV_MODE_EMACS). Concretely small; conceptually load-bearing. Together they ratified the observer identity in code, not just in reports: TempleDB now diagnoses drift instead of trying to make drift impossible, and materialize respects the working tree instead of asserting authority over it. The five phases that follow build on that stance rather than fight it.

Next steps, re-iterated

Nothing about the plan changes; the reflection confirms rather than perturbs. Priorities in order:

  1. Finish Phase 0. The TEMPLEDB_DEV_MODE_EMACS symlink escape hatch for the Spacemacs layer. ~1–2 hours. Closes the tranche and removes the last known daily-friction item where the Emacs layer stays stale relative to the checkout.
  2. Phase 1 — SourceSnapshot. Weeks 3–4. Reframe file_contents as immutable historical observation via a view; add store_path → source_snapshot provenance edges. Groundwork for the graph model.
  3. Phase 2 — EditIntent. Weeks 5–6. New table + CLI (templedb intent {create, list, apply, cancel, dry-run, revert}). Makes Workflow A tractable end-to-end.
  4. Phase 3 — entity/relation model + doctor entities. Weeks 7–10. Biggest phase. This is where TempleDB earns the “semantic fabric” identity across workflows B, D, F, and G.
  5. Phase 4 — SCIP + ingestion discipline. Weeks 11–13. Delegates workflow C to the SCIP ecosystem; formalizes each authority’s ingestion algebra as a first-class concept.
  6. Phase 5 — retire authority-over-source. Weeks 14–16. Vocabulary shift, docs update, FUSE removal from the mental model.

The recommended immediate next step is item 1: close Phase 0 with the Emacs symlink hatch. It’s small enough to do inside a single session, completes the observer-plan tranche, and gives a natural pause point to see how the Phase 0 fixes hold up in a few weeks of daily use before committing to Phase 1’s architectural work.
