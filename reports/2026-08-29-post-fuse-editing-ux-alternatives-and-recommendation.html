Post-FUSE editing UX — alternatives and recommendation

Assessing replacements for the ~/temple/ FUSE mount ahead of a hard removal. Written 2026-08-29 during a bza pruning session that surfaced FUSE-adjacent regressions (mount-view truncation hiding ghost records, hook fragility, and the standing write-truncation risk).

Why remove FUSE at all

FUSE was pitched as the low-friction path for interactive editing: vim ~/temple/bza/foo.ts and save. In practice, three categories of pain keep recurring:

  • Silent write truncation. Large piped writes and Edit-tool operations through FUSE occasionally truncate mid-file with no error — the DB write reports success and file cat returns the truncated content. Only a byte-count or parse check catches it. Recorded as an unfixed hazard in templedb-write-broken memory.
  • Truncated mount view. The FUSE mount surfaces only files with retrievable content in file_contents. Ghost records (metadata rows without a current blob) are invisible via FUSE, so ls ~/temple/bza/ silently under-reports what the DB actually tracks — masking real problems (see task #9).
  • Split brain in agent workflows. Agents/hooks reflexively redirect writes to FUSE paths (a Write-tool hook does exactly this), while CLAUDE.md tells tools to use the CLI. The two paths interact in confusing ways (session fanout, cache invalidation races). Every project's CLAUDE.md ends up documenting the tension.

Removing FUSE deletes the whole category. But it also removes the one workflow FUSE is genuinely good at: launch your editor at a path, edit, save. This report evaluates replacements for that UX.

What we're solving for

The current interactive editing surface has three shapes:

  1. One-shot edit. "Change one line in one file." templedb file edit already covers this via $EDITOR round-trip.
  2. Session edit. "Open 3–10 files, edit them over an hour, save intermittently, commit at the end." This is what FUSE is best at today and what the alternatives compete on.
  3. Multi-file navigation + LSP. "Jump-to-definition, rename symbol across files, run tests in-editor." FUSE only kind of supports this — LSPs work but startup is slow, and any tool that walks the tree hits the truncated-view problem.

Alternatives

1. templedb file edit only Keep

Ships today. Opens the DB blob in $EDITOR, writes back on save. Fine for one-shots, useless for anything requiring cross-file navigation. Keep as the primary path for shape #1.

2. Materialized checkout + templedb commit Keep

templedb project checkout <slug> /tmp/work --writable gives a real directory with full LSP/navigation. Edits happen normally. templedb commit <slug> /tmp/work diffs and commits. This is what the tool workflow already documents. Promote to the recommended path for shapes #2 and #3. Downsides: the workspace-diff hazard (deletion sweep) exists, and per-session checkouts fill /tmp unless pruned.

3. templedb watch daemon (new) Build med

Userspace file watcher (inotify on Linux) over a mirrored directory. Any write triggers templedb file set in the background. Preserves the "just save the file" UX without a kernel mount. Roughly 1–2 days to build a minimum viable version. Risks: initial mirror drift, permission on-disk mismatch with DB, deletion semantics ("did they mean to delete or was it a rename?").

4. Git as the interface Build med

Every project already publishes to a git remote (github mirror seen in publish run output). Formalise it: expose a project as a bare repo the user git clones, edits normally, and git pushes. A post-receive hook syncs commits back to the DB. Zero new UX to learn. Downsides: every project needs a mirror configured, the DB becomes derived state instead of source of truth (an inversion), and the vcs_working_state / vcs_sessions abstractions get harder to justify.

5. Editor plugin (Emacs Tramp / VS Code FS provider) Build high

Register a templedb:// URL scheme handled by editor plugins. M-x find-file templedb:bza/src/foo.ts opens the DB blob, save writes back. Per-editor implementations required. Solves LSP/navigation well within one editor. Doesn't help command-line tools (grep, rg, build systems).

6. Auto-checkout on demand Build low

Cheap variant of #2. templedb edit <slug> (new top-level command) creates or reuses a checkout at a stable path, launches your editor, and prints the commit command on exit. Half a day. Nudges the "session edit" shape into the checkout workflow without asking you to remember the ceremony.

7. Poll-based bidirectional sync Build med

Cousin of #3 without inotify. Daemon polls disk + DB every few seconds and reconciles. Simpler and more portable than inotify but slower feedback. Merge semantics on concurrent edits get gnarly fast.

8. HTTP-served virtual filesystem Skip

Mount DB as an HTTP file server. Almost no useful tool speaks "filesystem over HTTP" natively. Skip.

Recommendation

Ship options #2 (already exists) and #6 (half-day build) together, and delete FUSE.

#2 handles power-user sessions correctly (LSP, navigation, testing); #6 is the ergonomic on-ramp that avoids the "remember to checkout first" tax. templedb file edit stays for one-liners. That's the whole spectrum FUSE was covering, with none of the FUSE failure modes.

Phasing:

  1. Land now: deprecation warning on templedb mount, update every project CLAUDE.md to remove FUSE references, add templedb edit <slug> as the session-edit on-ramp.
  2. One–two days later: delete src/temple_fuse.py, mount/unmount CLI commands, FUSE cache invalidation code, the FUSE-oriented Write-tool hook.
  3. Ongoing: as new bug surfaces appear (session fanout, ghost records, checkout-diff crash), fix or rationalise the CLI path — that's now the only path.

Non-goals

  • Emacs Tramp / VS Code FS providers are attractive but per-editor. Punt until #2 + #6 prove insufficient.
  • Git-as-interface (#4) is worth revisiting once the FUSE dust settles — potentially it obsoletes the whole vcs_working_state abstraction. Not this quarter.

Open questions

  • How many users besides the primary user actively rely on the FUSE mount today? If >1, add a migration guide before deleting.
  • Does removing FUSE simplify or complicate the templedb-agent integration? Agent likely uses CLI already — verify.
  • The Write-tool hook that reflexively redirects /tmp/* paths to ~/temple/* lives outside the templedb repo. Coordinate removal with the harness config owners.
