Proposed schema after observer/integrator plan

Maps the current 131-table TempleDB schema onto the target shape implied by the observer/integrator plan and the cross-session handoff proposal. The overarching move: collapse the sprawl of typed tables into a small load-bearing core (entities, relations, content_blobs) plus first-class junction objects for the shapes that carry identity (Deployment, EditIntent, Build, Handoff). Existing typed tables become materialized views for backward compatibility. Diffs and byte-level source history stop being ours to keep; git and nix reclaim those. Explains what each group of current tables becomes: keep as-is, shrink to metadata + FK to entity, demote to materialized view, retire, or new/promoted.

The five framings that drive every schema decision

  1. Authority per fact, not per system. Every stored fact carries source_authority (git, nix, ssh-probe, agent, scip, human) and observed_at. Truth becomes a per-column property, not a table-wide property.
  2. Observer over owner for source bytes. Git is authoritative for commit-file bytes; we snapshot for query, not for authorship. The write path becomes EditIntent, not file set directly to blob storage.
  3. Promote junctions to first-class objects. Any relationship that acquires identity/history/state transitions becomes an entity with its own row and lifecycle. Build, Deployment, EditIntent, Handoff, Report↔Commit all fit this shape.
  4. One core, many views. Two tables (entities, relations) plus one blob store (content_blobs) carry the load. Existing typed tables become materialized views over the core so old queries keep working.
  5. Ingestion algebras, not schemas. Each authority (git, nix, scip, ssh-probe, agent runtime) has a small adapter that upserts entities and relations. Schema doesn’t grow when authorities do — adapters do.

The load-bearing core after the plan

Everything else is an adapter, a view, or a decoration on these:

content_blobs             -- content-addressable byte store
  (hash_sha256 PK, content_text/blob, size, refcount, storage_location)

entities                  -- every noun in the system
  (id, kind, external_ref, source_authority, label,
   observed_at, created_at, UNIQUE(kind, external_ref))

relations                 -- every typed edge
  (id, from_entity_id, kind, to_entity_id, source_authority,
   observed_at, attributes_json,
   UNIQUE(from_entity_id, kind, to_entity_id))

Every ingestion adapter upserts entities and relations with its own source_authority tag. Every existing typed table becomes either a materialized view over these (for read-side backward compatibility) or a first-class junction with its own row when the relationship itself carries identity (see below).

Design invariant Adding a new authority never requires a new table. It requires a new adapter that emits into entities and relations. Adding a new junction object does require a new table — but only when the relationship has its own lifecycle (states, timestamps, references, ack semantics).

The junction objects that get first-class tables

Not every relation deserves its own table. A relation gets promoted when it acquires: identity (queryable by id independent of endpoints), state transitions (created → applied → reverted), attributes distinct from either endpoint (timestamps, hashes, reasons), or lifecycle history (audit trail).

Table-by-table disposition

On diffs specifically We do not store per-commit diffs today and will not add them. Snapshots (via content_blobs + source_snapshots view) are the storage shape; diffs are computed on demand from two blobs. Under Phase 5, even snapshots become optional for source paths — if git holds the bytes and we hold the provenance, we can re-fetch bytes when a query needs them. The remaining reason to hold source bytes locally is offline queries and cross-project dedup, both satisfied by opportunistic content_blobs caching, not by full history mirroring.

The ingestion adapter layer (new; no schema per se)

Each authority has a small adapter that reads its native format and upserts entities + relations. No schema growth on adapter addition. Freshness policy per adapter, all recorded in ingestion_runs. 

authority           adapter                    facts emitted
git                 git-walker                 Commit, FileSnapshot, contains, parent-of
nix                 nix-store queries          Derivation, StorePath, built-from, produces
NixOS (per host)    SSH probe                  Generation, running-on, deployed-at
agent runtime       direct DB write            Session, ToolCall, EditIntent, proposed, applied-to
LSP / language      SCIP export                Symbol, defines, calls, references
human               report/decision markup     Report, Decision, motivated, implemented-in

templedb doctor entities walks each entity, asks its authority whether the fact is still current, records the check in invariant_checks. Load-bearing from day one (Phase 3), not deferred — this is the reconcile pattern every industry coordinator (Hive, Terraform, Istio) learned the hard way to build in early.

Migration ordering

The schema evolution is incremental; every migration keeps existing queries working.

  1. Phase 0 (shipped) — no schema changes; gitignore rules and drift diagnostics on the filesystem side.
  2. Phase 1 — add source_snapshots view over file_contents. Document the reframing. No writes change.
  3. Phase 2 — wire edit_intents as the canonical write path. file set becomes intent create && apply. vcs_working_state gets a view definition against intents.
  4. Phase 2.5 — add handoff_notes. Independent of the main pipeline; ~1 day.
  5. Phase 3 — promote entities and relations to load-bearing. Adapters begin writing here. Existing typed tables get view definitions layered on top. Add ingestion_runs, invariant_checks. Ship templedb doctor entities. Promote junction objects (deployments, tool_calls, decisions).
  6. Phase 4 — SCIP adapter. Code-facts ingestion externalized. code_symbols becomes a view over SCIP-emitted facts.
  7. Phase 5 — retire vcs_file_states for source paths. Reconstruct file bytes from git on demand. Optionally retire system_config once ast-based config deploy is stable.

What the schema stops doing

  • Stops storing per-commit inline file content. Git holds bytes; we hold hashes and metadata. Full-history mirror is gone.
  • Stops being the write path for source bytes. Writes go through edit_intents. The file set shortcut remains but is a wrapper.
  • Stops duplicating nix-store metadata. Closure structure, path info, refs — queried from nix on demand, cached opportunistically.
  • Stops growing a new table per authority. New authorities are new adapters, not new tables.
  • Stops silently truncating on FUSE writes. The FUSE mount retires (Phase 5). Editing is filesystem-native via templedb edit <slug> workspaces; agent edits go through edit_intents.

What the schema starts doing

  • Tags every fact with its authority and observation time. source_authority and observed_at on every entity and relation.
  • Records ingestion runs. ingestion_runs makes freshness queryable per adapter.
  • Reconciles against authorities. templedb doctor entities walks the graph, asks each authority to confirm, flags drift.
  • Checks commuting-diagram invariants. invariant_checks holds named laws like hash(snapshot(c)) = provenance(build(c)) with last-checked-at.
  • Promotes junctions to objects. Build, Deployment, EditIntent, Handoff, Decision, ToolCall each carry identity and lifecycle rather than being invisible fks.
  • Supports the five-hop provenance query. “Which store path is running on this machine, from which deployment, from which commit, from which agent-session-and-intent-chain, motivated by which report?” is a graph walk over relations.

Open questions and risks

Where do views actually live? SQLite supports CREATE VIEW but views can’t be written to, and complex views (multi-table joins with lifecycle) can be slow. Some “view” entries above may end up as materialized tables kept in sync by triggers, which reintroduces the write-consistency problem the plan is trying to avoid. Decision needs to be made per-view during Phase 3.
The entities/relations table gets huge Every symbol, every commit, every relation with an observed_at row grows the graph fast. Retention policy matters. Options: partition by domain (code vs deploy vs report), garbage-collect superseded observations, allow per-adapter TTLs. The plan flags this as risk explicitly; must be settled before Phase 4 (SCIP will dump millions of symbol facts).
Adapter rot budget Every authority we adapt (git protocol changes, nix schema changes, SCIP evolves, LSP servers vary) is a maintenance cost. Adapters are small and isolated by design, but this is a recurring monthly cost, not a one-time build.
Backward compatibility of dropped-column data Shrinking vcs_commit_metadata, vcs_file_change_metadata, etc. into entities.attributes_json means historical data needs migration. The right time to do this is during Phase 3 when entities becomes primary; skipping it leaves the sidecar tables around forever.
CRSql layer needs to catch up Existing sync_* replication targets specific tables. When entities/relations become primary, they need crsql tracking too. Not conceptually hard, but a Phase 3 dependency worth naming.

Where this leaves us

The schema goes from 131 tables to roughly the same number of tables on paper — but with a different center of gravity. The load-bearing shape becomes three storage tables (content_blobs, entities, relations) plus a handful of junction objects with identity. Everything else is either a view for backward compatibility, a per-adapter cache, or a specialized-metadata sidecar. Adding a new authority no longer grows the schema; adding a new junction does, but only for shapes that genuinely carry lifecycle.

The end state is more disciplined than today’s sprawl and more general than the DB-as-truth model it’s replacing. It has clear industry precedent (Hive/Iceberg for metastores, Terraform for infra state, dbt for semantic layers) and a reconcile story from day one that those precedents wish they’d built earlier. It also happens to make the “commuting-diagram invariants” from the critique machine-checkable rather than aspirational, and gives cross-session handoff a natural home.
