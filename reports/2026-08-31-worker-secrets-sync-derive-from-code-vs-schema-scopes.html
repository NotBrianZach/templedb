Worker secrets sync — derive from code vs. schema scopes

Assessing how bza’s Cloudflare Worker secrets list should stay in sync with the code that actually uses those secrets. Written 2026-08-31 after the Spotify prune commit (8d1529a5) left two dead entries in deployment_config.app_deploy.worker_secrets until they were manually removed. If we don’t fix the mechanism, the same drift will happen again.

Where the pain lives today

bza’s deploy pipeline pulls each name from a flat list at projects.deployment_config → app_deploy.worker_secrets, looks up the value in TempleDB’s per-project env store, and runs npx wrangler secret put <NAME> --name aireadalong for each. Simple, works, but:

  • The list is manually maintained. Nothing enforces that entries correspond to process.env.<NAME> references in the code. Add code that reads a new env var → you remember to add it to the list, or the Worker crashes at runtime (env.NEW_KEY is undefined). Delete code → nothing prunes the entry.
  • Silent drift after refactors. Spotify was removed from the frontend surface in one commit but the deploy config still listed SPOTIFY_CLIENT_ID + SPOTIFY_CLIENT_SECRET until I noticed them. A dead secret in Cloudflare isn’t a security incident, but it is noise, it’s a rotation target that shouldn’t exist, and it’s a signal that the pipeline doesn’t know what its own Worker needs.
  • No blast-radius visibility. If OPENAI_API_KEY rotates, which routes stop working? Nobody knows without greping.

Three options

1. Auto-derive from process.env.* references Recommended low

On deploy: grep -roE 'process\.env\.[A-Z_]+' frontend/ (plus env.[A-Z_]+ for Cloudflare-bindings syntax), take the unique set, intersect with TempleDB’s known secret store for this project, push only the intersection. That’s the entire algorithm.

Semantics:

  • Additions: add code referencing process.env.NEW_KEY, set the value once in TempleDB via templedb var set bza NEW_KEY … --secret, next deploy pushes it. No config edit.
  • Deletions: delete the code (as I did with Spotify). Next deploy’s derived list omits the name. Optionally also delete from Cloudflare in the same step via wrangler secret delete NAME for any entries in Cloudflare-but-not-derived. Rotation and cleanup handled together.
  • False positives: template strings, dynamic lookups (process.env[key]) — won’t be caught. Rare in this codebase (verified). Escape hatch: an explicit worker_secrets_extra: […] field for the few dynamic cases.
  • False negatives: derivation catches env vars a build-time script or config file reads but doesn’t appear in frontend/**. Same escape hatch.

Implementation cost: ~30-50 lines in src/services/app_deploy_service.py, replacing the current manual-list read with a derive-then-intersect step. No schema change. No user-facing config change unless the escape hatch is needed.

2. Add a secret_scopes DB table Overkill for today high

Tag each secret with what it’s for:

CREATE TABLE secret_scopes (
  project_id  INTEGER NOT NULL,
  secret_name TEXT NOT NULL,
  scope_type  TEXT NOT NULL,  -- 'feature' | 'route' | 'component'
  scope_value TEXT NOT NULL,  -- 'spotify' | '/api/tts' | 'BookReader'
  PRIMARY KEY (project_id, secret_name, scope_type, scope_value)
);

Enables templedb feature rm spotify to sweep code + secrets + tests + DB columns as one operation. Also gives real blast-radius answers: “what breaks if I rotate OPENAI_API_KEY?” becomes a join.

Downsides: new abstraction to explain, new bookkeeping to keep honest, and the gain only compounds if you routinely delete whole features. bza deletes a feature roughly once every 6–12 months. Option 1 already fixes the common case (drift after refactor) for a fraction of the effort.

3. Both: derive-as-source-of-truth, scopes-as-annotation Later

Same derive step as #1, but the resulting list plus manual worker_secrets_extra gets normalised into secret_scopes. Then queries like “which secrets power the newsletter flow?” answer themselves.

Right end-state if you decide the schema is worth it. Wrong first move because it front-loads schema work before proving the scoping model actually earns its keep. Reach for it only after option 1 is running and you find yourself wanting typed queries.

Recommendation

Ship option 1 now. Small, surgical, zero new abstractions. Prevents the exact class of drift the Spotify prune just demonstrated. Preserves the escape hatch for edge cases via worker_secrets_extra.

Revisit option 2 only when a concrete workflow demands it — e.g. the day you actually want templedb feature rm to do a coordinated sweep. Until then, the code itself is the scope definition, and derivation keeps it authoritative.

Rollout sketch

  1. Add _derive_worker_secrets(working_dir) to src/services/app_deploy_service.py — walks frontend/ looking for process.env.[A-Z_]+ and env\.[A-Z_]+, returns a sorted deduplicated set[str].
  2. Change the deploy step: instead of reading worker_secrets verbatim, derive from code, union with worker_secrets_extra (new optional field, default []), intersect with what TempleDB actually has a value for, and push that.
  3. Log the diff on every deploy: “pushed 11 (unchanged); detected 0 stale in Cloudflare” — visible signal that the sync is working.
  4. Optional follow-up: on detecting a Cloudflare-only secret (present in CF, not in derived set), print a warning + include a --prune-stale-secrets flag to run wrangler secret delete for each.
  5. Migrate deployment_config.app_deploy.worker_secrets to worker_secrets_extra on the projects that have it (bza, others). The migration is: rename the key, empty the value if all names are already derivable.

Non-goals

  • Feature-level DB scoping — deferred to option 2 when demand is real.
  • Cross-project secret sharing (system_config → bza via env_projects) — already handled at a different layer, not affected here.
  • Non-Cloudflare targets — the derive step is portable, but this proposal only touches the CF Workers deploy path.
