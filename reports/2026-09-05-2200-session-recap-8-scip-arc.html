The three SCIP adapter versions

1.0 — File→defines→Symbol only

Shells out to scip-typescript index on a project's materialized checkout, converts via scip print --json, walks Index.documents[*].symbols[]. Mirrors python's discipline: per-file __module__ synthetic, external_ref {slug}:{path}:{name}, scoped pruning on source_authority='scip-typescript'. Deliberately does NOT re-upsert File entities — git provenance survives.

Packaging: nix/scip-typescript.nix in templedb's flake, writeShellApplication wrapping npx --yes @sourcegraph/scip-typescript@0.4.0. Not fully hermetic (first invocation fetches from npm cache), but avoids the two-hash hunt buildNpmPackage/mkYarnPackage would need. Wired into the templedb wrapper's --prefix PATH alongside pkgs.scip. Commit F1D0C4CA (later repaired by 4537FDB3, see below).

1.1 — Symbol→uses→Symbol from occurrences

Restructured to two-pass. Pass 1 emits defines + builds scip_symbol → entity_id map (global for regular symbols, per-file for local N scoped). Pass 2 walks Document.occurrences[]; for each non-Definition reference, resolves the target via the map, finds the source symbol by innermost enclosing_range containing the reference, falls back to the file's __module__ when no def encloses. Added inline range-containment helpers (_norm_range, _range_contains, _find_enclosing_sym_id) to handle SCIP's 3-element single-line vs 4-element multi-line range formats.

Only uses emitted, not calls or inherits — scip-typescript@0.4.0's symbol_roles doesn't reliably distinguish call sites from other reads (verified empirically: all 52,406 non-Definition occurrences have symbol_roles=0). Dead-imports doctor already accepts uses as a bridge kind, so this is enough for that surface. Commit 66838F85.

1.2 — File→imports→File + label polish

Two additions:

  • File→imports→File. The original v1.2 plan was to filter on symbol_roles & 2 (SCIP's Import role bit). Verified empirically after the first attempt yielded zero edges: scip-typescript@0.4.0 doesn't populate the Import bit at all. Pivoted to inferring imports from cross-file references: any reference where target's defining File differs from source File implies a static dependency, which is what dead-imports doctor wants. Superset of pure import statements (also catches inline uses of imported symbols), but for the dead-imports semantic that's exactly right.
  • Label polish. Trailing SCIP descriptor cruft (., (), ().) stripped for labels. Erefs UNCHANGED — mutating them would break idempotency across v1.1↔v1.2 ingest cycles without a rename migration. Empty-display leaves (from scip_syms ending in /) get labeled scip (anonymous).

Result: 329 File→imports→File edges on bza/frontend, and entity explore now shows clean semantic labels. Commit 0F6BC1F9.

Three fallout bugs found + fixed along the way

1. Scanner false positives (145 → 0)

Symptom Every templedb vcs status --refresh reported ~50-60 files as "modified" with staged_by_session_id=NULL, even though the workspace content matched DB current byte-for-byte. Cleared them manually; they came back on next refresh.

Root cause: _refresh_working_state in src/cli/commands/vcs.py passed project['repo_url'] to WorkingStateDetector. For templedb, that's /home/zach/templeDB (a legacy import path last touched 2026-08-17). But the operational checkout lives at ~/.config/templedb/checkouts/templedb/. Every file whose content had drifted between the two directories produced a spurious "modified" row on each scan.

SyncManager.get_checkout_path() already resolves the right path (active checkout record → falls back to repo_url only if none). One-line change routing _refresh_working_state through it. Went from 145 spurious rows → 27 real drift rows on the first scan after the fix. Commit 6D6D1B55 (later repaired to include the actual code by 4537FDB3).

2. Stale blobs in commits (FUSE→is_current propagation gap)

Symptom templedb publish run templedb refused to materialize because two just-committed commits' file blobs didn't match the workspace. Commits F1D0C4CA (SCIP 1.0) and 6D6D1B55 (scanner fix) claimed changes their actual stored blobs didn't contain.

Root cause: Edit tool through the FUSE mount wrote new content to the workspace, but the FUSE→DB propagation didn't update file_contents.is_current — it went into vcs_working_state for session 41 (the fuse-auto session) instead. Later vcs add hashed the pre-Edit blob still in is_current, staging content that matched the commit message but not the intended diff.

Fix: templedb file set --verify for the two affected files (updates is_current from workspace content), then a fresh commit. Landed as 4537FDB3 — "actually include SCIP wiring + scanner fix (F1D0C4CA/6D6D1B55 shipped stale blobs)". entity.py escaped this class of bug because it happened to have been file-set'd via a different flow that did update is_current.

3. FUSE was dead code kept alive by a zombie

Symptom Investigating the FUSE→is_current propagation bug turned up: no temple_fuse.py in current source, no mount CLI subcommand, no fusepy importers. But ~/temple/templedb/ was mounted and writable.

Root cause: process 1643805 was still running templedb mount /home/zach/temple from a nix store path (afchk35cb5nf3j37irbkpga6zw7md9n3) that had been garbage-collected long ago. It was serving BOTH ~/temple and ~/status FUSE mounts with the retired-11-days-ago FUSE code, complete with the write-path propagation bug.

Retirement (per the 2026-08-29 report's Phase 2 recommendation which had been half-completed): killed zombie process, unmounted both paths, disabled + removed templedb-mount.service, deleted the dead mount.enable/mount.path scaffolding from homeManagerModule, removed fusepy from pythonEnv and devShell, removed Bash(fusermount:*) from Claude Code permissions, fixed the stale src/temple_fuse.py example in CLAUDE.md. Commits 54D87C3A and 3006521C.

Silver lining: the "FUSE Edit → is_current propagation bug" this arc was originally chasing turned out to be a non-issue on the current build. No live FUSE writer exists any more.

Three metacognition moments

1. Question I should have asked once, asked twice

Offered "npx" vs "add to system_config" for scip-typescript packaging without first checking nixpkgs. User picked system_config — then nix eval nixpkgs#scip-typescript showed it's not packaged there. Had to re-ask with buildNpmPackage / mkYarnPackage / npx options. Then during the buildNpmPackage attempt discovered scip-typescript actually uses yarn (no package-lock.json), so pivoted to writeShellApplication. Two forced pivots that five minutes of upfront tooling verification would have avoided.

2. User course-correct: ownership matters

User redirect (mid-run) "also since templedb depends on scip can we make it a templedb flake thing? as opposed to system wide?"

Correct call — templedb is the consumer, templedb should own the packaging. Undid the system_config edits, put nix/scip-typescript.nix in templedb, wired into the wrapper's --prefix PATH + devShell + packages output. Anyone with templedb installed now gets scip capability for free; no system_config surgery required for other users. Better encapsulation, better handoff.

3. The publish-conflict was the hint

If publish run hadn't done its checkout-vs-DB drift check, the SCIP 1.0 and scanner-fix commits would have been pushed to github with the wrong contents and nothing would have caught it until someone ran the built binary and it didn't have scip-typescript on PATH. The intent-ahead detection guardrail landed just yesterday (commit E98CD602 in recap 6) is what surfaced the bug. Two independent hygiene systems (publish drift check + intent-ahead detection) caught the same class of bug from different angles.
