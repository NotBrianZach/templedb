Resumable was a guess

The roster had been labelling sessions interrupted — resumable since it shipped. It derived that from status, while the code that performs a resume checks something else entirely, so 160 of 173 interrupted-or-failed rows claimed to be resumable when a resume would refuse. Pressing r failed, so the cheap move was always to open a new session — which is how one project accumulated seven separate “what's next” threads for a single unfinished port. This is that bug, the two other defects found next to it, the regression the first fix introduced, and the per-project altitude the roster never had.

The triage that started it

The session began as ordinary fleet triage: what is stuck, what is worth killing, what is waiting on me. The answer to the last one was short — three rows in done saying your turn, one in attention — and ask list --live returned No pending asks, so nothing was blocked on an answer that could still arrive. Nothing was stalled. The provider was healthy.

The roster was not jammed. It was illegible. Of 334 sessions, 133 carried no project and no title, and 121 of those were a single cohort: created between 2026-07-22 and 2026-08-29, every one interrupted with nought to two messages, and every one showing the same updated_at — something had bumped them en masse about 24 days earlier. They even carried phantom findings and todos in a repeating 5,0 / 0,1 / 1,1 pattern every ~34 ids. Test fixtures, not work, inflating the fleet's open-todo count by 30.

A correction worth recording: the Emacs roster was never showing those ghosts. It already passes --recent-days 14 via templedb-agent-roster-recent-days. They only appear in raw templedb --json ai agent fleet calls — which is what an agent doing triage runs. Advice aimed at the wrong surface is still wrong advice.

Three defects, sitting next to each other

1. A destructive command reporting a false zero

ask expire was asked to write off 16 asks past their deadline, the oldest 41 days old. It printed: 

Expired 0 ask(s) past the 600s handler deadline.

It had expired all 16. store.expire_stale_asks() ended in return execute(UPDATE …), and execute() returns cursor.lastrowid — meaningless after an UPDATE. db_utils.py already ships execute_rowcount() whose docstring warns about exactly this mistake. The fix was one identifier.

The interesting part is the failure mode. A false zero on an irreversible command reads as nothing happened, which invites running it again. It was only caught by checking agent_pending_asks directly after the command claimed to have done nothing — the 16 rows had flipped to expired, and the per-session breakdown matched the dry-run list exactly.

2. The label and the precondition disagreed

AgentService.resume_run requires a pending user turn at the tail of the conversation: 

if messages[-1]["role"] != ROLE_USER:
    raise ValueError("Nothing to resume: last message is not from user")

classify_fleet_row never consulted that. It mapped status == "interrupted" straight to "interrupted — resumable". The two had no relationship. Across the fleet:

For the 83 rows whose tail is an assistant message with text, refusing is correct — the previous run did answer, and what you want is a new message, not a resume. Those only needed an honest label. The three empty ones were a different thing entirely.

3. A placeholder that outlived its run

send_message inserts an empty assistant row before calling the provider and streams text into it: 

assistant_msg = store.add_message(session_id, ROLE_ASSISTANT, "", run_id=run_id)
# ... then provider.send(...) fills it

If the provider dies first, that row stays empty forever — and it is now the tail, so resume_run refuses on the grounds that the question was already answered. It was not answered. It was never even attempted.

Session #331 was the clean example. Its user message #1696, “do we have the option of using deepseek”, and its empty assistant row #1697 share a timestamp to the second — the moment the run died on OAuth session expired and could not be refreshed. Six sessions were stranded this way:

Why it mattered more than it looks

A wrong label on a rarely-used key would be cosmetic. This one shaped behaviour. templedb-rust had seven sessions — #333, #328, #321, #320, #318, #315, #314 — all variants of “what's next in the rust port”. Three died failed: idle_timeout, three interrupted. Seven entry points, one unfinished port, no advancement.

That is what a lying affordance produces. The roster said resumable, resume refused, and starting fresh was one keystroke away. Compounding it, fleet --idle-days defaults to 2: a row that is your turn demotes into idle after 48 hours and sits beside a session nobody has touched in a month. Work waiting on you became indistinguishable from work abandoned.

The fix, and the half of it that was wrong

fleet_rows now reports the tail's shape and classify_fleet_row exposes a real resumable field mirroring the precondition. A row from list_sessions has no message columns, so it returns None — unknown — and keeps the optimistic label rather than inventing a verdict. resume_run discards the dead placeholder through a helper narrow enough that it cannot touch a row with content, a non-assistant row, or anything but the tail.

#331 resumed and answered a three-day-old question with 2,024 characters about where DeepSeek is already wired in. Exactly one copy of the user message survived, so the no-duplication guarantee held.

Then two more sessions were resumed in the background — and the parent process exited, killing both mid-stream. They came back like this:

sessiontail after the killrun
308assistant, 75 chars — I'll pick up where we left off. Let me find the current stat866 running
286assistant, 365 chars — I'll start by finding out what already exists — there's an867 running

Both now read as already answered. The fix keyed on the tail being empty, which catches only the first failure mode. A reply killed mid-sentence has text and looks finished. Two sessions that the fix had just unstranded were re-stranded by the act of using it.

The real signal was never emptiness — it is whether the run that produced the tail reached completed. fleet_rows now joins agent_runs through agent_messages.run_id and both the predicate and the deleter key on that status, so the empty placeholder and the truncated sentence are the same case. One subtlety had to be made consistent in both: a tail with content and no run_id is pre-run_id history and counts as a real answer, otherwise the deleter would eat old answers the predicate considered final.

The deleter does destroy content in the truncated case. That is intended — a half-written reply from a process that no longer exists has no reader, and the run row and its events survive, so the attempt stays in the history.

The altitude that was missing

templedb summary was already the authoritative 1000-foot view: entity graph, per-adapter ingestion, systemd, 42 doctor invariants, open reconciliations, per-machine reconcile, python hygiene, handoff inbox. It covered every authority except the agents. The roster had the opposite problem — it answered “what is this session doing” with no way to ask “which project needs me”. Nobody could see both.

store.fleet_rollup() groups fleet() by project and reports needs-you, working, stalled, attention, idle, resumable, todo debt, expired asks and the oldest wait. needs_you merges the needs_input and done buckets deliberately: at this altitude “blocked on a question” and “finished, your turn” are one call to action.

templedb                     1       0     2    27     7    111  22h

templedb-rust                0       1     0     7     5     19  -

Three renderers consume that one function — the summary pane, fleet --rollup, and a new Emacs buffer at SPC a T m that colour-codes each project by what it wants and descends into that project's roster on RET. Keeping the aggregation in one place means they cannot drift; it was also the reason to build it before the surface question was settled, since any surface renders the same rollup without rework.

Operational traps found on the way

Five things cost real time and are worth not rediscovering:

A pin can be correct and the deploy still stale

After publish run system_config --pin-input templedb, the checkout's flake.lock held the new rev while the DB's copy still held the old one. system-switch refuses on that divergence and suggests --force — which would overwrite the good lock with the stale one and deploy the previous templedb while reporting success. Diff jq -r '.nodes.templedb.locked.rev' on both sides; the direction is not guessable from the error.

system-switch hangs silently without a TTY

From a non-interactive call it produced zero output for 180 seconds, including under --dry-run. It blocks on a prompt that --yes does not cover. printf 'n\n' | fixes it. An empty output file looks identical to a dead command.

A running serve keeps the build it started with

The process hosting an Emacs session keeps the templedb modules it imported at launch, so a successful switch does not reach it — the CLI picks the fix up immediately, Emacs does not until the serve restarts. Check tr '\0' '\n' < /proc/<pid>/cmdline for the store path. Comparing the python interpreter env instead is useless: that path is shared between builds and matches either way.

Do not background an agent run from inside an agent session

When the parent exits, the run dies mid-stream, leaving agent_runs stuck at running with completed_at NULL and a truncated message. This is how 308 and 286 broke.

recover_interrupted_sessions() has no session exclusion

It sweeps every run with status = 'running' to interrupted — including the caller's own live session. serve calls it unconditionally at startup, which is how the orphaned runs 866 and 867 eventually got cleaned up, but it also means it cannot be used as a targeted repair from inside a live session.

Still open

  • The fleet has no session-retirement path. ai agent offers serve, doctor, sessions, fleet, ask, chat, resume, log, notify, stop-stale — nothing prunes. --recent-days hides rows; nothing reclaims them. That is why two thirds of the roster is dead weight.
  • The 121-row ghost cohort is still there, still counted, still carrying phantom todos.
  • Four sessions remain stranded by choice rather than by bug — 19, 282, 301 and a re-stranded 286 — on the judgement that an agent answering whats next from 16-day-old context produces confident nonsense, and that a 75-day-old design thread is better left as a record that a question went unanswered.
  • Whether “manager” should also mean agents supervising agents rather than a view for a human. The roster would be its input and ai agent resume one of its verbs. The argument for caution is in this report: the one autonomous action taken unsupervised here is the one that broke two sessions.
