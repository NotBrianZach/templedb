The bug hunt that made this session interesting

Recap 4 stopped at 21% saying "diminishing returns; remaining candidates need type inference." Turns out that was true for some candidates, but three separate systemic bugs were hiding behind them:

1.12a — re-export chase (planned)

from repositories import BaseRepository where repositories/__init__.py does from .base import BaseRepository. Direct lookup on the __init__ file fails; needed to chase transitively. Implemented _chase_reexport(t_slug, t_path, t_name, depth=3) called at all three post-pass sites (calls / inherits / uses).

1.12b — relative imports never resolved (unplanned)

After shipping 1.12a, the delta was disappointing (88 → 85). I spot-checked blob.py imports repositories and found the call from BlobCommands.__init__ to BaseRepository() still wasn't resolving. The chase ran, but the ultimate target file's local_defs didn't have BaseRepository either — because the chase started from __init__.py whose imports_map was empty. Because: 

elif isinstance(node, ast.ImportFrom):
    if node.level != 0 or not node.module:
        continue  # ← every relative import silently dropped

Every from .base import X in the entire codebase had been going into the void since the resolver was written. Added _resolve_relative_import(this_path, level, mod_name) that handles __init__.py's package-is-directory rule, walks up level - 1 directories, and appends the module name.

Lesson A resolver that silently skips syntax it doesn't handle is worse than one that errors. The old code had continue where it should have had an _resolve_relative_import call. Silent skip means: (a) the graph has a systematic hole nobody notices, (b) the metrics understate coverage, (c) everyone treats the tool's output as "the number you get" rather than "the number the tool would report if it weren't dropping edges." Doctor invariants can't help because there's no ambient signal that a code path is dead.

1.13 — __init__ files with only re-exports

backup/__init__.py imports .base and .local_provider just to expose them — it never calls them itself. So dead-imports flagged both as unused. Semantically wrong: the re-export IS the use, since callers depend on the composition.

1.13 adds a post-pass for every __init__.py file: each import becomes <init>:__module__ → uses → <target>:<name>. Chases through further re-exports for long chains.

1.14 — bare-Name references (the biggest single win)

from db_utils import DB_PATH; sqlite3.connect(DB_PATH) — DB_PATH is a bare Name, never a Call. Every db_utils import that used constants (many, many of them) looked dead.

1.14 adds a reference-scan post-pass. For each symbol's body, walk every ast.Name and Attribute-root Name. If in imports_map, emit Symbol → uses → Symbol — or, for module-level constants that don't have a Symbol entity, fall back to <target>:__module__. Deduplicates per (symbol, ref) so a CONSTANT used 20 times doesn't spam 20 uses edges.

Operational note: a real commit hang

Mid-session, templedb commit deadlocked on a README.md conflict — silently, without prompting. Two commit processes stacked up, both waiting on stdin that the harness wasn't feeding. Kill required. On retry with an interactive terminal, the conflict prompt appeared normally and I resolved by taking the DB version. Root cause is that templedb commit's interactive prompt path doesn't degrade to a non-interactive default when stdin is closed. Worth a follow-up.

Also noticed templedb vcs session list --active shows 9 sessions from today, all from this single-user session. That's session leakage — an ended_at IS NULL row per invocation that never closes. Not blocking anything today, but worth a follow-up because session-count is a proxy for lock-fanout.
