summary is not a function of the database

Forty-nine invocations of templedb-rust are byte-diffed against Python on every run of just check, and the method works because of a property nobody has had to state: every implemented command is a pure function of the database. summary is the first one that is not. It has five inputs that are not rows, and the reason it has been deferred for three porting steps is the same reason it cannot be stored, cached, compared across the fleet, or read back out of an agent transcript six hours later. This report argues the fix is not an injected clock — that is just the enabling trick — but a split between observing and interpreting, and it lists seven defects found by reading the command closely enough to port it.

The property nobody named

The Rust port's verification method is a byte diff: run both binaries, compare stdout and the exit code. It has been applied to every command as it landed, and on 2026-10-17 it covered 49 invocations with zero unexpected differences. That method has a precondition, and it has been silently satisfied until now: both processes must be reading the same input, and the input must be the only thing they read.

Every command ported so far satisfies it. file cat, entity trace, vcs show, search content — each is a pure function from database state to bytes. Run one twice, get the same answer. Run it on another machine against a copy of the database, get the same answer. That is why the cross-backend diff is even meaningful: asking whether SQLite and Postgres agree is only a question you can ask about a function.

So the byte-diff harness has been doing a second job without being asked: it is a purity test. A command that cannot be byte-diffed against a second implementation is a command with a hidden input. The README records three such commands and treats them as unrelated exceptions — project list (different layout), search content (different semantics), summary (deferred). The first two are deliberate output choices. The third is a different kind of thing, and conflating them hid that.

The five hidden inputs

summary reads the database and then reads five other things. Each one makes the output a function of something a caller cannot see:

InputWhereWhat it makes non-reproducible
Wall clock summary.py:457, _age_hint via julianday('now'); also date('now') in reconciliation_service.counts() Every age string. Two runs a minute apart disagree. This is the one everybody notices.
Parent process id summary.py:304 — f"{socket.gethostname()}-{os.getppid()}" The handoff inbox. The same database shows a different inbox depending on which shell invoked the command.
Hostname same line Same, across machines. Two fleet members reading one database see different inboxes by construction.
systemd _print_systemd → services/systemd_health.collect(), which shells out to systemctl show across two scopes The whole pane. Not in the database at all, and correctly so — the module's docstring is explicit that "a systemd unit is not a row" — but it means the output describes this machine, not the data.
Environment TEMPLEDB_SESSION_ID, read directly Overrides the inbox identity, invisibly.

Four of the five concern one pane each. The clock concerns all of them.

Why this is worse here than it would be elsewhere

A relative age is a perfectly good thing to print at a terminal. The argument against it is specific to what TempleDB is.

TempleDB stores the absolute fact and the surface throws it away. ingestion_runs.started_at is 2026-10-18 18:36:57. The pane renders last 6min ago — and, to its credit, prints the timestamp beside it. The doctor and reconcile panes do not: they print (15h ago) and idle 0d with no absolute anywhere. Those strings are undatable the moment they leave the terminal.

And they do leave the terminal, into the same database. This is the part that makes it more than a style preference. TempleDB runs agents (templedb ai agent serve), their tool calls are ingested as ToolCall entities — 21,322 of them in the graph right now — and the output of a command an agent ran is stored. So summary's output becomes a row, in a database that knows exactly when that row was written, saying 15h ago relative to an instant the reader has to reconstruct. The information was in the database, was converted to a relative form for a human who is no longer the only reader, and the absolute form is not recoverable from the text.

The fleet makes it structural. There are six machines in fleet_machines. summary on two of them cannot be compared, because each output embeds its own now, its own hostname and its own ppid. The one command that aggregates system health is the one command whose output is machine-local.

Seven defects, found by reading it closely enough to port it

1. It writes ANSI escapes into pipes, and has no flag to stop

_c() wraps every coloured string in escape codes unconditionally. There is no isatty check, no NO_COLOR support and no --no-color — the command registers with no arguments at all, so templedb summary --no-color exits 2 with an argparse error. Piping it produces: 

  Entity graph       ESC[32m70,099ESC[0m entities, ESC[32m78,296ESC[0m relations

vcs show and vcs diff both take --no-color; the port implements it and the sweep exercises it. summary is the command most likely to be piped — into a log, into an agent's context, into a handoff note — and it is the one that cannot be.

2. --json is accepted and ignored

--json is a global flag on the top-level parser. templedb --json summary runs, exits 0, and prints the same ANSI-coloured panes. For an agent, this is the worst of the three possible behaviours: an error would say "not supported", plain text would at least be honest, and silent acceptance says the output is JSON.

The two defects compound into one sentence: the command designed to be read at a glance is the only one with no machine-readable form, in a system whose heaviest readers are machines.

3. A pane disappears silently when it breaks

    try:
        from services import reconciliation_service as svc
        counts = svc.counts()
        rows = svc.listing(live_only=True, limit=50)
    except Exception:
        return      # table absent (DB one migration behind) — say nothing

The comment names one cause and the handler catches every cause. A schema change, a typo in the service, a locked database, a query returning an unexpected shape — all of them produce a summary that is missing a section, on a command whose entire job is to tell you when something is wrong. The failure mode is indistinguishable from "no reconciliations to report", which is the output a healthy system produces. A health surface that hides its own breakage is inverted.

4. ancient starts at the threshold times 24

    if hours < threshold_hours * 24:
        return (f"{int(hours)}h ago", 'stale')
    return (f"{int(hours / 24)}d ago", 'ancient')

Read with the doctor pane's threshold of 1 hour, that is 24 hours and looks deliberate. The reconcile pane passes threshold_hours=168, so its cutoff is 4,032 hours — 168 days. A machine that has not reconciled since July renders as 2184h ago rather than 91d ago, and never reaches the red class until it has been unreconciled for most of a year. The intent was plainly "a day's worth of the threshold"; the effect is "a threshold's worth of days".

5. Exactly an hour ago renders as 59 minutes, and is classified fresh

Not a typo — a float boundary, and it is reproducible: 

(julianday('2026-10-17 12:00:00') - julianday('2026-10-17 11:00:00')) * 24
  -> 0.9999999962747097     # 'hours < 1' is TRUE  -> "59min ago", fresh
(julianday('2026-10-17 06:30:00') - julianday('2026-10-17 05:30:00')) * 24
  -> 1.0000000074505806     # 'hours < 1' is FALSE -> "1h ago", stale

A Julian Day is about 2.46 million, an f64 resolves it to roughly 47 microseconds, and _age_hint truncates with int(). The same one-hour gap therefore lands on opposite sides of the threshold depending on the time of day. A row stamped exactly one minute ago renders 0min ago for the same reason.

This is not worth fixing in Python and the Rust port reproduces it deliberately — the point of recording it is that it is the sharpest available illustration of the thesis. The output depends on the clock so finely that it depends on the clock's rounding.

6. The doctor pane has no schedule behind it

systemctl --user list-timers on zMothership2 lists five: ingest, reconcile, backup, poincare-sync and tmpfiles-clean. Nothing runs doctor entities. The pane's header says "(latest results)", which reads as live and is not.

Python has already mitigated this twice — the pane carries the age of its stalest check, chosen over the newest precisely because --check X persists only X — and the output today says stalest 11d ago. That is the right fix for a surface. It is not a fix for the missing timer, and the gap between "9 violated" and "9 violated, as of eleven days ago" is the difference between a health check and a souvenir.

7. There is no summary in summary

Today's output says, across six panes: the entity graph is fine, two of nine ingest adapters are 12 and 14 days stale, one systemd unit is failed, nine invariants are violated with the pane eleven days old, eight reconciliations are open, the one deployed machine reconciled six minutes ago and is ok, and one project is 100% dead imports. Is the system healthy?

The command does not say. Each pane colours itself green, yellow or red, and nothing combines them into a verdict — so the reduction the command exists to perform is left to the reader, which is exactly the work the docstring promises to save ("would otherwise require running four commands and squinting"). And the per-pane classification that is computed is carried in ANSI colour, so it is the first thing lost to a pipe.

What the shape should be

The clock seam built on 2026-10-17 makes summary portable. It does not make it well-formed, and the port should not ship a faithful reproduction of a command whose central problem is structural. The split that falls out of the five inputs is three layers:

LayerDepends onVerifiable by
Observation — the facts: counts, per-adapter last run and tallies, per-check status and ran_at, per-machine last reconcile, open-reconciliation rows, unacked handoff counts The database, and nothing else The existing method. Byte-diffable against Python, mirrorable, comparable across backends and across machines.
Interpretation — "6min ago", fresh/stale/ancient, the colour, the verdict The facts plus an instant passed in as an argument Unit tests at fixed instants, plus the CPython oracle already written for the arithmetic.
Environment — systemd, session identity The machine Nothing a database diff can reach. Should be visibly separate, not interleaved between two database panes.

Stated as a rule the rest of the port can use: a command should be a pure function of the database, and where it cannot be, the impure inputs should be arguments rather than ambient. The clock becomes a parameter; the session id becomes a parameter; systemd becomes a separate surface. What is left is a function, and the harness that has verified 49 invocations works on it unchanged.

This is not a new principle for this codebase — it is the same move search content made when matching left SQL, and the same one the graph walk made when sorting left ORDER BY. Both times the reason was that an answer computed in two places by two engines is two answers. An answer computed from two inputs when one of them is invisible is the same problem wearing different clothes.

What the port will do

Recommendations, in the order they should be taken. The first three are the port's own business; the last three are proposals against Python.

#ActionWhere
1 Implement the observation layer as pure functions in templedb-db, returning facts with absolute timestamps. Mirror the seven tables it needs (ingestion_runs, invariant_checks, reconcile_runs, fleet_machines, handoff_notes, reconciliations, reconciliation_items), which also makes them available to the cross-backend diff. port
2 Render in the CLI with Clock::from_env() and an explicit session id, so TEMPLEDB_RS_NOW plus a fixed session makes the whole command deterministic and therefore testable against a recorded expectation. port
3 Honour --no-color and NO_COLOR, default to no colour when stdout is not a terminal, and print absolute timestamps beside every age rather than only in the ingest pane. These are deliberate divergences and go in the README's list with the rest. port
4 Replace the bare except Exception: return with a caught "table absent" case that still prints the pane, saying it could not be read. A health surface should fail loudly in place. Python
5 Fix the threshold_hours * 24 cutoff, or make the two thresholds explicit arguments so the reconcile pane's ancient boundary is stated rather than derived. Python
6 Add a timer for doctor entities, or stop describing the pane as "(latest results)". The stalest-check date mitigates the symptom and the cause is a missing unit. systemd

The part that generalises to the write path

The write-path report (2026-10-15) recommends a clock seam, an exit-code fix and a state-diff harness before any write, and both of the first two are now done. This report sharpens why the first one mattered, and the sharpening is not about summary.

Every write is impure in exactly the way summary is. commit_hash is sha256(f"{id}-{message}-{time.time()}"); every row stamps datetime('now'); session resolution reads the ppid and creates a row if it misses. A write path built the way summary is built — ambient clock, ambient identity, read wherever they are needed — produces a database state that cannot be diffed against Python's, which is precisely the problem the state-diff harness exists to solve and cannot solve on its own.

So the rule above is not a style note for one command. It is the precondition for the harness: the clock and the identity must be arguments threaded from the entry point, not reads performed at the point of use. summary is a good place to learn that, because it is a read, and being wrong is free.
