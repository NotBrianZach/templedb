Cross-session handoff semantics

Written from a session that just had to leave a Markdown file in /tmp/ and tell the user to hand the path to another Claude Code session, because TempleDB has no first-class channel between concurrent agent/CLI sessions. This report argues that a small pull-based “handoff” surface — a single table plus templedb handoff {send,list,pop,ack} — is a natural fit for the observer/integrator direction from the own-vs-observe report: cross-session coordination has no filesystem analog, so it’s exactly the kind of thing TempleDB should own. Sketches the design space, picks a v1, calls out what should be deferred.

Where the gap actually is

Concrete scenario from the session that produced this report: the user was running two Claude Code sessions simultaneously (one on the CLI, one via templedb ai vibe start), asked session A to hand context to session B, and there was no better answer than “I’ll write a Markdown file to /tmp/, you paste the path.” That is the failure mode this report is scoped to.

Design space

Axis 1: pull vs. push

Pull (receiver polls or is prompted): one table, one CLI. Trivial to build, trivial to reason about. Receiver only sees messages when a human/agent asks it to check.

Push (sender wakes receiver): needs a daemon, socket, or a per-session inotify watcher; interacts badly with Claude Code’s request/response model where the agent is only “live” between prompts. Not worth it for v1 — Claude Code sessions already can’t be interrupted mid-turn from outside.

Axis 2: addressed vs. broadcast

Messages can target a specific session id, target a role (“whichever session is next working on templedb”), or be broadcast to a topic other sessions subscribe to. All three are useful; the discriminator lives in to_session being an id, a query, or NULL.

Axis 3: ephemeral vs. archival

A handoff note is not a report — it’s a message-in-a-bottle for another agent. But once ack’d, some notes have long-term value (design decisions, unblocking hints). The right compromise: keep everything, mark read_at and acked_at as separate transitions, add a TTL on display not deletion. Preserves the audit trail; hides stale mail from handoff list.

Axis 4: content-in-band vs. content-by-reference

Small notes can live in the row. Large briefings should live in an existing content-addressed place — a reports/ file, a git commit, a project file — and the handoff row is a pointer plus one-line context. This keeps the handoff table small and matches how the rest of TempleDB handles content (content_blobs for files, reports/ for narrative). Add optional ref_report, ref_commit, ref_file columns.

Recommended v1

A pull-based pinboard, one table, a small CLI, no daemons. Everything else deferred.

Schema sketch

CREATE TABLE handoff_notes (
    id              INTEGER PRIMARY KEY,
    from_session    TEXT NOT NULL,      -- TEMPLEDB_SESSION_ID or fallback (host+ppid)
    from_actor      TEXT,               -- 'claude-code', 'vibe', 'human', 'temple-agent', ...
    to_session      TEXT,               -- session id, or NULL for broadcast
    to_topic        TEXT,               -- 'templedb', 'refactor:foo', or NULL
    subject         TEXT NOT NULL,
    body            TEXT NOT NULL,      -- markdown, ~few KB
    tags            TEXT,               -- comma-separated, indexed on demand
    ref_report      TEXT,               -- reports/YYYY-MM-DD-...html
    ref_commit      TEXT,               -- commit hash
    ref_file        TEXT,               -- project_slug:path
    project_id      INTEGER REFERENCES projects(id),
    created_at      TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    read_at         TIMESTAMP,
    acked_at        TIMESTAMP,
    expires_at      TIMESTAMP           -- display-only; don't hard-delete
);
CREATE INDEX handoff_notes_to_session ON handoff_notes(to_session, acked_at);
CREATE INDEX handoff_notes_to_topic   ON handoff_notes(to_topic, acked_at);
CREATE INDEX handoff_notes_project    ON handoff_notes(project_id);

CLI surface

templedb handoff send [--to SESSION | --topic TOPIC | --broadcast] \
                      [--project SLUG] [--tag TAG]... \
                      [--ref-report FILE | --ref-commit HASH | --ref-file SLUG:PATH] \
                      --subject "..." [--body "..." | --stdin | --editor]

templedb handoff list [--for SESSION] [--topic TOPIC] [--project SLUG] \
                      [--unread] [--include-acked] [--json]

templedb handoff show <id>              # marks read_at
templedb handoff ack  <id> [-m "note"]  # marks acked_at; optional reply-note appended
templedb handoff pop  [--for SESSION]   # show + ack the oldest unacked in one call
templedb handoff tail [--for SESSION] [--follow]   # polling loop, --follow = pull every 2s

Discovery hook

The point of pull-based is receiving agents actually check. Two natural hooks:

  • Include unread count in existing status surfaces: templedb status, templedb project show, vcs status --refresh footer.
  • Optional shell integration: templedb handoff tail --for $TEMPLEDB_SESSION_ID in a tmux status line, or a one-shot check bundled into templedb ai vibe start’s context bundle.

Neither is required for the mechanism to work — humans can just prompt “check your handoff inbox.”

Semantic decisions worth naming

read_at, acked_at, expires_at are three different things

read_at = “an agent has seen this” (opened, showed, tailed). Cheap side effect of viewing.

acked_at = “this handoff is done, no further action needed.” Explicit. Can carry a short reply note. Analogous to closing a GitHub issue.

expires_at = “stop showing this in default list after this time.” Never deletes. Recover with --include-expired.

Three separate transitions because they mean different things. Collapsing them (as Slack does with just “unread”) loses the “is this still my problem?” signal.

Session identity across processes

Piggyback on TEMPLEDB_SESSION_ID (already established by vcs sessions). Fallback for the not-explicit case: host + user + ppid, the same fallback vcs status uses. This means CLI sessions can send/receive without extra setup, and explicit multi-agent workflows get accurate addressing.

Broadcast vs. topic subscription

to_session NULL + to_topic NULL = broadcast to all future sessions (like a message pinned to a bulletin board). to_topic set = anyone who lists with --topic X. to_session set = direct message. Simple, no subscription table, no fan-out.

Ordering and idempotence

Handoff notes are not events — they don’t need vector clocks or causal order. created_at is enough. send is not idempotent by design (two sends = two notes); if you want deduplication, hash the body and check first.

Not doing (yet)

  • Real-time push. Agents don’t have a listener loop. Adding one is a bigger project than the mechanism it would serve.
  • Cross-machine sync. Falls out of the eventual DB-sync work; not scoped here.
  • Structured payloads / RPC. Handoff is prose + refs, not a command channel. Command channels want MCP or the agent runtime, not this table.
  • GUI dashboard. A /handoff page in the GUI is a five-minute add later; the CLI is the primary surface.
  • Threading / replies. A single-note reply via ack -m covers 90% of cases. If real threading matters, add parent_id in v2.

Fit with the observer/integrator direction

Validation This is exactly the kind of surface the own-vs-observe report calls DB-native (“no filesystem analog”), same category as session-scoped VCS staging and the agent runtime. It doesn’t re-own anything git or nix already handles — there is no filesystem or VCS surface for “message another concurrent agent” today, at any scale. Building it is subtraction pressure: once handoff exists, we stop reaching for ad hoc /tmp/ files.

It’s also a natural place to apply the “promote junction to first-class object” pattern discussed in the same-day critique-response notes: a Handoff is an object with identity, timestamps, and state transitions, not a bare fk between two sessions. That framing generalizes — EditIntent (Phase 2) and Report→Commit (workflow F) should use the same shape.

Concrete first step

Migration for handoff_notes, service in src/services/handoff_service.py, CLI in src/cli/commands/handoff.py registered in cli/__init__.py. Wire unread count into templedb status footer. Skip GUI, skip push, skip TTL enforcement (add expires_at column, ignore it for now). ~1 day of focused work; the design decisions above are the load-bearing part.

Deferred to a follow-up: a templedb ai vibe start banner that lists unread handoffs for the current project as part of the bundled context, so a new vibe session automatically picks up what a previous session left behind. That’s where the mechanism starts paying real ergonomic dividends.
