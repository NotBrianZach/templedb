session recap — feedBack onto the WSL desktop guest

A one-line request — "install feedback music game software on my desktop computer" — turned into migrating the zachgigamothers NixOS-WSL guest from channels to the flake, because that was the prerequisite nobody had ever exercised. feedBack now serves on generation 6. The interesting part is not the deploy: it is that two of the three things that went wrong this session were signals I accepted as confirmation when they confirmed nothing, and that a comment in the config asserting the whole thing was impossible took one SSH command to disprove.

What triggered the session

The ask was "could u use templedb to install feedback music game software on my desktop computer" — ambiguous on two axes at once. Which machine: this session runs on zMothership2, which already had feedback.service live on 8766, so "my desktop" had to mean something else, and the fleet has six host configs of which only two machines were reachable. Which build: feedBack ships a web app (packaged) and feedBack-desktop, a JUCE/C++ native build with lower audio latency that is explicitly not packaged — and "on my desktop computer" reads either way.

Both got resolved by one question, but only after collecting enough to make the question answerable: hostname, Tailscale peer status, every hosts/*.nix, and ping/SSH reachability. The answer was zachgigamothers (the Windows box's WSL guest) and the web app.

That answer carried a consequence the request did not mention: there was no flake-based system on that guest at all. It tracked the nixos-26.05 channel with a hand-written /etc/nixos/configuration.nix, and hosts/zachgigamothers.nix existed as a deliberately faithful transcription that had never been deployed from. Installing anything declaratively there meant doing the channel→flake migration first.

What I noticed about my process

didn't — the probe that could not fail

I predicted the unsigned-closure/trust problem before deploying, which was good, and then tested for it by running nix copy of nixpkgs#hello to the guest. It succeeded. I wrote "settled empirically" and moved on. It was not settled at all: hello came from the binary cache and carries a signature, so the probe was structurally incapable of reproducing the failure I was probing for. The real transfer died on its first unsigned path 1.1 seconds in.

Pattern: when testing whether a trust or permission barrier will bite, the probe must share the exact property that trips it. I tested the transport when the question was about provenance. "I tested it and it worked" is only worth something if the test could have failed.

didn't — a pipeline ate the exit code

I backgrounded nix copy ... | tail -5. The harness reported "completed (exit code 0)" — that was tail's status. The copy had failed. I caught it only because I had appended COPY_EXIT=${PIPESTATUS[0]} out of habit and then actually read it. Worse, I had already told the user the mechanism was confirmed working, and had to walk that back.

Pattern: set -o pipefail on any backgrounded pipeline whose success matters — a completion notification reports the last stage, not the stage I care about. And the physical tell was right there: a 2.4 GB transfer that "finished" in 1.1 seconds is not a fast transfer, it is a failed one. Implausible timings are findings.

keep doing — check comments that assert impossibility

zMothership2.nix says, twice, that a WSL guest "has no multi-user target to start one under" — stated as the reason a service like this cannot live there. That is a load-bearing claim: taken at face value I would have told the user it was impossible, or gone off designing something exotic. Disproving it cost one SSH command (systemctl is-system-running → running, multi-user.target → active).

Pattern: a comment is evidence about when it was written, not about now. The ones worth spending a command on are specifically the ones that would stop the work.

notice — exit codes were wrong in both directions

Both failures above were caught by checking end state, not return codes. Then the opposite happened: systemd-run exited 1 with D-Bus connection terminated while waiting for jobs on a switch that had fully succeeded — the activation re-execs systemd, which kills the monitoring connection. A false failure right after two false successes.

Pattern: on this kind of work, return codes are a hint and end-state queries are the answer. readlink -f /run/current-system, systemctl show -p Result, "is the path on the target", "does the port answer" were right every single time this session. Four checks, zero wrong calls — against three misleading exit codes.

notice — a written procedure nobody had run

The host file's header confidently documents its own deploy command: nixos-rebuild switch --flake .#zachgigamothers --target-host nixos@zachgigamothers --use-remote-sudo. It cannot work — trusted-users = root, deploy user nixos, unsigned local closure. It was never wrong-in-the-past; it was never executed.

Pattern: this is a second flavour of the standing "verify landed claims" habit. That one is about features claimed as shipped. This one is about procedures claimed as working — and a documented command in a config that has never been deployed is a hypothesis wearing the costume of an instruction.

keep doing — stage so failures are attributable

Deploying baseline-then-feedback instead of one combined switch meant the channel→flake migration got proved on its own, and a failure in either half would have been immediately attributable. It cost one extra activation. Given that the first switch attempt did fail (on PATH), having a narrow blast radius each time was worth more than the time it saved.

keep doing — if the edit falsifies a neighbouring comment, the comment is in the diff

Adding services.feedback made two nearby claims false. Patching them in the same change took three minutes and prevents the exact archaeology that cost time at the start of this session, when I had to work out whether the "no multi-user target" comment was true.

Meta-meta

Two of this session's three real errors were the same error: I accepted a proxy for the thing. A signed cache path standing in for an unsigned local one. tail's exit code standing in for nix copy's. Neither was carelessness in the usual sense — I ran a test in both cases, and both tests came back green. The defect was in what the test was attached to.

Set against the one thing I did cleanly for the same class of question: faced with a comment claiming the service could not run on WSL, I queried the actual target instead of reasoning about it. That is the same move the two failures skipped.

So the thing to carry forward is narrower than "verify more". It is: when a check comes back green, ask what would have made it red. If there is no answer, no checking happened. That question would have caught both failures before they cost anything, and it costs one sentence of thought.

Worth noting the shape of the whole session, too: the user asked to install an app, and the honest answer involved a system migration they had not asked for and probably did not know was required. Surfacing that as an explicit decision — with both closures already built so the choice was real and reversible rather than hypothetical — was better than either silently doing it or refusing to proceed. Doing the non-destructive work first is what made the question cheap to ask.
