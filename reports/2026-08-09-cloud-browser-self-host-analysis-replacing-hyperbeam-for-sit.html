Cloud browser self-host analysis: replacing Hyperbeam for SitePanel

aireadalong.com's /site feature currently uses Hyperbeam ($0.15/hr, persistent profiles paywalled). This report scopes the effort of self-hosting a Hyperbeam-equivalent limited to only the features aireadalong actually uses, and lands on a concrete recommendation.

TL;DR

Recommendation: Provision zHost (a new home/office box, or activate the already-declared-but-not-provisioned WilliamZacharyAbelTheZeroth), run Neko in Docker, expose via cloudflared tunnel to browser.aireadalong.com. Total spend: $0 marginal (electricity). Persistent profiles free. SitePanel does a health check on Start and shows an explicit "Cloud browser is offline" error when the tunnel is down — no automatic Hyperbeam fallback.

Don't build WebRTC from scratch (2–3 weeks), run MJPEG hacks, or upgrade vultr-woofs (mixing browser sessions onto woofs.com's nginx box invites OOM incidents).

Actually first, though: email founders@hyperbeam.com and ask if they'll enable persistent profiles on our account. Solo devs often get accommodated. If yes, this whole analysis parks itself for later.

Existing infra reality check

We already have vultr-woofs (Vultr, 45.32.195.217, NixOS) tracked in fleet_machines. Before spinning up a new host, does it have capacity for a Neko container?

Live inspection (2026-08-09):

  • 1 vCPU, 1.9 GiB RAM, 47 GB free disk
  • NixOS running nginx on :80/:443 (woofs.com), sshd on :22, load 0.00
  • Docker not installed
  • Uptime 20 days, essentially idle CPU-wise but memory-constrained

Verdict: too small for Neko as-is. Chromium + GStreamer + Xvfb + Pulse per session runs ~1.2–1.5 GB RAM. Plus nginx + OS overhead already using ~200 MB → we could fit exactly one session and the OOM killer would show up under real use. 1 vCPU is the harder blocker — WebRTC video encode from 1280×720@24fps needs ~1–2 cores; on 1 vCPU total, framerate collapses or nginx starves.

Recommended path: Neko + wrapper

Neko is a Docker container that runs Chromium + Xvfb + Pulseaudio + a Go control server that streams the display over WebRTC and forwards input events. It's production-used by ~10k+ deployments, actively maintained, and MIT-licensed.

What actually needs writing

  1. zHost setup: NixOS host with Docker + cloudflared. See the "Cloudflared tunnel + graceful degradation" section for the full module.
  2. neko-manager service (~200 LOC Node or Python):
    • POST /session — accepts {userId, startUrl}, mounts /var/neko-profiles/<userId> as the Chromium userDataDir, starts a Neko Docker container on a free port with an auth secret, returns {sessionId, embedUrl, authSecret}.
    • DELETE /session/<id> — docker stop the container.
    • GET /session/<id> — is container still running?
    • Bearer-token auth so only aireadalong can call it.
  3. Cloudflare / DNS: point browser.aireadalong.com at the VPS. TLS via Caddy or Cloudflare's proxy.
  4. NekoProvider in aireadalong (~80 LOC — same shape as HyperbeamProvider): 
    class NekoProvider implements BrowserProvider {
  async createSession(opts) {
    const res = await fetch(`${NEKO_MGR_URL}/session`, {
      method: 'POST',
      headers: { 'Authorization': `Bearer ${NEKO_MGR_TOKEN}` },
      body: JSON.stringify({ userId, startUrl: opts.startUrl }),
    })
    const { sessionId, embedUrl, authSecret } = await res.json()
    return { sessionId, embedUrl, adminToken: authSecret }
  }
  async endSession(id) { /* DELETE */ }
  async getSession(id) { /* GET */ }
}
  5. SitePanel client swap: replace @hyperbeam/web with Neko's client. Neko exposes an <iframe> embed URL that works OOTB, but for shadow-DOM parity with the current setup you'd use neko-client npm package.

Persistent profile "for free"

Neko's Chromium runs against --user-data-dir=/home/neko/.config/chromium by default. Mount /var/neko-profiles/<userId> onto that path in the Docker run and the user's cookies/localStorage/passwords persist across sessions. This is the exact behavior Hyperbeam wants to charge premium for.

Security note: per-user profile dirs on the VPS store the user's browsing state (cookies for MA, potentially anything else they log into). Encrypt at rest with LUKS or restrict filesystem perms; document in the aireadalong privacy policy.

Cloudflared tunnel + graceful degradation

Cloudflare Tunnel replaces ngrok cleanly: free, no session TTL, integrates with the existing Cloudflare DNS zone for aireadalong.com, and terminates TLS at the edge (no cert management on zHost).

NixOS module sketch (add to zHost config):

services.cloudflared = {
  enable = true;
  tunnels."browser-aireadalong" = {
    credentialsFile = "/var/lib/cloudflared/tunnel-creds.json";
    default = "http_status:404";
    ingress = {
      "browser.aireadalong.com" = "http://localhost:8080";
    };
  };
};

virtualisation.docker.enable = true;

Graceful-error UX in aireadalong (POST /api/browser-session):

if (process.env.BROWSER_PROVIDER === 'neko') {
  try {
    const health = await fetch(`${process.env.NEKO_MGR_URL}/health`,
      { signal: AbortSignal.timeout(3000) })
    if (!health.ok) throw new Error('unhealthy')
  } catch {
    return NextResponse.json({
      error: 'Cloud browser is offline. It typically comes back within a few minutes.',
      code: 'ZHOST_UNREACHABLE'
    }, { status: 503 })
  }
}

SitePanel already surfaces server errors as a red banner via the existing setError() path — no client changes needed beyond checking for the specific error code if we want a nicer message.

Cost model

Hyperbeam (current)

  • ~$0.15/hr per active session (their standard tier).
  • 1 user × 1 hr/day × 30 = ~$4.50/mo.
  • 10 users × 30 min/day × 30 = ~$22.50/mo.
  • Persistent profiles: paywalled (contact sales).

Neko on our infra

  • Upgrading vultr-woofs to 4 vCPU / 8 GB: ~$24/mo (delta ~$18 vs current). Handles 3–5 concurrent sessions.
  • Sibling Vultr HF 2 vCPU / 4 GB: ~$12/mo new spend. Handles 1–2 concurrent.
  • Local mothership (if 24/7 + reachable): $0 marginal.
  • All options: profile persistence free, no per-hour metering, unlimited session length.

Break-even

Neko wins in $/mo from month one at current usage, but only if we ignore the 3–5 days of setup time. Rough labor-cost break-even:

  • If Hyperbeam bill grows to > $30/mo consistently, Neko setup pays back in ~year one (assuming labor at $50/hr internal-project rate).
  • If Hyperbeam bill stays < $15/mo, keep paying them unless persistent profiles are blocking us and they won't enable it free.

Risks + open questions

Operational risks (Neko path)

  • You now run a VPS: OS updates, Docker maintenance, disk fills up with unused profiles. Realistic: ~1 hr/mo of hygiene.
  • WebRTC through Cloudflare: CF WARP has been known to interfere with UDP-based WebRTC. May need to bypass CF's proxy for the WebRTC endpoint (orange-cloud OFF for browser.aireadalong.com).
  • Single point of failure: one VPS = no HA. Fine for a personal-scale product; add failover before you'd tell an investor.

Legal / ToS risks (unchanged from Hyperbeam)

  • Math Academy's ToS may still be uncomfortable with any programmatic browsing, even if the user is driving it. Not changed by whether we host our own Chromium or pay Hyperbeam.

Open questions

  • Does Neko's client SDK expose the underlying <video> element similarly to Hyperbeam (needed for our Capture flow)? Docs suggest yes via document.getElementById('neko-video'), but verify before committing.
  • What's Neko's actual RAM footprint per container? Docs say ~500 MB; needs confirmation before sizing the VPS.
  • How gracefully does Neko handle a stale/crashed container relative to our "auto-reap on next Start" logic in /api/browser-session?

Decision framework

Answer these three questions in order:

  1. Is our Hyperbeam bill under $15/mo AND will they enable persistent profiles for free/cheap? → Stay on Hyperbeam. Zero engineering.
  2. Are we hitting > $30/mo on Hyperbeam OR do we want ownership over the runtime? → Ship Neko. 3–5 days.
  3. Do we need > 50 concurrent sessions or aggressive latency guarantees globally? → Stay on Hyperbeam (their edge presence justifies the price at scale). Not our situation.
