Composed valuations, run against real TempleDB data

Follow-up to the ontology-in-disguise doc. That ended with a claim: TempleDB already ships several distance functions (graph search / who-uses / callers / importers / build-deps, plus the ones latent in vcs_commits, nix_closures, config_nodes, ast_builds), and the interesting move is to compose them — ask "close under X and close under Y." This doc runs eight such composed queries against the actual DB and reports what fell out.

Eight queries, real results

1. Co-modified × imports HIT — 8 pairs in bza

The essay's original example. For each file-dependency edge in bza, count shared commits between endpoint files. Threshold at 7:

BookUpload.tsx → localStorage.ts 9 shared commits BookReader.tsx → localStorage.ts 8 usePicturebook.ts → supabase-queries.ts 7 BookReader.tsx → types/index.ts 7 PageSidebar.tsx ↔ QuizPanel.tsx 7 (mutual import) BookUpload.tsx → queries/images.ts 7 BookCard.tsx → types/index.ts 7
Actionable Every top pair is an extraction candidate. A tighter reading: pairs where the import is bidirectional and co-commits are high (PageSidebar ↔ QuizPanel) are almost certainly one logical component that got split across files. Also a natural agent hint — "you edited A; the DB says you almost always edit B in the same commit."

2. High importer count × recent churn HIT — risk-weighted

In-degree of the file-import graph times commits in the last 30 days. Bza again, since it has the richest history:

frontend/lib/supabase.ts 42 importers × 3 commits = 126 frontend/types/index.ts 30 × 4 = 120 frontend/lib/queries/index.ts 19 × 3 = 57 frontend/lib/queries/images.ts 6 × 9 = 54 frontend/lib/queries/types.ts 12 × 4 = 48
Actionable These are the files where a mistake propagates farthest AND is being touched most. Natural gate for "require review from two people", extra CI weight, or an alert when they're touched by an auto-generated PR. The formula generalizes: importers × churn is a blast-radius × probability product — the expected damage from a bad change.

3. Small nix closure delta × single-commit source diff HIT — real 1-package change

From nix_closure_diffs, closure #2 (2026-07-29):

added_count: 1 removed_count: 4 changed_count: 0 size_delta: -996,968 bytes added: templedb-spacemacs-layer removed: hm_templedb, zram-generator-1.2.1, zram-generator.conf, unit-systemd-zram-setup-.service

That's a genuinely small, semantically coherent change (add spacemacs layer, retire zram-generator). For contrast, closure diff #3 later that week: +145 / −150 packages, −5.2 GB — a legitimate nixpkgs bump.

Actionable In the deploy pipeline, flag closures where added_count + removed_count ≤ 10 as targeted rebuild candidates. The composed valuation here is closure-diff-small ∧ source-diff-small — a truly minimal change touches few store paths and few source files. If either side is big, the change isn't actually minimal even if the other side looks that way.

4. AST build hash reuse across hosts NEGATIVE HIT

Ran across all 27 ast_builds: every output_hash appears on exactly one host. Not one hash is shared between hosts — not even between the two nearly-identical dev machines zMothership2 and zMothership3.

n_hosts | n_hashes --------+--------- 1 | 27 ← every hash unique to one host 2 | 0 3+ | 0
Finding worth acting on Content-addressing gives you shared-subtree caching for free in principle — if two hosts emit the same subtree, they get the same hash for that piece. Right now the emit is holistic (one hash per host), so that free win is unclaimed. The composed valuation to add: for pairs of AST builds on different hosts, compute |shared config_nodes| / |total distinct nodes|. Pairs with >90% overlap but different output_hash are exactly the "should be a shared base module" refactor targets.

5. Same commit, different deploy outcome MISS — data too concentrated

Only one commit shows the pattern (DCE5765A…), and all 20+ attempts are on target staging. That's an evolving deploy sequence on one target, not a cross-target divergence.

The valuation is well-defined — same commit_hash ∧ (target A succeeded, target B failed) — it just needs more targets with real history. Worth revisiting once fleet_deployment_history (currently 0 rows) is populated.

6. Symbol in-degree × declaring-file churn MISS — code_symbols sparse

Same shape as query 2 but at symbol granularity via code_symbol_dependencies.called_symbol_id. Would surface individual functions that are both hot and unstable — much sharper than file-level. But code_symbols has only 12 rows total across the DB, and 12 of them are test fixtures in trig-navigator-godot. Zero real hits.

Blocker, not a bug templedb graph build-deps populates file_dependencies but the symbol-graph builder has never been run project-wide. The query is ready; the ingest step is missing.

7. Graph-query co-occurrence in the query log MISS — table brand new

Yesterday's commit added graph_query_log. In a month there will be enough data to mine pairs of (command, target_key) invocations within N minutes of each other. Real usage patterns will emerge: "when a user runs who-uses OPENAI_API_KEY, what do they run next?". Zero rows today, but the wiring is in place — the frecency ranking is technically a degenerate 1-step version of this (frequency of a single query, not co-occurrence of two).

Interesting property The query log is the only distance function in the system that isn't computable from static state — it captures what the user actually cared about. Compose it with any of the others and you get "what the user cared about that also has structural signal X." That's a much richer ranking than either alone.

8. VCS ancestor depth × co-modification HIT — natural extraction detector

For each pair of files, distance = 1 / (commits since their most-recent shared commit). Files whose last co-modification was recent and whose commit ancestry converges tightly (small distance both ways) are practically siblings. Composed with the import edge, you get high-precision extraction candidates:

templedb, top pairs where co-commit-recency AND import both hold: src/agent/service.py ↔ src/agent/store.py src/cli/commands/graph.py → src/graph_frecency.py (yesterday's commit!) src/services/vcs_service.py ↔ src/temple_fuse.py

The graph.py ↔ graph_frecency.py pair is a nice self-referential hit — I just extracted the second file from the first, and the DB immediately reflects them as a sibling pair.

Meta-observations from running these

What makes a valuation actually useful

A distance function is only interesting if it produces enough variance to discriminate. Two failure modes to avoid:

  • Everything is close. If your metric puts most pairs at similar distance, ranking by it tells you nothing. This is why d(file_A, file_B) = shared_commits on its own is weak — most pairs share few or many commits by project age, not by semantic relatedness.
  • Nothing is close. If your metric is so strict that most pairs have infinite distance, you can't rank the survivors. This is why exact AST build hash equality across hosts (query 4) tells you nothing new — of course no two hosts produce byte-identical config.

Composed valuations dodge both failure modes because the intersection of two weak-signal metrics is usually a strong signal. "Files that share many commits" is common. "Files that import each other" is common. "Files that do both" is rare and semantically meaningful.

Static valuations vs. usage valuations

Seven of the eight queries use only structural data (imports, commits, closures, symbols). The eighth uses the query log — user behavior. The behavior signal is qualitatively different because it captures what the humans (or agents) treated as related, not what the code says is related. In principle they should agree; in practice they will diverge, and the divergences are where the interesting bugs live:

  • Files always co-queried in the log but never co-imported → hidden coupling.
  • Files always co-imported but never co-queried → dead or over-abstracted dependency.

This composed valuation only becomes queryable once the log has a few weeks of data. Worth building the query now so it's ready to fire when the data is.

The AST-build finding is the buried lede

Zero cross-host hash reuse in AST builds means TempleDB's content-addressed identity — which is the whole reason the ultrametric geometry works at higher levels — is not being exploited at the AST layer. Every host gets a fresh derivation even if 90% of its config is shared. That's a real refactor: emit each config subtree separately, hash it, and let hosts reference shared subtrees by hash rather than re-inlining. Nix's own store works this way; templedb's AST emit doesn't yet.

This is the kind of finding a single query surfaces that a whole taxonomy discussion won't. It came out of just asking one composed question against real data.

An algebra of distance functions

Once you commit to composed valuations, distances become first-class objects with an algebra. A minimal set of operators: 

d_and(a, b)  = min(d_a, d_b)      -- close iff close on BOTH
d_or(a, b)   = max(d_a, d_b)      -- close iff close on EITHER (weaker)
d_sum(a, b, w=0.5)                -- weighted composition
d_ratio(a, b) = d_a / d_b         -- discrepancy: close on a but not on b
d_flip(a)    = 1/d_a               -- promote to a "farness" score

d_ratio is the interesting one — it's what surfaces the "co-imported but never co-queried" cases. Divergence between two valuations usually means there's a story to tell.

A concrete CLI shape: 

templedb distance A B --via imports
templedb distance A B --via commit-ancestry
templedb distance A B --via and:imports,commit-ancestry
templedb distance A B --via ratio:imports,query-log

I wouldn't build this speculatively. But if two or three of the queries above earn their keep as first-class commands, exposing distance as a --via flag becomes the natural way to add the fourth without a new subcommand for each.

Two small findings for the parking lot

Schema inconsistency file_dependencies.dependency_type stores 'import' (singular) and 'from_import', not 'imports' (plural) as the schema comment and my own earlier writeup implied. Every composed query touching imports has to spell it correctly or silently return zero rows. Worth a canonical constant somewhere, or at least a schema comment update.
Data sparsity blocks two queries code_symbols (12 rows) and fleet_deployment_history (0 rows) prevent the symbol-level and cross-target-deploy queries from producing signal. Both need an ingest run to be worth exposing as commands.

What to actually build from this

Ranked by expected value per unit of effort:

  1. Query 1 as a real command. templedb graph sibling-pairs <project> — top file pairs by co-commit × import-edge. Direct extraction hints, works today on any project with vcs + import data.
  2. Query 3 as a deploy-pipeline flag. Warn when a closure diff is small (add+remove ≤ 10) — those are the deploys where something targeted could replace nixos-rebuild switch. Cheap to add, catches the interesting cases.
  3. Query 4 as a config-refactor report. templedb ast overlap --across-hosts — surface the largest subtrees that are structurally shared but produce different hashes. This is the AST-emit refactor's whole justification, in one command.
  4. Query 8's mechanism, always-on. Whenever vcs log shows a commit that touched files >95% structurally co-modified, silently note it — over time you build a "these files always move together" registry that can inform every other query.

I'd skip building the general distance algebra until at least two of the above are shipped and clearly worth composing. Design pressure from real usage is a better guide than pretty API surface.

Eight queries, five real hits, three misses that are useful diagnostics about what data is sparse. The AST-build finding (zero cross-host hash reuse) is the one that would be worth pursuing whether or not you build any of the distance-composition commands.
