Nix as a projection of TempleDB

Design proposal, not implementation. TempleDB and Nix each behave as if they are the ambient source of truth for the same content (Python source, Emacs .el files, NixOS config). The result is drift: five reproducible “edited the wrong copy” incidents in the last month. This report argues that the durable fix is to make Nix a projection of TempleDB — the DB emits derivations, the store paths are named views, and drift becomes a category error rather than a bug. Includes the cheaper interim (templedb file where diagnostic), a mirror inventory, and a rough migration path.

Why we keep editing the wrong copy

Five recent drift bugs, one shape:

  1. Emacs org-ai layer — edited under the FUSE mount, but Spacemacs loaded the nix-store copy that hadn’t been rebuilt.
  2. Migrations dir missing at runtime — 084 registered in the sequence, applied in dev-mode, but the nix package didn’t bundle migrations/*.sql. Fix required editing the flake’s installPhase, not the migration.
  3. Dead launcher — templedb_launcher.py registered new MCP tools; the real entrypoint was _launcher.py. Six weeks of templedb_ask_user silently broken.
  4. templedb-agent.el edited in ~/.config/templedb/checkouts/templedb/ — read-only, materialized output, silently overwritten on next publish.
  5. Cursor-hijack fix — edited in edit-workspaces/, but three other copies live in ~/status/, ~/temple/, and the nix store spacemacs layer path. Verifying deployment meant grepping ~50 store paths.

The shape is: TempleDB wrote content, some other system had a stale copy, that other system won. The other system is usually Nix (immutable store paths keyed on the flake input rev), sometimes home-manager (symlink forest keyed on the same), sometimes git (materialized checkout as a git repo for external tools). Each wants to be canonical for its slice of reality.

The philosophical shape

Two systems both believe they are the canonical form of the same content:

  • TempleDB’s claim: content is rows in file_contents; everything else is a projection generated by project checkout / publish run.
  • Nix’s claim: content is store paths keyed on a hash; the “source” is a flake input revision that points at a git tree.

These are peer authorities. Every mirror is a system asserting its own claim, and every edit has to choose one. The philosophy problem isn’t how many mirrors we have; it’s that no single authority ordering exists.

Analogy Two authoritative DNS servers with different records for the same name. You can add caching, TTLs, sync jobs — all worthwhile — but nothing dissolves the underlying ambiguity until one server is declared a projection of the other.

The proposal: Nix as a projection

Invert the authority ordering:

  • TempleDB is the single source of truth. Every piece of content, including the flake that builds templedb itself, lives in the DB.
  • Nix derivations are emitted from DB rows. Just as the AST-deploy pipeline emits NixOS system config from config_nodes, the templedb flake and its derivations are emitted from a similar table (call it flake_nodes).
  • Store paths are content-addressed views. The hash of the store path is the fingerprint of the DB slice that produced it. Given a store path, you can traverse back to the exact DB commit hash that emitted it.
  • Edits never happen to a store path. They happen to DB rows; the store path is rebuilt as a side effect. There is no “edit the wrong copy” because there is only one place editable copies exist.

This is what the AST-deploy work (docs/AST_DEPLOY_DESIGN.md) already does for NixOS config. The proposal is: extend the same discipline to templedb’s own build, then to the spacemacs layer, then to any other derivation templedb owns. The graph becomes one-directional: 

DB → AST → nix expression → nix build → store path → runtime consumer

There are no back-edges. Nix ceases to be a peer and becomes a well-typed export of the DB.

Tradeoffs

Cost Every derivation templedb owns has to be representable in the AST tables. The parser has known gaps (the “outputs FnDef body silently dropped” note in memory). Nix is a full language; faithful bidirectional representation is a multi-month project.
Risk External consumers of the flake (bza today, hypothetical others) expect a normal git repo with authored .nix files. Turning those into generated artifacts either requires committing the emitted output back to the checkout (loses the “single source” property from the consumer’s perspective) or making consumers speak the DB protocol.
Payoff “Did drift happen?” becomes unanswerable in the affirmative — the store path is the current DB by construction. Every “edited the wrong copy” class bug becomes structurally impossible, not just caught by a linter.

The cheaper interim

Full Nix-as-projection is a quarter of work. The immediate pain can be solved for a day of work:

  1. templedb file where <slug> <path> — walks a static list of known mirror roots (checkouts/, edit-workspaces/, active nix store paths from ~/.nix-profile and ~/.emacs.d/private/local-layers/), prints each location’s content hash next to the DB’s is_current hash. Color drift red, agreement green, immutability blue.
  2. Content-hash xattrs on writable mirrors. Every project checkout sets user.templedb.content_hash on each file. Every templedb file set checks the xattr of the mirror and refuses (or warns) if it disagrees with what the DB thinks was there.
  3. Retire templedb file edit since templedb edit <slug> covers it — one fewer write verb without touching the mirror problem.

This is drift-visible, not drift-impossible. Cheap, doesn’t block the deep fix, buys most of the value.

Migration path (if we commit to the deep fix)

  1. Round-trip the templedb flake through the AST tables. Parser passes on every existing file; emitted output matches original byte-for-byte. Nothing consumes the emitted output yet.
  2. Emit the spacemacs layer derivation from the AST. Home.nix switches from ${templedb}/integrations/emacs/... to templedbFlake.packages.spacemacsLayer. First real consumer of a projection.
  3. Bootstrap. The templedb CLI itself is emitted from DB. Requires a chicken-and-egg break: keep one bootstrap flake authored by hand, use it to build a templedb that then emits the “real” flake. Same trick as Guix’s bootstrap-binaries.
  4. Deprecate authored flakes. Every remaining .nix file in the checkout is a bug — the checkout is emitted output, not input.
