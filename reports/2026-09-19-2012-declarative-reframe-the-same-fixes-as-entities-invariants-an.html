declarative reframe — the same fixes as entities, invariants, and reconcile

Companion to the imperative followup spec. Same six problems, reframed as facts, relationships, and invariants inside the existing templedb entity graph — instead of new CLI verbs, print statements, and shell heuristics. The declarative version is smaller in total surface, composes better with what's already there, and doesn't leak behavior into the caller's environment.

Side-by-side, at a glance

Imperative version Declarative version
Auto-detect agent context + write pin file Sessions get a context column; TEMPLEDB_CONTEXT=claude-agent in env declares identity — no detection
vcs session gc CLI verb Sessions declare lifetime + reap policy at creation; doctor invariant + existing reconcile timer enforce
--expect-rev flag on publish Deploy stages become entities; invariant #12 checks each stage's input hash == prior stage's output hash
Stage hash print-logging at each boundary Same stage entities carry those hashes durably; provenance queryable across the chain
file trace walks symlinks + probes filesystems at query time File :mirrored_at Location relationships; trace is a graph query; new mirror kinds = new ingest adapters
templedb.devMode global nix flag Files have edit_mode attribute; home.nix reads per-file; file mark --edit-mode live-symlink sets it

Net footprint of the declarative version: 1 new table (deploy_stage_runs), 1 new CLI verb (file mark), and 3 new columns across 2 existing tables. Everything else piggybacks on doctor, reconcile, provenance, vcs session start, and the ingest-adapter pattern. Compare against the imperative spec: 4 new CLI verbs / flags, 30+ new print statements, 2 new shell heuristics, plus a new nix module.

Why declarative here

Templedb already has a declarative substrate. Per the CLAUDE.md header: "TempleDB observes source (git is authoritative), owns intents + relationships + the cross-authority knowledge graph. Six ingest adapters keep the graph in sync (hourly systemd timer). Ten doctor invariants + one active-probe reconcile (daily systemd timer) detect drift." My original followup spec bolted six imperative CLI features on top of that, when in most cases the right move is to extend the graph and add invariants.

Signs a fix wants to be declarative: (a) it detects state at runtime and mutates something; (b) it involves cross-project or cross-stage reasoning; (c) it's about "the world should look like X" not "run X." All six of the previous specs check at least two of those boxes.

The primitives we're leveraging

  • entities — typed nodes (files, projects, hosts, commits, sessions, deploy stages, mirror locations). Already 12k+ populated by ingest adapters.
  • relationships — typed edges (:contains, :mirrors, :derived_from, :consumes). The "seven-hop chain" for templedb-agent.el is literally a path through this graph, we just haven't modeled the hops yet.
  • intents — writes recorded as facts (edit_intents) with author + session + hash + timestamp. A commit is "apply all applied intents matching filter."
  • doctor invariants — declarative predicates checked on a schedule ("no file has drift between DB and checkout that isn't explained by an unapplied intent"). Ten exist; adding an eleventh is idiomatic.
  • reconcile — active drift correction where the fix is unambiguous. Daily timer.
  • provenance — cross-authority queries (templedb provenance machine <host> already exists). "What motivated this artifact" is a graph traversal.

§1 → Agent sessions as declared context

Imperative

Detect "agent context" at runtime via env-var sniffing + TTY absence heuristic. If detected AND no pin, auto-write a session pin file. Log a hint. Expire in 4h. Special-case doctor check for stale auto-pins.

Declarative

Sessions get a context attribute; sessions are derived from context, not from PID.

Add one nullable column to vcs_sessions: context TEXT. When TEMPLEDB_CONTEXT=<name> is set in env, session resolution matches on (author, host, context) instead of (author, host, sid). Set-once, share across shells, no file pin, no runtime heuristics.

Claude Code's setup writes TEMPLEDB_CONTEXT=claude-agent into its Bash tool env (once, in ~/.claude/settings.json). Every subsequent templedb call joins that session by name. No detection, no pin file, no expiration timer — the environment declares the session identity.

The current SID / pin mechanism stays for interactive humans who want it. But agents get named contexts as the canonical path.

What changes

  • Migration: ALTER TABLE vcs_sessions ADD COLUMN context TEXT.
  • VCSService.get_current_session(): check env TEMPLEDB_CONTEXT before SID; upsert a session with that context name.
  • Docs: add one line to CLAUDE.md pointing at TEMPLEDB_CONTEXT. Done.

§2 → Sessions have a declared lifetime

Imperative

Ship vcs session gc subcommand. User (or timer) runs it periodically. Command imperatively enumerates candidates and reaps them.

Declarative

Sessions declare their lifetime; a doctor invariant enforces it.

Add columns to vcs_sessions: expected_lifetime_seconds INT and reap_policy TEXT ('orphan_stages' | 'preserve' | 'discard'). Default: 24h + orphan_stages.

New doctor invariant #11: "No session is past its expected_lifetime with unended state." Doctor reports violations. Reconcile (already daily) resolves them per each session's declared reap_policy — orphaning working-state rows, preserving them for manual review, or discarding entirely.

No new CLI verb. The gc becomes a policy, not an action. Users tune it per session at creation time.

What changes

  • Migration: two columns + backfill (24h/orphan_stages for existing rows).
  • New invariant + reconcile handler in the existing doctor/reconcile infra.
  • Session-create flags: --lifetime 4h, --on-expiry orphan_stages.

§3 + §4 → Deploy stages are entities in the graph

Imperative

--expect-rev flag on publish, plus print-statement hash logging at each stage. Users write shell scripts that call publish → parse output → pass hash forward. Assertion is a runtime flag.

Declarative

Every stage is an entity; stages record their inputs and outputs as relationships. The deploy chain is a graph, and drift is a query.

Templedb already tracks system_deployments and nix_generations. Extend that pattern: every stage of the chain writes a row when it runs, with input_hash and output_hash. Stages: file_set, vcs_commit, materialize, git_push, flake_resolve, nix_build, system_switch.

Once stages are entities:

  • Invariant #12: "Each stage's declared input hash must equal the previous stage's declared output hash." Doctor reports mismatches. No runtime assertion needed — the check runs offline, deterministically.
  • Provenance query: given a running binary's nix store hash, walk backward through the stage graph to the originating edit_intent. "Why is this file this way?" becomes a graph traversal, not a shell archaeology dig.
  • No --expect-rev flag needed. If rebuild's flake_resolve stage records output_hash != publish.git_push.output_hash, the invariant flags it. Publish's job is to state its facts, not to police downstream stages.

What changes

  • New tables: deploy_stage_runs (id, stage_kind, slug, started_at, input_hash, output_hash, prev_stage_run_id, metadata_json).
  • Each existing stage gains a small "record my run" call. Cheaper than print statements because it's already in the SQL boundary.
  • One new invariant in doctor, one new provenance query, and templedb file trace (see §5) reads from these entities instead of walking symlinks.

§5 → File mirrors are relationships

Imperative

templedb file trace walks symlinks and probes filesystem paths at query time. Each hop is discovered procedurally. Hash comparison happens on the fly.

Declarative

Each mirror is a File :mirrored_at Location relationship with a declared derivation_rule. The graph knows the chain; trace is a query.

Model:

File (slug, path)
  :mirrored_at (rule="materialize")   → CheckoutMirror
  :mirrored_at (rule="edit-workspace") → EditWorkspaceMirror
  :mirrored_at (rule="home-manager-overlay",
                via="templedb-spacemacs-layer") → NixStoreMirror
  :mirrored_at (rule="symlink",
                via="/home/zach/.emacs.d/private/local-layers")
                                       → LiveOverlaySymlink

Relationships are populated by ingest adapters (one per derivation-rule kind). Doctor invariant: "For each File, all :mirrored_at targets agree on content hash unless the mirror's rule declares expected lag (e.g. home-manager-overlay is expected to lag until the next rebuild)."

templedb file trace <slug> <path> becomes a one-shot graph query, not a symlink walk. Adding a new mirror kind (e.g. someone else's Emacs config, another host's copy) just means adding a new ingest adapter.

What changes

  • Extend the existing entity graph with MirrorLocation entity kind and :mirrored_at relationship.
  • New ingest adapters: checkout_mirror, edit_workspace_mirror, nix_store_mirror, symlink_overlay_mirror. Each ~30 LOC.
  • Invariant + reconcile: expected-vs-observed hash per relationship.
  • templedb file trace is thin over the query — no symlink walking, no runtime filesystem probing.

§6 → Files declare their edit mode

Imperative

Toggle templedb.devMode = true in home.nix; conditional branch generates a symlink vs. copy. Global switch, not per-file.

Declarative

Files carry an edit_mode attribute in DB; consumers (home.nix, etc.) read the attribute.

Add edit_mode TEXT column to project_files: 'immutable' | 'hot-reload' | 'live-symlink'. Default: immutable.

Home.nix's Spacemacs layer generator queries templedb file ls --edit-mode live-symlink for each project and emits symlinks for those specifically. Everything else goes through the normal materialize path.

Marking a file hot-reload becomes: templedb file mark --edit-mode live-symlink templedb integrations/emacs/templedb-agent.el. The mark is a persistent fact; every subsequent rebuild picks it up automatically. No templedb.devMode global flag, no imperative override — the file's own metadata declares its treatment.

What changes

  • One column, one CLI verb (file mark).
  • Home.nix reads a new templedb-generated JSON manifest listing live-symlink files.
  • Doctor invariant: "Every live-symlink file has a valid backing FUSE path." If FUSE is unmounted, doctor reports.

What this buys you over the imperative version

  • Uniform observability. Everything shows up in templedb summary / doctor / provenance. No new subcommands to remember.
  • Automatic scheduled enforcement. Doctor's daily timer already exists. Adding invariants is close to free. Manually-run gc commands, print-log grepping, and shell-script assertions all evaporate.
  • Cross-cutting queries fall out. "Which projects have live-symlinked files?" "Which files drifted this week?" "Why is this store path what it is?" All graph queries against the same substrate.
  • State, not behavior, is what gets copied around. Right now, agents need to know a bunch of imperative rituals (pin your session, pass --commit, run publish --pin-input). In the declarative version, the agent sets TEMPLEDB_CONTEXT and everything else is inferred from graph facts.
  • Adding a new mirror / stage / file-mode is one adapter, not a code path through five files. New mirror kind? One ingest adapter. New deploy stage? One record-run call. New edit mode? One enum value. The extension points are declarative, not surgical.

The imperative pieces that remain

A few things stay imperative because they're inherently side-effectful or interactive:

  • Writes themselves. file set still mutates content_blobs. Nothing to do about that; a write is a write.
  • Publish's push to remote mirrors. Network I/O, not modelable purely as a graph fact. But its outcome (git push landed → remote_head = X) can be recorded as a stage run.
  • Nix's rebuild. External process, opaque to templedb except for its recorded outputs. That's fine — templedb declares intents and observes outcomes; it doesn't own the builder.

Even for these, the framing changes: templedb's job is to record facts about them, not to orchestrate them imperatively.

Meta

Reframing this made me notice: the imperative spec was, in effect, papering over the fact that templedb's declarative substrate isn't being fully exercised. Sessions, deploy stages, and file mirrors are all things that could already be first-class entities but aren't yet. Once they are, the "fix" reduces to "add an invariant." That's the same pattern the earlier Phase-3 migration to observer/integrator followed — pull mutable procedural state up into the graph, then let doctor and reconcile do the enforcement.

If we go this direction, the natural next step after landing §1/§3+§4 is to look for other imperative pockets that should be declarative facts. My hunch: project_tests, fleet_deployments, and the various nix cache / eval-cache timers are candidates. But that's a different session.
