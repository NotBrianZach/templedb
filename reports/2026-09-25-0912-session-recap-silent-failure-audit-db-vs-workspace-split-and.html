Session recap: silent-failure audit, DB-vs-workspace split, and 12 fixes

Started as "how is TempleDB looking?" and turned into an audit of things failing silently. Found a 10-day entity-graph outage, a data-loss bug that ate this session's own report, a dead full-text index, a crash-looping MCP daemon, and 45 dead checkout rows. 28 commits across four projects. One problem is left deliberately unfixed and needs you to run one command after this session ends — see Do this first.

Do this first — the WAL is 6.9 GB.

Every read against the live DB is currently ~100x slower than it should be (templedb summary: 2.1s on a copy, >200s live). The WAL cannot drain while this session's ai agent serve / ai mcp serve processes hold read snapshots. Once the session exits, run: 

python3 -c "import sqlite3; c=sqlite3.connect('$HOME/.local/share/templedb/templedb.sqlite'); \
print(c.execute('PRAGMA wal_checkpoint(TRUNCATE)').fetchone())"

Expect (0, 0, 0) and -wal dropping to near zero. Restarting the GUI does not help — that was tested and disproved.

The second architectural theme: the database and the edit workspace are two sources of truth, and different commands trust different ones. file set, reports reindex and file cat speak to the DB; vcs commit, vcs status --refresh and nixos home-rebuild speak to the checkout. Four separate bugs today were instances of that split.

Two futures: what the diff actually looks like

The root cause behind four of today's bugs is that the database and the workspace are both authoritative. There are two coherent endpoints. The point of writing them out is that the half-state is worse than either, and the schema makes the choice concrete rather than philosophical.

  • DB-authoritative → the workspace becomes a pure derived cache; commit is DB→disk, never disk→DB; the reconciliation-delete disappears entirely.
  • Disk-authoritative (the observer plan) → file set becomes a workspace write + ingest, and the DB stops being a write target.

A. DB-authoritative — CLI

  • vcs status --refresh — flag deleted; there is nothing to refresh from.
  • vcs add — stops scanning disk entirely.
  • templedb commit <slug> <workspace> — deleted. It is the disk→DB path.
  • Commit's reconciliation-delete — deleted. That is the line that ate this session's own report.
  • templedb edit — needs an explicit --save/import step.

Cost: you lose "edit in a workspace with vim and commit what's there". That is the workflow people actually like, and it becomes an explicit import.

B. Disk-authoritative — CLI

This is the large deletion. templedb vcs has 15 subcommands; eleven of them become git: 

add  reset  discard  commit  status  log  branch  switch  merge  diff  show   -> git
session  edit  import-history  export                                        -> survive

Plus top-level commit and push fold into publish/git. What remains gets better, because it is the part git cannot do: search, graph, entity, doctor, ingest, deploy, env/ var, nixos.

A and B are divergent, not sequential. A deletes the disk→DB path; B deletes the DB→disk write path. They point opposite directions. Doing A does not defer the decision — it forecloses B, and reaching B afterwards means rebuilding what A removed.

This matters because vcs_working_state already half-believes both models, which is roughly how the current state arrived: a sequence of individually-reasonable small diffs, none of which was the decision.

Where the truth should live

The question hides two questions, and they have different answers. "Where does file content live" is not "where does everything else live", and TempleDB's value is overwhelmingly in the second while its pain is entirely in the first.

File bytes belong in git. The database has no comparative advantage at storing them, and this session produced the receipts:

  • content_blobs holds 11,866 blobs for 1,879 current files — a 6.3× history multiplier. That is a second object database sitting beside git's, with a worse implementation.
  • 28 of 30 projects already carry a repo_url. Git is not a future migration; it is already underneath.
  • Every defect found today was a problem git solved in 2005, re-solved badly: a commit reporting Files: 2 while writing one, reconciliation hard-deleting rows, staging state derived from a disk scan that could be wrong, two parallel tables for "files in a commit".
  • The one moment ACID-across-projects could have earned its keep — the flake pin touching templedb and system_config together — it did not fire. The real dependency was on a published git rev, not a transaction.

Everything else belongs in the database, and that layer demonstrably works: the entity graph, invariants, EditIntent provenance, env/secrets, deploy state. It turned a ten-day outage into an eleven-second recovery. Git cannot express any of it.

So the thesis does not need abandoning — it needs restating. A database-native development environment, not a database-native VCS. The valuable claim was never "we store your bytes better than git".

Recommendation: B, with the scope named precisely — git owns file content and history; the DB owns everything derived and everything git cannot express. An earlier draft of this report recommended A on the grounds that it was the smaller diff and preserved the thesis. That reasoning was wrong twice over: it mistook a commitment for a stepping stone, and it defended a thesis that was never the valuable part.

No-regret work, correct under either answer

Do these regardless, and do them first — none of them prejudices the source-of-truth decision:

  • The five seam invariants (§ Open, item 2).
  • Deleting the four confirmed CLI aliases.
  • Consolidating the health surfaces.
  • Error translation at the CLI boundary.
  • Turning today's six reproductions into integration tests.

What would change the recommendation

  • If the cr-sqlite CRDT work is meant to sync file content across machines rather than just the entity graph. The sync_* shadow tables are a real investment; if file bytes are supposed to ride them, DB-resident content is load-bearing and this needs re-arguing.
  • If any of the 9 projects with no tracked files cannot have a git repo for a concrete reason.
  • If cross-project atomic commits are load-bearing for a workflow not seen in this session. Only one candidate appeared, and it did not need them.

Shrinking the CLI: 43 → ~16

43 top-level commands today. The help text lied in at least two places this session, which is what a surface this wide produces. Three moves, in increasing order of disruption:

1. Delete the confirmed aliases (43 → 39). Their own help strings identify them:

new-machine   "(Deprecated) Use templedb bootstrap instead"
build         "alias for deploy nix build"
push          "alias for publish run --force"
commit        "alias for project commit"

2. Fold the five health surfaces into one (39 → 34). doctor, reconcile, summary, hygiene, status, validate, source all answer "is this healthy?" and none of them was the place anyone looked when things broke. One templedb health with subcommands, one exit code, one alert path.

3. Fold the graph-query surfaces (34 → ~30). entity, tool, provenance, report are all queries over the entity graph and belong under graph. search stays top-level — it is used constantly and by humans.

That lands around 30 without touching semantics. Getting to ~16 requires the source-of-truth decision above: under B the entire vcs tree goes; under A it stays but commit, push and the workspace-diff path go. Either way the remaining nouns are roughly: 

project  file  search  graph  health  env  secret  deploy
publish  ingest  edit  gui  ai  nixos  admin  sync

Worth doing in that order — steps 1 and 2 are pure wins available today and independent of the bigger decision.

Notes for whoever picks this up

  • Write new files into the edit workspace, not via file set. file set on a new path still needs vcs status --refresh before vcs add will see it. This bit twice today, including for a migration file.
  • Always check the staged list before committing. templedb vcs session show <id>. Commit reported Files: 2 while writing one.
  • Verify after committing, not just after writing. templedb file cat <slug> <path> | sha256sum. A write can verify clean and still be destroyed by the commit that follows.
  • publish run before any nixos rebuild, and check the generation number actually advanced. Both the command output and system_deployments are identical between a real rebuild and a no-op.
  • Three search commands, three behaviours. search content (contents, FTS), graph who-uses (contents, substring), graph search (names/paths/commits only). CLAUDE.md now has the table.
  • Copy the DB with the backup API, not cp. A shutil.copy2 of a WAL-mode DB gave a silently wrong snapshot today and nearly produced a false conclusion. Use sqlite3.Connection.backup().
